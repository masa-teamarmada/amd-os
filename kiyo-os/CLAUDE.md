## 相手が誰かで話し方を変える

このリポジトリのセッションは、**まさが開いている場合**と**きよが開いている場合**がある。
分からなければ最初に一度だけ聞く。以降は覚えて話し方を合わせる。

**きよ相手のとき**:
- 専門用語を使わない。使うなら必ず 1 行で言い換えを添える
- コマンドは「どこに」「何を打って」「どうなったら成功か」まで書く
- 選択肢を出すときは 2〜3 個まで。おすすめを最初に置く
- エラーは推測で断定しない。「このメッセージをそのまま貼ってください」と頼む
- 作業が 1 分以上かかるものは、先に「これは○分くらいかかります」と言う

**まさ相手のとき**:
- 結論から。前置きを削る
- AMD OS / えいみOSスイートとの整合や、後で効いてくる設計上の判断を先に出す

## 中身を決めるフロー（勝手に実装しない）

```
きよの発言・要望
   ↓  えいみが書き取る
docs/INTAKE.md（候補置き場・まだ作らない）
   ↓  きよ or まさが「これ作って」と選ぶ
docs/DESIGN.md（作ると決めたものの正本）
   ↓  実装
src/ + src/lib/modules.ts
```

- **INTAKE を飛ばして実装しない。** 思いつきは INTAKE に書いて提案する
- **DESIGN に無いものを実装しない。** 実装したなら同じ commit で DESIGN に書く
- えいみOSスイートに同じ機能があっても、それは「きよが欲しい理由」にはならない。
  移植を提案するのは良いが、決めるのはきよ

## モジュールの足し方

画面（モジュール）は `src/lib/modules.ts` の 1 配列で管理している。
ここに 1 件足して、対応する `src/app/(os)/<slug>/page.tsx` を作れば、
ナビとダッシュボードのカードは自動で増える。

1. `src/lib/modules.ts` に定義を追加
2. `src/app/(os)/<slug>/page.tsx` を作る
3. `docs/DESIGN.md` の画面一覧に追記
4. `npm run typecheck && npm run build`
5. commit → push

**ナビを手で書き足さない。** modules.ts が唯一の正本。

## データの扱い

- Supabase 未接続でも全画面が動く状態を**壊さない**。
  `src/lib/supabase.ts` の `isSupabaseConfigured()` で分岐し、未接続ならダミーデータを出す
- 新しいテーブルが要るときは `supabase/migrations/` に SQL を足す。
  **勝手に本番へ適用しない**（適用はまさの承認後）
- RLS を付けない table を作らない

## 変更したら必ず通すもの

```sh
npm run typecheck
npm run build
```

- どちらか落ちたまま「できました」と言わない
- 落ちた場合は、落ちたという事実とエラーの要点を報告に含める

---

## やらないこと

- ブランチ / worktree を作る（AGENTS.common.md §5.1）
- `git add .` で全部まとめて stage する。**触ったファイルだけ**を指定して add する
- 相手の未 push commit を消す・巻き戻す
- 会社（AMD OS）の本番 Supabase に書き込む
- 秘密値をファイル・commit・チャットに出す
- 「たぶん動くはず」で完了報告する

```
<type>(<scope>): <日本語で1行>

- 変更点

Worked-by: kiyo   ← または masa。誰の作業かを必ず残す
```

`type` は `feat` / `fix` / `docs` / `chore` / `refactor`。
2 人が同じ GitHub アカウントを使うので、`Worked-by:` を省略しない。
