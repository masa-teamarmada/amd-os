- 作成日: 2026-06-01
- 位置づけ: 特許出願司令塔レビュー用の内部ドラフト
- 共有制限: 外部送付禁止。弁理士送付禁止。このままメール添付・Drive共有・チャット共有しない。
- 目的: 既存の内部相談パックから、営業秘密・内部事情・実案件情報を落とし、弁理士初回相談前に「何を開示候補にするか」を確認する。

## 0. このドラフトの使い方

この文書は、弁理士へ渡す完成版ではない。

内部レビューで、以下を確認するための削除版ドラフトである。

1. 初回相談で伝える発明概要が、営業秘密を出しすぎていないか。
2. 弁理士に見せる資料候補が、抽象化済みの範囲に収まっているか。
3. 実施例が、実案件名・実判断・個別プロジェクト本文なしで説明できるか。
4. 現OSとの差分を、実装パスや内部admin詳細ではなくretrofit候補として話せるか。
5. 公開済み資料棚卸しを、新規性喪失リスクの断定ではなく確認候補として扱えているか。

## 1. 相談目的

弁理士への初回相談で確認したいことは、発明をゼロから作ってもらうことではない。

相談目的は以下。

- 既存の内部ドラフトを、国内出願可能な明細書・請求項・図面の形へ整えるための論点確認。
- 請求項の主軸を、広いAI経営支援ではなく、証拠付き候補生成、人間承認、feedback、protocol化、outcome、governanceの閉ループに置く方針の確認。
- prompt、score条件、実データ、実案件、導入運用ノウハウを伏せたまま、実施可能要件・サポート要件を満たせるかの確認。
- 発明者、出願人、権利承継、共同発明者の整理。
- 初回相談から国内ミニマム出願へ進める場合の予算レンジ、追加サーチ要否、PCT判断時期の確認。

弁理士に依頼しないこと。

- 内部prompt、score条件、評価calibrationの設計。
- 実案件の営業戦略、価格、契約、導入運用のレビュー。
- 研究機関や顧客ごとの交渉戦略。
- AMD OS内部運用やconnector運用の再設計。

## 2. 今回の狙い

今回の出願準備は、短期のライセンス収益を主目的にしない。

狙いは、研究機関導入、共同研究、提携交渉、投資家説明、外部開示前の防御に使える最小限の優先日を押さえること。

特許化する候補は、実データやスコア式ではなく、以下のワークフロー / データ構造の組み合わせである。

```text
複数業務データ源
  -> 証拠メタデータ付き候補生成
  -> 人間承認 / 却下 / コメント
  -> 承認済みのみ正本反映
  -> feedbackの後続処理反映
  -> 抽象protocol化
  -> 複数事例の関連付け
  -> multi-horizon outcome
  -> system parameter governance
```

競争優位の本体である実データ、実運用、prompt、score条件、個別プロジェクト判断、導入先ノウハウは、営業秘密として残す。

## 3. 発明概要

対象発明は、研究機関、大学、企業研究所、又はスタートアップスタジオ等における研究シーズの事業化判断を支援する情報処理方法、装置、及びプログラムである。

発明の要点は以下。

- 複数種類の業務データ源から、事業化判断に関する候補データを生成する。
- 元データ全文を正本データベースへ保存せず、source種別、日付、短い抜粋、hash、抽出処理識別子、信頼度等の証拠メタデータを保持する。
- 候補データは、人間の承認、却下、コメントを受け付ける確認インターフェースへ提示される。
- 承認済み候補のみ正本へ反映され、却下又はコメントは後続の抽出条件、判定ルール、設定値、又はワークフロー定義へ反映される。
- 承認済み候補から、固有名詞を除いた事業化判断protocolを生成し、複数プロジェクト事例を関連付ける。
- 結果観測は複数期間でappend-onlyに保持し、矛盾する観測も上書きせず提示する。
- system parameterの変更候補はpending proposalとして保存され、人間承認後にversion化される。
- 法人設立前の研究シーズについて、入力カテゴリと結果観測に基づく設立時期推奨カテゴリを生成する。

## 4. 請求項の狙い

### 主請求項の候補

主請求項では、少なくとも以下を一体の閉ループとして書けるかを確認したい。

1. 複数業務データ源からの候補生成
2. 全文非保存又は必要最小限の証拠メタデータ付与
3. 人間承認 / 却下 / コメント
4. 承認済みのみ正本反映
5. feedbackの後続処理反映
6. 抽象protocol生成又は更新

確認したい論点は、protocol生成まで主請求項に含めると狭すぎるか、逆にHITL + feedbackだけだと先行技術との差が弱くなるかである。

### 従属項の候補

従属項では、以下を段階的に足す想定。

- 業務データ源の種類。
- 証拠メタデータの永続化と承認状態との関連付け。
- approved-only正本反映。
- feedbackを抽出条件、判定ルール、設定値、ワークフロー定義へ反映する構造。
- 抽象protocolと複数事例の1:N関連付け。
- multi-horizon outcome ledgerと矛盾観測表示。
- 複数異種evidence参照。
- system parameter governance。
- 法人設立前研究シーズに対する設立時期推奨カテゴリ。
- 候補、証拠、review状態、protocol、outcome、proposalの少なくとも一部を表示する確認インターフェース。
- 装置、プログラム、必要なら記録媒体の形式。

### 弱める / 出さない方向

- 実装固有のID、内部画面名、内部DB名には寄せない。
- prompt注入の具体アルゴリズムには寄せない。
- score weight、threshold、calibration、正解ラベルは請求項に入れない。
- 実案件名、実PJ本文、顧客名、研究機関名、個人名、契約条件、価格は実施例に使わない。

守秘義務又はNDA前提で、必要に応じて説明してよいこと。

- 事業化判断OSが複数業務ソースを構造化データへ変換する設計を持つこと。

## 11. 合成実施例の安全な説明

実施例は、実案件名や実データを出さず、以下のような抽象例に留める。

### 安全例A: 顧客候補検証の広狭をfeedbackで直す例

ある法人設立前の研究シーズについて、情報処理装置は、会議記録、予定イベント、クラウド文書、及び月次活動記録への参照から、顧客候補検証に関する候補データを生成する。

候補データは、根拠となるsource type、日付、短い抜粋、hash、抽出処理識別子、信頼度とともに確認インターフェースへ提示される。

レビュー担当者が「用途候補を狭く限定しすぎている」とコメントした場合、情報処理装置は、当該コメントを後続の候補生成処理における抽出条件又は判定ルールの変更候補として保存する。

候補が承認された場合、情報処理装置は、個別シーズ名及び顧客名を除去した事業化判断protocolを生成又は更新する。

### 安全例B: 設立時期推奨とmulti-horizon outcomeの例

ある法人設立前の研究シーズについて、情報処理装置は、技術成熟度、知的財産関連状態、顧客候補又は外部連携状態、チーム状態、資金又は制度対応状態、及び過去の結果観測カテゴリを参照する。

情報処理装置は、不足又は矛盾するカテゴリを識別し、設立時期推奨カテゴリを生成する。

その後、推奨に基づくアクション後の結果を、1か月後、6か月後、24か月後等の評価期間カテゴリでappend-onlyに保存する。短期でpositive、長期でnegativeの観測が生じても、一方を上書きせず、異なるhorizon及びvalenceを持つ結果観測として確認インターフェースへ提示する。

この例では、実案件名、顧客名、研究機関名、個人名、実スコア、判定weight、threshold、calibration、実source本文は使用しない。

## 12. 現OS乖離チェックの反映

現OSとの差分は、出願不能理由ではなく、retrofit候補として扱う。

弁理士へ伝える要点は以下に留める。

- 中核である候補生成、証拠メタデータ、人間承認、正本反映、feedback、protocol化は、現OSの設計・実装で比較的強い裏付けがある。
- outcome ledgerのUI、矛盾観測表示、複数evidence参照、汎用system parameter governance、設立時期推奨、統合確認UIは、設計又は部分実装に寄る。
- 出願書類では、単一画面や実DB構造に縛らず、「関連画面群」「少なくとも一部」「証拠参照又は中間関連データ」と抽象化したい。
- 弁理士には、未実装又は部分実装の要素を請求項に残す場合の説明可能性、retrofit優先順位、分割候補化を確認する。

初回相談での安全な聞き方。

> 一部要素は現OSでは分散画面又は部分実装です。明細書上は抽象実施例として書き、出願前後に最小retrofitを行う前提で、請求項に残せる範囲を確認したいです。

## 13. 公開済み資料棚卸しの反映

公開済み資料については、法的評価や新規性喪失リスクを断定しない。

弁理士へ確認したい公開候補一覧として、以下の粒度に留める。

| 公開・外部共有候補 | 現時点の扱い | 弁理士に確認したい点 |
|---|---|---|
| イベント登壇・文字起こし・配布資料候補 | 発明コアをどこまで説明したか未確認 | 概要説明のみだった場合に必要な記録の粒度 |
| 営業資料・導入提案資料候補 | 送付履歴・NDA有無・記載粒度が未確認 | どの粒度でWS-1〜WS-5/WS-6が入ると発明公開に近づくか |
| Web / note / blog / public manuscript候補 | 公開状態と発明コア表現が未確認 | 公開前後で削るべき表現、出願前に避ける表現 |
| 内部admin画面の外部画面共有候補 | 原則外部にはそのまま見せない | 守秘義務前提の画面共有で足りるか、削除版が必要か |
| 研究機関向け説明候補 | 実際の提示範囲は未確認 | 「出願準備中」「出願予定」「出願中」の安全な表現 |
| 投資家・提携先・共同研究・RFP向け説明候補 | NDA有無・資料送付有無が未確認 | 出願前に説明してよい範囲と、出願後に開示してよい範囲 |

次に集めるものは、各資料の存在、日付、外部性、資料配布有無、NDA有無、発明コアに触れた可能性である。

## 14. 弁理士に聞く質問（5個）

1. 主請求項は、HITL + feedback + approved-only master の独立候補Aと、protocol / outcome まで含む閉ループ候補Bの二段構えで検討すべきか。

3. outcome ledger、矛盾観測UI、複数evidence参照、system parameter governanceは、基幹出願に入れるべきか、分割候補にするべきか。
4. Before-Zero / 設立時期推奨は従属項・補強に留めるべきか、独立請求項も用意する価値があるか。
5. 発明者候補を代表者単独、出願人を会社とする場合、承継書面、職務発明整理、共同発明者確認として何を用意すべきか。
