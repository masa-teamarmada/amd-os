## 0. 使い方

このパックは、既存の相談パックをさらに絞った「相談当日の開示運用表」。

相談前にまさが確認することは3つ。

1. 弁理士へ見せる順番がこれでよいか。
2. `渡してよい / NDA下なら可 / 口頭限定 / 出願書類に書かない営業秘密` の分類に違和感がないか。
3. 予算上限と、今回の相談で必ず聞く質問を5個以内に絞るか。

## 1. 今回の狙い

今回の初回相談は、発明を弁理士にゼロから作ってもらう場ではない。

狙いは以下。

1. 国内出願に進める前提で、既存ドラフトの請求項・明細書・図面の形式を整える。
2. 主軸を、広いAI経営支援ではなく、`複数業務データ源 -> 証拠メタデータ -> 人間承認 -> 正本反映 -> feedback -> 抽象protocol -> outcome ledger -> governance` の閉ループに置けるか確認する。
3. 競争優位の本体である実データ、実運用、prompt、score条件、導入ノウハウを出願書類へ出しすぎない。
4. 研究機関導入、共同研究、提携交渉、投資家説明で「出願中」と言える最小限の優先日確保を狙う。
5. 15〜30万円又は30〜50万円レンジで、国内ミニマム出願として何ができるか確認する。

## 2. 相談目的

弁理士に頼むこと。

- 既存の内部版出願書類たたき台を、国内出願可能な明細書・請求項・図面形式へ整える。
- 請求項1をどこまで閉ループ化するか、狭すぎる点と弱すぎる点を見てもらう。
- 先行技術に近い単体要素を避け、ワークフロー/データ構造のAND結合として請求項を設計できるか確認する。
- 営業秘密を伏せたまま、実施可能要件・サポート要件を満たせるか確認する。
- 発明者、出願人、権利承継、共同発明者の整理を確認する。
- 予算レンジごとの作業範囲、追加サーチ要否、PCT判断時期を確認する。

弁理士に頼まないこと。

- promptやscore条件の設計。
- 実案件の営業戦略や導入運用のレビュー。
- 研究機関ごとの交渉戦略。
- AMD OS内部運用の再設計。

## 6. 開示してよい抽象表現

明細書や相談資料に入れてよい粒度。

- 複数種類の業務データ源から、事業化判断に関する候補データを生成する。
- 元データ全文を正本DBへ保存せず、source種別、日付、短い抜粋、hash、抽出処理識別子、信頼度等の証拠メタデータを保持する。
- 候補データは、人間の承認、却下、コメントを受け付ける確認インターフェースへ提示される。
- 承認済み候補のみ正本へ反映され、却下又はコメントは後続の抽出条件、判定ルール、設定値、又はワークフロー定義へ反映される。
- 承認済み候補から、固有名詞を除いた事業化判断protocolを生成し、複数プロジェクト事例を関連付ける。
- 結果観測は複数期間でappend-onlyに保持し、矛盾する観測も上書きせず提示する。
- system parameterの変更候補はpending proposalとして保存され、人間承認後にversion化される。
- 法人設立前の研究シーズについて、入力カテゴリと結果観測に基づく設立時期推奨カテゴリを生成する。

## 7. NDA下なら説明可

弁理士の守秘義務又はNDA前提で、必要に応じて説明してよいこと。

- AMD OSが複数業務ソースをL2データへ変換する設計を持つこと。
- 採否・コメント・feedbackを次回抽出へ参照する設計思想。
- protocolと事例を1:Nで管理する設計思想。
- 短期と長期で判断結果の評価が変わるため、multi-horizon outcomeが必要なこと。
- 評価モデルや抽出設定を人間承認なしに反映しない設計思想。
- 研究シーズの設立前段階で、技術、知財、顧客候補、チーム、資金、制度対応を見ながら設立時期を判断する実務があること。

このランクでは、実案件名、顧客名、個人名、契約条件、価格、個別資料本文は出さない。

## 8. 口頭限定

相談の流れで必要なら口頭だけで触れること。

- どの市場・研究機関・共同研究先に対して、出願中であることが交渉カードになるか。
- なぜロイヤリティ収益より、防御・交渉・価格維持・後出し出願防止を重視するか。
- Before-Zero領域を外部へ見せすぎると、市場機会そのものを教えるリスクがあること。
- 現OSでは一部機能が分散画面又は部分実装であり、出願前後にretrofitしたいこと。
- 弁理士へ渡す版を作る前に、社内で営業秘密混入チェックをもう一段かけたいこと。

口頭でも、実名、個別商談、契約、未公開技術、未公開知財の中身は出さない。

## 9. 出願書類に書かない営業秘密

出願書類へ入れない。弁理士にも詳細開示しない。

- system / extractor / evaluator / score revision系のprompt全文。
- few-shot、negative examples、commentを次回抽出へ変換する具体ロジック。
- model選定、fallback、temperature、chunking、retrieval条件。
- 実メール、議事録、チャット、クラウド文書、月次レポートの本文。
- 実source所在、内部source id、長い抜粋、embedding、raw transcript。
- production DBの実行、実レコード、実ログ。
- 顧客名、研究機関名、個人名、契約条件、価格、商談ログ。
- scoreの実weight、threshold、calibration、イベント加点、正解ラベル。
- 設立時期推奨の実判定条件。
- 個別案件の分岐点、判断材料、アクション、結果本文。
- 長期outcomeの個別解釈、成功/失敗ラベル、教師データ。
- connector認証、権限、監視、復旧、watch対象、運用PC、抽出スケジュール細部。
- 導入機関ごとのonboarding、レビュー会議体、担当者routing、URA/EIR訓練順序。

- 実案件名、顧客候補、商談状況、実コメント、判定条件、score条件、未公開技術・知財は出さない。

安全な聞き方。

> 実案件名や実データを出さず、匿名の法人設立前研究シーズを例に、候補生成、レビューコメント、protocol化、複数期間の結果観測、設立時期推奨カテゴリを説明するだけで、明細書の実施例として足りますか。

- 中核である候補生成、証拠メタデータ、人間承認、正本反映、feedback、protocol化は、現OSの設計・実装で比較的強い。

## 13. 予算レンジ

### 15〜30万円

初回の本命。

- 既存ドラフトの形式整備。
- 請求項レビュー。
- 営業秘密の出しすぎ防止確認。
- 国内ミニマム出願の手続き。

向いている場合:

- まず優先日を押さえる。
- 追加調査やPCTは後で判断する。
- AMD側が発明提案書、請求項案、先行技術メモを用意済み。

### 30〜50万円

基幹出願を少し厚くする現実ライン。

- 図面清書。
- 実施例の過不足レビュー。
- 先行技術差分の最低限レビュー。
- 請求項の広狭と分割候補の整理。

向いている場合:

- 研究機関導入や共同研究説明で、出願中ステータスをより安心して使いたい。

### 100万円超

今は急がない。

- 正式サーチ。
- PCT、分割、複数出願戦略。
- 請求項・図面・実施例の本格整備。

向いている場合:

- 外部展開や共同研究契約の見込みが強くなった後。
- 投資家説明や海外展開の材料として使う段階。

## 14. まさ判断事項（5個以内）

1. 初回相談の予算上限を、まず15〜30万円に置くか、30〜50万円まで許容するか。
2. 今回の出願目的を、ロイヤリティではなく、防御・交渉・価格維持・後出し出願防止に固定するか。
3. 弁理士へ最初に渡す資料は、請求項見直し案と明細書たたき台の削除版だけに絞るか。
4. outcome / governance / 設立時期推奨の薄い箇所を、基幹出願に残すか、分割候補・従属項へ下げるか。
5. 弁理士相談前に、公開済み資料棚卸しを先に1ページで済ませるか。
