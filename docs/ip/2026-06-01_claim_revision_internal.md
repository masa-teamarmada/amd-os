## 1. 結論

既存の請求項たたき台は、WS-1〜WS-5を個別に説明できている一方で、競合が一部要素だけ外すと回避しやすい。

弁理士相談前の内部方針としては、主請求項を以下の閉ループに寄せる。

> 複数業務データ源 -> 証拠メタデータ付き候補生成 -> 人間承認/却下/コメント -> 承認済みのみ正本反映 -> reject/commentの後続抽出反映 -> 抽象protocol化 + 1:N事例 -> multi-horizon outcome ledger -> system parameter governance

狙いは「広いAI経営判断支援」ではなく、AMD OS実装に近いワークフロー/データ構造のAND結合を押さえること。

## 2. 見直し方針

### 強める

- 主請求項の中に、候補生成、証拠メタデータ、HITL確認、正本反映、reject/comment feedbackを一体で入れる。
- 従属項で、abstract protocol、1:N事例、multi-horizon outcome、parameter governanceを段階的に積む。
- 外から見えるUI/workflow/export/admin画面要素を従属項に入れる。
- Before-Zero / 設立タイミング推奨は、主軸ではなく補強として残す。

### 弱める / 下げる

- `source_meeting_id` のような狭い実装名は、主請求項から外す。
- `title hash` のような特定手段は、主請求項ではなく実施例または従属項に落とす。
- `Cobb-Douglas`、実weight、score軸、calibrationは請求項に入れない。
- prompt注入の具体アルゴリズムやcomment-to-guidance変換は書かない。
- 実PJ事例本文や実データを実施例に使わない。

## 3. 改訂主請求項案

### 請求項1案: 事業化判断支援の情報処理方法

事業化判断を支援する情報処理方法であって、コンピュータが、

1. 対象プロジェクトに関する複数種類の業務データ源からソースデータ又は当該ソースデータへの参照を取得し、
2. 前記ソースデータ又は参照に基づいて、事業化判断、事業化readiness根拠、プロジェクト状態変化、又は意思決定候補の少なくとも一つを示す候補データを生成し、
3. 前記候補データに、前記ソースデータの全文を保存することなく、ソース種別、ソース識別子、ソース所在情報、日付、タイトル、所定長以下の抜粋、ハッシュ値、抽出処理識別子、及び信頼度の少なくとも一部を含む証拠メタデータを付与し、
4. 前記候補データ及び前記証拠メタデータを、承認、却下、又はコメントを受け付ける確認インターフェースに提示し、
5. 承認入力を受けた候補データを、対象プロジェクトの正本データベースに反映し、
6. 却下入力又はコメント入力を、後続の候補データ生成処理に用いられる抽出条件、入力プロンプト、判定ルール、又は設定値の少なくとも一つに反映し、
7. 前記正本データベースに反映された候補データに基づいて、プロジェクト固有情報を抽象化した事業化判断プロトコルデータを生成又は更新する、

情報処理方法。

### 内部コメント

- 既存案の「電子メール、クラウドストレージ...」列挙は従属項に下げる。主請求項では「複数種類の業務データ源」と広める。
- 「LLMへの入力プロンプトに自動注入」だけに限定せず、「抽出条件、入力プロンプト、判定ルール、設定値」に広げる。
- ただし、reject/comment feedbackは必ず入れる。ここがAMD OSらしい閉ループ。
- `正本データベース` と `事業化判断プロトコルデータ` まで主請求項に入れ、ただのHITL抽出ツールから離す。

## 4. 従属項案

### 請求項2案: 業務データ源

請求項1の方法において、前記複数種類の業務データ源は、電子メール、クラウドストレージ文書、カレンダーイベント、チャットメッセージ、会議録、ナレッジ管理ページ、月次レポート、又はプロジェクト台帳のうち少なくとも二以上を含む。

### 請求項3案: 証拠メタデータの永続化

請求項1又は2の方法において、前記証拠メタデータは、抽出処理識別子ごとに永続化され、前記候補データの承認状態、却下状態、又はコメント状態と関連付けて保存される。

### 請求項4案: 正本反映の制御

請求項1から3のいずれかの方法において、前記コンピュータは、承認入力を受けていない候補データを前記正本データベースへ反映せず、承認入力を受けた候補データのみを前記正本データベースへ反映する。

### 請求項5案: feedbackの後続抽出反映

請求項1から4のいずれかの方法において、前記コンピュータは、却下入力又はコメント入力に基づいて生成されたフィードバックデータを、後続の候補データ生成処理における抽出スコープ、抽出条件、入力プロンプト、判定ルール、又は信頼度判定の少なくとも一つに反映する。

### 請求項6案: 抽象protocol化

請求項1から5のいずれかの方法において、前記コンピュータは、承認された候補データから、プロジェクト固有名詞を除去又は抽象化した意思決定パターンを生成し、当該意思決定パターンを、分岐点、判断材料、アクション、及び結果カテゴリの少なくとも一部を含む事業化判断プロトコルデータとして保存する。

### 請求項7案: 1:N事例構造

請求項6の方法において、前記コンピュータは、同一又は類似の意思決定パターンを同一のプロトコル識別子に関連付け、前記プロトコル識別子に対して複数のプロジェクト固有事例を紐づけて保存し、各プロジェクト固有事例は、当該事例に固有の分岐点、判断材料、アクション、対象プロジェクト識別子、発生日、及び出典証拠識別子の少なくとも一部を含む。

### 請求項8案: multi-horizon outcome ledger

請求項6又は7の方法において、前記コンピュータは、前記事業化判断プロトコルデータ又は前記プロジェクト固有事例に紐づくアクション後の結果を、観測時点、評価期間カテゴリ、評価極性カテゴリ、信頼度、要約、及び証拠メタデータの少なくとも一部を含む結果観測データとしてappend-onlyに保存する。

### 請求項9案: 矛盾観測の保持UI

請求項8の方法において、同一のプロトコル識別子又はプロジェクト固有事例に対して、評価期間カテゴリが同一であり評価極性カテゴリが異なる複数の結果観測データが共存する場合、前記コンピュータは、当該複数の結果観測データを上書きすることなく、意思決定者の確認インターフェースに呈示する。

### 請求項10案: 異種evidence統合参照

請求項8又は9の方法において、前記結果観測データの証拠メタデータは、会議録、月次レポート、組織内キーパフォーマンス指標、戦略シグナル、プロジェクト状態変化記録、又は外部制度情報のうち少なくとも二以上の異種ソースからの参照を含む。

### 請求項11案: system parameter governance

請求項1から10のいずれかの方法において、前記コンピュータは、大規模言語モデルへの入力プロンプト、抽出ルール、判定ルール、設定値、スコアリングモデル、又はワークフロー定義のうち少なくとも二以上を含む複数種類のシステムパラメータに対して、AI又は人間が生成した変更候補をpending proposalとして保存し、前記pending proposalを確認インターフェースに提示し、承認入力を受けた場合に限り、当該変更候補を反映した新たなシステムパラメータを新規versionとして保存する。

### 請求項12案: governanceの統一適用

請求項11の方法において、前記コンピュータは、前記複数種類のシステムパラメータに対して、pending proposalとしての保存、確認インターフェースへの提示、承認入力に基づく新規version保存、及び過去version保持を含む同一の処理パターンを統一的に適用する。

### 請求項13案: Before-Zero適用

請求項1から12のいずれかの方法において、前記対象プロジェクトは、法人設立前の研究シーズ段階にあるプロジェクトであり、前記コンピュータは、前記正本データベースに反映された候補データ、前記事業化判断プロトコルデータ、又は前記結果観測データの少なくとも一つに基づいて、当該研究シーズについて法人を設立すべき時期を推奨する設立時期推奨データを生成する。

### 請求項14案: UI/外部検出可能要素

請求項1から13のいずれかの方法において、前記確認インターフェースは、候補データ、証拠メタデータ、信頼度、承認状態、却下状態、コメント、プロトコル識別子、プロジェクト固有事例、結果観測データ、又はpending proposalの少なくとも一部を表示する。

### 請求項15案: 装置/プログラム

請求項1から14のいずれかの方法を実行するプロセッサ及びメモリを備える情報処理装置、又は当該方法をコンピュータに実行させるプログラム。

## 5. 既存案からの主な変更点

| 論点 | 既存案 | 見直し案 |
|---|---|---|
| 主請求項 | 業務データ源列挙 + candidate + evidence + HITL + prompt injection | 複数業務データ源 + evidence + HITL + approved-only master DB + feedback + abstract protocolまで一体化 |
| source | `電子メール、Drive...` を主請求項に列挙 | 主請求項は「複数種類の業務データ源」、列挙は従属項 |
| prompt feedback | LLM promptへの自動注入 | 抽出条件、prompt、判定ルール、設定値に広げる |
| protocol identity | 題目hashを明示 | 主軸はidentity determination、hashは実施例/従属項候補 |
| examples | `source_meeting_id` | `出典証拠識別子` に広げる |
| outcome | schema中心 | 矛盾観測保持UI + 異種evidence統合参照を前面に |
| governance | score model寄り | prompt/rule/config/model/workflow stepの横断governance |
| Before-Zero | 独立請求項感が強い | 従属・補強で残す |

## 6. 弁理士に確認したいポイント

1. 主請求項にabstract protocol生成まで入れると、狭くなりすぎるか。逆にHITL抽出だけに留めると先行技術で弱くなるのではないか。
2. reject/comment feedbackを「prompt注入」と明示するか、「抽出条件/判定ルール/設定値への反映」と広く書くか。
3. `full text非保存` はBigID回避のため必須要素にするべきか、従属項に下げるべきか。
4. protocol identityを、hash、embedding cluster、manual tag、UUIDなどを含む広い表現にするにはどう書くべきか。
5. outcome ledgerは、FHIR/OMOPを避けるため、矛盾観測保持UIと異種evidence統合参照をどこまで請求項に入れるべきか。
6. system parameter governanceは、基幹出願に入れるか、分割候補として切り出すか。
7. Before-Zero/設立タイミング推奨は従属項で十分か、独立請求項を残す価値があるか。
8. 請求項14のUI/外部検出可能要素は、侵害検出上の実益がある一方、不要に狭くならないか。

## 7. 出願書類に書かないこと

## 8. まさ向け判断

この見直し案では、弁理士相談時の軸を以下に固定する。

- 広い「AI経営判断支援」ではなく、AMD OSの閉ループを押さえる。
- 単体要素の独占ではなく、WS-1〜WS-5のAND結合で取る。
- prompt/score/calibration/実例本文は出さない。
- Before-Zero/設立タイミングは補強に置く。
- 侵害検出用に、外から見えるUI/workflow要素を従属項に入れる。
