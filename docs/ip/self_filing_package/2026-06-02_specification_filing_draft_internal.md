# 明細書候補（内部提出形式候補版）

- 作成日: 2026-06-02
- 位置づけ: 完全セルフ出願に向けた明細書提出版候補。実提出版ではない。
- 重要: 外部送付禁止。JPO提出禁止。弁理士問い合わせ禁止。
- 記載制限: 実案件名、顧客名、個人名、契約条件、未公開知財詳細、prompt全文、score weight / threshold / calibration、実DB行、source permalinkは入れない。

## 0. 公式形式メモ

JPO「明細書: 特許」では、`書類名 明細書`、`発明の名称`、`技術分野`、`背景技術`、`発明の概要`、`発明が解決しようとする課題`、`課題を解決するための手段`、`発明の効果`、`図面の簡単な説明`、`発明を実施するための形態`、`符号の説明` 等の記録項目が示されている。また、段落番号は4桁のアラビア数字で連続番号を付す形式が示されている。

## 1. 明細書候補

```text
【書類名】明細書

【発明の名称】
研究シーズの事業化判断を支援する情報処理装置、情報処理方法、及びプログラム

【技術分野】
【0001】
本発明は、研究機関、大学、企業研究所、又はスタートアップスタジオ等における研究シーズの事業化判断を支援する情報処理技術に関する。

【0002】
より具体的には、本発明は、複数種類の業務データ源から事業化判断に関する候補データを生成し、証拠メタデータを付与し、人間の承認を経て正本データベースへ反映し、却下又はコメントを後続処理へ反映し、事業化判断プロトコル、プロジェクト固有事例、結果観測データ、及びシステムパラメータの改訂履歴を管理する情報処理装置、情報処理方法、及びプログラムに関する。

【背景技術】
【0003】
大学又は研究機関発の技術シーズを事業化する過程では、技術成熟度、知的財産、顧客候補、研究者又はチームのコミットメント、資金調達可能性、規制、共同研究、及び市場仮説等の情報が、複数の業務ツールに分散して存在する。

【0004】
例えば、電子メール、クラウドストレージ上の文書、カレンダーイベント、チャットメッセージ、会議録、ナレッジ管理ページ、月次レポート、プロジェクト台帳、プロジェクト状態変化記録、戦略シグナル、及び外部制度情報等に、事業化判断に必要な情報が断片的に記録される。

【0005】
従来、CRM、プロジェクト管理ツール、議事録要約ツール、文書検索ツール、データカタログ、又はスタートアップ評価ツール等は存在する。しかし、これらは、個別の情報整理、検索、要約、又は評価に留まることが多い。

【0006】
また、AI等により抽出された候補情報をそのまま正本データベースへ反映すると、誤抽出、過剰な要約、根拠不明な評価、又は営業秘密の混入が生じるおそれがある。

【0007】
さらに、一度行われた事業化判断が短期的には有効でも、中長期的には異なる結果をもたらすことがある。このため、結果を単一フィールドで上書きするだけでは、判断知見を再利用しにくい。

【発明の概要】

【発明が解決しようとする課題】
【0008】
本発明が解決しようとする課題は、複数業務データ源からAI等により生成された候補を、根拠証拠、人間確認、正本反映、後続処理へのフィードバック、抽象プロトコル化、及び結果観測へ一貫して接続し、誤抽出の正本混入と判断履歴の断絶を抑制することである。

【0009】
具体的には、本発明は、以下の少なくとも一部を実現することを目的とする。
（1）複数業務データ源に散在する判断材料を、出典証拠とともに候補データ化すること。
（2）元データ全文を正本データベースへ保存せず、必要最小限の証拠メタデータで監査可能性を確保すること。
（3）AI等が生成した候補データを、人間の承認、却下、又はコメントによって制御すること。
（4）却下又はコメントを後続の候補生成処理へ反映し、同種の誤抽出を低減すること。
（5）承認済み候補データから、プロジェクト固有情報を抽象化した事業化判断プロトコルを生成すること。
（6）1つの事業化判断プロトコルに複数のプロジェクト固有事例を関連付けること。
（7）同一判断に対する短期、中期、長期の結果観測を上書きせず保持すること。
（8）矛盾する結果観測を保持したまま意思決定者に提示すること。
（9）システムパラメータの変更候補を、人間承認を経てversion管理すること。
（10）法人設立前の研究シーズについて、法人設立時期の推奨を支援すること。

【課題を解決するための手段】
【0010】
本発明の一態様は、研究シーズの事業化判断を支援する情報処理方法であって、コンピュータが、対象プロジェクトに関する複数種類の業務データ源からソースデータ又は当該ソースデータへの参照を取得し、当該ソースデータ又は参照に基づいて候補データを生成し、候補データに証拠メタデータを付与し、候補データ及び証拠メタデータを確認インターフェースに提示し、承認入力を受けた候補データを正本データベースへ反映し、承認入力を受けていない候補データを正本データベースへ反映しないよう制御し、却下入力又はコメント入力を後続の候補データ生成処理へ反映する、情報処理方法である。

【0011】
本発明の別の態様では、コンピュータは、承認済み正本レコードに基づいて、プロジェクト固有情報を抽象化した事業化判断プロトコルデータを生成又は更新し、当該事業化判断プロトコルデータに複数のプロジェクト固有事例を関連付け、当該プロジェクト固有事例に紐づくアクション後の結果を、複数の評価期間カテゴリ及び評価極性カテゴリを含む結果観測データとしてappend-onlyに保存する。

【0012】
本発明のさらに別の態様では、コンピュータは、複数種類のシステムパラメータに対する変更候補をpending proposalとして保存し、確認インターフェースに提示し、承認入力を受けた場合に限り、新たなシステムパラメータを新規versionとして保存する。

【0013】
本発明のさらに別の態様では、対象プロジェクトは法人設立前の研究シーズ段階にあるプロジェクトであり、コンピュータは、正本データベースに反映された候補データ、事業化判断プロトコルデータ、プロジェクト固有事例、結果観測データ、又は承認済みシステムパラメータversionの少なくとも一つに基づいて、法人設立時期推奨データを生成する。

【発明の効果】
【0014】
本発明によれば、複数業務データ源に分散した研究シーズの事業化判断材料を、出典証拠とともに構造化し、人間承認を経て正本化することができる。

【0015】
また、元データ全文を正本データベースへ保存しない証拠メタデータを用いることで、機密性を維持しながら判断候補の根拠を確認できる。

【0016】
また、却下入力又はコメント入力を後続の候補生成処理へ反映することにより、AI等による同種の誤抽出又は過剰抽出を抑制できる。

【0017】
また、承認済み候補データからプロジェクト固有情報を抽象化した事業化判断プロトコルを生成し、複数プロジェクト事例を関連付けることにより、個別案件の経験を再利用可能な判断知見として蓄積できる。

【0018】
また、同一判断に対する短期、中期、長期の結果観測をappend-onlyに保存し、矛盾する結果観測を保持したまま提示することにより、判断の有効性を時間軸に沿って評価できる。

【0019】
また、システムパラメータに対する変更候補を、人間承認を経てversion管理することにより、評価ルール又は処理条件の変更を監査可能にできる。

【0027】

【0029】

【0030】

【0031】
図5に示すように、結果観測管理部200は、事業化判断プロトコル270又はプロジェクト固有事例280に紐づくアクション後の結果を、観測時点、評価期間カテゴリ、評価極性カテゴリ、信頼度、要約、及び証拠参照300の少なくとも一部を含む結果観測データ290としてappend-onlyに保存する。

【0032】

【0038】
図8に示すように、統合確認インターフェース又は関連画面群330は、候補データ230、証拠メタデータ240、信頼度、承認状態、却下状態、コメント、事業化判断プロトコル270、プロジェクト固有事例280、結果観測データ290、証拠参照300、パラメータ変更候補310、又は法人設立時期推奨データ340の少なくとも一部を表示してもよい。

【0039】
本実施形態における抽象レコード遷移の一例は以下の通りである。第一に、source referenceとして、source type、日付、title、短い抜粋、hash、run idが生成される。第二に、candidate dataとして、検証状態、知財関連状態、チーム状態等の候補が生成される。第三に、review feedbackとして、approve、reject、comment summary、target categoryが保存される。第四に、承認済み候補のみがmaster recordとして正本化される。第五に、固有名詞を除いたbranch point、criteria、action、result categoryがprotocolとして保存される。第六に、horizon、valence、confidence、summary、evidence roleを含むoutcome observationが保存される。第七に、抽出条件又は判定ルール等の変更候補がparameter proposalとして保存される。第八に、不足又は矛盾カテゴリに基づくrecommendationが生成される。
```

## 2. 先行技術別の逃げ方

| 攻撃されるカテゴリ | 明細書上の差分 |
|---|---|
| データカタログ / BigID系 | 全文非保存単体ではなく、正本DB全文非保存、短い抜粋又はhash、run単位evidence、HITL、approved-only master、protocol / outcomeへの連鎖を明記 |
| 企業内検索 / RAG / Seek AI / Glean系 | 単なる検索又は要約ではなく、事業化判断候補の正本化、reject/comment feedback、protocol化、outcome追跡を明記 |
| FHIR / OMOP等の観測スキーマ | 医療観測ではなく、事業化判断protocol / action後のmulti-horizon outcome、矛盾観測、異種evidence参照を明記 |
| MLOps / Ciena系 | model approvalではなく、抽出 / 判定 / workflow等の複数parameterを事業化判断ループへ接続することを明記 |
| CRM / BI / decision log | dashboardではなく、証拠付き候補、approved-only master、再利用protocol、feedback loopを明記 |

## 3. 営業秘密scan

- 実案件名、顧客名、個人名、契約条件は記載なし。
- prompt全文、few-shot、comment-to-guidance具体ロジックは記載なし。
- score weight、threshold、calibrationは記載なし。
- production DB row、source permalink、実URL、実テーブル名は記載なし。
- 実施例は抽象レコード遷移に限定。
