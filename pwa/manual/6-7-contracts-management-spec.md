# 契約管理

`/admin/contracts` は、契約締結の予兆から押印版保存までを追う backoffice 画面。契約書は機密性が高いので、初期実装では admin だけが見られる。

## 見るもの

主リストは契約書ファイル一覧ではなく、**AMDが当事者として確認済みの契約台帳**。**1行は1つの契約**を表す。ドラフト、修正版、PDF / Wordなどの形式違い、押印版は別契約にせず、その契約の「文書と版」にまとめる。AMD非当事者の第三者間契約と雛形は主リストへ出さない。

一覧はパソコンでもスマホでも表で表示する。情報を項目ごとの列で見比べられる。

| 表示項目 | 見られる列 |
|---|---|
| 基本情報 | PJ、契約名、相手先、種別、状態、押印証跡、締結日、開始日、終了日、契約額、月額、支払条件、契約書、確認事項 |
| 実務条件 | 更新、通知期限、金額・支払、税、業務範囲・目的、成果物、検収、費用、報告、知財、利用権、秘密保持、再委託、競業、解除、責任、管轄、担当などをそれぞれ別の列で確認 |
| 全項目 | すべての32列を表示 |

最初は「基本情報」。表の上のボタンで切り替える。横へスクロールすると右側の項目が見られる。見出しと契約名を固定しているので、スクロールしても比較中の契約を見失わない。パソコンではPJも固定する。

長い内容は2行まで表示する。契約名を押すと詳細モーダルが開き、全文・契約の文書と版・関連記録を確認できる。「契約書」のリンクから現在版を直接開くこともできる。金額が未確認の場合は「未確認」、確認済みの0円は「0円」と表示する。押印完了後の保存手順は上部の「押印完了後の保存・登録方法」を開いて確認する。

一覧上部で、契約の状態、PJ状態、並び順、PJ個別指定を切り替えられる。PJ状態は `稼働中PJ`、`非アクティブ/未確認PJ`、`全PJ状態`。稼働中PJは `active` と `sales` を含む。並び順は `締結日 新しい順 / 古い順` を基本に、終了日、更新通知期限、最新活動、PJ、契約名でも並べ替えられる。締結日が未確定の契約は、押印予定日、発効日、最新活動日の順に代替して並べ、日付がないものは末尾に置く。

モーダルの最初の `実務条件` には、当事者、状態、PJ現行指定に加えて、期間・更新、金額・支払、業務・成果物、費用負担、知財・利用、秘密保持・制限、解除・責任、文書・根拠をカテゴリ別に出す。例に挙がった項目だけを固定カラムにしない。

「押印済み記録」と「現在版の押印証跡」は別に確認する。現在の契約記録が指す押印版IDまで一致した時だけ「押印完了」。現在状態が押印済みでも一致する押印版がなければ「証跡なし」、以前の押印版があっても新しい修正・再締結が進行中なら「更新中」と表示する。

契約の終了日は、その契約に登録された終了日だけを確定回答に使う。PJの終了予定やPJへ反映済みの契約期間があっても、対象契約へ直接紐付いていなければ参考表示に止める。

送付先確認、微修正、DocuSign送付依頼のような過去の作業記録は消さない。ただし主リストの契約を増やさず、「関連記録」にまとめる。保存後は同じ契約IDで明示的に結び、契約名の似かたに頼り続けない。

実務条件は契約ごとに保存する。PJコックピットへ表示する契約は `現行契約として表示` を選び、複数契約は混ぜずに別々に表示する。同じPJ内の未紐付け候補を回答へ混ぜない。未確認を `0円`、`なし`、`申請可` と表示しない。

契約詳細の `PJコックピット用サマリ` には、法務条項の要約ではなく、請求タイミング、振込タイミング、業務、成果物、経費、推進条件だけを短く入れる。通常契約のコックピットは契約期間を合わせた最大5項目で、請求・振込タイミングを必ず表示する。知財、秘密保持、解除、責任などは契約詳細に残し、PJ契約タブの「契約の論点・必要な手続き」と折りたたみの条項要約でも確認できる。NDAだけは利用目的と運用条件を優先する。

初期表示は `AMD当事者契約`。人が当事者を確認した契約と Contract Apply 済み契約だけを出す。自動取込は `当事者判定待ち` に止め、AMD名を含むだけでは主台帳へ出さない。第三者間契約と雛形は除外区分で保持する。

`要確認` は「OSでユーザーが手入力する」意味ではない。OSが5生データ、Drive、押印版、請求・見積などから拾った候補について、根拠を見て採用・除外・補正するレビュー状態。たとえば相手先名が空の場合は、契約本文・押印版・請求/見積の根拠から正式名称候補を採用できるか確認する、という意味になる。

| 項目 | 内容 |
|---|---|
| 契約予定枠 | 予兆または手動で作った契約候補 |
| status | `予定枠` / `作成中` / `レビュー中` / `押印待ち` / `押印済み` / `停滞` / `中止` |
| version history | 契約書ドラフト、修正案、赤入れ、押印版のDrive metadata |
| signed missing | 押印版がまだ登録されていない契約 |
| 契約条件候補 | D-13 が見つけた契約No・期間・金額・相手先の候補。review後に applied へ進むまでは本番数字へ反映しない |
| dry-run | 5生データからの予兆候補と、Slack nudge候補 |

## ファイルの置き場

契約書ファイル本体はDriveに置く。

```text
共有ドライブ/ARMADA/a3_backoffice/契約
```

OSにはDrive file id、link、version label、押印版かどうかだけを保存する。契約書本文やメール全文はDBに入れない。

## DocuSign / クラウドサイン完了後

押印リレーが終わっても、現時点ではOSがDocuSignやクラウドサインから完了PDFを自動取得してDriveへ保存するわけではない。完了後は管理者が次の作業をする。

1. DocuSign / クラウドサインから完了PDFを取得する。完了証明書や署名証明書が別ファイルで出る場合は、それも同じ契約の証跡として扱う。
2. Driveの `共有ドライブ/ARMADA/a3_backoffice/契約` 配下で、該当PJまたは該当契約のフォルダへ保存する。
3. `/admin/contracts` で契約行を開き、`文書と版` の `Drive文書を追加` から `文書の種類 = 押印版` を選んでDriveリンクを登録する。
4. 登録すると、OSは `contract_documents` にDrive metadataを保存し、契約状態を `押印済み記録` に更新する。

自動で行うのは、Driveリンク登録後の台帳更新と、押印版が未登録の契約を通知候補に出すところまで。DocuSignからのファイル取得、Drive保存、Drive共有変更、Slackへの実送信はまだ自動化していない。

## 予兆検知

予兆dry-runは Gmail / Slack / Notion / Drive / Calendar の5生データを見て、`契約書`、`NDA`、`業務委託`、`共同研究契約`、`MOU`、`押印`、`電子署名`、`DocuSign`、`クラウドサイン`、`修正案`、`法務確認` などを拾う。

高確度のものだけ予定枠化候補。曖昧なものはreview扱いにする。

MTGタイトルや議事録本文に「契約」「締結」があるだけでは契約台帳行にしない。契約種別、契約文書、署名/押印/修正/法務確認などの具体的な文書アクションが揃わないものは evidence のまま残す。

契約No・見積No・期間・金額に加えて、支払、業務範囲、成果物、検収、報告、費用負担、更新、知財、利用/公開、秘密保持、再委託、独占/競業、解除、責任、準拠法/管轄を読める場合は、契約条件候補として表示する。候補の段階では契約条件も売上・予実・報酬capも確定しない。adminが内容を確認して `applied` にした後、Contract Apply 経由で契約台帳と `projects.contract_terms_json` / `value_plan_cycles` / `billing_cycles` に反映される。

NDAや覚書のように金額・契約期間が未確定でも、実務条項は `条件だけ反映` できる。この場合はPJの料金、PJ期間、請求cycleを変更せず、契約台帳とPJコックピットだけを更新する。

monthly_fixed 契約でも、未確定の月別 `billing_cycles.budget_yen` と現行 `value_plan_cycles.budget_yen` は契約 cap (= 月額税抜×65%、バッファなしの場合) へ整合する。古い一括生成データにクライアント支払額そのものが入っていると、当月自動確定だけが正しい65%へ直り、未来月だけ古い値が残る。KUTE で起きた事故はこの混在が原因なので、Contract Apply はこの状態を温存しない。契約/シーズンバッファがある PJ は単純上書きせず、バッファ込みのシーズン原資を優先する。

## Nudge

押印版が保存されないまま一定日数を過ぎた契約は、Slack nudge候補になる。初期実装はdry-runだけで、Slackへ実送信しない。

実送信に進む時は、送信先PJ channel、文面、対象件数、送信タイミングを確認してから進める。

## PJから秘密情報の開示条件を確認する

コックピットの「PJ管理 → 契約」を開く。各現行契約の下に「契約の論点・必要な手続き」がある。問いを押すと、回答、必要な手続き、まだ確定していないこと、原文・条項・確認日を読める。「追加確認が必要」は最初から開いている。

「条項確認済み」は条項を読んだ結果であり、今回の開示が承認された意味ではない。「契約上の義務」と「開示前の確認」を分けて読む。開示する情報・相手先・目的・範囲に対する承認記録を確認してから開示する。原本リンクはDriveの閲覧権限に従う。「権利・制限・責任の条項要約」では、秘密保持・知財・再委託などの全文要約を確認できる。未登録の論点は手続き未確認と表示する。

SOLの大学との契約では、個人情報の漏えい・目的外利用禁止と、大学の承諾を条件とする再委託を確認できる。技術・事業の秘密情報全般の開示条件は、大学との別NDA・仕様書等と大学への確認が残る。開示先とのNDAだけで大学の情報を開示できるとは扱わない。


## 押印申請と契約メールのアラート（2026-10-08）

管理メニューの「業務フロー」、または「きよ」→「押印承認」を開く。契約管理の未締結AMD契約の詳細からも「契約フロー」を開ける。

1. 「契約フローを開始」で、相手先・契約の種類・契約名・対象PJ・契約の目的を入力する。株式会社チームアルマダが当事者となることを確認する。押印希望日は任意。契約書がまだなくても開始できる。すでに登録した契約は「登録済みの契約」から選び、相手先・種類を確認する。
2. 開始すると「契約書の準備中」として保存され、同じ案件の詳細が開く。詳細の「フローの進み方」には開始・契約書の準備・きよの承認・押印と締結版の保存・締結版の照合・完了を常時表示する。「現在」と次の担当・必要な作業を確認する。
3. 契約本文と添付を含む最終版PDFをDriveに保存し、詳細にDriveリンクを登録する。WordはPDFに変換する。登録済みの最新版PDFも選べる。「きよへ押印申請」でPDF・契約条件が固定され、まさ・きよへ個別Slackで承認依頼を通知する。準備開始だけでは承認依頼の通知は送らない。
4. きよが固定PDFと条件を確認し、承認またはコメント付きの差戻しを行う。まさ自身は承認できない。
5. まさが承認対象を確認して「承認対象の押印手続きへ進む」を押す。紙や電子署名サービスでこの版に押印・署名する。
6. 完了PDFをDriveに保存し、この詳細で「締結版を登録」する。契約管理の「文書と版」からの登録も使える。締結版がそろうと「きよの締結版照合待ち」となる。きよが締結版と承認対象を照合し「締結版を照合して完了」にする。

差戻し・文書や条件の変更では「契約書の準備」に戻る案内が出る。申請者が「再申請を準備」で新しい申請を開始する。前の申請・承認・差戻し理由は履歴として保持し、変更後に元の承認を使わない。実際の締結版がすでに登録されている場合は、契約管理で事実と次の手続きを確認する。準備中でも申請者がフローを取り下げられる。取下げは契約台帳の削除や契約取消を意味しない。

まさの送受信メールを5分ごとに確認し、契約のやりとり・署名/押印依頼・完了連絡を検知すると、まさときよの個別Slackへ件名とOSリンクを送る。本文や添付は送らない。監視開始前のメールは通知しない。ルールで見つけるので見逃し・誤検知はあり得る。「契約メールの監視」で最終確認時刻、検知したメール、2人への配信結果を確認できる。完了連絡は承認記録との照合が必要。監視停止や配信失敗が表示されたら接続を確認する。配信結果不明は二重通知を防ぐため自動再送しない。

このフローでOS内の承認を必須にできる。紙の印章や外部電子署名の操作自体を止めるには、それぞれの保管・権限の制御も必要だよ。以前からあるD-13の通知候補確認とは別の、今回指定された2人への通知経路。

2026-10-10: 業務フローはスマホでも申請・検索・閉じる操作を押しやすく統一。最終版の未押印PDFが未登録なら、契約管理で登録してから申請。監視開始の成功が未確認の状態は、監視中として表示しない。

2026-10-10 21:00 JST: 契約フローを相手先・種類・目的の登録から開始し、全ステップ・現在地・担当・必要な文書を同じ案件で確認できるように変更。準備開始と押印申請・通知を分離。

詳細を開くと先頭に相手先・契約の種類と「フローの進み方」が表示される。入力欄はその下にあり、現在の担当と次の作業を確認してから操作できる。
