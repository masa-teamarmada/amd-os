# 6-11 きよ お金の流れ

## 目的

きよが月次経理の作業（立替精算・請求書・メンバー支払）に入る前に、AMDに「どこからいくらお金が入り、何に使われたか」の全体像を会計知識なしで理解できるようにする。B/Sや試算表の再現ではない。1円単位の正確な帳簿はfreeeが正本で、この画面は構造を掴むためのざっくり全体図と位置づける（画面上にもこの旨を明記する）。

まさ確定（2026-08-27）: A案（流れ図）+ B案（3ステップの数字リスト）のハイブリッド。行クリックのドリルダウンあり。

## 画面

`/admin/kiyo` のタブ先頭に **「00 お金の流れ」** を追加する（`KIYO_TASKS` の先頭、step "00"）。既定で開くタブは現状どおり立替精算のまま。

上から順に:

1. **期間切替**: 「今月 / 今シーズン / ぜんぶ」の3択セグメント。既定は今シーズン。シーズン境界は `pwa/src/lib/finance/season-finance.ts` の既存定義を使う。
2. **流れ図（A）**: 自作SVGのサンキー風。左=どこから（PJ別、金額比例の帯）、中央=AMDの財布（最新残高を表示）、右=何に使ったか（5分類）。ノードは細い棒、ラベルは棒の外側横に「名前 金額」1行。**縮尺（円→px）は全列共通**で、帯の太さ=ノードの高さを厳密に一致させる（列ごとに正規化すると帯がノードからはみ出す）。入りが出より少ない期間は、財布ノード下部に入り帯の無い領域が残り「財布の残りから出した分」が視覚的に見える（金額は財布カードの差引行に示す）。帯・ノードのクリックで下のB該当行を展開してスクロール。
3. **3ステップ（B）**: 「1 入ってきたお金」「2 AMDの財布」「3 使ったお金」。広い画面（xl以上）では流れ図の右に財布カード+ことばのまとめ+注記を並べ、その下に「入ってきた」「使った」の2カラム。財布カードは大きな数字の1枚看板にせず、残高・期間の入り・出・差引・借入残の密な表にする。1と3は行ごとに横棒+金額、行クリックで内訳をアコーディオン展開（「何を数えているか」の説明も展開時に表示）。
4. **ことばのまとめ**: 固定文。「クライアントから入ったお金のうち約65%は、そのPJで働いたメンバーへの報酬になる。残りで会社の家賃やツール、社会保険・税金、借入の返済を払い、余った分がAMDの財布に貯まる。」
5. **注記**: 「この画面はお金の流れを掴むためのざっくり全体図。数字は万円で丸めていて、1円単位の正確な帳簿はfreeeで見る。」

表示原則:

- 金額は万円で四捨五入（ドリルダウンの支払明細だけ円単位可）。
- **実績のみを数える。予定を実績として出さない**（予定×経過月数のような掛け算は禁止。返済予定などは金額ではなく理由行として添える）。
- PJはクライアント名（請求書の宛先）を併記する。`projects` にクライアント名の列が無ければPJ名のみで出し、正本にその旨を追記する。
- 色は入り=緑系、出=暖色系。既存きよページのフラットなテイスト（rounded-none、border、ライト/ダーク両対応）に合わせる。ネオン系にしない。
- モバイル幅でも崩れない。流れ図が読めない幅ではBだけでも完結して読めること。
- **情報密度（まさ絶対ルール）**: 流れ図はSVG実寸固定（幅720px）で、ウィンドウ幅に合わせて拡大しない。幅いっぱいに伸ばすと文字と余白だけが膨らんで密度が落ちる。広い画面の余り幅は隣の財布カードと下の内訳表が使う。狭い幅では図をコンテナの横スクロールで見せる（縮小して文字を潰さない）。1画面（1280×800）で図・財布・入り出両表が同時に見えること。

## データ定義（分類と出どころ）

すべて既存テーブルの読み取りだけで作る。新テーブル・手入力は作らない。

### 入ってきたお金（どこから）

| 項目 | 出どころ |
|---|---|
| PJ別の入金 | `billing_cycles` で `payment_confirmed_at is not null`。期間判定は `payment_confirmed_at`（JST）。金額は `budget_reported_amount` 優先、無ければ `budget_yen / 0.65` で逆算（`live-monthly-pl-inputs.ts` と同じ規約）。両方nullは0円の月として数えない |
| 別財布の収入 | `billing_cycles.extra_revenue_json` を `extra-revenue.ts` の既存展開関数で合算し、該当PJの行に含める |

ドリルダウン: PJ行 → 月別の入金リスト（◯年◯月分・金額・入金確認日）。

### 使ったお金（5分類）

| 分類 | 出どころ | ドリルダウン |
|---|---|---|
| メンバーへの報酬 | `member_payout_settlements`（freee銀行明細と消込済みの実振込）。期間判定は `paid_on` | 人別合計（`members.member_name` で表示）→ 人クリックで `monthly_reward_payout` のPJ別のめやす（発生ベースのため振込額とはズレる旨を小さく注記） |
| 役員報酬 | `company_actual_monthly` の `category='fixed_cost'` かつ `account_name='役員報酬'`。期間判定は `ym` | 月別 |
| 社会保険・税金 | `company_payment_obligations` の `status='paid'`（`paid_amount_yen` 優先、期間判定は `paid_at`）+ `company_actual_monthly` の `account_name='租税公課'` | 支払記録の明細（title・支払日・金額） |
| 会社の運営費（家賃・ツールなど） | `company_actual_monthly` の `fixed_cost` から「役員報酬」「法定福利費」「租税公課」を除いた全科目 | 科目別合計（地代家賃、通信費、消耗品費…は科目名のまま表示） |
| まだ分類できていない | 口座の実際の出金合計 − 上記4分類の合計（下の「口座の実際の動きへ合わせる」参照） | 既知の理由行 + **freeeの「自動で経理」に未処理のまま残っている実明細**（`freee_reconciliation_findings` の最新runの `unprocessed_entry`。日付・摘要・口座・金額）。freeeで登録すべき作業リストとしてそのまま使える |

**借入の返済は独立分類として出さない**。`company_finance_recurring_items` の月額は予定であり、実績として掛け算してはいけない（2026-08-27 まさ指摘で是正）。実際の返済は freee 取引履歴の `loan_payment` カテゴリに入る想定だが現状0件のため、口座から出た分は「まだ分類できていない」に含まれ、予定額は理由行として添える。

二重計上の防波堤: `fixed_cost` の「法定福利費」は社会保険の納付（`company_payment_obligations` 側で計上済み）と重なるため、**どの分類にも入れない**。

### AMDの財布

| 項目 | 出どころ |
|---|---|
| いまの残高 | `company_actual_monthly` の `category='cash_balance'` の最新 `ym`。無ければ「同期待ち」表示（freee APIを画面から直叩きしない） |
| 期間の増減（差引） | アンカリング時は口座の実際の増減（現金カテゴリの入り − 出）。非アンカリング時は内訳で拾えている分の差。どちらを見せているかは財布カードに一行で明記する |
| 借りているお金の残り | `company_budget_inputs` の loans に残高情報があればそこから算出して表示。無ければ第一版では出さない |

### 口座の実際の動きへ合わせる（アンカリング）

内訳は請求台帳（入金確認）・銀行明細・freee仕訳（発生）の3系統から作るため、必ず口座の実際の動きより少なくなる。**内訳の合計を「入り」「出」として出すと、同じ画面の残高と矛盾する**（差引が実際の増減と合わない）。そこで:

- 期間内の経過月すべてで `company_actual_monthly` の現金カテゴリ（入り: `cash_inflow` / `spot_income` / `loan_disbursement`、出: `cash_outflow` / `spot_expense` / `loan_*` / `tax_payment_*` / `social_insurance`）が揃っているとき、**入り・出の合計を口座の実額に一致させる**（`wallet.anchoredToBank = true`）。
- 実額と内訳の差は「**まだ分類できていない**」として、入り側は擬似PJ（`UNCLASSIFIED_PROJECT_ID`）、出側は `key: "unclassified"` のカテゴリで**グレーの帯として明示する**。差を隠さないことが目的で、この帯が小さいほどお金の流れを説明できている。
- 揃っていない期間（例: 現金カテゴリが2026年6月以降しか無いため「ぜんぶ」）はアンカリングせず、内訳で拾えている分だけの合計を出し、その旨を warning に出す。

**役員報酬が0円になる場合**: freee試算表の行自体はあるのに `役員報酬` の科目だけ無い月は、freeeへ給与仕訳が未計上ということ。0円を「払っていない」と読ませないため、欠測月を検出して分類の注記と「まだ分類できていない」の理由行に出す。口座から出ている分はグレー帯に含まれ、freeeに計上されれば自動で役員報酬へ移る。

各カード下部には「何を数えているか」の一行説明を置く。

## API・性能

- 集計は server 側の1本のAPI（例: `GET /api/admin/kiyo/money-flow?period=month|season|all`）に集約し、ドリルダウン用の明細も同じレスポンスに同梱する（明細は高々数百行）。クリック時の追加fetchはしない。
- このデータは可変系（入金確認・支払記録で動く）だが更新は日単位。`spec/5-10-reference-data-caching-current-spec.md` に従い、サーバのプロセス内キャッシュTTL 5分で返す。
- 権限は既存 `/admin` 配下のガードに乗る（admin専用。人別の報酬金額を含むため、member向けに露出しない）。
