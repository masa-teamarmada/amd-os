## データ変更履歴

`/admin/change-history` は、OS内のデータ変更を新しい順に読むadmin専用の監査台帳。初期表示は「実行者・時刻・PJ・対象名・何をどう変えたか」の短い日本語要約を1〜2行で表示する。同一transactionの連続行に加え、service roleが同じテーブル・操作・PJへ1秒以内に連続実行した別transactionの行は、表示上の「同じ自動処理」として件数へまとめる。メタ監査行（`project_management_field_audit`）はDBの生ログには残すが、二重表示で本体変更を埋めないよう台帳からは除く。画面、iOS、macOS、GAS、定期処理のどこから書き換わっても、DBの同一トランザクションで記録する。

メンバー台帳の履歴は、メールアドレスではなく`member_name`または`code_name`と`member_id`で対象者を示す。`last_login_at`の自動更新を同じメンバー・同じ自動処理としてまとめるときは、「誰の最終ログインを何回更新したか」と集約前の実効的な変更前→変更後を1行で表示する。監査日時と差分の日付時刻はすべてAsia/Tokyo（日本時間）で表示し、秒以下の差を見分ける必要がある場合だけミリ秒を付ける。

「詳細を展開」すると集約前の個別履歴、主キー、変更前後、戻し操作を確認できる。集約は表示だけで、戻し操作は各履歴行の安全条件を個別に判定する。検索・操作種別の絞り込み・ページ送りは元の履歴行単位で行う。

記録開始は2026-09-16。導入前の変更を現在値から推測して遡及生成しない。秘密値は伏せ、大きい本文は冒頭だけに縮める。`OS自動処理`はservice role経由で実行者を特定できない処理、`実行者未確認`はJWT・行の帰属列のどちらにも実行者が無い処理を示す。変更履歴自体は追記専用で、更新・削除できない。

安全条件を満たす履歴行には「この変更を戻す」を表示する。確認後、現在値が履歴の変更後と一致した場合だけ同じトランザクションで逆操作する。一致しない場合は競合として何も変更しない。秘密値・大きい値・主キーを取得できない行、すでに戻し操作を行った行、戻し操作そのものは対象外。戻し操作は実行者と元履歴へのリンクを持つ新しい履歴として残る。

## 外部アクセス要求

許可されていないメールアドレスが研究機関ワークスペースのログインリンクを求めた場合、公開画面には登録有無を示さず、管理者限定の`workspace_access_requests`へ要求を記録する。まさ（`ID001`）へSlack DMを送り、DM内の`許可する` / `許可しない`で決定できる。許可時は申請先の研究機関またはPJワークスペースの`readonly`・`invited`だけを付与する。停止済みaccount・停止/剥奪済みgrantは自動復活しない。

同じ要求のSlack通知は30分に1回、全体で1時間20件まで。上限を超えた要求も`/admin/access`の承認待ちへ残る。共有資料直リンクからも対象を特定してSlackから許可できる。対象を特定できない要求は編集画面で対象の人へ場所を追加する。許可後にOSからメールを追加送信せず、本人がもう一度ログイン操作した時に既存のOTP経路がログインリンクを送る。

## DDパッケージ（投資家・金融機関向けの開示面）

DDはPJ見出し・領域選択・33資料を7分類した左メニュー・本文の順で開く。分類は初期状態ですべて展開する。管理者プレビューの帯や一覧タブはなく、技術・競合比較・ビジネスモデル・試算表・資本政策表・コスト試算・ドライブから本文を直接開く。未登録のページも入口を残す。3つの領域の表示ページは設計書「3領域の表示ページ」の◯表で確認できる。

投資家・金融機関には、コックピットやワークスペースへは入れず、DDパッケージで表示対象になっているページ全体と公開資料を見せる。中身はワークスペースの最新の内容そのもので、元データを直すとDDの表示も変わる。正式に提出する版は、その時点の内容をPDFに出力して渡す。仕様の正本は `/spec` の「DDパッケージ仕様」（`pwa/spec/5-17-dd-package-current-spec.md`）。

- **どこで管理するか**: 見出しの下に並ぶ「コックピット」「ワークスペース」「DDパッケージ」のうち「DDパッケージ」で独立したDD画面を開き、「設定」を押す。管理者には全PJで入口を出す。未登録なら「まだない」と出る。左メニューの「組織・権限」→「DDパッケージ」（`/dd`）からも入れる。
- **パッケージの状態**: 未公開（管理者だけがプレビューできる）→ 公開中（付与した人だけが閲覧できる）→ 受付終了（誰も閲覧できない）。SOLは付与した人だけが閲覧できる公開中。「公開を始める」を押しても招待メールは送られない。
- **ページ本文**: 表示対象のページは自動で共通の内容を表示する。技術は全体像・区分・トピックを切り替えて見られ、競合比較も掲載項目の登録なしで表示される。ページごとの追加・公開操作は不要。
- **資料とPDF対象を選ぶ**: ドライブに見せる資料は追加して「公開する」。資料以外は「PDFに含める」「PDFから外す」で正式版の対象を選ぶ。PDF対象から外しても共通ページの本文は表示される。
- **正式版（PDF）**: 「PDFを出力」で印刷画面が開き、公開中の項目をいまの内容で1つの文書に並べる（表紙に出力日時と目次、A4横、項目ごとに改ページ）。「PDFに保存（印刷）」を押すと出力の記録が残り、印刷画面で「PDFに保存」を選ぶ。保存先はGoogleドライブの該当PJフォルダの `YYMMDD_件名/`。出力の記録（日時・出力した人・項目数）はDD管理画面の「PDFの出力の記録」で見られる。
- **未確認事項と根拠資料**: 項目の「編集」で、未確認事項（1行に1件）を書き、同じパッケージの資料項目を根拠資料として結び付ける。元データの「要確認」「未定」「未解決の確認事項」は自動で加わる（項目ごとに外せる）。コスト試算の自動分は研究者への質問文、到達実績の自動分は社内の作業メモがそのまま入るので、公開前に見直す。
- **外す**: 資料を外すと外部から見えなくなる。資料以外の項目を外す操作は正式版PDFの選択を変え、共通ページの本文には影響しない。
- **閲覧権限**: DD管理画面の「閲覧権限」でメールアドレスを入れて付与する（外部アカウントが無ければ「外部アカウントが無ければ作る」）。閲覧だけか、資料のダウンロードも許すかを選び、期限も付けられる。停止・再開・失効は一覧から行い、相手がログイン中でも次の操作から効く。DDの権限だけではワークスペースにもコックピットにも入れない。付与してもメールは送られず、本人がログイン画面でメールアドレスを入れるとリンクが届く（リンクは同じブラウザで開く）。
- **閲覧記録**: 外部の人がトップ・項目・資料を見た記録とダウンロードを、DD管理画面の「閲覧記録」で見られる。管理者のプレビューは記録しない。
- `/admin/access` の下に、全パッケージのDD閲覧権限の一覧（読むだけ）が出る。

`/admin`とGlobalNavのAdmin導線は`/admin/schedule`へ着地する。管理カレンダーは、契約・支払義務・会社属性・公的ルールから生成した税務、労務、報告、契約、ガバナンスの期限と準備工程を12か月で確認する読み取り画面である。

## admin/kiyo (= きよの月次経理作業台)

URL: `/admin/kiyo`

### 何をする画面か

きよが月次経理をこのURLで完了する主入口。画面名は `きよ`。

1. `立替精算`: 申請・編集、PM承認・差戻し、admin承認・却下。adminには「承認済み」台帳が常設で並び、`status=approved`（互換で`paid`も含む）の全メンバー分をadmin承認日降順（欠測時は発生日で安定sort）で一覧できる。件数・合計金額の見出し付きで、発生日・PJ・摘要・申請者・費目・金額・PM/admin承認者と承認日・領収書リンクを1行ずつ確認する。承認待ち（`submitted`のPM承認待ち / `pmApproved`のadmin承認待ち）と自分の申請だけを出す一覧では、admin承認が済んだ他メンバー分がここに出ないため、月次照合はこの台帳を使う。
2. `請求書`: 発行前確認、freee取引先設定、請求書発行、発行取消
3. `メンバー支払`: 報酬確認、支払通知書発行、PDF確認、送付、入金確認nudge

上の3taskは `/admin/kiyo?task=...` で切り替わる。専用画面へのリンクではなく、`/reimburse`、`/admin/invoices`、`/admin/payouts` の現行作業componentを同じページ内に埋め込む。そのため処理内容、権限、保存先、server-side guardは各専用画面と一致する。

「読み取り専用」の状態一覧には戻さない。確認したあと別画面を探す運用も作らない。

3taskの切替UIは丸角カードではなく横並びタブ（`role="tablist"` / `role="tab"` / `aria-selected`、角丸ゼロ・影ゼロ・border-only）。PCは3taskを同じ幅の3区画として隣接表示し、縦の境界線で区切る。選択中の区画は古典的なタブのように上辺・左右辺を持ち、下辺を作業面の背景色で消して下の作業面とつながる前面状態にする。非選択の区画は薄い面色と下辺を持つ。1段目に番号+名称、2段目に工程説明を置き、区画幅は説明の長さに引っ張られず3等分で固定する（説明は省略記号で切る）。mobileは各タブに安定したmin-widthを持たせ、タップ領域44px以上を保ったまま意図的な横スクロール1行タブにする。見出し・タブ・埋め込み作業面の余白は4/8/12px系の密な間隔にし、埋め込み時は各専用画面側の重複見出し（`請求書発行` / `Payouts` 等）を出さず、きよのタブ見出しだけで用途を示す。専用route（`/reimburse` / `/admin/invoices` / `/admin/payouts`）はカード型の見出しをそのまま維持する。

## admin/invoices (= 請求書発行)

URL: `/admin/invoices`

### 何をする画面か
月次の請求書発行ページ。2列レイアウトで、左列に請求先PJの一覧（未完了件数バッジ付き）、右列にPJを選んだ後の作業面を出す。

右列は上から: ①契約条件（期間、基本報酬、請求配分、支払条件、立替精算、月報）、②13か月分の請求台帳（稼働月/請求月/基本額/承認済立替/請求候補/状態/発行条件）、③選んだ月の内訳ワークベンチ、の3段。PJ×13か月を生成して台帳をleft joinするため、欠損月も `月次台帳未生成` として見える。

内訳ワークベンチは「基本額」「承認済立替」「請求候補」「未承認参考」を密に並べる。請求候補は基本額+承認済立替。基本額は `contract-money.ts` の正本ロジックで算出し、`budget_yen` は使わない。立替は全ステータスで表示する。

未来月、稼働期間外、freeze後は台帳に表示しない。請求額を読めないcycleは隠さず、契約設定を直せるよう `請求額なし` として表示する。過去滞留は稼働月ではなく請求月 (`invoice_ym || ym`) で判定する。

発行不可のblocker条件: `月次台帳未生成`、`freee取引先未設定`、`請求額なし`、`立替未承認 N件`、`月報未確定`。未承認は月報に関係なく必ず発行を止める。担当PMまたはadminが申請中を「PM承認」、adminがPM承認済みを「admin承認」できる。freee発行側はDBで発行権を原子的にclaimするため、並行クリックの片方は409で止まる。freee送信後に台帳記録が失敗した場合はclaimを保持し、照合なしの再発行を許さない。

請求書発行モーダル（`AdminInvoiceIssueDialog`、既存コンポーネントを流用）は、件名、基本明細行、承認済み立替、調整行、請求日、支払期日、備考を確認してから freee 発行する。件名とヘッダーは請求先名 (`client_name`) を使い、AMD内部のPJ名やproject idを出さない。月額固定契約で基本行合計が契約月額と違う場合は、差分を確認してから発行する。

旧 `/admin/billing` は廃止し、互換のため `/admin/invoices` へ自動遷移する。

## 立替申請

URL: `/reimburse`

### 何をする画面か
AMD メンバーが業務関連で立替えた費用 (= 出張 / イベント参加費 / 書籍 等) を申請。
- 領収書 (= 写真 / PDF アップロード)
- 金額 / 用途 / PJ 紐付け
- 承認フロー (= まさが /admin で確認 → 月次支払に合算)

### 交通費は片道の金額を入れる

カテゴリが交通費のとき、**金額欄に入れるのは片道ぶん**。「往復」を選ぶと OS が自動で 2 倍して申請する。往復の合計額を入れてから「往復」を選ぶと 2 倍の 2 倍になる。

申請画面ではこれが分かるように、金額のラベルに「片道ぶんを入れて」と出し、出発地・到着地の下に注意書きを置く。金額を入れると、その下に「往復: ¥1,000 × 2 = ¥2,000 で申請」のように**実際に申請される金額**が出るので、送信前に確認できる。

### 申請されたときの通知

新規申請が入ると、admin (= `is_admin` かつ在籍中、Slack ID 登録済み) 全員に Slack DM が届く。申請者自身が admin の場合、自分宛てには届かない。DM には PJ名・申請者・発生日・カテゴリ・金額・摘要・領収書件数と `/reimburse` を開くボタンが入る。

**申請者本人にも同時に受付控えの DM が届く**。「受け付けたよ」+ 申請内容 + 「承認まで 24 時間ごとに admin へリマインドが飛ぶ」の一文が入るので、申請が通ったかどうかを画面を開かずに確認できる。

既存申請の**編集では鳴らさない**。編集のたびに DM が飛ぶと通知が摩耗して、本当に見るべき新規申請を見落とすため。

Slack が落ちていても申請自体は必ず保存される (通知は best effort)。届かなかった場合は API の返り値 `warnings` に理由が残る。

### 承認されないときの 24 時間リマインド

承認されないまま放置された立替は、**24 時間ごとに admin 全員と申請者本人へ再送信**される。

- 毎日 JST 10:00 に cron (`/api/cron/reimbursement-reminders`) が走り、前回送信 (初回は申請時) から 24 時間以上経った未承認申請だけを拾う。深夜には鳴らない。
- 対象は `approved` / `rejected` / `paid` **以外**の状態。つまり PM 承認待ちでも admin 承認待ちでも鳴り続け、**承認・却下した時点で自動的に止まる**。回数上限は設けていない。
- admin 向け DM には「◯日間 未承認のまま」と現在の状態 (PM 承認待ち / admin 承認待ち) が入る。申請者向け DM には「まだ承認されてない」+ 「admin にもリマインドを送った」が入る。
- 申請者が admin の場合は本人向け DM に寄せ、二重には送らない。このとき本人向け DM に承認ボタンを付ける（付けないと、admin 宛ての送信先から自分が外れる分だけボタンがどこにも届かなくなるため）。

### Slack から直接承認する

申請の DM とリマインドの DM には、状態に応じた**承認ボタン**が付く。OS を開かずにその場で判断できる。

- まだ PM が見ていない申請 (= 申請中) には `PM承認` / `差戻し`。
- PM 承認済みの申請には `admin承認` / `却下`。
- 押せるのは権限を持つ人だけ。PM ボタンはそのPJの PM だけ、admin ボタンは admin だけが通る。権限が無い、状態がもう進んでいる (= 誰かが先に処理した) 場合は、押しても反映されず理由がスレッドに返る。
- 反映先は OS と同じ正本なので、Slack で承認した内容はそのまま `/reimburse` の一覧に出る。二重に承認し直す必要はない。
- 押してから反映されるまでは数秒。2026-08-21 に、ボタンの押下を受け取る仕組みを外部の中継サーバー経由から OS 本体へ直結させた（受け口そのものは 2026-08-13 に用意し、Slack 側の送信先を切り替えた 08-21 から実際に直結で動いている）。以前は中継側が1分ごとにまとめて処理していたため、押してから反映まで最大1分待つことがあった。中継の設定はそのまま残してあるので、問題が起きたら送信先を戻すだけで元の動きに復帰できる。

### 承認待ちカードに出る情報

`/reimburse` の承認待ちカードには、交通費の場合、**どこからどこまで移動したか**が出る。出発地 → 到着地、移動手段 (電車 / バス / タクシー / 自家用車 / その他)、片道か往復かが 1 行にまとまる。往復申請では、表示金額 (= 往復合計) の下に片道いくらだったかも出る。摘要だけでは判断できなかった「これは妥当な区間か」をカード上で判断できる。

### 領収書の保管先

添付した領収書は 2 箇所に入る。

1. Supabase Storage `reimbursement-receipts` (= 一次保管、OS 画面から参照する正本)
2. 共有ドライブ `ARMADA/a3_backoffice/立替精算領収書/<発生月 YYYY-MM>/` (= 二次保管、経理が Drive だけで月次処理を閉じられるようにするため)

Drive 側のファイル名は `発生日_PJ名_申請者_金額円_元ファイル名`。月フォルダは初回申請時に自動作成されるので、手で作る必要はない。

Drive への複製に失敗しても申請は通る (= 一次保管には必ず残る)。その場合 Drive にはファイルが無いので、経理側で見つからないときは OS の `/reimburse` から原本を確認する。

- Cron Control: 稼働中・停止中の処理、旧頻度、入力、出力、Run Now 可否
- DB Settings: `settings` table の key/value

### 重要な仕様
- `Stopped` の operation は意図的に止めている。旧 LLM cron や subscription automation 移管対象なので、すぐ復活させない
- `Run Now` できるものも、`dryRun` がある時はまず `dryRun=1` で確認する
- 表示内容の正本は `pwa/src/lib/operations-catalog.ts`

詳細は **[6-1 章 Operations Settings](6-1-operations-settings-spec.md)**。

## /proactive (= 先手 TODO リスト)

URL: `/proactive`

### 何をする画面か
全 PJ 横断・期限順・1 画面の先手 TODO リスト。「外部 MTG が終わったあと AMD ボールが止まる」「相手から催促されるまで動かない」を防ぐためのリスト。

### どこから TODO が湧くか
毎朝 09:15 JST に動く `/api/cron/proactive-todo-extract` が自動投入する (= MVP は daily 運用。物足りなければ後で頻度を上げる)。検知元は 2 つ:

1. **過去 14 日の開催済みMTGの `next_actions`**: AMD ボール or 主語不明のものだけ。「○○先生が」「相手側」など相手主語のものは入らない
2. **PJ連絡先から届く期限つきGmail依頼**: 返信・返送・日程回答など、期限を読める依頼だけを積む

予定MTGの agenda / 進行案準備は Codex の W-Prep / prep worker で行う。2026-08-11 以降は `次回MTG準備` を先手TODOへ新規生成せず、既存の未対応・ブロック中も「関係ない」へ自動退避する。

開催済みMTGの `next_actions` から作る TODO は、本文内に「2026-08-04 次回MTGまで」「8/4のMTGまで」「7/17まで」などの日付つき期限があればそれを期限にする。明示期限が読めない場合だけ、前回MTG日 + 7 日を仮期限にする。

### 使い方
- タブ: 未対応 / ブロック中 / 完了 / 関係ない
- 行をクリックで展開、元 MTG・元 next_action テキスト・期限・ボール種別が見える
- 3 ボタン:
  - **✅ 完了**: やった
  - **⏸ ブロック中**: 待ち中 (任意で 1 行メモ、3 日経つと自動で「未対応」に復帰する)
  - **🗑 関係ない**: cron 誤検知扱い、二度と同じものを積まない
- 期限超過の open は 🔴 red になり、dashboard 上段のバッジが赤くなる

### dashboard 上段のバッジ
左上の「先手 TODO」バッジは admin のみ表示。未対応件数 / 期限超過件数を 1 行で出し、クリックで `/proactive` へ。

### 過去の経緯
2026-06-12 に「ループカーネル × 役割レンズ」として `/loop` の 5 段ループ盤面 (観測 → 評価 → 判断 → 実行 → 学習) と dashboard 上段の `LoopKernelBoard` を実装したが、(a) 5 段のうち先手と関係する段が「実行」だけだった (b) 完了UIが無く超過 666h の seed が叫び続けた (c) heartbeat の受け側 (= 司令塔セッションのえいみ) が実運用で機能しなかった、という理由で 2026-06-27 まさ判断で**白紙やり直し**。詳細仕様は [`pwa/spec/2-4-proactive-todo-current-spec.md`](../spec/2-4-proactive-todo-current-spec.md)。
