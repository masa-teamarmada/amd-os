# 通知・つくよみ修正依頼・正本反映ゲート

AMD OS の通知は、まさが今判断または実行する必要がある時だけ出す。保存完了、同期完了、情報共有、チーム作業、相手待ちは通知理由にしない。候補の採否通知も、採用・見送りで正本や次の行動が本当に変わる場合だけ。

## 先に知っておく言葉

| 用語 | 意味 |
|---|---|
| **通知** | ユーザーに見せるカード。単なるお知らせもあるが、多くは候補データの確認依頼。 |
| **正本反映ゲート** | 候補を正式データにしてよいか、人間が「はい / いいえ / コメント」で判断する入口。 |
| **L2 通知** | L2 候補や差分候補を確認する通知。例: PJ ナレッジ、MS 進捗、XRL 根拠、経営ハイライト。 |
| **経営ガードレール** | 見落とすと後戻りが大きい注意点を、PJ / アクションのタグから事前検知する通知。 |
| **candidate / pending** | 未確認候補。表示されても、まだ OS の確定事実ではない。 |
| **active / confirmed / applied** | 確認済み、または正本へ反映済みの状態。 |
| **l2_feedbacks** | 「ここが違う」「次回からこう見てほしい」という修正依頼の保存先。次回抽出の prompt に入れる。 |
| **つくよみ** | L2 抽出と修正依頼ループの担当名。Manual Q&A のつくよみとは別の運用概念。 |

## 通知の種類

| 種類 | 主なテーブル | 役割 |
|---|---|---|
| L2 通知 | `l2_notifications` | L2 候補・差分候補の確認 |
| MTG 通知 | `meeting_notifications` | 議事録 / MTG サマリ確認 |
| アプリ通知 | `app_notifications` | OS 運用上の通知 |
| Slack nudge | Slack DM + signed URL | 入金確認、PL承認など |

## 先手TODOと通知の入口

先手TODOは、既存 Codex automation `amd-os-proactive-heartbeat` が毎日10:15〜20:15 JSTの毎時15分に生成する。別automationは使わない。

入力は既存TODOや通知候補ではなく、直近のGmail / Drive / Calendar / Slack / Notionの保存証跡と開催済み会議要約。Codexが全証跡を意味で読み、次のどちらかだけをapproved TODOとして直接作る。

- まさの採否で次の進行が分岐する
- まさ本人の権限・本人確認・本人アカウントがなければ完了できない

MTG prepはCodex task内で完結し、OSへ重複表示しない。チーム作業、一般提案、情報、完了報告、相手待ち、根拠不足は作らない。期限は証跡内の明示日時だけを使い、仮期限を作らない。

TODOを作っても通常は通知しない。通知するのは、24時間以内の明示期限、取り消せない判断機会の終了、まさ本人にしか解除できない現行blockerだけ。候補0件は正常で、通知も空payloadも作らない。

詳細は [`spec/2-4-proactive-todo-current-spec.md`](../spec/2-4-proactive-todo-current-spec.md)。

## H-1の会議確認通知

**H-1** は、終わった会議の記録、議事録なしの再確認、前後24時間の予定カード、ノーション議事録のひも付けを整える定期確認。毎時動くけれど、毎回まさに報告するものではない。

通知が出るのは、会議記録・予定カード・ノーションのひも付けを新規保存または更新した時、判断が必要な時、または処理が止まった時だけ。既存カードを確認して変化なし、候補なし、更新なしは内部の実行記録には残るが、通知箱には出ない。

通知の件名は「会議確認: 記録または予定を更新」「会議確認: 確認が必要」「会議確認: 処理が止まった」のいずれか。本文の最初にH-1の役割と、今回まさが見るべきことを日本語で出す。「まさがやること・直接開く場所・完了条件」が全部ある処理停止だけ緊急通知になり、どれかが欠ける内部失敗は通知せず次回runで再試行する。

## つくよみ外部リサーチ

この節が、つくよみ外部リサーチの日常運用の正本。
運用を確認するために、設定ファイルやローカルの実行スキルを探す必要はない。

### いつ、どこまで調べるか

平日09:00 JSTに、対象PJへ直接効く新しい公開情報を調べる。
月曜日は週末を含む過去72時間、火曜日から金曜日は過去24時間が検索範囲。
公式発表、公募ページ、当事者の発表など、公開日または公式更新日を確認できるページだけを候補にする。
検索結果の要約、一般的な業界概況、過去イベントの振り返り、PJの具体的判断につながらない情報は候補にしない。

新しい候補が0件の日は正常終了。
通知を作らず、古い記事で穴埋めせず、日次まとめも送らない。

| SE | マイクロ波ワイヤレス給電、インフラ防災、自立型センシング |

### 通知に出る3種類

| 種類 | 通知に出すもの |
|---|---|
| 業界・市場 | 規制変更、競合の具体的な動き、技術上の具体的な進展 |
| 助成金 | 応募可能な公募中、または近日公募予定の助成金 |
| 協業候補 | 関係組織・人物の具体的な動き、接点を検討できる協業候補 |

候補はSlackへ送らず、AMD OSの `/notifications` に1件ずつ通常通知として出す。
候補をまとめた1枚の通知にはしない。

### 同じ内容をどう止めるか

新しい通知を作る前に、過去の未判断・採用・見送り・保管済みの全履歴と、まだDBへ反映していない候補を照合する。
同じURLは、計測用のクエリ、ページ内リンク、末尾のスラッシュを除いて比較する。
URLが違っても、対象、発生日、出来事が同一と判断した情報は再通知しない。
記事タイトルの日付や表現だけを変えた情報、転載、同じ内容へのURL差し替えも候補にしない。

締切の確定、採択結果、金額変更など、PJの判断を変える新事実が加わった続報だけは別候補にできる。
単なる言い換えを「続報」として扱わない。

### 通知で決めること

| 操作 | その場で起きること | PJコックピット |
|---|---|---|
| 採用 | 候補を確認済みにする | 該当PJの `経営ハイライト → 採用リサーチ` に残る |
| 見送り | 候補を不採用にする | 表示しない。ただし履歴は次回の重複防止に使う |
| コメントだけ送信 | 正本へ反映せず、修正依頼を保存する | 表示しない |

未判断の候補は通知にだけ置く。
採用前の候補をPJコックピットへ先回りして表示しない。
採用リサーチは、従来の経営ハイライトである `重要な動き` と分けて表示する。

### いつもと違うとき

| 状況 | まさがやること | 完了の見方 |
|---|---|---|
| 同じ情報がもう一度届いた | `見送り`にして、必要ならコメントに「重複」と書く | 回答済みに移り、コックピットへ追加されない |
| 通知が届かない | 新規候補0件なら対応不要。情報があるはずなら、Codexのオートメーション一覧で当日09:00の実行結果を確認する | 新規0件の正常終了、または失敗理由が確認できる |
| PJが違う | `見送り`にして、コメントに正しいPJを書く | 誤ったPJのコックピットへ追加されない |
| 採用したのにコックピットに出ない | 通知が回答済みになったことを確認して、該当PJのコックピットを再読み込みする | `経営ハイライト → 採用リサーチ` に同じ件名が1件だけ表示される |

外部リサーチは、Slack送信、候補0件の日の通知、採用前のコックピット保存を行わない。
失敗した実行だけがオートメーション側の要確認になる。

## 通常通知と緊急性の高い通知

通知画面では、同じ通知を「緊急性の高い通知」と「通常通知」に分けて表示する。

| レーン | 何を見るか | 例 |
|---|---|---|
| 通常通知 | OSに新データが入った、候補が増えた、通常レビューが必要 | L2候補、MTGサマリ、VCニュース、通常の取り込み経路確認 |
| 緊急性の高い通知 | 見落とすと事故る復旧・ガードレール・明示 blocker | Notion等の再認証、high以上の経営ガードレール、明示 critical の要対応、重要 automation blocker |

緊急性の高い通知は、対応が終わっても削除せず、既読欄から再試行できるものがある。特に connector 再認証は、リンクを開いたことと復旧完了は別なので、復旧できたかは対象 automation の次回成功で確認する。

緊急性の高い通知は右下ポップアップにも出る。アプリ通知は、writerがcritical候補と明示しただけでは鳴らない。「まさがやること・直接開く場所・完了条件」が全部揃った時だけ緊急になる。再認証も直行リンクがある時だけ緊急。MTGサマリ、契約予兆、総会/役会、D-11メディア掲載、`importance` が高い L2 候補は、タイトルや本文に「事故」「blocker」「再認証」などの語が含まれていても通常通知に残す。

## `/notifications` でやること

`/notifications` は admin 向け。カードを展開して、候補の内容・根拠・既存 feedback を見て判断する。

OS通知の全カードには「まさがやること」「開く場所」「完了条件」が出る。結果報告なら「対応不要」と出るので、何をすべきか推測しなくていい。本文が長い時は「続きを読む」で全文を確認でき、通知一覧自身へ戻るだけのリンクは表示しない。L2/MTGの判断カードには、これまで通り「確認・反映先」「追加・更新する情報」「この操作の結果」が出る。

| 操作 | 何が起きるか |
|---|---|
| はい・反映 | candidate / pending を active / confirmed / applied へ昇格 |
| いいえ・不採用 | rejected / invalid にする |
| コメントだけ送信 | 正本反映せず、`l2_feedbacks` に修正依頼として保存 |

回答後は未対応から外れ、回答済みとして扱う。

すでに正本へ保存済みの通知 (`saved_count >= total_count`) は、画面上では「はい・確認済み」として扱う。D-11メディア掲載のように collector が `project_media_mentions` と通知を同時に作る通知は、採否というより確認・学習フィードバック用になる。ただし `coverage_gap` は例外。候補行が保存済みでも採否は未完了なので、「はい・確認済み」ではなく「重要メモにコピー / コピーしない」の判断ボタンを出す。

D-14 要対応 (`action_item`) は、通知作成時点で `action_items.review_status='candidate'` として保存済み。「はい・確認済み」で `confirmed` になり、dashboard / PJ cockpit の要対応面へ表示される。「いいえ・不採用」は `rejected` にする。

通知を展開したとき、正本行の専用表示がまだ無い種類でも「抽出された行が見つからない」とは出さず、通知本文を詳細欄の fallback として表示する。D-11メディア掲載は `project_media_mentions` の保存済み行を表示する。ただし `coverage_gap` で元候補が見つからない場合は、通知本文だけで採否を迫らない。「コピー前に元情報を確認」と表示し、重要メモへのコピーは押せないようにする。

`coverage_gap` は、会議メモにあった内容が保存済みの会議要約に入っていないか、弱く書かれている可能性があるときに出る確認通知。PWAでは `未OS化の可能性`、`D-6`、`raw transcript`、`取りこぼし`、`条件付き投資家関心`、`目立たない話` のような内部語を出さず、具体候補が取れている場合だけ「重要メモにコピーする？: ...」という質問として出す。展開すると、最初に「コピーされる文章」を表示し、続けて「判断の目安」と「コピーしても起きないこと」を表示する。「重要メモにコピー」は、保存済みの会議要約とは別に重要メモへコピーする操作で、出資決定や正式合意としては扱わない。H-1要約本文を元に戻す操作でも、書き換える操作でもない。具体候補が取れない場合は「コピー前に元情報を確認」と表示し、このカードだけでは判断できないこと、内容が分からなければコピーしないこと、再確認したい場合はコメントに書くことを出す。

### 「開催履歴を追加する？」が出たとき

これは、メールや資料から見つけた総会・取締役会の開催情報の下書き。まだ正式な履歴には入っていない。カードに出る `会社概要 → 総会・取締役会` を開いて、会議種別・開催日・議題・決議・添付ファイル名を確認する。`この開催履歴を追加する` を押すと、その5項目を開催履歴として1件追加する。メール送信、資料アップロード、元メールや元資料の編集はしない。違う・不要なら `追加しない` を押せば、開催履歴は増えない。

### 「BZM追記候補」または「経営ノウハウ追加候補」が出たとき

これは、AMD OS内の記録から再利用できそうな実務知見を抜き出した D-7 の確認通知。カードには提案本文を一度だけ表示したあと、**追加先**と、その場所へ実際に保存する情報を表示する。候補を見ただけでは、BZMにも経営ノウハウにも追加されない。

- **BZM追記候補**は、Before Zero の読者が使う実践テキストへ残す候補。カードにはBZM内の追記先と候補の型を出す。`BZM追記を承認` を押すと候補を承認済みにするだけで、この画面から本文は書き換えない。後続のローカル反映処理が、承認済みかつ必要なレビューを通った候補だけをBZMへ追記する。元の会議メモやAMDプロトコルは変更しない。
- **経営ノウハウ追加候補**は、AMD社内で使う運用・経営の知見を `管理 → 経営ノウハウ` に残す候補。カードには `分類 / 成熟度 / タグ / 再利用する場面 / 次に確認すること` を本文とは別に出す。`経営ノウハウに追加` を押すと、本文とこの構造化情報を経営ノウハウ台帳へ1件保存し、候補を反映済みにする。元の会議メモ・AMDプロトコル・BZM本文は変更しない。`追加しない` なら経営ノウハウは増えない。

保存先は、候補の型だけから画面側が推測しない。抽出時に明示された保存先が無い候補は、正本を変える判断通知として表示しない。

通知カードには `No.1` のような通し番号を出す。これは表示中リストで探すための番号で、DB上の永続IDではない。フィルタを変えると番号も変わる。

## iOS Swift版の「通知」タブ

iOS版は下部の `通知` タブから、同じ `l2_notifications` / `meeting_notifications` / `l2_feedbacks` を使う。スマホで連続処理しやすいよう、PWAの一覧とは表示を変えている。

- `判断 / 未読 / 履歴` の3セグメント
- `判断` は未回答を縦に連続表示する。下へスクロールすると次のカードも続けて読め、各カードに `n / total` を出す
- カード内に `観測 → 候補 → 判断 → 正本`、`OSの見立て`、`押すと起きること`、折りたたみ式の`根拠`を表示する
- 判断カードには `追加先` と `追加・更新する情報` も表示する。開催履歴候補は `会社概要 → 総会・取締役会`、会議種別・開催日・議題・決議・添付ファイル名を明示し、`この開催履歴を追加する / 追加しない` を出す。D-7は、BZM候補ならBZM内の追記先、経営ノウハウ候補なら `管理 → 経営ノウハウ` と保存する `分類 / 成熟度 / タグ / 再利用する場面 / 次に確認すること` を出す。採用はPWAの同じfeedback APIを通り、開催履歴または経営ノウハウの該当1件だけを追加する
- ボタンは汎用の「はい / いいえ」ではなく、`MS進捗を確定 / 提案を破棄`、`採用候補にする / 見送る`、`根拠として確定 / 不採用`、`確認した / 修正する` のように結果を明記する
- `修正・コメント` は違う箇所のチップと自由記述を `l2_feedbacks` へ保存する
- `あとで` は端末内の永続状態を増やさないセッション内保留。通知画面を開き直すか、全件保留時の`もう一度見る`でキューへ戻る

iOSとPWAで書き込み境界を混同しない。iOSの `project_registry_diff` 採用はcandidate diffをacceptedにするところまでで、実DB（OS台帳）反映はPWA/helperの安全な反映処理が行う。`meeting_summary` の `確認した` は確認記録だけで、要約を再抽出しない。

`connector_auth` は採否候補ではないが、未読の間は `再認証を開く / あとで` の復旧カードとして判断キューに出る。リンクを開いたことは復旧成功ではないため、既読後も履歴から再認証を開き直せる。

## 正本反映ゲート

| l2_kind | 保存時 | はい | いいえ |
|---|---|---|---|
| `member_knowledge` | `candidate` | `active` | `rejected` |
| `project_knowledge` | `candidate` | `active` | `rejected` |
| `protocols` | `candidate` | `active` | `rejected` |
| `founding_members` | `tentative` | `active` | `invalid` |
| `project_registry_diff` | `pending` | DB反映 + `applied` | `rejected` |
| `xrl_evidence` | `candidate` | `confirmed` | `rejected` |
| `ms_progress` | `pending revision` | `confirmed` / progress 反映 | `discarded` |
| `guardrail_match` | `open` | `acknowledged` | `dismissed` |

`project_config_gap`（抽出設定不足）は採否候補ではないため、通知一覧には出さない。dashboard の「抽出状況」で、5つの情報源の最終保存時刻と、PJごとのメール・Slack・Drive設定不足を確認してPJ台帳から直す。

抽出状況の「保存」は、L2の根拠として残った証跡であって、connector の最終チェック時刻ではない。保存が古いことだけを異常にしない。MTG抽出で実際に使えた時刻を別に表示し、未読の再認証通知、PJ設定不足、Calendar接続エラーだけを理由と解決先つきの対応事項にする。既読の再認証通知は過去の案内として扱い、現在の再認証要求にはしない。

Slackを使わないPJは、PJ台帳の `Slack CH` 列で「チャンネルなし」をチェックする。これは空欄のまま放置するのとは違い、抽出状況で設定不足として扱わない明示設定。

経営ハイライト (`project_strategy_signals`) は `candidate` / `confirmed` / `rejected` / `archived` を持つ。cockpit には candidate も表示するが、未確認であることを明示する。

## つくよみ修正依頼

```text
候補に違和感がある
  ↓
通知 / cockpit からコメントを送る
  ↓
l2_feedbacks に保存
  ↓
次回抽出 prompt に過去 feedback を含める
  ↓
抽出結果を改善する
```

`l2_feedbacks` は「まさが直したいと思ったこと」の正本。コメントは短くてもよいが、何が違うのかを書くと次回抽出が改善しやすい。

例:
- 「これは LOI じゃなく NDA」
- 「この人は創業候補ではなく VC 担当」
- 「この MS は PM 手動確定済みなので上書きしない」
- 「この external signal は SX には追い風だが CTB には関係ない」

### マニュアル限定つくよみ Q&A

`/manual` と `/manual/[slug]` 右下の **つくよみ Manual Q&A** は、上の修正依頼ループとは別物。Gemini が該当する `pwa/manual/*.md` の本文を読んで回答し、「ここ見たらOK」の参照章リンクを返すだけの read-only 実験導線。つくよみキャラとして敬語は使わず、高校生にも分かるくらい噛み砕いて案内する。

- DB に書き込まない
- `l2_feedbacks` / `tsukuyomi_chat_logs` に保存しない
- PJ コックピットや Venture Map の内容を修正しない
- global の visible mascot は復活させず、マニュアル route だけで表示する

## 既読と履歴

- `notified_at`: iOS / APNs などへ通知した時刻
- `read_at`: PWA で人間が開いた時刻
- `applied_count`: feedback が抽出 prompt に含まれた回数
- `last_applied_at`: 最後に使われた時刻

通知行は削除せず蓄積する。UI は最新100件 + タブで整理する。

### 「契約締結の承認対応」が出たとき

契約の通知では、まず `管理 → 契約`、契約名、相手先、種別、現在の状態、変更後の状態、期限を確認する。`契約状態を更新` はその契約1件と要対応の回答だけを更新し、メール・文書・別の契約は変更しない。契約名やIDがない候補は、OSがどの契約か確認できていないので人へ通知しない。契約台帳は更新せず、生成側の `needs_source` として契約ID・契約名・相手先・現在状態・変更後状態の補完を待つ。
