# PJ コックピット

AMD OS の **中心画面**。各 PJ ごとに 1 つあり、URL は `/project/{project_id}/cockpit` (例: `/project/p21/cockpit` = SX)。

## 社内コックピットとPJ共有ダッシュボード

同じPJに、用途の違う3つの画面がある。

| 画面 | 主な利用者 | 表示するもの |
|---|---|---|
| `/project/{project_id}/cockpit` | AMDの全PJ横断メンバー | AMD Score、契約・報酬・経営判断を含む社内コックピット |
| `/project/{project_id}/workspace` | PM / PJ責任者 / 当該PJメンバー | テーマ接続済みPJのテーマ進捗、週次差分、担当負荷、全体ガント、関係先、論点・仮説を扱うPJの正規ワークスペース |
| `/project/{project_id}/weekly-control` | 旧URL利用者 | `/project/{project_id}/workspace`へ転送する互換入口。独立画面は持たない |
| `/project/{project_id}/navigation` | COO / PM / PJ責任者 | 全体依存ガント(依存航路)、クリティカルパス、関係先リスト、制約ボード。週次会議直前に数秒でPJ全体の状況・遅延・介入点を掴む |

PJワークスペースは社内コックピットの簡略版ではなく、PJを動かす人の実行面。共通タブは`週次差分 / ガント / 関係先 / 論点・仮説 / コスト試算 / 知財 / ドライブ`。テーマ接続済みPJだけ先頭に`テーマ進捗`が加わる。別の簡易ダッシュボードは併設しない。AMDの内部評価、契約、採算、経営判断はコックピット側で扱う。

LiSTieのコスト試算は、2026年8月時点では膜＋電力の部分試算だけを表示する。総コスト目標の3 USD/kgと、資料にある円/kgの部分試算は工程範囲・通貨が異なるので、直接比較しない。

ワークスペースの論点カードは、論点→仮説→根拠→検証→判断→決定後の行動を同じ流れで管理する。判断待ちを決定済みへ更新したら、担当・期限・完了条件・次回確認日を持つ行動を続けて置き、完了時は完了メモと完了日を残す。決定済みでも未完了行動がある論点は要フォローから外れない。

SX (`p21`) のワークスペース変更は、同じ `project_management_*` 正本と変更履歴から既存D-6（経営ハイライト）とH-1（議事録）へ渡す。コックピットにワークスペースの件数や作業一覧を複製しない。経営に効く完了事実だけがD-6の通常審査を通って経営ハイライトになり、その根拠から元のワークスペースへ戻れる。

AMDメンバーは従来どおり `/dashboard` がトップで、SX (`p21`) カードから共有ダッシュボードへ入れる。`os_access_scope='project'` のPJ限定メンバーは、参加PJが1件ならその共有ダッシュボードがトップになり、複数なら `/my-projects` がトップになる。

外部アカウントは `/admin/access` でメールアカウント・機関ワークスペース所属・個別PJ権限を明示して付与する。SX (`p21`) は機関ワークスペースの一覧へ混ぜず、個別PJ権限だけで開く。外部向けのSX入口はPJ名と共有資料室だけを表示し、内部の週次差分、ガント、関係先、論点・仮説、担当工数は出さない。`contributor` と `manager` は資料を追加でき、`readonly` は閲覧だけできる。

## 誰がいつ使うか
- **PM / PL / 伴走メンバー** (= PJ を動かす AMD メンバー) が日常的に開く
- **月次確認**で月次報告書 draft の「これでいい？」nudgeに返す
- 経営判断のタイミングで **経営ハイライト** を確認・採否
- **まさえいMTG** で議題を出すときに、各 PJ の candidate をここで見る

## 画面構成 (上から)

```
┌─────────────────────────────────────────────────────┐
│  PJ ヘッダー (= 名前 / status / 分類 / PJメンバー)       │
├─────────────────────────────────────────────────────┤
│  タブ: 進捗管理 / 週次差分 / ガント / 関係先 / 論点・仮説 /       │
│        スコア詳細 / 事業計画 / コスト試算 /                      │
│        知財 / 資料室 / PJ概要 / 会社概要                        │
├──────────────────┬──────────────────┬──────────────┤
│  年間 MS リスト   │  経営ハイライト    │  月次確認       │
│  月次サマリ       │  助成金            │  ステータス     │
│                   │  MTG サマリ        │               │
└──────────────────┴──────────────────┴──────────────┘
```

(= 通常は 2 カラム。凍結中 / 再開予定などのステータスがある場合だけ右カラムを出す)

PJ ヘッダー最上部に置くのは、PJ名・状態・分類・PJメンバーと共有ワークスペースへの導線だけ。現行契約ごとの「契約上の実行条件」は **PJ概要** タブ (`/project/{projectId}/cockpit?tab=overview`) にある (2026-08-28 まさ依頼で最上段から移した。毎日開く進捗管理を月次の動きへ集中させ、月単位では変わらない前提は必要なときだけ開く)。通常契約は `契約期間` / `請求・振込` / `業務・成果物` / `経費申請` / 必要時だけ `推進条件` の最大5項目。請求タイミングと振込タイミングは金額の補足に必ず表示し、経費は申請可否と、旅費・外注・立替などの条件を短く出す。業務・成果物にはPJを進めるうえで必要な範囲と提出物だけを置き、現地対応、貸与物、事前承認などは推進条件へ置く。短文は `projects.contract_terms_json.currentContracts[].terms.cockpitSummary` の `invoiceTiming` / `paymentTiming` / `scope` / `deliverables` / `expense` / `execution` を正本にする。知財、秘密保持、解除、責任、準拠法などの詳細条項は通常契約のコックピットへ常設せず、admin契約台帳で確認する。NDAだけは金額・経費ではなく `利用目的` と `運用条件` を表示する。未確認値を勝手に `申請可` や `なし` にしない。

コックピットのタブは12個（KUTEだけ規程・内規が増えて13個）。左から、PJを動かす面（進捗管理 / 週次差分 / ガント / 関係先 / 論点・仮説）、測る面（スコア詳細 / 事業計画 / コスト試算）、調べる面（知財 / 資料室 / PJ概要 / 会社概要）の順。

**週次差分・ガント・関係先・論点・仮説** の4つは、2026-08-28（まさ「コックピットとワークスペースを統合できそうじゃない？」）にPJワークスペースから取り込んだ。画面の中身も編集のしかたもワークスペースと同じもので、作り直したコピーではない。同じ場所を2つのURLから開けるだけ。4つのタブを行き来してもデータを読み直さないので、切り替えは速い。

大学・SUに見せるPJワークスペース（`/project/{project_id}/workspace`）は別のURLのまま残してある。統合したのはAMD側の見え方だけ。外の人が見る画面は「見せるものだけを組み立てる面」のままにして、コックピットにタブを足しても外へは出ない。

コックピットを開くと、名前の行のすぐ下がタブの列で、その下が **進捗管理** の中身。2026-08-28（まさ「さっき貼ったオブジェクト全部移動して」）に、名前の行とタブの間にあったものを全部 **PJ概要** タブへ移した。移したのはPJの見出し行（アウトカム、レーン、設立、起源機関、PL / PM / クローザー、事業概要、沿革・メンバー・事業会社）と **XRL進捗グラフ**。同じ日に、そこにあったBZM 2.2の$J/P/Q/S$は表示そのものをやめた（2026-08-27「古いモデルの試算結果は、混乱の元になるのですべて削除してほしい」でスコア詳細から外したのと同じ表示が、ここにだけ残っていた）。XRLはPJ概要タブで横幅いっぱいを使い、狭い画面では600pxの横スクロールにする。スコア詳細は2026-08-27に古いモデルの試算結果（BZM 2.2 暫定パイロット、旧SPS帯の内訳、BZM 2.1 / 2.0 / Legacy AMD のトグル）を全部外した。現在この面にあるのは2つだけで、最上段が「現行SPS｜産業創出価値」の評価カード、その下がBZM 3.0（産業創出価値 V）のスコアパネル。評価カードは2026-08-28まさ依頼でコックピット上部から移したもので、出すのは評価済みか / SPS帯 / 根拠レベル / 評価日 / 対応シーズの5つに限る（帯の定義式・算出過程・q要因は8-27に外した「古いモデルの試算結果」なので戻さない）。BZM 3.0のパネルはシーズ詳細と同じものを使うので、同じPJをPJ側から見てもシーズ側から見ても同じ数字・同じ根拠が出る。シーズが紐づいていないPJでは黙って空にせず、何をすれば算出できるかを出す。正規URLは `/project/{projectId}/cockpit?tab=score-detail`。旧 `/venture-map/amd-score/{projectId}` はこのタブへ自動転送する。

進捗管理タブの一番下には、対になる2つの欄を置く。

上が「これまでに得てきたもの（獲得台帳）」で、そのPJが何を得てきたかを日付順に並べ、同じ行に、閉じた条件・使ったもの・できるようになったことを並記する。件数や合計は出さない。得たものの数を足して余力の点数にすることは、BZM 2.2の考え方に反するため。行は通知で「重要情報として保存」を押した時に自動で増える。現在は第1段で表示専用、$J/P/Q/S$にも戦略余力にも一切入らず、画面にもそう明示する。数式へ入れるのは第2段で、どの制約が「不明・違反」から「充足」へ動いたかを判定してからにする。空欄の行は「まだ判定していない」であって「無かった」ではない。2026-08-14にスコア詳細タブから移した。数式の内訳ではなくPJの歩みそのものなので、歩みを読む場所へ置く。

下が「AMDがこのPJへ行ってきたこと」で、AMD側が何を投じたかを日付順・月区切りで並べる。週次の活動記録、カレンダー、メール、MTGサマリからAMD OSが自動で拾い、手で書き足す欄は持たない。誰がやったかはコードネームで出し、その人のマイページへ飛べる。記録から推定した行には「推定」と付ける。直近2か月を開き、それ以前は折りたたむ。最下部の件数は貢献の大きさではなく拾えた記録の母数として置く。ここに無いことは「やっていない」ではなく「記録から拾えていない」。足りないと感じたら、この欄を編集できるようにするのではなく、活動記録が拾えていない原因を直す。

2026-08-13以降、イベント表示は縦の複数レーンではなく、評価月M0から計算地平までの一本の横時間軸を使う。登録方針は地平全体の帯、技術・設備・商流・資金イベントは該当月の点と上下の説明として置く。その真下へ同じ月列の売上、原価、粗利、人件費、研究開発費、販管費、営業利益を並べる。SX（p21）はさらに、月初資金、営業C/F（簡易）、設備投資、株式調達、融資、助成金等入金、月次純C/F、月末資金を同じ列で読める。融資は金額・時期未登録なら0円にせず「未計画」。PSI Step 2の6,000万円はPhase 0に1回だけ入れ、FY2027へ重複させない。最後のBZM経済CFは会社の資金繰りと別の事業価値計算用。イベントの点を押すと、その月の前提にした進め方と通過値・停止時価値を読める。月見出しまたは「月を入力」から`project_pl_monthly`を直接編集でき、つくよみヒアリングも同区画から開く。金額は表の外に「単位：百万円」を一度だけ示し、各セルはMなし・右寄せで表示する。月次表の直下には、同じ値を4月始まりの年度（FY）ごとへ畳んだ年次集計グラフを置く。FYを連続した横列に固定し、上段で売上・費用内訳・営業利益を同じ尺度で、下段の別尺度「資金レール」で株式調達・助成金等入金・年次純C/Fを読む。調達を売上へ混ぜない。設立前PJ支出はNewCoのP/L・営業利益へ混ぜず、資金レール内で「NewCo P/L外」として独立表示する。コックピット上部とHUDにあった独立した「試算表」ボタンは置かない。

2026-08-17改定: 年次グラフは幅を`max-w-6xl`へ抑え、年度ごとの棒を同じ幅でそろえる。グラフの直下に、同じFY列を持つ年度別数値表を置き、内訳と正確な金額を読めるようにする。設立前PJ支出は資金レールと数値表で「NewCo P/L外」として独立表示する。

**事業計画** タブは全PJ常設 (2026-08-21 まさ依頼で全PJへ拡大)。正規URLは `/project/{projectId}/cockpit?tab=business-plan`。全PJ共通の中身は、100%株主構成推移 → 編集可能な資本政策表 (`CapitalPlanWorkspace`) の2つ。2026-08-21 (v3.88.3) から、スコア詳細タブにあった「イベントと月次試算表」と「年度別の事業・資金推移」(年次グラフ+年度別数値表) をこのタブへ移した。BZM 2.2の暫定試算がある PJ でだけ共通部分の上に出て、対象外の PJ では表そのものを出さない (空表やエラーを見せない)。イベントの月は、スコア詳細タブのシミュレーターで動かした値ではなく登録済みの月を使う。スコア詳細タブと同じ試算データを一度だけ読み込んで両タブで共有するので、タブを行き来しても再取得しない。資本政策表は会社概要タブからこのタブへ移したので、全PJでラウンド計画の編集はこのタブで行い、会社概要には確定済みの法的会社情報・株式イベント・年度決算を残す。資本政策プランが未作成のPJでは、プラン未作成の案内と新規作成の導線だけが出る (空の表を偽装しない)。

SX (`p21`) だけは、この共通部分の上下にSX固有のフェーズ表と年次試算表を足す。最上段は、列を「PSI・設立準備 / Seed→A / A→B / B→C / C→IPO」、行を「事業開発 / 技術開発 / 組織開発 / 資金調達」とするフェーズ表で、各セルに具体的な実行項目、費用、次フェーズへの出口条件、到達XRLを表示する。表の枠は直接的な表題・項目名だけで構成し、SX固有の事業仮説と数値はフェーズのセルおよび編集可能な計画データに置く。表の直下の **Excel出力** は、このフェーズ表だけをダウンロードする。期間・フェーズ予算・調達ラウンド・資金源・到達XRL・固定費バーン上限と、各レーンの費用・活動・出口条件・関連XRLを、先頭2行とレーン列を固定した横長1シートに出す。保存済みの資本政策・会社情報へは書き込まない。タブ全体の並びは、フェーズ表 → イベントと月次試算表・年度別の事業・資金推移 → 年次試算表 → 100%株主構成推移 → 編集可能な資本政策表 (`CapitalPlanWorkspace`) の順。フェーズ表と年次試算表はSX固有データなので他PJには出さない。金額・日付・評価額は計画仮説で、確定実績として扱わない。

2026-07-28 更新: 表全体は白・墨色・藍を基調にし、色は状態と株主識別だけに使う。GRLは内閣府SIP準拠の**ガバナンス成熟度レベル（1〜8）**で、制度・規制・標準・ガイドラインの社会実装準備を示す。採用・役割・社内運用はHRLで扱い、Phase 0 / Seed / A / B / C-IPOのGRL到達値は `1 / 3 / 5 / 6 / 8`。資本政策表は横スクロールのみとし、株主別の詳細は初期折り畳みでFD比率を1行表示、必要な株主だけを展開する。年次試算表は百万円・整数・3桁区切りで、売上原価と人件費等のPL費目、助成金の特別損益、資金繰り上の助成金入金を分けて表示する。年次試算表の直下にある初期折り畳みの「前提パラメータ」は、年次の売上・原価・助成金・役員/社員別の人数、報酬・旅費・消耗品費、研究開発・その他販管費・工場以外の設備投資・IPO以外の株式調達、4段階の自社工場の建設年度/投資額、IPO年度/公募調達額を動かし、PL・設備投資・株式調達・期末現預金を即時に再計算する。これはブラウザ内だけの未保存試算であり、資本政策表・株主構成・会社情報を更新せず、再読み込み時に初期値へ戻る。

KUTE (`p25`) では、ヘッダー直下に **年度内ロードマップ** を表示する。2026年6月から2027年3月までの横軸で、規程整備レーン (`2027年1月目途で整備完了`) と、シーズ発掘 / after GTIE レーン (`2027年3月までに支援実務の型化`) を同時に確認する。根拠は 6/11 キックオフ資料と `PROJECT_BRIEF` の年度内スケジュール。

KUTEだけは **規程・内規** タブ (`/project/p25/cockpit?tab=regulations`) を追加する。契約上AMDが整備する7規程（大学発SUとの兼業、知財取扱・大学発SUライセンス、大学発SUへの出資・新株予約権、大学発SUとの共同研究、利益相反マネジメント、大学発スタートアップ認定、大学発SUの共有機器利用）を先頭に置く。認定委員会内規・大学発スタートアップ支援細則・認定審査チェックシートは、認定規程を実装する随伴文書として分離する。台帳は説明文を主役にせず、`S0 対象確定 → S1 原典確認 → S2 AMD原案 → S3 学内調整 → S4 決裁・施行` の5段階と `S?/4` の五分割ゲージで、進んでいる規程と止まっている規程を比較できるようにする。各行には現状、次ゲート、次ゲートの時期、実在する最新版docxまたは原典、保管済みの途中版数を小さな文字で並べ、進捗順に表示する。一律の最終期限は行へ繰り返さず、全体工程として「8月: 残り6規程の素案」「9/4: 修正案・進捗確認」「9〜11月: 学内議論・修正」「1月: 施行版・様式・運用フロー」を固定表示する。原案未作成・原典回収待ちはリンクを偽装せず明示する。文書実体はKUTE共有ドライブの `00_規程・内規_版管理` に集約し、コックピットはメール本文・個人情報・秘密情報を保存も表示もせず、文書の管理状態とDriveリンクだけを扱う。

## PJ Status (= AMD Score / XRL)

### AMD Score
- PJ / SU の価値・成熟度を見る総合スコア。p00 の `AMD Management Score` とは別物
- 現行 primary は SPS (`M x P x R x S`)。legacy M-X-F / 7軸 Cobb-Douglas は comparison と evidence 用に残す
  - `P` = Potential / 潜在規模
  - `R` = Reach / Readiness (= TRL/BRL/GRL/SRL/HRL の contribution product)
  - `S` = Survival (= σ_SU / FRL / R_net の contribution product)
- legacy M-X-F の構成
  - `σ_SU` = Macrotrend / Triple Helix (= 学術 μ_A × 産業 μ_I × 政府 μ_G)
  - XRL = 会社側の readiness (= TRL/BRL/GRL/SRL/HRL)
  - FRL = CEO / founder 側の leadership readiness (= ALQ / Grit / Resilience 等)
- **過去 = 実線** (黒)、**未来予測 = 破線** (5 4 dash) で表示
- 右上 pill (大数字) は **現在のスコア** (= 過去最終点)
- legacy M/X/F カード = SPS の根拠・比較用。現行 primary に戻さない

### XRL 進捗 (5 軸)
- TRL (技術) / BRL (事業化) / GRL (制度) / SRL (社会) / HRL (人材)
- 1-9 段階で内閣府 SIP 体系互換

### MS変更履歴

今期 MS リストの直下に **MS変更履歴** を折りたたみ表示する。初期表示では閉じておき、必要なときだけ展開して確認する。

## 今シーズン収支

PJ cockpit の進捗管理タブでは、今期 MS リストの直下・月次カードの手前に **今シーズン収支** を表示する。目的は、MS 設計と報酬計算が AMD の運営費・バッファを勝手に削っていないか、シーズン頭から確認できるようにすること。

表示するもの:
- シーズン合計: `クライアント支払` / `バッファ` / `原資上限` / `PJ予算` / `メンバー支払` / `期末未払`
- 月次行: 各月の `クライアント支払` / `バッファ` / `PJ予算` / `メンバー支払` / `未払残` / `収支`

クライアント支払は契約ベースの `contractBackedClientAmount` に、別財布売上 (`billing_cycles.extra_revenue_json`) の**現金入金額**を加算する。別財布の開発期間按分はPLだけのルールで、ここでは使わない。別財布ごとの実入金月 (`payment_received_ym` / `payment_received_at`) があればその月へ総額を一括計上し、未確認なら既存 `invoice_ym`、次に `billing_date` とPJ支払条件で入金見込み月を解決する。契約が schedule_based の場合は `contract_terms_json.monthlySchedule.amountTaxExcl` も予定売上として読む。バッファは `value_plan_cycles.buffer_breakdown_json` にシーズン全体の内訳がある場合はそれを優先し、未設定の PJ だけ `billing_cycles.budget_buffer_amount` を読む。原資上限は `(クライアント支払 - バッファ) × 65%`。PJ予算は `billing_cycles.budget_yen + extra_budget_yen`、メンバー支払・未払残は `billing_cycles.reward_summary_json` を読む。未払残は支払通知対象の外部メンバーへ将来払う残高だけで、役員の繰越分は未払残に混ぜず会社留保側の内部検算に含める。`収支` は現金主義の月次表示として `クライアント支払 - バッファ - メンバー支払` で出し、役員向け報酬相当額や未払残はその月の現金流出ではないため含めない。役員向け報酬相当額は検算には含めるが、メンバー向けの PJ cockpit では表示しない。期末未払が 1 円でも残る場合、または PJ予算が原資上限を 1 円でも超える場合は、赤い停止帯と不足表示を出し、報酬計算側で最終月に自動上乗せしてゼロに見せない。MS 設計の保存は `/admin/ms-overview` で、同じ数字を使った保存前検算が不足状態を `blocked` にする。

## 経営ハイライト (= 旧「経営・事業シグナル」)

> **これは「進んだこと・起きたこと」だけを書く場所**。未了 / TODO / アイディア / 議論中は **書かない** (= MS 展開欄の TODO、`/proactive`、MTG サマリの次アクションなど、用途が合う場所で扱う)。
> (まさ #26 #27 2026-05-24 確定)

上部の棚は2つ。

- **重要な動き**: 会議やOS内の根拠から作った従来の経営ハイライト。未確認候補も明示付きで見える。
- **採用リサーチ**: つくよみが外部公開情報から見つけ、通知で「採用」したものだけ。業界・市場 / 助成金 / 協業候補で見分ける。

外部リサーチの未採用候補はここへ直接入らない。まず `/notifications` で内容を見て、残す価値があるものだけ採用する。

### 分類

| 分類 | 色 | 含まれる signal_type |
|---|---|---|
| 🏛 **経営全般** | violet | `management_decision` / `strategic_pivot` / `funding` / `next_move` |
| 🚀 **事業開発** | emerald | `business_progress` / `commercial_progress` / `partnership` |
| 🔬 **技術開発** | sky | `tech_progress` (= 自社特許 / 技術スタック進捗) |
| 🌐 **外部環境** | amber | `ip_regulatory` (= 他国規制等) / `risk` |

外部マクロ一覧の正本は **Atlas** (= header の「Atlas で全マクロ ↗」リンク)。ただし PJ にとって重要な外部シグナルも cockpit に並ぶ (= 例: 5/21 中国レアアース → SX 重金属回収追い風)。

### Polarity アイコン (= まさ #29 #26 4 種類確定 2026-05-24)

### candidate と confirm の違い
- **candidate** = Codex automation が抽出したばかり、まさが内容を確認する前 (= 「⚠️ 未確認」注釈)

- **rejected** = 抽出が誤りでまさが却下したもの (= 表示しない)

詳しいフローは **[2-4 章 2.2 まさえいMTG](2-4-amd-cockpit.md#22-まさえいmtg)**。

## MTG サマリ

- `project_meeting_summaries` テーブル
- 入力: Calendar (= 開催情報) + Slack / Notion / Drive (= 議事録本文) + dialogue API (= まさえいMTG)
- `source_kinds` で種別判別: `regular` (= 定例) / `dialogue` (= まさえいMTG) / `upcoming` (= 日時確定済みの予定MTG) / `upcoming_tentative` (= 日程未確定の仮置き)
- MTGサマリ先頭では、`source_kinds='upcoming'` や `upcoming+calendar+manual-prep` のように `upcoming` token を含み、かつ開始時刻が現在より後の row を「予定MTG / 準備中」に出す。`source_kinds='upcoming_tentative'` は別欄を作らず同じ「予定MTG / 準備中」欄に入れ、日付欄に `日程未確定` と表示する。`meeting_id` が `upcoming:` で始まっても、`source_kinds` が開催済みソース (`notion` / `gmail` / `drive` / `slack` / `calendar` など) なら準備カード扱いしない
- 通常の PJ コックピットでは、MTGサマリ一覧を小さな枠内でスクロールさせない。カードが増えたときは一覧全体を縦に伸ばし、コックピット全体のページスクロールで読む
- 開催済み議事録を開いた時に出す会議前準備メモは、手動で作った準備メモまたは prep worker の成果がある場合だけ表示する。カレンダー同期だけで作られた薄い予定テンプレートは、会議後に `MTG準備情報` として残さない
- H-1 routine は今後60日の確定Calendar予定を `POST /api/meeting-prep/calendar-sync` に渡し、前回議事録がまだ無いPJでも `source_kinds='upcoming'` の予定MTGカードを作る。recurring series はシリーズごとに次回1枚だけを表示し、同じ定例が複数カードとして並ばないようにする
- 一覧カードの短い説明は `summary_short`。詳細モーダルは `narrative_md` があればそれを主表示する
- 詳細モーダルで `narrative_md` (= H-1の MTG サマリ抽出 routine が、そのMTGに参加していなかったメンバーでも背景・議論の流れ・決定/未決・次の一手を理解できる構成に書き直したもの) を主表示
- 詳細モーダルの Markdown 本文に active AMDメンバーの `members.code_name` が standalone mention として出る場合、`/mypage?memberId=<members.member_id>` へ自動リンクする。これは admin が OS 内本文からメンバー詳細へ移動するための導線で、既存の Markdown link / code / pre は維持する。短い code_name が `しかるべき` や `こうして` のような長い語へ埋まっている場合はリンクしない
- raw 配列 (= 元データ) は折りたたみ「元データ」へ
- 今後の議事録本文は `## 🎯背景` → `## 📊経緯` → `## ✅決まったこと` → `## ▶️次の一手` → `## ⚠️残課題` の順で書く。絵文字・見出し文言・順序は固定で、絵文字と語の間に空白を入れない
- 今後の議事録本文は、`🎯背景` と `📊経緯` を段落、`✅決まったこと`・`▶️次の一手`・`⚠️残課題` を1項目1論点の `- ` 箇条書きにする。番号付きリストとチェックボックスは使わない
- 手動修正する場合も、`narrative_md` はこの5見出し順と段落/箇条書きの役割を守る。`✅決まったこと` には会議で実際に合意・確認されたことだけを書き、資料だけからの推定や未決事項は `📊経緯` または `⚠️残課題` に残す
- MTG詳細モーダルの「表示内容を編集」は、表示している section を同じ位置で textarea 化する。`narrative_md` が表示されている通常MTG / dialogue は `narrative_md` を編集し、`decided / progress / next_actions / risks` の raw section が表示されている場合だけ、その raw section を編集する。予定MTGでは `risks` 列を破壊せず、UI上は「必ず確認すること」として表示・編集する
- 通常MTG / dialogue は `POST /api/meeting-summary/manual-update` で `title / summary_short / narrative_md / decided / progress / next_actions / risks` を更新できる。手動修正は `source_hash` を変えないため、同じ元ソースに対する自動抽出の再実行で上書きされにくい。MTG 詳細モーダルには「つくよみに修正依頼」を置かず、人間が直した本文を `manual-edit` として保存する
- `narrative_md` は議事録本文の正本。`summary_short` と raw 配列だけの保存は品質劣化なので、開催済みMTGの backfill / routine は narrative なしで保存しない。既存の長い narrative は migration 098 と manual-update API で、空欄や5見出し構造を欠く更新から保護される
- `notion:<page_id>` 由来で narrative なしの弱い手動 duplicate が、同じ日・同じタイトルの強い row と並ぶ場合は、一覧では強い row を優先して表示する
- 詳細モーダルの「添付資料」では、md / docx / xlsx / pptx / txt / csv / zip / 画像 / PDF など一般ファイルを MTG に紐づけて保存できる。ファイル選択、drag & drop、クリップボードのファイル/画像ペースト、browser の画面キャプチャを同じ `meeting_assets` に保存する。Markdown (`.md` / `.markdown`) はOS内モーダルで本文を読める
- 新規添付の実ファイルは Google Drive の当該PJ folder (`projects.drive_folder_id`) 配下に `YYMMDD_会議名` folder を作成/再利用して保存する。カード上には `保存先: PJフォルダ / YYMMDD_会議名` を表示する。旧添付の private Storage `meeting-assets` は互換表示する
- 「本文へ」を押すと、添付画像 / ファイルリンクが `narrative_md` の添付資料 block に Markdown で挿入される。本文には `/api/meeting-assets/file/{asset_id}` だけを残す
- 各カードを開くと URL が `?meeting=<meeting_id>` に変わる。この URL を共有すると、同じ PJ コックピットを開いた時点で該当 MTG 詳細モーダルが開く
- 詳細モーダル上部の共有操作では、`PDF保存` / `議事録コピー` / `準備メモコピー` / `共有URLコピー` が使える。`PDF保存` は共有用に整えた本文を直接PDF化し、その後ろに `meeting_assets` の PDF / PNG / JPEG を並び順どおり連結する。投影資料を先、参加者からの共有資料を後に並べ、会議本文と同じPDFで渡せる状態にする。`議事録コピー` は `narrative_md` または fallback section から会議後サマリだけを、件名候補・日時・概要・本文つきのプレーンテキストへ整える。`narrative_md` 末尾に `参考: 会議前準備メモ` がある場合は議事録から除外し、`準備メモコピー` で別にコピーする。`共有URLコピー` は OS 内で同じ MTG 詳細を開くための `?meeting=` link をコピーする

### MTG Prep セッション自動立ち上げ (2026-06-22 まさ確定)

> **何が嬉しいか**: 「明日 MTG あるけどまだ準備してない、codex を毎回開いて『背景はこうで…』と説明するのがだるい」を OS 側で解決する。現行の **W-Prep** が、翌7日までのMTGごとに visible prep task を事前に立ち上げる。taskの中では、契約範囲・過去MTG・未完了action・保留・直近チーム入力を横断して論点を引き継ぎ、まさは背景を思い出すところからではなく、今回の判断相談から始められる。

#### prep の timing

- **post-MTG 即時主義**。前回 MTG の翌日から、今回 MTG の 24時間前までの間で、まさカレンダーの空き枠を探して prep を入れる
- 24時間前が土日など H-1 が動かない日に当たる場合は、同じ時刻のまま直前の稼働日に繰り上げる。例: 月曜12:00のMTGなら、金曜12:00に prep 枠を作る
- セッションは prep 枠の開始時刻までに立ち上げ完了している状態を目標にする。H-1 が毎時15分に動く都合で、金曜12:00枠なら直前の金曜11:15 run で session を起動する
- 過去同シリーズが無い MTG (= 完全初回) は、検知された瞬間から prep を始められる
- ギリギリではなく、余裕がある日に前倒しでやる (= 先手先手主義)

#### prep 枠 (= まさカレンダー上の prep 作業時間)

- prep 作業自体を **「＋ <PJコード> MTG準備: <MTGタイトル>」** という Calendar event としてまさカレンダーに作る
- prep 枠には、その PJ の Calendar 色を自動で付ける。色は `CFG_ColorPJHistory` を PJコードから逆引きして決め、既存 prep 枠が無色・別色なら次の H-1 run で色だけ補正する
- タイトル先頭 `＋` = 動かせるタスク (= 既存 H-1 `+<PJ>` 規約と統一)
- まさが「この日無理」と思って枠を別日時にドラッグしたら、次の H-1 run (毎時) で追従して spawn 時刻を再計算する
- 対象は **まさのカレンダーだけ** (= 他メンバーには prep 枠を作らない、まさ確定)

#### MTG カードの表示

- 翌7日に予定MTG (= `source_kinds='upcoming'`) がある PJ では、cockpit MTG サマリの予定MTGカードに以下が表示される:
  - **readiness pill**: 緑 80↑ (準備OK) / 黄 50-79 (もう一押し) / 赤 <50 (要相談)
  - **session 状態 chip**: 「prep セッション準備中」 / 「ready (codex で開いてね)」 / 「起動失敗」
- 共有資料は初回に自動生成しない。opening prep briefで相談した後、まさが「この前提で資料を作って」等と明示した場合だけ、Drive `PJfolder/YYMMDD_MTG名_prep/` にHTML draftを置く
- worker が会議前の AI Meeting Notes page を見つけた場合は、PJ 固有名詞・略称・拾うべき論点を `AI Meeting Notes用コンテキスト` として先に入れる。見つからない場合は、`prep_draft_md` に手動貼り付け用contextと状態を残す。通常Notion議事録draftは初回に自動作成しない
- `AI Meeting Notes用コンテキスト` は「作った」だけでは完了扱いにしない。worker は当日の AI Meeting Notes page に marker 付きで入ったことを確認してから `ready` にする。見つからない、書けない、候補が曖昧、既存 `prep_notion_page_id` が過去 page を指す場合は、その状態を `prep_readiness_reasons.notion_ai_context` に残し、`prep_draft_md` に手動貼り付け用 context を残す

#### prep session の開始点

- prep session を開いた時の最初の有用出力は、`ready` や保存先の技術報告ではなく、まさと会議設計を始めるための opening prep brief にする
- opening prep brief は `前回までの流れ / 今回の論点 / 推定着地 / まさがやること / 相談入口` の5項目を持つ
- 同シリーズの前回だけでなく、契約時の依頼範囲、PJ内の別MTG、未完了action、保留事項、直近のチーム内検討まで論点台帳へ集める。各論点は「今回扱う」「ownerと再確認日を置いて後続へ送る」「根拠付きで対象外」のどれかにする
- 各論点から既存規程・契約・申請・資料・システム・関係者工程への二次影響も確認する。全体スケジュールと呼ぶ場合は、主要成果物だけでなく後続の改定工程まで含める
- 黙って消えた論点が1件でもある、二次影響を確認していない、先送りにowner/再確認日がない、全体日程から対象が落ちている場合は、機械gateでreadyにしない
- 会議冒頭で読み上げるセリフ案だけを置かず、定型の「これであってる？どうする？」も強制しない
- 初回は共有資料を作らず、このbriefを使った相談から始める。資料化はまさの明示write後だけ行う

#### prep worker が作る共有フォルダ資料

- opening prep briefで相談した後、まさが資料作成・反映を明示した場合だけ作る。初回task起動時に先回りして資料化しない
- 資料化前に論点台帳と現在の構成を再突合し、未完了論点の黙った欠落がないことを確認する
- 生成した資料 draft は Drive `PJfolder/YYMMDD_MTG名_prep/` に置く
- prep 資料の主成果物は **HTML** に統一する。Google Docs / Markdown / Slides / Sheets を主成果物として作らない
- 表、チェックリスト、提案書、アジェンダ、試算は HTML 内の section / table / callout で表現する
- HTML は AMD OS のデザインコードに従い、原則 self-contained な `.html` として作る。ファイル名は `YYMMDD_MTG名_用途.html`
- 連続型の投影HTMLは、desktopで白背景の左固定menuを置き、section anchor、関連資料を別tabで開く操作、meeting memo、コピー・文言編集・HTML保存・消去buttonを備える。mobileでは上部menuへ組み替える
- 投影前提では、本文、table、menu、label、button、注記を含むすべての可視文字を16px以上、資料番号や比較対象番号を28px以上にする
- section名は中立な事実名称を最大見出しにし、提案、推定着地、結論、日程案をheroやeyecatchとして押し出さない。未確定事項は本文・比較表で `案` / `確認事項` / `協議事項` として示す
- MTG前の提示資料には合意事項・決定事項・会議結果sectionや結果入力buttonを置かない。提示資料は論点、比較材料、確認事項、日程案までを扱い、決定内容は開催後の議事録へ記録する

#### Slack DM nudge

- H-1 run は `prep_worker_status='ready'` になった MTG を自動で Slack DM しない。MTGカードに readiness / threadId を保存するのが既定動作
- まさから明示的に通知依頼がある場合だけ、まさ専用 Slack DM にまとめて送る (= 同じMTGには重複送信しない)
- 送信ルートは `/Users/masa/projects/AMD/amd-os/scripts/send-eimi-slack.mjs` 固定。Codex / ChatGPT / Slack connector から直接送らない
- 形式 (つくよみ口調):
  ```
  🌙 まさ、prep セッション立ち上げといたよー

  📌 KUTE定例 (明日10:00, p25, オンライン)
     readiness 75/100  🟡
     codex で開いてね、待機してるよ

  📌 pHydrogen KR訪問 (明後日14:00, p07)
     readiness 35/100  🔴
     codex で開いてね、資料draftは作ったけど着地点要相談
  ```
- まさは codex desktop を自分で起動 → 該当 session に入って対話開始。ターミナル操作不要。session 側は保存完了報告ではなく、会議設計スターターで待機する
- 各 PJ の facilitator (= kaz / かる / ちこ等) には同じDMを送らない (= **まさ専用 DM だけ**、まさ確定)

#### codex のみで spawn 統一

- session は codex で立ち上げる (= claude code は使わない、まさ 2026-06-22 確定)
- codex は ChatGPT サブスク認証で動くため、prep セッションで定額外トークン課金は発生しない

PM 向けの cockpit 右カラム step UI は廃止済み。コックピットでは月次カードから対象月を開き、`CockpitMonthlyModal` で進捗・報酬・月次報告書を確認する。自動生成された月次報告書 draft に対する軽い確認は Slack nudge 側で扱う。

### 月次報告書の社内版 / 提出版

月次モーダル右上の名称は全 PJ 共通で `社内版` / `提出版` / `本文を編集` の3操作に固定する。クライアント名は帳票の契約情報に表示し、操作名へ埋め込まない。`社内版` (総合判定・MS前月/当月/差分表・ガント・体制・次月計画を可視化した帳票) と `提出版` は同格のリンクで、どちらもクリックすると印刷ビューを新しいタブで開くだけの操作。`本文を編集` はこの2つとは別の第三の操作で、可視化帳票が参照する `monthly_reports` の本文 (社内版本文) を直接編集するパネルを開閉する。パネルを開くと二段階クリックを挟まず直接編集状態に入り、`保存` / `確定` はパネル内で行う。

画面上の本文編集・保存・確定は LLM を呼ばず、AI token を消費しない。月次本文の自動生成は月末最終日の Claude Code Scheduled Task `amd-os-l2m1-monthly-report` が定額内で担当する。旧 `/api/report/generate` と `/api/monthly-report/edit-by-tsukuyomi` は 410 を返す停止経路で、月次モーダルには生成・再生成・AI修正ボタンを置かない。

社内版本文は固定8見出しのナラティブ本文を正本とし、`社内版` 帳票は表紙・要約・進捗・工程表・実施体制・次月計画・添付資料を持つ既存のリッチ帳票としてこれを可視化する。提出版は各PJの先月実提出版と同じ書式を維持し、`monthly_reports_external.body_md` を1本の連続文書として組版する。提出版だけ章ごとの強制改頁を入れず、自然改頁で流す。章間の `---` 等は生成・保存・表示時に除去し、印刷時はブラウザ既定の日付・`AMD OS`ページタイトル・URLを出さない。丸数字を含む章見出しは前月提出版と同じ日本語フォントで表示する。自社メンバーは姓、府省共通研究開発管理システムは `e-Rad` と表記する。

`billing_cycles.invoice_ym` が稼働月と違う場合 (= 複数月を後からまとめて請求) でも、PM cockpit に請求 step は出さない。請求月の繰延は `/admin/invoices` / `/admin/payouts` / finance 系で扱う。

## 🏛 会社概要タブ + 要対応 (2026-06-15 ガバナンス欄として追加、2026-07-16 常設「会社概要」タブへ統合、2026-08-09 キラー要素カタログ追加)

PJ cockpit に常設タブ「**会社概要**」が出る (進捗管理・スコア詳細と並ぶタブの1つで、`会社概要` タブは全 AMD メンバーに表示される。旧 admin 限定の「🏛 株主・ガバナンス」欄は廃止しこのタブに統合した)。**終了した PJ でも表示される** (株主総会・清算・持分は卒業後も残るため)。

- 表示: 会社基本情報 (登記・定款等の現在値)、**cap table** (発行済み株数・完全希薄化後株数、確定した株式イベントを積み上げた資本構成の推移)、**資本政策表**（ラウンド別の株数・持株比率・発行価額・時価総額）、資金調達ラウンド/バリュエーション、転換前証券 (J-KISS・SAFE等。現在の持株比率には混ぜず、転換シナリオとして別枠表示)、**総会・取締役会履歴一覧**と決議・AMD対応 (委任状提出、書面決議への同意など)、年度決算、そのPJの確定済み要対応。登記済み株式数とcap table合計が一致しているかの照合 (tie-out) も表示する。
- **資本政策表** (2026-08-29 追加。まさ「確定済みの調達・潜在株式のところは正式な資本政策表にするべき。全PJとも、ちゃんと表形式に」): 以前はラウンドと転換前証券がカードで並んでいたところを、**全PJ共通の正式な資本政策表**に置き換えた。ラウンドを横（列）、株主を縦（行）に並べ、1ラウンドにつき `新規割当分` `発行済株数` `払込金額` `顕在株比率` `新規発行SO` `発行済SO` `潜在込比率` の7項目が出るので、ラウンドをまたいだ株数と持株比率の動きをそのまま追える。株主は 創業者 / AMD / まさ / VC / エンジェル / 事業会社 / 役職員・SO / その他 の区分でまとめ、区分ごとの小計も出る。表の一番下に `合計` `発行価額` `調達金額` `累計調達金額` `プレ時価総額（顕在）` `ポスト時価総額（顕在）` `ポスト時価総額（潜在込）` が並ぶ。項目の並びと呼び方は、AMDが実務で使っている cap table の雛形に合わせてある。列が多いときは右上の「増減・払込の列を隠す」で、発行済株数・顕在株比率・潜在込比率の3項目だけに絞れる。**表に出るのは確定済みの株式イベントだけ**で、計画中のラウンドは事業計画タブの資本政策プランが正本。株主名の列は横スクロールしても左に固定される。**まだ株主として登場していないラウンドの欄は `－`** で、0株とは区別する。ストックオプションは「完全希薄化後 − 顕在株」で自動的に分けて数える。
- **ラウンド一覧**: 資本政策表の下に、登録済みのラウンドが日付順で全件出る（日付 / ラウンド / 発行価額 / 調達金額 / 累計調達金額 / プレ時価総額 / ポスト時価総額 / リード投資家）。株式イベントに紐づいていない計画ラウンドやJ-KISS検討中の行も、ここには必ず残る。**株式イベントをまだ登録していないPJでは資本政策表は出ず、このラウンド一覧だけが出る**（空の表を偽装しない）。株主別の内訳が要るときは株式イベントを登録する。
- **転換前証券** (J-KISS・SAFE等) も同じセクション内の表で見る（保有者 / 種別・状態 / 発行日・期限 / 元本 / 評価上限 / ディスカウント / 転換見込株式）。現在の持株比率には混ぜず、転換見込のシナリオとして別に持つ。
- **キラー要素カタログ** (2026-08-09 追加、2026-08-10 段階評価へ更新): 工程失敗や資金切れとは別に、事業化見込みを大きく削る事象を **予防統制** と **常時監視** の二群へ分け、filterで隠さず同時に見る。予防統制は「起きたら記録」ではなく、SHA・定款の交代条項などAMDが発生前に完了させる打ち手で、`未確認 / 未整備 / 整備中 / 実装済 / 運用確認済` の成熟度を記録する。`統制逸脱` は成熟度とは別の重大状態。常時監視は経営ベクトルや中核メンバー関係などを `未確認 / 兆候なし / 要観察 / 明確な悪化 / 重大事象` の悪化度で記録する。画面先頭の **このPJの全体判定** は、`危険 > 要対応 > 要確認 > 要観察 > 安定` の順で状態を集約し、重大・要対応・要観察・未確認・安全の件数も併記する。未確認は安全扱いしない。要素の雛形は全PJ共通で、どのPJから追加しても全PJへ現れるが、状態・状態日・PJ目標日・根拠メモ・記録者はPJ別。根拠は議事録・契約書・定款・報道などの記録・文書に限り、CEO本人の自己申告だけでは状態を確定しない。今回は記録と表示までで、自動通知・成功確率の再計算・LLM呼び出しは行わない。
- **資本政策ワークスペース（cap table 統合グリッド）** (2026-07-16 追加、2026-08-21 に事業計画タブへ移動済み。会社概要タブ側は上記「資本政策表」が担当する): cap table は「設立・Seed・QST現物出資」等のイベント列を横に並べた1枚のグリッドで見る。各イベント列の見出し (日付+ラベル、クリック可能) の直下にそのイベント時点の株主構成を縦積み100%グラフで表示し、共通の0-100%スケールで隣の列と比較できる。グラフの下には発行済株式・新規発行・調達額・発行価額・pre/post-money・株主ごとの持株数と比率が、イベント列ごとにコンパクトな表として並ぶ。正史が設立イベントから始まっていないPJでは「創業時のシェアを遡って再現できない」旨の警告を出し、その場で創業時の株式イベントを追加する導線を出す。
- **資本政策プラン台帳** (2026-07-17 追加、build v3.44.5、2026-08-21 に事業計画タブへ移動済み、旧・単発で保存されなかった「次回ラウンド試算」欄と「保護株主」概念を置き換え): cap table グリッドの下に、設立からIPOまでの複数ラウンドを名前を付けて保存できる作業台帳が出る。**閲覧・編集は管理者限定ではなく、登録済みAMDメンバー全員が可能**。**シナリオは名前を付けて複数保存でき**、入力すると約800ms後に自動保存される (自分で保存ボタンを押す必要はない)。他のメンバーが同時に同じシナリオを編集した場合は、保存時に競合を検知して最新のサーバー内容を提示する。株数・金額・単価・評価額など台帳上の driver 項目は自由に編集でき、それぞれ「入力値・自動計算・確定値・取込・手動上書き」のどれかの由来ラベルが付く。ポストマネー評価額・調達額・新規発行株式数などの**自動計算セルには「自動」バッジが付き**、✎ボタンで明示的に「上書き」でき、上書き後は元の自動計算値も後から確認できる。新規に株主を追加した直後は金額欄が空欄のままでもよく、`valuation_and_investment` 方式のイベントでは金額を入力すると単価から株数が自動計算される。計算方式 (評価額×調達額 / 単価×株数 / 目標比率) を直接切り替えると、切替後にdriverになる項目・自動計算になる項目のラベルが自動的に張り替わり、古い上書き状態は意味を持たなくなるためリセットされる。セカンダリ（既存株式の譲渡）イベントでは、譲渡人（売り手）側の株数はマイナス値として入力し、譲受人（買い手）側のプラス株数と合計が0になる必要がある。転換前証券（J-KISS等）の転換は自動発生せず、ユーザーが転換イベントを手動で作成し、消込分（マイナス）と発行分（プラス）の両方を入力するまで反映されない。**「保護株主」という概念はこの台帳には無い**。増資イベントごとに株主の目標保有比率を個別入力するだけで、特定の株主を自動的に守る仕組みは作らない。イベント列に縦積み100%グラフを揃えて表示し、株数が整数でない・比率合計が100%にならない・pre/post-moneyが不整合、などのエラーが1つでも残っている間は**確定（freeze）ボタンが押せず**、押せない理由は画面上の「検証結果（エラー／警告件数）」一覧とボタンのツールチップで確認できる。確定すると、サーバー側が保存内容を自動計算し直したうえで、その確定済みの内容が改変不可の確定版として1件追加され、過去の確定版は履歴として残り続けて後から書き換えられない (migration `180_freeze_capital_plan_derived_document.sql`)。**VC向けのExcel出力は、この確定版からしか作れない**（作業中の未確定シナリオからは出力できない）。出力ファイルには会社名入り提出情報（サマリー）・資本政策（イベント列に揃えて中央寄せしたグラフ付きcap table、ラベルはすべて日本語）・投資家別スケジュール・潜在株式/譲渡（希薄化）・検算の5シートが入る。**スマホ幅でも表とグラフはそのまま表示され続け**、株主ラベル列とイベント列見出しは縦横どちらにスクロールしても画面上に固定表示されたまま、横スクロールで全イベント列を確認できる（表が消えて1イベントだけの画面に切り替わることはない）。表の下にある詳細設定を開いたときの個別イベント編集フォームだけは、スマホ幅で選択中の1イベントを◀/▶で切り替えられる。
- **数値と株主識別の表示** (2026-07-31 更新): 台帳内の金額・株数などの数値は3桁ごとのカンマで表示する。自動算出を含む金額は省略記号で隠さず、セル内で折り返して全額を読めるようにする。FD比率の縦積み棒と凡例は、見分けやすい色・凡例の外周・棒の区切り線で株主を識別する。色は株主名の識別専用であり、成功・注意・エラーなどの状態を表すものではない。
- 総会レコードには総会関連資料 (招集通知・議案・契約・決算書・cap table 等) がリンクで添付される。メール抽出時に添付本文が渡された場合、実ファイルは Google Drive の当該PJ folder (`projects.drive_folder_id`) 直下に `YYMMDD_会議名` folder を作成/再利用して保存し、cockpit には Drive の `webViewLink` を押せるリンクとして出す。例: `260616_取締役会書面決議`。

- **Excel / PDF 出力**: タブ右上の書き出しボタンから、cap table・資本構成・ラウンド等を Excel (xlsx) または PDF として保存できる。
- **要対応 (期日順)**: `/dashboard` と `/notifications` の先頭に、全PJ横断 + 会社/個人スコープの「期日つき要対応」(株主総会の議決権・事前承諾、契約更新、振込期限など) が期日順 + 「あと何日/期限超過」で出る。「対応済にする」を押すと、成功時は**押した行だけ**がその場で消え、ほかの要対応は読み込み直しで消えない。保存に失敗したときだけ元の位置へ戻る。表示対象は `review_status='confirmed'` かつ未完了 (`open` / `in_progress`) のものだけ。未確認 `candidate` はレビューキューに留め、PJ cockpit の会社概要正本欄には混ぜない。

## 📜 知財タブ (2026-08-21 追加)

PJコックピットの `知財` タブ (`?tab=ip`)。AMDはbefore zeroから入るので、**自社の出願だけでなく、その技術領域の権利地図全体**を1つの台帳で見る。

載せる対象は5つの立場:

| 立場 | 何を載せるか |
|---|---|
| 自社 | AMD / PJ法人が保有・出願中の権利 |
| 大学 | 大学の基本特許。実施許諾・不実施補償の交渉対象 |
| 共同 | 共同出願 |
| 障害 | 他社が押さえていて、回避かライセンスが要る特許 |
| 監視 | 競合動向として見ておくだけ |

### 画面の並び

1. **サマリ帯** — 立場ごとの件数。admin は右端の「＋追加」から登録する
2. **⏰ 期限** — 審査請求・PCT国内移行・拒絶理由応答・年金など。期限超過と30日以内は赤、90日以内は琥珀
3. **🗺️ 特許マップ** — 3つの見方を切り替える
   - `権利範囲マップ`: 横=技術区分、縦=権利の広さ。**上のほうに赤 (障害特許) がある技術区分は、参入前に回避設計かライセンス交渉が要るゾーン**
   - `時系列マップ`: 横=出願年、縦=技術区分。どの領域がいつ混み始めたかを見る
   - `出願人マトリクス`: 誰がどの技術区分を何件押さえているかのヒートマップ
   - 凡例のチップを押すと、その立場の表示/非表示を切り替えられる
4. **立場別リスト** — 自社・共同 / 大学 / 障害・ウォッチ の3ブロック
5. **詳細** — カードを押すと、番号・日付・出願人・IPC・権利者とライセンス状態・経緯が開く。JP は J-PlatPat、海外は Espacenet へ番号で検索リンクが出る

### 誰が編集できるか

読むのはAMDメンバー全員、追加・編集・削除は admin だけ。編集ボタンは admin にしか出ない。

同じ台帳は**PJワークスペース (`/project/{project_id}/workspace`) の `知財` タブ**にも出る (2026-08-21 追加)。コックピットと同じ画面をそのまま共有しているので、どちらから開いても内容・操作・権限は同じ。ワークスペースを開いている外部アカウントにはこのタブごと表示されない。

### まだ繋がっていないもの

特許庁の特許情報取得APIとEPO OPSからの自動同期、期限の通知飛ばし、`/admin/ip` のAMD自社知財の取り込みは未接続。今は手入力で登録する。詳細は [`/spec/3-19-project-ip-current-spec`](/spec/3-19-project-ip-current-spec)。

## SX COO統合経営ダッシュボード（`/project/p21/workspace`）

### PJワークスペースの一本化（2026-08-12更新）

`/project/{project_id}/workspace`は、従来`/weekly-control`にあった完成済みの4タブ式PJ管制をそのまま表示する。`/weekly-control`は互換転送だけにし、同じPJの実行画面を二重管理しない。

タブ列は `週次差分 / ガント / 関係先 / 論点・仮説 / 知財 / ドライブ` で、`知財` はコックピットの知財タブと同じ台帳 (2026-08-21 追加)。SX（`p21`）にはこのタブ列の末尾に**ドライブ**がある。ここは別のファイル置き場ではなく、コックピットの「資料室」と同じPJ資料室を読む。PJ全体共有の資料・フォルダ、検索、追加、HTML編集（別タブの編集画面）、プレビュー、削除（保管）は共通するが、AMD内部資料・フォルダはドライブに出さず、開示範囲の操作も置かない。内部資料の確認と開示範囲管理はコックピット資料室に残す。

2026-08-11に追加した別デザインの`共有PJ管制`は、現行PJ画面と無関係な代替面だったため撤回した。外部アカウントには、大学・SU向けの正式レンズが現行画面と同等の品質・認可・公開版契約を満たすまで、簡易代替画面を出さない。

### 最初の1画面の読み方 = 統合タイムライン（2026-07-25 2回目更新）

最初の1画面は、上から3つの帯で読む。

1. **判定バー**: 左から「業務判定（重要経路の遅延見込み+N日。最大遅延の柱も併記）」「運用判定（データ充足と重大未確認の件数。画面のデータがどこまで信用できるか）」「STEP2消化（金額データが確認できるまでは未確認と表示）」「設立判断まで 残N日」。業務の遅れとデータの穴を別の枠で読む。
2. **経営状況図（統合タイムライン）**: このページ唯一の時間軸。左の列に柱ごとの工程・タスク名、右に月グリッドと今日線を置く。薄いバーが計画期間、同じバー内の濃い塗りが登録済み進捗。通常バー末尾の縦線、完了見込み記号、予定との差、工程間の破線は表示しない。先へ進むためのマイルストーンだけをひし形で表示する。行を押すとガント幅を削る右ペインではなく、ガントを背後に残した重畳モーダルで詳細が開く。詳細値を押した後は、その1枚の本文そのものが編集フォームへ切り替わる。フォームの周囲へ別の枠・背景・見出し・対象工程ブロックを置かないため、見た目にも操作上もモーダルは1枚だけ。未保存入力がある状態で外側の閉じる・Esc・背景を使うと、破棄確認が出る。
3. **今週の意思決定・次の経営介入**: 意思決定待ちの論点全件と、優先順の介入上位5件（図のピンと同番号）。介入には最大遅延の柱の案件を必ず1件含める（候補が台帳に無いときはその旨を注記）。

前版にあった「事業化ロードマップ」のセクションは、この統合タイムラインに吸収して廃止した。旧・対応待ち/直近アクションの2枠は「次の経営介入」上位5件+意思決定待ちへ一本化した。

**遅れの読み方（2026-07-25 更新）**: 「予定より後ろ」を3つに分けて表示する。赤=**期限超過**（予定日を過ぎてまだ終わっていない＝実際に遅れている）、橙=**遅延見込み**（予測日が予定日より後ろで、日付が確定しているか見直し理由が登録されている）、灰=**予測差（仮）**（予測日が後ろだが、日程が仮置きで見直し理由も未確認）。現在のSXは9件すべてが7/14に初期登録したときの仮置き値なので、灰の「予測差（仮）」として表示され、判定バーも「予測差 +28日 / 期限超過なし・仮日程の見込み差」と出る。実際に遅れている項目はまだ無い。各行をクリックすると、その予測日の根拠（例:「初期Seed。予測日は仮置きで、変更理由は未確認」）が詳細に出る。

**行をクリックすると詳細がモーダルで開く**: 以前は画面下へスクロールしていたが、図から視線が飛ぶためモーダルに変えた。閉じるボタン・Escキー・背景クリックで閉じる。モーダルには予定/予測/担当/予測日の根拠と、その ゲートに紐づく論点・関係先・依存・次の成果が入る。

**図から直接データを追加・修正できる**: 管理権限がある人は、柱の見出しにカーソルを合わせると出る `＋` でその柱にマイルストーンを追加、各行にカーソルを合わせると出る `✎`（またはモーダルの「日程・担当を編集」）で予定日・予測日・担当・状態などを修正できる。「計画詳細」の全マイルストーン詳細表からも、マイルストーンの追加・依存関係の追加・選択中ゲートの編集ができる。閲覧のみの人にはこれらのボタンは出ない。

**遅れの言葉づかい（2026-07-25 2回目更新）**: 「予測差+N日」という表記はやめた。図と判定バーは「予定よりN日後ろ（仮置き）」「予定よりN日遅れ見込み」「期限超過」「予定よりN日前倒し」のどれかで書くので、進んでいるのか遅れているのかが言葉だけで分かる。いまのSXは仮置きの見込みだけが後ろにある状態なので、判定バーは「実際の遅れなし / 仮置きの見込みは予定より最大28日後ろ」と出る。

**年月の2段表示・凡例の廃止・縮尺6倍・変更の即時反映（2026-08-07 追加、build v3.58.19〜）**: ガントの日付ヘッダは、上の段に年、下の段に月を置く2段になった。年は年が変わる最初の月にだけ出る。時間軸を伸ばしたときに年と月の文字が重なって読めなくなる状態を直したもの。あわせて、レーンの右端に出ていた赤茶色の「詰まり: 〜〜」の文字を消した。詰まりは各タスク・MSの詳細で読む。ガント下にあった凡例も、記号の意味を並べるだけで場所を取っていたので全部消した（設立前提の2件は塗りつぶしのひし形、通常のMSは中抜きのひし形という**見た目の違いはそのまま残る**）。縮尺スライダーの上限は4倍から**6倍**に上がり、長い期間をさらに拡大して日付を読めるようになった。

**並べ替えの保存と再読み込み（2026-08-18 更新、build v3.80.1〜2）**: 同じ階層のタスクを上下に並べ替えたときは、兄弟タスク全体の順序を1回の保存でまとめて確定する。途中の1件だけが失敗して表示順が元へ戻る状態は起こさず、他の人の同時編集があれば全体を保存せず最新状態を読み直す。ワークスペースを開く途中も、完成画面と同じAMDブルー・白・チャコールの背景を表示し、旧来の生成り・淡緑・淡橙の背景へ一度切り替わらない。再読み込みでは、変更頻度の低いPJ名とメンバー表示だけを短時間再利用し、ガント・論点・関係先・週次データは毎回最新値を読む。

関係先リストの `担当` プルダウンからは、「紹介接続待ち」「先方回答待ち」「担当者未確認」のような**状態の説明を自動で候補から外す**ようにした。人名ではないため。ただし既に保存されている値はその行の選択中として残るので、いま入っている内容が消えることはない。

「関係先リスト」はメール接点、PoC候補先、VCを別リストにせず、1社1行で表示する。`全関係先 / PoC候補先 / VC` は同じ一覧の排他的タブ。VCにはPartners Fund、DAVP、BNV、いよぎんキャピタルが入る。列は `評価 / 関係先 / 現在の状況 / ゴール / 次にやること / 次回面談 / 担当・期限 / 現在地の根拠 / 排液 / 接点の経緯 / 履歴・保有`。`接点の経緯`は、つながった理由と紹介者を固定2段で比較する。現在地とゴールだけを一覧で比較し、確認済み接点（古い順）、現在地、未完了作業、次の一手、ゴールの可変長な全進行状況は会社名下のsegment railから開く履歴モーダルへ置く。segmentもモーダル内blockと同じ件数・順序になる。進行状況railは固定段階へ丸めない（PoC営業の段階チップは別物で、営業段階の実データを表示する）。行動、担当、期限、止まるタスクは同じ保有事項から表示するので、「当方」とだけ出て具体的な作業が分からない状態を作らない。管理者は一覧の表示値を押して該当cell内で直接修正し、行全体や右端件数はモーダル入口にしない。履歴モーダルでは全やり取りと未完了/完了の保有事項を閲覧できるが、関係先全体の編集フォームは開かない。メール本文、アドレス、URL、個人連絡先、内部source refは保存も表示もしない。

新しい関係先は関係先名だけで追加でき、分類は任意。役割欄は分類と重複するため、新規・編集のどちらにも出さない。ほかの状態・合意・期限などは安全な未確認値で作成し、必要になった時に一覧や履歴から足す。「排液調達」のチェックは押した場所でそのままオン・オフして保存し、モーダルを開かない。移行前の行は最初の操作までは試料台帳から表示を導出するが、操作後は明示したチェック値を正本にする。

技術証明と工数入力は既存の `/workspace` に残る。週次管制から「既存ワークスペース」で移動する。
5. 低頻度の詳細（運用準備、4本柱の詳細比較表、目的→成果→KPI、意思決定の記録、判断→実行→確認、測定・資金・体制・約束、非表示にした情報の復元）は、ページ下部の単一の折りたたみ「管理台帳・編集」にまとまっている。個別の折りたたみを一つずつ開く必要はない。
6. 最後に週次エフォートを入力し、柱・接続ゲート・次の成果へ紐付ける。これは実行能力とデータ鮮度の補助面で、経営判定の代替にしない。AMD OS側の4人を研究チーム全体とみなさず、「研究側メンバー未確認」を体制上の不足として扱う。

### 更新と権限

portfolio/adminは共有台帳を更新できる。PJ限定メンバーは自PJの許可範囲だけを更新し、他PJ、契約本文、報酬、メール本文、内部交渉メモは見えない。更新APIはresourceごとにstatus列を使い、decisionの画面値「未決」はDBの`pending`へ変換する。KPIの`範囲内`は上限必須かつ下限以下を検証し、金額は100を上限にしない。削除は非表示化と監査履歴で扱う。

## PJ管制ダッシュボード（`/project/{project_id}/navigation`）

正規PJ workspaceとは別URLで、PJ全体を俯瞰してから必要な情報へ掘り下げ、同じ画面で更新する。

最初に判定帯で「予定内 / 要介入 / 判定不能」、最終ゲート、次の期限、最大の詰まり、計画比の最大遅延、判断待ち件数を読む。その下の階層WBSガントは重要経路を最初から展開し、4本柱を期間要約バーで並べる。柱を展開すると、マイルストーン、技術試験、論点、履歴イベントが同じ時間軸に現れる。

ガントのバーは1タスク1本。薄い面が予定期間、黒い縦線が予定終了日、青緑の縦線が登録済み進捗位置、同じバー末尾の赤い区間が予測遅延。重要経路は専用グループ、赤い左レール、`CRITICAL` 表示、直角の接続線で判別する。曲線と二段の積み上げ棒は使わない。

技術開発を展開すると、マニホールド型を現行ラインから除外した確認履歴、回収・封じ込め・処理性能などの開発テーマ、紐づく技術試験と論点を確認できる。ジスプロシウム回収では、確認済みの「吸着可能性が見えた」と、未評価の実排液選択性・酸脱着・1/3/5サイクル耐久を別行で読む。

論点を選ぶと、右の詳細に `論点 → 仮説 → 根拠・反証 → 検証 → 判断 → アクション` が連続表示される。portfolio/adminは既存行を編集し、新しい仮説、根拠、検証、判断、アクションをその場で追加できる。工程と技術試験も追加・更新できる。

関係先比較レーンは、全件を共通7段階 `候補 → 情報交換 → 条件整理 → 面談調整 → 検証準備 → 合意確認 → 実行` で表示する。各行で `x/7`、段階名、合意、現在ボール、次の約束、期限、目標状態を同じ列で比較できる。行を選ぶと、合意済み/未合意、履歴、当方・先方の保有事項、これまでの約束まで掘れる。portfolio/adminは関係先と保有事項を追加・更新できる。

390pxと768pxでは `ガント → 選択詳細 → 関係先` の順に縦積みする。ページ本体は横に動かさず、ガント時間軸と関係先比較表の内部だけ横スクロールできる。

### RSCデータ最小化

この画面は `getProjectWorkspaceBundle` の全量をブラウザへ渡さない。サーバー側で画面専用の最小データ（`SxNavigationViewModelV2`）だけを組み立てる。メンバーの連絡先、工数の内訳、契約・報酬、source URLなど、この画面で表示しない情報はネットワーク上にも流さない。
## 2026-08-20 追補: Seed → Cockpit → Workspace の入口と共通ワークスペース
