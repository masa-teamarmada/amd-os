# AMD OS 外販 — 必要機能と実装状況の棚卸し

> **状態**: 2026-08-30 作成。まさ指示「そのそれぞれ向けに提供するために、どういう機能が必要で、現状のOSにはそのうちどの部分が実装されているのか、未実装部分でどこがどのくらい重たいのか」
>
> **前提**（2026-08-30 まさ確定）
> - 産連メンバー: 案件を同じ物差しで比べられる ＋ 仕事が楽になる、の両方が提供価値
> - 研究者・SUメンバー: 仕事が楽になる、だけが提供価値。スコアは裏側
> - 5生データへのアクセスは、研究者本人のメール・カレンダー・資料まで含む前提（そうでないと本人の仕事が減らない）
>
> **重さの目安**: 軽 = 既にあるものの設定と表示を変える程度（〜1週）／中 = 新しい画面か処理を作るが土台は既にある（2〜4週）／重 = 土台の作り替えで既存機能の全体に影響する（1〜3か月）

---

## 0. 結論

流用できる部分は多い。**自動生成の中身（打合せの記録・月次報告・進捗・シグナル）はほぼ完成していて、そのまま顧客の情報に当てられる。**

一方、外販に必要な土台のうち3つが、AMD 1社で使う前提のまま作られている。ここが未実装の中心で、いずれも重い。

| # | 何が足りないか | なぜ重いか |
|---|---|---|
| 1 | **顧客ごとのデータ分離** | 今は AMD 1社分のデータが1つの箱に入っている。顧客の区別という考え方自体が入っていない |
| 2 | **顧客ごとのメール・資料への接続** | 今は接続先が設定ファイルに1組だけ書いてある。顧客ごとに持ち替える構造がない |
| 3 | **自動生成を顧客の数だけ回す仕組み** | 今はまさのMacと別マシンで、まさのアカウントの接続を使って動いている。顧客分をサーバで回す仕組みがない |

3つとも「機能が足りない」のではなく「1社用に作られている」ことが原因なので、部分的な追加では済まない。

## 1. 両方に必要な土台

| 機能 | 何のため | 現状 | 重さ | 補足 |
|---|---|---|---|---|
| **顧客ごとのデータ分離** | 愛大のデータをAMDや他機関から見えなくする | **未実装**。組織の区別を持たない | **重**（2〜3か月） | 全テーブルに組織の区別を入れ、既存データを移し、読み書きの全経路で確認を入れる |
| **顧客ごとのメール・資料への接続** | 各機関・各研究者の情報を読む | **未実装**。接続先は環境設定に1組のみ。読み書きの部品自体は完成している | **重**（1〜1.5か月） | 顧客が自分で接続を許可する画面、接続情報の暗号化保管、切れたときの再接続導線 |
| **自動生成を顧客分回す仕組み** | 打合せの記録・月次報告などを毎日つくる | **未実装**。今はまさの手元のマシン2台で、まさのアカウントの接続を使って動く | **重**（1.5〜2か月） | サーバ側の実行基盤、失敗時のやり直し、顧客ごとの実行枠。**生成AIの利用料が顧客あたり毎月かかる**（原価として料金に乗せる） |
| **外部組織のログイン** | 大学の先生・研究者が自分で入る | **骨組みあり**。外部利用者の入口はあるが、法人・機関そのものと役職の区別がない | **中**（3〜4週） | 代表・担当者・退任時の失効を扱えるようにする |
| **役割ごとの表示分け** | 産連にはスコア、研究者には出さない | **部分**。管理者かどうかの区別はあるが、機関の役割別の区別がない | **中**（2〜3週） | 上の「外部組織のログイン」と同時にやると効率がいい |
| **顧客ごとの見た目・名称** | 大学名で使ってもらう | 未実装 | **軽**（〜1週） | 優先度は低い |

## 2. SU・研究者向け（仕事が楽になる）

### 2-1. そのまま使えるもの

| 機能 | 何をするか | 現状 |
|---|---|---|
| **打合せの記録** | 会議ごとの決定事項・進捗・次の一手・懸念を自動生成 | **稼働中**。AMDで毎時動いている |
| **月次の進捗報告** | 案件ごとに、その月に何が動いたかの下書き | **稼働中**。毎月動いている |
| **マイルストーンの進捗** | 節目がどこまで進んだかを動きから推定 | **稼働中** |
| **案件の重要な動き** | 方針転換・提携・リスク・次の一手を拾う | **稼働中** |
| **案件コックピット** | 1案件の全体が1画面 | **完成** |
| **通知と採否** | 自動生成の下書きを人が採否する仕組み | **完成** |
| **名刺** | 撮影して読み取り、案件に紐づける | **完成** |

### 2-2. 途中まで作ってあるもの

| 機能 | 現状 | 残りの重さ |
|---|---|---|
| **締切と要対応の一覧** | 仕組みはあるが、拾ってくる部分が段階運用中 | **中**（2〜3週） |
| **重要情報の抽出**（決算・契約・補助金・期限を資料本文から） | 27件で試験済み。定期実行が未登録 | **中**（2週） |

### 2-3. 未実装

| 機能 | なぜ要るか | 重さ |
|---|---|---|
| **契約の予兆検知** | 契約更新・押印漏れを防ぐ | **中**（2〜3週） |
| **取りこぼしの検知** | 全案件を横断して「OSに入っていない重要情報」を出す安全網 | **中**（3週） |
| **研究費の管理**（科研費・受託・共同研究の枠と消化） | 大学の予算体系はAMDの会計と別物 | **中**（3〜4週）。学内会計との自動連携まで求めると**重** |
| **報告書の下書き生成**（実績報告・中間報告） | 研究者が一番時間を取られる作業。ここが刺さると本人がアクセスを許可する理由になる | **中**（3〜4週）。月次報告の仕組みを様式に合わせて作り替える |

> 報告書の下書きは、研究者側の困りごととして**まだ本人に確認していない仮説**。石原先生の困りごと（プロマネ・進捗・予算）は聞き取り済みだが、研究者本人の困りごとは未確認。優先度を決める前に確認する。

|---|---|---|---|
| **横断ダッシュボード** | 全案件の現在地、止まっている案件、締切が近い案件 | **完成**（AMDのホーム画面） | 軽（表示の作り替え） |
| **案件の評価** | 事業化の見込みと、いま一番のボトルネック | **算出は完成**。ただし手元のコマンドで1件ずつ動かす形（1件2〜3分） | **中**（2〜3週）。定期実行に載せ、画面から見えるようにする |

## 4. 全体の見積もり

| 段階 | 内容 | 期間 |
|---|---|---|
| 土台 | 顧客ごとのデータ分離・接続・実行基盤・ログイン | **5〜7か月** |
| SU向け機能 | 部分実装の完成と、未実装4件 | 2〜3か月（土台と並行可） |
| 産連向け機能 | 評価の定期実行と画面 | 1.5〜2か月（土台と並行可） |

土台が律速で、並行しても**最短6〜8か月**。

## 5. 段階を切る2つの選び方

土台の重さは、どう配るかで変わる。

| | 案A: 1つのシステムに全顧客 | 案B: 顧客ごとに別のシステムを立てる |
|---|---|---|
| 初期の重さ | **重**（データ分離が必須。5〜7か月） | **軽〜中**（コピーして設定を変える。1〜2か月） |
| 顧客が増えたとき | 楽（1つ直せば全員に反映） | **破綻する**（顧客の数だけ保守・更新が要る） |
| 月3,000円で多数に配る | **これでないと無理** | 不可能 |
| 愛媛大1機関だけ | 過剰 | **これで足りる** |

**現実的な順序**: 愛媛大を案Bで始めて実運用の証拠と初年度の売上を作りながら、案Aの土台を並行して作る。2機関目からは案Aへ乗せる。

案Bで始める場合、接続と実行基盤は「その顧客専用の設定」で済むので、土台3つのうち2つ（データ分離・実行基盤の顧客別化）を先送りできる。ただし**接続の顧客別化だけは案Bでも要る**（愛大の先生のアカウントを読む必要があるため）。

## 6. 未確認・要判断

| 項目 | 内容 |
|---|---|
| 研究者側の困りごと | 報告書の下書きが本当に刺さるかは未確認。石原先生経由で研究者数名に聞くのが最短 |
| 生成AIの利用料 | 顧客あたり月いくらかかるかを試算していない。料金設計の前提になるので、愛大の想定件数で実測する |
| 学内会計との連携 | 大学ごとに仕組みが違う。初期は月末データの取り込みで回避する前提 |
| 案Bで始める場合の移行 | 案Aへ乗せ替えるときのデータ移行の手順を、始める前に決めておく |
