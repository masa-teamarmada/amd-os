# Before Zero の現場で実際に起きること — 良い技術なのに進まない理由

> この章は何か: Before Zero で繰り返し起きるズレを、関係者別・局面別に整理します。ここで扱うのは「失敗談」ではなく、BZM の変数へ入る前の生々しい観察です。

## 1. 関係者ごとに見ている時間軸が違う

Before Zero の難しさは、関係者が同じ技術を見ていても、期待している時間軸と成功条件が違うことにあります。

| 関係者 | 見ているもの | ズレやすいこと |
|---|---|---|
| 研究者 | 研究としての新規性、論文、次の研究費 | 事業化に必要な再現性・顧客検証を過小評価しやすい |
| 大学・研究機関 | 知財、共同研究、外部資金、社会実装実績 | 会社化後に誰が責任を持つかが曖昧になりやすい |
| 企業 | PoC の成果、導入リスク、既存事業との整合 | 技術が面白くても調達・法務・現場導入で止まりやすい |
| VC / CVC | チーム、成長市場、資本効率、出口 | 研究の価値は理解しても CEO / BRL / HRL の弱さで止まる |
| 行政 | 政策目的、地域・産業波及、制度適合 | 予算や制度のタイミングと事業化タイミングがズレる |
| 知財関係者 | 出願可能性、公開リスク、権利範囲 | 論文化・外部相談・営業資料との順序を間違えると壊れる |

このズレは「誰かが悪い」話ではありません。BZM では、それぞれのズレを `TRL`、`BRL`、`GRL`、`SRL`、`HRL`、`FRL`、`σ_SU`、ERS のどこに現れるかへ接続します。

## 2. 「良い技術なのに進まない」典型パターン

### パターン A: 技術は良いが、用途がまだ粗い

研究成果は強いのに、最初の顧客・用途・課題の粒度が粗い状態です。現場では「すごい技術です」という説明が続きますが、誰の業務・製造・治療・研究フローをどう変えるのかが定まっていません。

- 現場の鬼門: 顧客候補との会話が「面白いですね」で終わる
- 見るべきもの: 課題の深さ、代替手段、支払い主体、検証順序
- 理論接続: 主に `BRL`。技術の強さだけなら `TRL` に閉じる

### パターン B: 研究者は進めたいが、担い手がいない

研究者本人が CEO をやるとは限らず、外部 CEO 候補もまだいない状態です。大学・研究機関側の支援者はいても、日々の意思決定を引き受ける人がいなければ会社は動きません。

- 現場の鬼門: 「誰が腹を括るのか」が最後まで曖昧
- 見るべきもの: CEO 候補、COO / CTO 補完、AMD の伴走余地
- 理論接続: `FRL`、`F_character`、`F_capability`、`HRL`

### パターン C: 外に出した瞬間に知財・論文・契約が絡まる

研究成果を企業やVCに見せたい一方で、出願前・論文化前・共同研究前の情報は扱いを間違えると戻せません。

- 現場の鬼門: NDA 前に話しすぎる、逆に情報を出せず検証が進まない
- 見るべきもの: 出願状況、公開予定、共同研究契約、開示範囲
- 理論接続: `GRL`、`BRL`、ERS の知財・制度支援

### パターン D: 市場が早すぎる、または遅すぎる

技術も人も揃い始めているのに、政策・産業・社会受容の波がまだ来ていない、または逆に過熱して期待だけが先行している状態です。

- 現場の鬼門: 会社化判断を、本人たちの熱量だけで決める
- 見るべきもの: 政策予算、産業投資、研究潮流、VC投資、世論
- 理論接続: `σ_SU`、`SRL`、AMD Score と Valuation の差分

## 3. 現場観察を BZM へ変換する

現場で起きることをそのまま文章で残すだけでは、次の PJ に再利用しにくい。AMD は観察を次の形に変換します。

1. 起きたことを、関係者・局面・時間軸に分ける
2. どの不確実性が律速だったかを仮置きする
3. BZM のどの変数に入るかを対応させる
4. GO / WAIT / NO_GO / HOLD / RESOURCE_SHIFT の判断に接続する
5. 後から観測結果を見て、仮説を修正する

この変換が、後半の [AMD Score](5-1-amd-score-integration.md) と [検証](6-1-retrofit-verification.md) へつながります。
