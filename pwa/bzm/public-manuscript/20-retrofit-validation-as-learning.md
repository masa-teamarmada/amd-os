# 20. 過去ケースで、地図を直す

投資家面談が終わったあと、部屋が静かになる。

「チームが弱いですね」
「市場がまだ見えません」
「少し早いかもしれません」

短い言葉が、それぞれの人に違う重さで残る。研究者には、自分の研究や人格を否定されたように響く。支援者には、自分の準備不足を責められたように響く。若い事業化人材には、何を直せばよいのか分からないまま失敗だけが残る。

このとき、過去を「成功」「失敗」で閉じてしまうと、次に使えるものが残らない。

必要なのは、責任追及ではなく学習である。

## 判断当時の地図に戻る

retrofitとは、結果が分かっている過去ケースに、あとから判断地図を当て直す作業である。

ただし、過去を正当化するためにやるのではない。「あのとき、何を見て、何を見落とし、どの軸を過大評価し、どの軸を過小評価したのか」を確かめるためにやる。

| 振り返るもの | 問い |
|---|---|
| 当時の仮説 | 何が成立していると思っていたか |
| 観測した事実 | 何を根拠に進めたか |
| 見落とした信号 | どの違和感を小さく扱ったか |
| 過大評価した軸 | どの準備度を高く見すぎたか |
| 過小評価した軸 | どの準備度を低く見すぎたか |
| 修正した問い | 次に同じ場面で何を聞くか |

この表があると、失敗は誰かの欠陥ではなく、地図の更新材料になる。

## 外れたときに、モデルを直す

モデルは、当たったことを誇るためのものではない。外れたときに直すためのものだ。

たとえば、企業の好反応をBRLの高さとして読んだが、実際には探索部門で止まったとする。この場合、次回からBRLの証拠に「予算部署」「評価条件」「導入責任者」を強く入れる必要がある。

外部経営者候補の経歴をF_capabilityとして高く読んだが、研究者との信頼が壊れたとする。この場合、FRLを見るときに、F_characterとの接続や研究者との関係構築をもっと丁寧に見る必要がある。

研究機関の支援メニュー数を苗床の強さとして読んだが、実際には責任pipelineがなかったとする。この場合、ERSではメニューの有無だけでなく、誰が判断を統合するかを見る必要がある。

外れたときに「誰が悪かったか」で止まると、次も同じことが起きる。外れたときに「地図のどこが粗かったか」まで戻れば、次の判断は少し強くなる。

## composite timelineで読む

公開本で過去ケースを扱うとき、実名や固有事情をそのまま出す必要はない。むしろ、複数の現場に共通する構造を取り出した方が、読者にとって使いやすい。

たとえば、次のようなcomposite timelineで十分である。

| 時点 | 起きたこと | 当時の読み | 後から見た修正 |
|---|---|---|---|
| 初回企業面談 | 好反応が出た | BRLが上がった | 課題と予算は未確認だった |
| 投資家面談 | チームが弱いと言われた | 人材不足 | FRLとHRLの両方が空いていた |
| 開示直前 | 資料が厚くなった | 前進 | GRLの確認が遅れていた |
| 研究者の疲弊 | 会議が増えた | 熱量の表れ | ERSの責任pipelineがなかった |

この形なら、読者は自分の現場に引き寄せて考えられる。誰かの失敗談を覗き込むのではなく、自分の判断地図を点検できる。

## validationは、支援者の倫理でもある

会社化前の支援者は、研究者の人生、知財、時間、信用に触れる。だから、自分たちの判断がどれだけ現実に合っていたかを確かめ続ける必要がある。

「あのときは仕方なかった」で終わらせない。

「あのときは何が見えていなかったのか」まで戻る。

この姿勢がなければ、モデルは現場を押し込める道具になる。逆に、validationを続ければ、モデルは現場から学ぶ道具になる。

## 今日の行動、まだ残る不安

今日できることは、過去にうまくいかなかった面談や支援を一つ選び、成功/失敗ではなく「当時の仮説、観測、見落とし、修正した問い」に分けて書くことだ。

それでも不安は残る。個別ケースから学んでも、そもそも研究機関という苗床が乾いていれば、同じ負荷はまた研究者に流れる。

次章では、研究機関の準備度を支援メニュー数ではなく、責任pipelineと苗床として読む。
