# BZM を構成する現場要素 — 現場の問いから理論変数へ

> この章は何か: BZM の各パラメータを、数式ではなく現場の観察から説明する章です。各要素について「現場で何が起きるか → 鬼門 → AMD が見るべきもの → 判断を間違えると何が壊れるか → 理論上どの変数に入るか」の順で読みます。

## 1. 先に現場、あとで変数

BZM の理論章では、`σ_SU`、`TRL`、`BRL`、`GRL`、`SRL`、`HRL`、`FRL`、`F_character`、`F_capability`、`frl_cap_amd`、ERS、AMD Score が数式や rubric として出てきます。

ただし Before Zero の現場では、最初から変数名で問題が現れるわけではありません。現場で見えるのは、例えば次のようなことです。

- いま社会や政策の波に乗っている気がする
- 技術はすごいが、誰が買うのか分からない
- 論文と知財の順番を間違えそう
- CEO 候補は魅力的だが、経営実務を誰が補うか不安
- 大学側の支援は強いが、実務の受け皿が薄い
- 点数は高く見えるが、次に何を直すべきか分からない

この章は、その現場語を BZM の変数へ翻訳するための橋です。

## 2. 変数別の現場読み

| `F_capability` | 経営実務・資金調達・採用・交渉・オペレーションを誰が担うかが問われる | CEO 個人の経験不足を、必ず本人だけの減点として扱う | COO / CFO / AMD伴走、経験者補完、実行体制 | 資質は強いのに事業運営が回らない | [FRL の経営実行力](4-1-frl-founder-readiness.md) |

## 3. XRL は「会社側の readiness」としてまとめる

`TRL`、`BRL`、`GRL`、`SRL`、`HRL` は、後半の理論では XRL 群としてまとめて扱います。

現場では、この 5 つは別々に見えます。技術が強いのに顧客が弱い、顧客は強いのに規制が詰まる、人はいるのに役割が足りない、というようにズレて現れます。BZM はそれらを一つの `X` としてまとめますが、判断では必ず内訳に戻ります。

顧客 readiness を独立の `CRL` として増やさないのは、BRL の中で見るためです。変数を増やすより、現場で「顧客課題・支払い主体・検証順序」を BRL の証拠として残すことを優先します。

## 4. FRL は「素質」と「経営実行力」を分けて読む

創業者の話は、現場ではかなり重要です。ただし「良い人」「優秀な人」では粗すぎます。

- `F_character`: 委譲できない資質。Authenticity、Grit、Resilience、倫理性、自己認識。
- `F_capability`: 補完できる経営実行力。経営経験、資金調達、採用、交渉、オペレーション。
- `frl_cap_amd`: AMD が `F_capability` の一部をどこまで補えるか。

この分解により、「本人の資質は抜群だが経営経験は薄い。AMD や COO で補えるか」といった現場判断を、単なる主観で終わらせずに扱えます。ただし `F_character` を AMD が代替できるとは見なしません。ここを間違えると、支援で埋まらない穴を支援で埋まるものとして進めてしまいます。

## 5. 研究者の真正性は、CEO機能の一部になりうる

ディープテックでは、研究者本人が持っている「この技術を社会に出したい」という真正性が、人を動かすことがあります。研究成果は、研究者にとって単なる資産ではなく、長い時間を注いできたものです。その人が自分の言葉で語るから、企業候補、採用候補、投資家、大学側の支援者が動くことがあります。

だから、研究者に経営経験がないことだけを見て、すぐに外部CEOへ置き換えるのは粗い判断です。一方で、真正性だけで経理、採用、資本政策、契約、資金調達、オペレーションまで回せるわけでもありません。

ここで必要なのは、CEOという肩書きではなく、CEO機能の分解です。

- 研究者本人が担う: 技術の意味、社会に出す理由、長期の夢、重要な技術判断
- 補完人材が担う: 経営管理、資金調達実務、採用、事業開発、契約交渉
- AMD が担う: 会社化前の論点整理、VC対話、知財・資本政策・採用・管理実務の橋渡し
- 研究機関が担う: 知財、制度、利益相反、研究継続、産学連携の支援

BZM では、この分解を `F_character` と `F_capability` と `frl_cap_amd` に分けます。「研究者には経営は無理」でも「研究者が全部やるべき」でもなく、どの機能を誰が持つと会社が前に進むかを見るためです。

## 6. AMD Score は結論ではなく、次の一手を見る道具

AMD Score は、7軸を統合して現時点の準備度を出します。ただし Before Zero で本当に使うべきなのは、点数そのものよりも次の問いです。

- どの軸が律速か
- その軸は AMD が動かせるか
- 動かすなら、誰に、何を、いつ確認するか
- 会社化を進めるべきか、WAIT すべきか
- Valuation や外部期待と準備度がズレていないか

後半の理論では、これを Cobb-Douglas、重み `α_i`、`K` の再校正、律速判定として定義します。ここでは、点数を「偉い順」ではなく「次にどこへ手を入れるか」の表示として読むことだけ押さえます。
