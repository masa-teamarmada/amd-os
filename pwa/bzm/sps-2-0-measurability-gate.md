# 測定可能性ゲート — 数字を出してよい条件

$q$（到達見込み）を計算して人に見せてよいのはどういうときか、を先に決めておくための章。7 つの問いすべてに答えが埋まるまで、予測値を出さない。

> **状態**：`questions-fixed v1.0`（全 7 問 2026-08-06 確定）
>
> **主張の地位**：`design-choice`。ゲートの妥当性そのものは前向き検証で確かめる対象であり、まだ確かめられていない。
>
> **運用台帳**：`pwa/bzm/BZM_2_0_MEASURABILITY_GATE.md`（確定文・証拠パッケージ表・変更履歴の正本）
>
> **関連**：[到達見込みモデル](./sps-2-0-reachability-model)、[SX 実測記録](./sps-2-0-sx-measurement-log)

## 0. きっかけ — 撤回された v0.1

2026-08-04 に最初の試算を回した。結果は SX が 10,000 回中 2 回、CX が 0 回。数字としては出たが、この試行は**撤回**した。撤回の理由は結果が低すぎたからではない。

- 入力値のほとんどが、その場の感覚で置かれていた。どの数字が誰の・何の情報から来たのか追跡できなかった。
- したがって値が変わったときに、**世界の何が変わったのか、こちらの見立てのどこが変わったのかを区別できなかった**。
- 到達目標の定義がプロジェクト間で揃っていなかったため、CX と SX の 2 と 0 を比べる意味がなかった。

数字が出ること自体には何の価値もない。**その数字がどこから来たかを言えることに価値がある。** v0.1 はそこで失格だった。以後、この試行はプロジェクトの成功確率、モデル整合性の警報、投資判断、GO 判定のいずれにも使わない。

この失敗を繰り返さないために置いたのが、以下の 7 問である。

---

## 1. 到達目標をどう定義するか（問 1〜4）

### 問 1：必要支出 $E_{\mathrm{req}}$ に何を含めるか

**確定**：判定時点の実際の活動水準を基準線とし、通常運営費・既存債務の履行・事業継続に不可欠な維持更新投資を含める。任意の成長投資は除く。基準線は直近 3 か月平均で固定し、費目リストを判定時に凍結する。

**なぜ**：もし研究開発費を「任意の成長投資」として外に出せば、開発を止めて延命している状態が到達成功として数えられる。しかしそのとき $\mathbf{P}$ はもう実現されない。**$\mathbf{P}$ を保ったまま到達条件だけを緩めない**という原則が、ここで最初に効く。

まさの指摘（2026-08-06）：「ゾンビ化させたら、そもそも自走状態に到達する可能性は限りなくゼロになるわけで、それはスコアが低くなって当然なのでは？」——そのとおりで、ゾンビ経路は**到達しなかった経路**として低い $q$ に現れるべきであり、到達成功として数えてはならない。

### 問 2：反復可能な外部対価 $R_{\mathrm{rep}}$ に何を含めるか

**確定**：契約基準（更新条項または 12 か月以上の契約期間がある）または実績基準（12 か月以上の入金実績がある）のいずれかを満たす外部からの対価。公的資金は、**資金の出し手が自らの効用のためにその財・サービスを買っているか**という実質基準で判定する。

**なぜ**：一回きりの受託や、成果報告のための補助金を「反復可能な対価」に数えると、次の 12 か月が保証されない収入で自給を宣言することになる。他方、自治体が実際にそのサービスを使うために継続発注しているなら、それは公的資金でも実質は顧客である。形式（補助金か売上か）でなく実質（買い手が自分のために買っているか）で切る。

### 問 3：フローと資金繰りをどう組み合わせるか

**確定**：二段構え。主要件はフロー自給（12 か月の対価 ≥ 12 か月の必要支出）、副次要件は月次の資金繰り（各月末で現金がマイナスにならない）。既存資金 $C_0$ の役割は入金と支払のずれを吸収することに限定し、主要件には算入しない。

**なぜ**：貯金込みの一本の式にすると、大型調達をした直後のプロジェクトほど「資金調達に依存しない状態」に近く見えるという逆転が起きる。まさの判断（2026-08-06）：「キャッシュフローがプラスじゃないならだめだよ」。

### 問 4：誰がどう判定するか

**確定**：証拠パッケージ（活動水準の基準線、凍結した費目リスト、契約書、入金履歴、公募要領、残高証明）を揃えたうえで、**独立した二名**が判定し、一致率を記録する。判定時点での判断と、後から答え合わせをする事後検証を分けて記録する。

**なぜ**：一人で判定すると、後知恵と願望が判定に混ざったことを検出できない。一致率そのものが、この判定基準の運用可能性を示すデータになる。

## 2. 情報が足りないときどうするか（問 5）

ここはまさの指示によって設計が変わった箇所である。当初こちらは「入力が揃うまで計算を止める」案を出したが、差し戻された。

> 全然足りないなら、おれから最低限の情報をヒアリングして、最低限の精度で計算できるようにしてほしい。徐々に情報を足して精度をあげていけばよくて、**精度が上がらないとスコアが見えないのは、その分得られる知見も減ってしまってもったいない**。精度が低い状態からどうあがっていくかをおれが観察するのが大事。
> — まさ、2026-08-06

**確定した規律**：

1. **入力の序列**。まず文書と実績（契約書、入金履歴、事業計画、予算書）。取れなければ構造化ヒアリング。それも取れなければ欠測とし、感度分析の幅に反映する。順番を飛ばさない。
2. **全体停止の条件は一つだけ**。計画版・期限・マイルストーン骨格が構成できない場合に限り計算を止める。個々の入力が欠けていることは停止理由にならない。
3. **出所タグを全入力に付ける**。`document` / `record` / `hearing` / `missing` の 4 種。
4. **精度は構成比と幅で観察する**。出所の構成比（文書が何割か）と感度分析の幅（入力が動いたとき $q$ がどれだけ動くか）を毎版記録し、版を追うごとに文書比率が上がり幅が狭まっていく過程を追う。

この 4 番目が、v0.1 との決定的な違いになった。v0.1 の値には出所がなく、変動が何によるものか説明できなかった。現在は、$q$ が動いたとき「誰の・どの情報で・どこを直したか」が必ず言える。

## 3. 入力をどこから取るか（問 6）

**確定**：入力の種類ごとに根拠源を対応表で固定する。AMD OS が保持する 5 つの生データ（Gmail / Drive / Calendar / Slack / Notion）とプロジェクトコックピットを一次源とし、そこに無いものだけをヒアリングで補う。

まさの指摘（2026-08-06）：「前回の失敗は、何のデータから取るかを失敗したのではなく、**一切データを使わなかった**ことが失敗でしょ」。

**講師注（重要な限界）**：工程レベルの成功確率は、社内の前例数が少なく、観測頻度として取れる入力ではない。ヒアリングで幅つきに聞き、評価者・日時・質問文を記録し、事後検証で答え合わせをする、という規律で扱っている。この入力種別について「データに基づく」という表現を使わない。

### 手応えを聞くときの落とし穴

SX の実測で実際に踏んだ失敗を記録しておく。「10 回やって何回成功するか」と尋ねたところ、まさから根本的な違和感が返ってきた。

> そもそも 10 回中何回成功するか？という問い自体が違和感がある。何回やったところで、現状見えてる条件とかリスク、難しさなどは同じなわけで、結果は同じじゃないの？

一回性の強い出来事に頻度の言い方をあてると、答える側に無理が生じる。「同じ条件で繰り返す」という状況が想像できないからである。パーセンテージで確信度を聞く形に変えたところ、即座に答えが返ってきた。

もう一つ、より重い失敗がある。工程の所要時間を聞いたとき、設立手続きを「Seed 合意の後に始まる 3 か月」と読んでいた。実際には DD や条件交渉と**並行して進む準備**であり、直列に足すべきものではなかった。この誤読が $q$ を不当に押し下げていたことは、確率をすべて成功に固定して時計だけを回す分解分析で特定できた。**手応えを聞くときは、その工程が何と並行し何の後に来るのかを工程ごとに明示する。**

## 4. 事前登録（問 7）

**確定**：計算を回す前に、次の 5 項目を凍結して記録する。

| 項目 | 内容 |
|---|---|
| 情報カットオフ | どの時点までの情報を使ったか |
| 到達目標 | $G_{\mathrm{self}}(12\mathrm{m})$ の適用文 |
| 政策 | どの支援・介入を前提とするか（SX は現行 AMD 支援の継続、BZSF 追加介入なし） |
| 期限 | 計画版 $v$ の $H_v$ |
| 感度ケース | どの入力をどれだけ動かすか、を計算前に列挙 |

**なぜ**：結果を見てから感度ケースを追加すると、都合のよい幅だけを見せることができてしまう。凍結の目的は、後から自分の手を変えられなくすることにある。

SX 版の事前登録は `pwa/bzm/SPS_2_0_PREREGISTRATION_SX_2026-08-07.md` に置いた。

## 5. 変更規律

- 確定した定義を変更するときは、旧版を残して改訂を追加する。**結果を見た後に都合よく合わせる変更を認めない。**
- 変更は [`9-5-appendix-changelog.md`](./9-5-appendix-changelog) へ日時つきで追記する。
- 7 問のいずれかが未回答に戻った場合、その時点で予測値の公表を止める。

## 6. このゲート自体の限界

1. **ゲートを通ったことは、値が正しいことを意味しない**。出所が追跡できることと、予測が当たることは別である。前者はこのゲートで担保されるが、後者は前向き検証でしか分からない。
2. **独立二名判定はまだ運用実績がない**。一致率のデータが貯まるまで、この基準が実務で機能するかは未確認。
3. **ヒアリング入力が主根拠である限り、評価者差の影響を除けない**。同じ工程を別の人に聞いたら値が変わる可能性がある。複数評価者での再測定は未実施。
