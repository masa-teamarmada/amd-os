# ADR 001：AMD運営カレンダーを派生読み取りモデルにする

- **状態**：採用。
- **決定日**：2026-07-16。
- **決定者**：まさ、えいみ。
- **関連仕様**：[AMD運営カレンダー仕様](../../spec/5-9-admin-operating-calendar-current-spec.md)。

## 背景

AMD運営の期限は、契約、報告書、請求、支払義務、会社属性、公的ルールに分散している。

予定入力型のカレンダーを追加すると、契約満了日や支払期日を元台帳とカレンダーの二か所で管理することになる。

二重管理では、どちらが正しいかをOSが判定できない。

一方、画面を開くたびに全期限を計算するだけでは、通知のexact-once、過去の期限変更、生成失敗の継続監視を扱いにくい。

## 検討した案

### 独立した予定台帳

カレンダー上で予定を作成し、日付と金額を管理する案である。

既存の契約、Finance、請求、報告書と二重管理になるため採用しない。

### 表示時の全件計算

元データを毎回結合し、保存せずに表示する案である。

表示だけなら成立するが、通知証跡、期限変更履歴、生成不能の未解決期間を保持できないため採用しない。

### 派生読み取りモデル

正本と版管理されたルールから期限を決定的に生成し、通知と監査のために派生行を保存する案である。

元データを修正すれば再生成でき、予定行を正本にしなくて済むため採用する。

## 決定

- カレンダー上に予定追加、日付編集、金額編集、担当者編集を置かない。
- 予定は、既存正本、AMD運営ファクト、公的ルールから生成する。
- 生成結果は`company_schedule_occurrences`へ保存するが、ブラウザから編集させない。
- 期限を生成できない場合も`needs_source`として保存し、黙って除外しない。
- 元正本が完了状態を持つ場合、カレンダーでは完了操作を受け付けない。
- 法定手続など完了記録の正本がない場合だけ、予定作成とは別の実行記録を保存する。

## 結果

契約、支払、報告書の修正は、それぞれの正本で行う必要がある。

期限発生日の保存により、再生成、通知、監査、期限変更履歴を扱える。

実装者は、見た目上便利でも`＋予定`やカレンダー内編集を追加できない。

新しい期限種別を追加する場合は、先に正本または自動取得経路を定義する必要がある。
