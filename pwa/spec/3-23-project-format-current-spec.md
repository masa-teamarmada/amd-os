## 1. 目的と決定

2026-10-03 まさ確定。

> すべてのPJについて、同じフォーマットで表示する設計にして。勝手にそれを書き換えないように制限をかけてほしい。今回のSOLみたいに新たなデータが入るときには、新たなグラフを入れるんじゃなくて、フォーマットで生成されているグラフにその数値データを入れる形にしてほしい。

- PJの画面は、PJタイプごとに1つの形（フォーマット）で描く。同じタイプのPJは、同じ区画・同じ行・同じグラフを持つ。
- PJごとの違いはデータだけで出す。PJ番号で表示を分けない。
- 新しい種類の数字が来たら、標準の行・グラフのどこへ入るかを決めて、データとして流し込む。区画やグラフを足さない。
- フォーマットの定義は鍵付き。まさの明示の承認なしに変えない。

同日、まさ確定（顧問PJの扱いの確認への答えと、統一の範囲）。

> １．おけ ２．てゆーか全部統一してないとだめ。OSの大原則。あと中身があるときだけ出るタブってなに？上記の通り、すべてのフォーマットが同じ状態で表示されてないとだめ。

- 統一はタブの並びにも及ぶ。同じタイプのPJは、同じタブを、データの有無にかかわらず全部持つ。中身が無いタブは、タブの中で「未登録」と出す。
- 見る人で出し分けてよいのは、役割で決まるもの（各領域の入場権限、PJワークスペースの外部の参加者）だけ。

## 3. 試算表タブの標準フォーマット

画面は `ProjectFinanceFormat`（`src/components/cockpit/ProjectFinanceFormat.tsx`）。コックピット・PJワークスペース・DDの資金計画が同じ部品を使う。試算表タブ（`CockpitFinancialProjection`）はこの部品だけを描く。

### 3.1 区画

`FINANCE_FORMAT_SECTIONS` の順に、データの有無にかかわらず全区画を描く。データが無い区画は「未登録」と出し、区画そのものは消さない。

| 順 | 区画 | 内容 |
|---|---|---|
| 1 | 計画とケース | データにある計画の切り替え（資料から取り込んだ計画を新しい順、次に登録済みの月次試算）と、計画が持つケースの切り替え |
| 2 | 要約 | 期間・売上計・費用計・調達計（株式・融資・助成金）・最低の月末資金・期末の月末資金 |
| 3 | 時間軸 | 試算（BZM 2.2）の時間軸のイベント、会社設立、設立前DD完了期限（設立の前月、AMDの必須ゲート）、資本政策の調達イベント |
| 4 | 月次試算表 | 出所・計上主体・P/Lの行・C/Fの行・元データの内訳（折り畳み）・BZM経済CF |
| 5 | 月次の資金推移 | 月ごとの入金と出金の横並びの棒、月末資金の折れ線、手元資金の目安（データにあるとき破線） |
| 6 | 年度別の事業・資金推移 | 4月始まりの年度ごとに、売上と費用の横並びの棒、年次純C/Fの折れ線（同じ目盛り） |
| 7 | 年度別数値 | 年度ごとの売上・費用計と内訳・営業利益・株式調達・融資（実行−返済）・助成金等入金・年次純C/F・年度末資金・設立前PJ支出 |
| 8 | 前提と注記 | 計画が持つ前提の表と注記 |

時間軸・月次試算表・月次の資金推移は、月の列をそろえるため1つの横スクロールの中に描く。金額の単位は表の外に「単位：百万円」と一度だけ書く。

### 9.2 事業の概要（会社情報 > 会社概要）

事業の一言（何をする事業か）は会社の話なので、PJ概要から会社情報 > 会社概要のいちばん上「事業の概要」へ移した。部品は `CompanyBusinessSummarySection`。共有ワークスペースの会社概要でも読み取りで出す。

- 正本は `project_business_summaries`（`summary`＝事業の一言、`detail`＝詳しい説明。全PJで持てる）。書けるのは管理者、または対象PJのコックピット/ワークスペースを明示的に編集付与された内部メンバー（service APIでPJ認可、DBの直接書込みは従来RLSのまま）。
