# コスト試算タブ 現行仕様

> **この章は何か**: PJコックピット / PJワークスペースの「コスト試算」タブ (2026-08-29 新設、2026-09-13 二段階化・シミュレーター化・作業の流れとオフサイト、2026-09-14 方式と装置の分離・誰がやるか・誰が持つか) の contract。
> 前提（変数）・費用明細・作業リストをDBに持ち、画面で数字を書き換えるとその場で全シナリオを再計算する。
> **計算結果は保存しない。保存するのは前提・明細・作業だけで、数字は常に導出する。画面での書き換えも保存しない（試算）。**

## 目的

このタブ単体で次の4つが分かることを要件にしている（まさ 2026-08-23 指摘）。

1. どういう系を想定して、どういう計算をしているか
2. CAPEX と OPEX がそれぞれいくらか
3. いくら以下ならユニットエコノミクスが成立するか
4. どのパラメータの確度が低いせいで精度が落ちているか

加えて、2026-09-13 のまさFBで次を要件にした。

5. **前提条件やまだ確定できない数値は、すべて画面で変えられる**（「とにかく前提条件とかまだ確定できない数値はすべてUI上で変えられるようにして」）
6. **スイッチの切り替えや数値の変更で全体がどう変わるかを、スクロールせずに確認できる**（「数値があちこちに分散してて、しかも変動させるボタンとかが全然違う場所にあるから、比較検討ができない」）
7. **人件費は作業リストで制御する**。「人件費を除くと」のような併記はしない（「作業リストに、それぞれの作業にかかる工数を入力できるようにして、作業単価も入力できるようにして、そこでコントロールすればいい」）
8. **全量がさばける前提でよいが、生産した菌体の何割が売れるか（販売率）を上下できる**

さらに同日、次を要件にした（まさ 2026-09-13 2回目のFB）。

9. **菌体使用回数は色素分解だけ**。金属回収は酸で菌体を溶かして金属を取り出すので1回で固定する（「金属回収は１回しか無理でしょ？使えるのは色素分解だけだと思うんだけど」）
10. **合計の作業工数と、作業の流れを見せる**（「合計の作業工数はどこに表示されてる？全体のフローも見せてほしい。どういう流れでどういう作業をしていく必要があるのか、そしてそれぞれにどのくらい工数がかかってるのかが視覚的にも把握しやすいようにして」）
11. **コストの内訳を常時見える位置に棒グラフで出す**（「下の方にあるけど、わざわざスクロールするのは使いにくい。どこがどのくらいの割合でコスト食ってるのか。棒グラフとかで見せてほしい。右側のサマリに加えて」）
12. **オンサイトとオフサイト（SX工場まで排液を運んで処理）を比べられる**

2026-09-14 のまさFBで、次を要件にした。

13. **方式はオンサイトとオフサイトの2つ。循環と投入は方式ではなく装置として分けて切り替える**（「方式がオンサイトとオフサイトの２種類になってないのが理解できてない。循環と投入ってなに？」）
14. **顧客工場での処理の運転は顧客がやる作業で、SXの原価に入れない**（「工数のほとんどが排液処理のところにかかってるけど、これは顧客側がやることだと思うよ。全顧客の工場にSXの社員が張り付くってありえないよ」）
15. **顧客側に残る作業の時間は、この試算で扱わない**。時間も円も出さない（顧客側に残る運転の時間について「知ったこっちゃなくない？SXのコストに含まれないじゃん」）
16. **色素分解の菌体使用回数は10回**。2026-07 の設備アドオン試算と同じ前提（「繰り返し使える色素分解の方が金属回収より高いのが変。もともと10回使える前提でしょ？」）
17. **顧客工場に置くリアクターと槽は顧客が買う**。SXの原価に入れない（「リアクターは顧客が買う前提だよ」）
18. **顧客工場で出る使用済み菌体の汚泥の処分は顧客がやる**（「汚泥の処理単価とかあるけど、これは顧客側がやることじゃないの？なんでSX側がやることになってるの？」）

Google Sheets が正本のままでは「前提を1つ動かしたときにシナリオがどう動くか」をMTGの場で出せない。これがDBへ移した理由。

## 二段階の計算（2026-09-13 まさ確定）

**菌体の製造原価は株で決まり、用途では変わらない。用途で変わるのは使い回せる回数と、そこから決まる必要菌体量。**
旧版はこの区別がなく、菌体の製造拠点の設備償却を「排水1m³あたりの固定額」で置いていた。そのため菌体使用回数を変えると、菌体1kgあたりに割り戻した原価が見かけ上 98円 → 約440円 → 約1,200円と動いた。二段階はこれを直すための形。

| 段 | 何を出すか | 何で変わるか |
|---|---|---|
| 第1段 菌体の製造原価 | 株（強化株 / 自然株）ごとの、売れた乾燥菌体1kgあたりの原価（円/kg-DCW）。CAPEX・年額固定費・製造拠点の作業・菌体量比例費を含み、販売率で割る | 株（強化株は閉鎖系の追加費用が乗る）、年間生産能力、販売率 |
| 第2段 用途別の処理原価 | 第1段の原価を一定として、用途（色素分解 / 金属回収）ごと・方式×装置×槽ごとの1単位あたり総コスト | 用途（濃度・取り込み効率・菌体使用回数・後処理）、株（取り込み効率・処理設備の閉鎖系費用）、方式（オンサイト / オフサイト）、装置（循環カートリッジ / 直接投入）、槽、作業を誰がやるか |

**菌体の製造拠点**: 顧客工場では培養せず、SX側の1拠点でまとめて菌体を育て、濃縮して各工場へ運ぶところ（2026-07-10 の設計）。DB の `scenario` の値は `中央培養` のままで、**画面では「中央培養」と書かない**（まさ 2026-09-13「中央培養ってなに？」）。表示名は `PRODUCTION_SITE_LABEL`、説明は `PRODUCTION_SITE_DESCRIPTION`。

## 方式と装置

切り替えは **方式**（どこで処理するか）と **装置**（菌体と排液をどう触れさせるか）の2つに分ける（まさ 2026-09-14）。2026-09-13 版は「A:循環・B:投入・C:オフサイト」を1つの切り替えに並べており、処理する場所と装置という別の軸が混ざっていた。

| 方式 | どこで処理するか | 処理の運転 | 設備・槽・汚泥の処分 |
|---|---|---|---|
| オンサイト | 顧客工場の槽の横に、顧客が買ったリアクターを置く。SX は菌体の搬入・搬出や交換で巡回する | 顧客 | 顧客（槽は前提で SX にすると既設 / 新設を選べる） |
| オフサイト | 排液をタンクローリーで SX工場まで運び、SX工場に新設する槽で処理する。処理水は SX工場から流す | SX | SX（槽は新設だけ） |

| 装置 | DB の `scenario` | 何をするか |
|---|---|---|
| 循環カートリッジ | `循環` | 菌体を筒（カートリッジ）に閉じ込め、ポンプで排液を通して槽へ戻す |
| 直接投入 | `投入` | 菌体を排液の槽に直接入れて混ぜ、処理後に膜でこして取り出す |

- **どちらの方式でも両方の装置を選べる**。シナリオは用途ごとに、オンサイト2（装置2）とオフサイト2（装置2）の4つ。オンサイトの槽を SX が持つ前提にすると、オンサイトは装置2 × 槽2 の4つになる（下の「誰が持つか」）。
- 数える明細・作業の範囲は `scopesFor(方式, 装置)` ＝ 装置の `scenario`・`共通`・（オンサイトなら `現場共通` / オフサイトなら `オフサイト`）。`現場共通` は顧客工場への菌体の巡回、顧客工場内の区画・立入制限など、`オフサイト` は排液の輸送・受け入れ・放流など。`中央培養`（菌体の製造拠点）は第1段で数え、方式・装置によらない（`rowAppliesTo`）。
- DB の `scenario` の値は変えていない。画面の呼び名は `LOCATION_SHORT_LABEL`（方式）と `METHOD_LABEL`（装置）、説明は `LOCATION_DESCRIPTION` / `METHOD_DESCRIPTION`。**画面に「A:循環」「B:投入」「C:オフサイト」を出さない**（契約チェック）。
- オフサイトの槽は常に新設で、新設槽と同じ前提（`new_tank_capex` / `tank_life_years`）を使う（`tankModesFor`）。シナリオの `key` はオンサイト `${用途}:${装置}-${槽}`、オフサイト `${用途}:オフサイト-${装置}-新設`。表示名は `scenarioLabelOf`（例: 直接投入・顧客の槽 / 直接投入・既設槽 / 直接投入・SX工場）と、方式つきの `scenarioFullLabelOf`（例: オンサイト・直接投入・顧客の槽）。
- **オフサイトの明細・作業が1行も無い試算（他PJ）にはオフサイトを出さず、方式の切り替えも出さない**（`listLocations` / `hasOffsite`）。用途なし・株なしの試算は、用途なし1系列・4シナリオとして従来どおり計算する。
- オフサイトは1社分の排液だけを処理する前提。複数の顧客の排液をまとめたときに設備と槽の償却が薄まる効果は入れていない。

## 誰がやるか（2026-09-14、migration 398）

作業ごとに誰がやるか（`project_cost_tasks.performer`）を持つ。**SX の原価と作業工数に入れるのは SX がやる作業だけ**。顧客がやる作業は、時間も円も数えず、画面にも出さない（行と「顧客がやる」の札だけを出す）。顧客側に残る時間は SX の試算の対象外（まさ 2026-09-14）。

| `performer` | 画面の選択肢 | 実際に誰がやるか（`resolvePerformer`） |
|---|---|---|
| `sx`（既定） | SX | SX |
| `customer` | 顧客 | 顧客。どの方式でも SX の原価に入れない |
| `site` | 場所による | 処理する場所の人。オンサイトは顧客、オフサイトは SX |

- 菌体の製造拠点の作業（`scenario='中央培養'`）は常に SX（制約 `project_cost_tasks_central_performer_check`。`resolvePerformer` も SX を返す）。
- SX のデータでは、処理の運転（`ct_run_circulation` / `ct_run_injection`）を `site` にした（migration 399）。循環カートリッジの処理の運転は、2026-09-14 に画面から `customer` で保存された（オフサイトでも顧客）。色素分解の脱水と処分の手配（`ct4_post_dye`）は、汚泥の処分と同じく `site`（migration 403）。巡回、モジュールと膜の交換、金属回収の後処理、閉鎖系の管理は `sx` のまま。
- 作業リストの「誰がやるか」で試算として変えられる。オンサイトで SX が運転まで請け負う形にすると、その分（強化株・色素分解・直接投入で 300円/m³、年2,250時間）が SX の原価と作業工数に入る。
- 無人運転で処理の運転の時間が減る効果は、SX が運転するオフサイト（と SX が請け負う形）の原価にだけ効く。

## 誰が持つか（2026-09-14、migration 402）

明細ごとに誰が持つか（`project_cost_items.bearer`）を持つ。**SX の原価に入れるのは SX が持つ明細だけ**。値と意味は作業の「誰がやるか」と同じ。

| `bearer` | 画面の選択肢 | 実際に誰が持つか（`resolveBearer`） |
|---|---|---|
| `sx`（既定） | SX | SX |
| `customer` | 顧客 | 顧客。どの方式でも SX の原価に入れない |
| `site` | 場所による | 処理する場所の持ち主。オンサイトは顧客、オフサイトは SX |

- 菌体の製造拠点の明細（`scenario='中央培養'`）は常に SX（制約 `project_cost_items_central_bearer_check`。`resolveBearer` も SX を返す）。
- 顧客が持つ明細は、総コスト・内訳・確度の帯グラフ・精度を下げている項目・初期投資のどれにも入れない。
- **オンサイトの槽を誰が持つか**は前提 `onsite_tank_bearer`（`value_text` が `customer` / `sx`。前提が無い試算は `sx`）で持つ。顧客のときはオンサイトの槽の2通り（既設 / 新設）を出さず、既設（SX の負担0）の1通りにする（`tankModesFor(location, onsiteTank)`）。シナリオの `key` は `${用途}:${装置}-既設` のままで、表示名は「直接投入・顧客の槽」。オフサイトの槽は、この前提によらず SX工場の設備として SX が持つ。
- 選択肢から選ぶ前提は `TEXT_CHOICE_ROLES`（role_key → 選択肢）に置き、操作パネルは数字の欄の代わりに選択肢を出す。
- SX のデータ（migration 403）: オンサイトで効く CAPEX 26行（顧客工場に置くリアクター。循環カートリッジ・直接投入の装置、処理槽の閉鎖系の設備など）と、色素分解の使用済み菌体の処分（`ci2_dye_disposal`）を `site`、それ以外は `sx`。オンサイトの槽を持つのは顧客。金属回収の酸処理（`シアノ回収後処理`）、顧客工場の装置の消耗品・電力・点検など（強化株・色素分解・直接投入で 62.8円/m³）、循環カートリッジの菌体保持モジュール交換費（300円/m³）は `sx` のまま。
- 明細の「誰が持つか」と槽の前提で試算として変えられる。SX が設備・槽・汚泥の処分まで持つ形に戻すと、強化株・オンサイト・直接投入で色素分解 102.6 → 240.0、金属回収 297.0 → 415.0円/m³。

### 作業リスト `project_cost_tasks`

| 列 | 意味 |
|---|---|
| `scenario` | 効く範囲。`循環`（循環カートリッジ。両方の方式）/ `投入`（直接投入。両方の方式）/ `共通`（すべて）/ `現場共通`（オンサイトだけ）/ `オフサイト`（オフサイトだけ）/ `中央培養`（菌体の製造拠点）。明細の `scenario` も同じ値（migration 396） |
| `strain` / `application` | 効く株・用途。null は共通 |
| `group_label` / `label` | 作業の流れの段と作業名。SX は `菌体をつくる` / `菌体を運ぶ` / `排液を運ぶ` / `排液を処理する` / `設備を保つ` / `使用済み菌体を後処理する` / `閉鎖系を管理する（強化株のみ）`（migration 397） |
| `hours_per_occurrence` | 1回の工数（人時）。**null は未確認で、0時間として計算する** |
| `count_driver` | 年間回数の決め方。`fixed`（`count_per_year` をそのまま）/ `batch`（年間バッチ数）/ `visit`（訪問回数 = 年間バッチ数 ÷ max(菌体使用回数, 1回の搬入でまかなうバッチ数)）/ `module_swap`（年間バッチ数 ÷ モジュール耐用バッチ数）/ `membrane_swap`（1 ÷ 膜交換年数）/ `truck_trip`（輸送の回数 = 年間処理量 ÷ 1台の積載量 `truck_capacity_m3`。migration 396） |
| `count_per_year` | 固定の回数のときの年間回数。`count_driver='fixed'` なら必須（制約） |
| `hourly_rate` | 作業単価（円/時）。**null は前提の共通の作業単価（`labor_rate`）を使う** |
| `expense_per_occurrence` | 1回あたりの経費（車両費・部材・外注費など、円） |
| `performer` | 誰がやるか。`sx`（既定）/ `customer` / `site`（オンサイトは顧客、オフサイトは SX）。**SX がやる作業だけを SX の原価に入れる**（上の「誰がやるか」。migration 398） |

- 製造拠点の作業（`scenario='中央培養'`）は第1段の年ごとの固定費に入るので、回数は `fixed` だけ、誰がやるかは `sx` だけを許す（制約 `project_cost_tasks_central_fixed_check` / `project_cost_tasks_central_performer_check`）。
- 工数の内訳が分かっていない作業（検査・フィルター交換など）は、工数を空欄（未確認）にし、分かっている年額を1回あたりの経費に置く。工数が分かったら工数を入れ、経費を部材・外注分へ直す。
- 流れの中で必要なのに工数も金額も分かっていない作業（SX の培養・濃縮の運転、使用済み菌体の後処理の作業）は、工数を空欄にして行だけ置く。0時間として数えるので総コストは変わらず、作業の流れに「工数未確認」と出る。

全テーブルに行単位の `visibility`（`amd_internal` / `workspace_shared`）。既定は内部。
RLS は `project_ip_*` と同形（read=`amd_os_is_member()`、write=`is_admin()`、`service_role` 全権）。
外部 `workspace_account` はこのポリシーに一致しない。外部へ見せる面は server component が service_role で読み、`workspace_shared` の行だけを返す設計にする（`toSharedBundle`。現時点で外部アカウントは未発行）。

## 計算エンジン

`pwa/src/lib/project-cost-model.ts`（純関数。DBアクセスもReactも持たない）

### 第1段 菌体の製造原価（`computeBiomassCost`）

菌体の製造拠点（`scenario='中央培養'`）の明細と作業で、選んだ株に効く行だけを使う。

```
培養設備の償却 (円/kg)       = Σ(初期投資 ÷ 耐用年数) ÷ 年間生産能力 ÷ 販売率
年ごとの固定費 (円/kg)       = Σ年額固定 ÷ 年間生産能力 ÷ 販売率
製造拠点の作業 (円/kg)       = Σ作業の年額 ÷ 年間生産能力 ÷ 販売率
菌体量に比例する費用 (円/kg) = Σ毎kg菌体比例の単価 ÷ 販売率
菌体の製造原価 (円/kg)       = 上の4つの合計
                              （biomass_cost_per_kg_override に正の値があれば、「上書き値 ÷ 販売率」で置き換える）
```

- 年間生産能力は `culture_capacity_kg_year`。**その量を作る前提**。
- **販売率**は `sales_rate`（%、既定100、1〜100に丸める）。生産した菌体のうち売れる割合。**売れ残りも作った分の費用はかかるので、第1段の全費用（償却・固定費・作業・比例費）を売れた量で割る**（まさ 2026-09-13。この解釈を既定にする）。販売率50%なら菌体1kgの原価はちょうど2倍になる。前提が無い試算は100%と同じ。
- 上書き値は「販売率で割る前の、生産1kgあたりの原価」として入れる。
- 出力: `productionPerKg`（生産1kgあたり）、`computedPerKg`（売れた1kgあたり）、`perKg`（第2段で使う原価）、`salesRate`、`soldKgYear`、`tasksAnnual`、行ごとの `rows`（`capex` / `fixed` / `tasks` / `variable`、いずれも販売率で割った後）。

### 第2段 用途別の処理原価（`computeCostModel`）

用途ごと、方式（オンサイト / オフサイト）× 装置（循環 / 投入）× 槽（オンサイトは既設 / 新設。槽を顧客が持つときは既設だけ。オフサイトは新設）。SX は4シナリオ、槽を SX が持つ試算は6シナリオ（オフサイトの行が無い試算は4シナリオ）。

```
必要吸着菌体量       = 対象物質濃度 × k_ppm ÷ 取り込み効率α
ロス込必要菌体量     = ÷ 菌体回収率η
使い切る菌体量 (kg)  = ロス込 ÷ 菌体使用回数 ÷ 1000        （金属回収は菌体使用回数 = 1 で固定）
菌体費 (円/単位)     = 第1段の原価 × 使い切る菌体量
総コスト             = 菌体費 + 方式・装置に効く明細のうち SX が持つもの（resolveBearer）+ 方式・装置に効く作業のうち SX がやるもの（scopesFor・resolvePerformer、選んだ株と用途に効く行）+ 槽（SX が持つ新設のとき）
```

- **金属回収は菌体使用回数を1回で固定する**（`deriveCostBasis` の `reuseFixed`）。前提 `reuse_count` に金属回収の行や共通の行があっても読まない。使い回せるのは色素分解だけ（まさ 2026-09-13）。SX の金属回収の使用回数の前提は migration 397 で消した。
- 輸送の回数 `truckTripsPerYear` = 年間処理量 ÷ `truck_capacity_m3`（既定10）。`count_driver='truck_trip'` の作業が使う。

`basis` による年間発生額:

| basis | 年間発生額 |
|---|---|
| `初期投資配賦` | 数量 × 単価 × 年換算 ÷ 耐用年数 |
| `毎m³比例` | 数量 × 実効単価 × 年換算 × 年間処理量 |
| `バッチ連動` | 数量 × 単価 × 年換算 |
| `毎kg菌体比例` | 数量 × 実効単価 × 年換算 × 使い切る菌体量 × 年間処理量（製造拠点の行は第1段で1kgあたりへ畳む） |
| `年額固定` | 数量 × 単価 × 年換算 |
| `内訳` | 0 |

`price_rule` による実効単価:

| price_rule | 計算 |
|---|---|
| `null` | `unit_price` をそのまま |
| `module_swap` | モジュール単価 ÷ 耐用バッチ数 ÷ バッチ容量 |
| `power_circulation` / `power_injection` | 動力kW × HRT × 電力単価 ÷ バッチ容量 |
| `spent_disposal` | 円/kg-DCW = 脱水後の湿重量倍率 × 汚泥の処分単価（`毎kg菌体比例` と組む） |
| `biomass` / `broth` | 旧形式。`unit_price` × 旧基準値との比。二段階版の SX 明細では使わない |

- **人件費は作業リストで持つ**（`taskAmount`）。2026-09-13 まで明細の `price_rule` にあった `labor_batch` / `patrol` / `patrol_module` / `patrol_membrane` は作業リストへ移して廃止した（migration 395 で制約からも外した）。**人件費だけを抜いた総コスト（`totalWithoutLaborPerUnit` など）は計算も表示もしない**。
- `breakdown` は総コストの内訳で、**足すと総コストに一致する**。区分と並び（`BREAKDOWN_ORDER`、積み上げ棒の順と色の順）: 菌体費 `biomass` / 運ぶ（巡回・輸送）`transport` / 運転・保守・管理 `labor` / 菌体の後処理 `postProcess` / 消耗品・電力・放流 `consumables` / 設備と槽の償却 `capex`。
  - 運ぶ = `count_driver` が `visit`（菌体の巡回）か `truck_trip`（排液の輸送）の作業（`isTransportTask`）。運転・保守・管理 = それ以外の作業。
  - 各区分は `parts`（中身。大きい順で、足すと区分の額）を持つ。菌体費は第1段の行（培養設備の償却 / 年ごとの固定費 / 製造拠点の作業 / 培地・CO2・濃縮など）× 使い切る菌体量、運ぶは作業名、運転・保守・管理は作業の流れの段、後処理・消耗品・償却は明細名（CAPEX は中項目、OPEX は中項目と小項目の長い方）と槽。
- `breakdown` の運ぶ・運転・保守・管理は **SX がやる作業だけ**で作る。顧客がやる作業はどの区分にも入らない。
- `siteTaskAnnual` / `siteTaskPerUnit` / `siteTaskHours` は方式・装置に効く作業のうち **SX がやるもの**の年額・1単位・年間工数（製造拠点の作業は含まない。拠点全体の工数は `biomass.taskHoursAnnual`）。**顧客がやる作業の時間や円はシナリオに持たせない**（顧客側の時間は SX の試算の対象外。まさ 2026-09-14）。`transportPerUnit` は運ぶの額。`location` は `onsite` / `offsite`、`method` は `循環` / `投入`。
- `strainSpecificPerUnit` は株固有の行（閉鎖系の追加など）の合計で、現場の明細・作業と、第1段から配った分を足す。内訳の外側に「うち」として出す。
- `postProcessPerUnit` は `group_label` が `シアノ回収後処理` / `使用済み菌体の処分` の OPEX 明細のうち SX が持つもの。
- 確度の帯グラフは、明細と作業を行ごとに数え、第1段の各行は「1kgあたりの額 ÷ 販売率 × 使い切る菌体量」で配る。上書き値のときは上書きの前提の確度で1本にする。
- 株・用途・作業を持たない試算（`strains=[]`, `applications=[]`, `tasks` なし）は、用途なし1系列・4シナリオとして従来どおり計算する。
- `COST_ROLE_KEYS` は計算が読む role_key の一覧。画面の操作パネルはこの前提だけを並べる（ここに無い前提は動かしても総コストが変わらないため、読み物の「すべての前提」に「計算に使っていない」と出す）。`onsite_tank_bearer` は数字ではなく `value_text` で読む（`onsiteTankBearer`）。

### 作業の流れ（`computeTaskFlow`）

選んだ株・用途・方式・装置で発生する作業（`rowAppliesTo`）を、`sort_order` の順に `group_label`（段）で束ねる。段の順は、段に含まれる作業の最小の `sort_order`。

- 段ごとに、SX がやる作業の顧客1社分の年間工数 `siteHours`、製造拠点の年間工数 `productionHours`（拠点全体）、SX がやる作業のうち工数が未確認の作業の数、SX がやる作業の顧客1社分の年額、SX の原価の1単位あたりの額（製造拠点の作業は「年額 ÷ 生産能力 ÷ 販売率 × 使い切る菌体量」。上書き値のときは0。顧客がやる作業は含まない）を出す。作業の行は、その方式で実際に誰がやるか（`performer`: `sx` / `customer`）を持つ。顧客がやる作業は行として段に残すだけで、工数・年額・1単位・未確認の数のどれにも入れない。
- 合計の `siteHours` / `siteAnnual` / `sitePerUnit` は、同じ株・用途・方式・装置のシナリオの `siteTaskHours` / `siteTaskAnnual` / `siteTaskPerUnit` と一致する（契約チェック）。

### 試算中の変更（`project-cost-model-draft.ts`）

`pwa/src/lib/project-cost-model-draft.ts`（純関数）

- 保存値（DB から読んだ束）はそのまま持ち、画面での書き換えは**下書き**（`CostDraft`: `${entity}:${id}:${field}` → 値）に持つ。計算と表示は `applyDraft(保存値, 下書き)` で行い、結果には保存値からの差を出す。
- 書き換えられる欄: 前提の `value`（選択肢で持つ前提は `valueText`）、明細の `unitPrice` / `quantity` / `usefulLifeYears` / `bearer`（`sx` / `customer` / `site` だけ）、作業の `hoursPerOccurrence` / `countDriver` / `countPerYear` / `hourlyRate` / `expensePerOccurrence` / `performer`（`sx` / `customer` / `site` だけ）、試算の `targetTotalCostPerUnit`。
- `setDraftValue` は、保存値と同じ値に戻すと下書きから消す。数字でない値、前提以外の負の値、空欄にできない欄の空欄は受け付けない。
- `draftToPatches` が下書きを API の patch（DB の列名）に変える。作業を「固定の回数」に変えるときは年間回数も同じ patch に入れる（DB の制約を満たすため）。
- 保存後に読み直した保存値と同じになった下書きは `pruneDraft` で落とす。
- 下書きと表示の選択（株・用途・方式・装置・槽）は、タブを行き来しても消えないようモジュールに持つ。**再読み込みで消える**。既定はオンサイト・直接投入・既設槽（槽を顧客が持つときは顧客の槽）。

## API

`/api/project-cost-model`（`runtime = "nodejs"`）

- `GET ?projectId=` → `{ ok, canEdit, bundle }`。`bundle.tasks` に作業リストを含む。`Cache-Control: private, max-age=60, stale-while-revalidate=300`。**`&fresh=1` のときだけ `no-store`**（保存直後の読み直し用。spec 5-10）
- `PATCH` → `{ entity: "assumption"|"item"|"task"|"model"|"question"|"note", id, patch }`。admin のみ。entity ごとに書き込み可能な列をホワイトリストで制限する
  - `assumption`: `value` / `value_text` / `confidence` / `source_kind` / `owner` / `note` / `is_key` / `visibility`
  - `item`: `unit_price` / `quantity` / `useful_life_years` / `bearer` / `confidence` / `source_kind` / `owner` / `note` / `visibility`（`bearer` は `sx` / `customer` / `site` だけ）
  - `task`: `hours_per_occurrence` / `count_driver` / `count_per_year` / `hourly_rate` / `expense_per_occurrence` / `performer` / `confidence` / `source_kind` / `owner` / `note` / `visibility`（`count_driver` は6値。`truck_trip` を含む。`performer` は `sx` / `customer` / `site` だけ）
  - `model`: `target_total_cost_per_m3` / `target_margin_rate`
  - 数字の列は有限の数字だけを通し、前提の `value` 以外は0以上。空欄（null）は、空欄に戻せる列（前提の値・耐用年数・工数・年間回数・作業単価・目標など）だけ。`count_driver` は計算エンジンの `TASK_DRIVERS` の6値だけ
- `loadCostModelBundle(projectId)` を export しており、server component からも service_role で読める

**参照系なので画面から素の fetch をしない。** 読み書きとも `pwa/src/lib/project-cost-model-client.ts` を通す（`loadProjectCostModel` / `peekProjectCostModel` / `prefetchProjectCostModel` / `saveCostPatches`）。
