> **この章は何か**: PJコックピット / PJワークスペースの「コスト試算」タブ (2026-08-29 新設、2026-09-13 二段階化・シミュレーター化・作業の流れとオフサイト、2026-09-14 方式と装置の分離・誰がやるか・誰が持つか・年間処理量から年に作る量・共通の作業単価と CAPEX / OPEX の区分・上端の槽を外し効かない前提を薄く出す・顧客工場の装置の費用を顧客に) の contract。

1. どういう系を想定して、どういう計算をしているか
2. CAPEX と OPEX がそれぞれいくらか
3. いくら以下ならユニットエコノミクスが成立するか
4. どのパラメータの確度が低いせいで精度が落ちているか

加えて、2026-09-13 のまさFBで次を要件にした。

5. **前提条件やまだ確定できない数値は、すべて画面で変えられる**（「とにかく前提条件とかまだ確定できない数値はすべてUI上で変えられるようにして」）

## 二段階の計算（2026-09-13 まさ確定）

**菌体の製造原価は株で決まり、用途では変わらない。用途で変わるのは使い回せる回数と、そこから決まる必要菌体量。**
旧版はこの区別がなく、菌体の製造拠点の設備償却を「排水1m³あたりの固定額」で置いていた。そのため菌体使用回数を変えると、菌体1kgあたりに割り戻した原価が見かけ上 98円 → 約440円 → 約1,200円と動いた。二段階はこれを直すための形。
2026-09-14 から、年に作る量は入力ではなく、方式ごとの年間処理量 × その方式で使い切る菌体量 ÷ 販売率 で計算する（下の「年に作る量と培養設備の系列」）。製造拠点の明細を培養設備の系列として並べるので、1kgあたりの原価は作る量で変わらない。変わるのは、拠点に1つの作業が作る量で薄まる分だけで、同じ株でも用途によってわずかに違う（強化株で色素分解 334.4円・金属回収 334.3円）。

| 段 | 何を出すか | 何で変わるか |
|---|---|---|
| 第1段 菌体の製造原価 | 株（強化株 / 自然株）ごとの、売れた乾燥菌体1kgあたりの原価（円/kg-DCW）。CAPEX・年額固定費・製造拠点の作業・菌体量比例費を含み、販売率で割る | 株（強化株は閉鎖系の追加費用が乗る）、1系列の年間生産能力、販売率、拠点に1つの作業（年に作る量で薄まる） |
| 第2段 用途別の処理原価 | 第1段の原価を一定として、用途（色素分解 / 金属回収）ごと・方式×装置×槽ごとの1単位あたり総コスト | 用途（濃度・取り込み効率・菌体使用回数・後処理）、株（取り込み効率・処理設備の閉鎖系費用）、方式（オンサイト / オフサイト）、装置（循環カートリッジ / 直接投入）、槽、作業を誰がやるか |

**菌体の製造拠点**: 顧客工場では培養せず、SX側の1拠点でまとめて菌体を育て、濃縮して各工場へ運ぶところ（2026-07-10 の設計）。DB の `scenario` の値は `中央培養` のままで、**画面では「中央培養」と書かない**（まさ 2026-09-13「中央培養ってなに？」）。表示名は `PRODUCTION_SITE_LABEL`、説明は `PRODUCTION_SITE_DESCRIPTION`。

## 方式と装置

切り替えは **方式**（どこで処理するか）と **装置**（菌体と排液をどう触れさせるか）の2つに分ける（まさ 2026-09-14）。2026-09-13 版は「A:循環・B:投入・C:オフサイト」を1つの切り替えに並べており、処理する場所と装置という別の軸が混ざっていた。

| 方式 | どこで処理するか | 処理の運転 | 設備・槽・汚泥の処分 |
|---|---|---|---|
| オンサイト | 顧客工場の槽の横に、顧客が買ったリアクターを置く。SX は菌体の搬入・搬出や交換で巡回する | 顧客 | 顧客（槽は前提で SX にすると既設 / 新設を選べる） |
| オフサイト | 排液をタンクローリーで SX工場まで運び、SX工場に新設する槽で処理する。処理水は SX工場から流す | SX | SX（槽は新設だけ） |

| 装置 | DB の `scenario` | 何をするか |
|---|---|---|
| 循環カートリッジ | `循環` | 菌体を筒（カートリッジ）に閉じ込め、ポンプで排液を通して槽へ戻す |
| 直接投入 | `投入` | 菌体を排液の槽に直接入れて混ぜ、処理後に膜でこして取り出す |

- **どちらの方式でも両方の装置を選べる**。シナリオは用途ごとに、オンサイト2（装置2）とオフサイト2（装置2）の4つ。オンサイトの槽を SX が持つ前提にすると、オンサイトは装置2 × 槽2 の4つになる（下の「誰が持つか」）。
- 数える明細・作業の範囲は `scopesFor(方式, 装置)` ＝ 装置の `scenario`・`共通`・（オンサイトなら `現場共通` / オフサイトなら `オフサイト`）。`現場共通` は顧客工場への菌体の巡回、顧客工場内の区画・立入制限など、`オフサイト` は排液の輸送・受け入れ・放流など。`中央培養`（菌体の製造拠点）は第1段で数え、方式・装置によらない（`rowAppliesTo`）。
- DB の `scenario` の値は変えていない。画面の呼び名は `LOCATION_SHORT_LABEL`（方式）と `METHOD_LABEL`（装置）、説明は `LOCATION_DESCRIPTION` / `METHOD_DESCRIPTION`。**画面に「A:循環」「B:投入」「C:オフサイト」を出さない**（契約チェック）。
- オフサイトの槽は常に新設で、新設槽と同じ前提（`new_tank_capex` / `tank_life_years`）を使う（`tankModesFor`）。シナリオの `key` はオンサイト `${用途}:${装置}-${槽}`、オフサイト `${用途}:オフサイト-${装置}-新設`。表示名は `scenarioLabelOf`（例: 直接投入 / 直接投入・既設槽）と、方式つきの `scenarioFullLabelOf`（例: オンサイト・直接投入）。**槽は選べるとき（オンサイトの槽を SX が持つとき）だけ名前に入れる**。オンサイトの槽が顧客の設備のときと、常に SX工場に新設するオフサイトは、名前に槽を出さない（まさ 2026-09-14）。
- **オフサイトの明細・作業が1行も無い試算（他PJ）にはオフサイトを出さず、方式の切り替えも出さない**（`listLocations` / `hasOffsite`）。用途なし・株なしの試算は、用途なし1系列・4シナリオとして従来どおり計算する。
- オフサイトは1社分の排液だけを処理する前提。複数の顧客の排液をまとめたときに設備と槽の償却が薄まる効果は入れていない。

## 誰がやるか（2026-09-14、migration 398）

作業ごとに誰がやるか（`project_cost_tasks.performer`）を持つ。**SX の原価と作業工数に入れるのは SX がやる作業だけ**。顧客がやる作業は、時間も円も数えず、画面にも出さない（行と「顧客がやる」の札だけを出す）。顧客側に残る時間は SX の試算の対象外（まさ 2026-09-14）。

| `performer` | 画面の選択肢 | 実際に誰がやるか（`resolvePerformer`） |
|---|---|---|
| `sx`（既定） | SX | SX |
| `customer` | 顧客 | 顧客。どの方式でも SX の原価に入れない |
| `site` | 場所による | 処理する場所の人。オンサイトは顧客、オフサイトは SX |

- 菌体の製造拠点の作業（`scenario='中央培養'`）は常に SX（制約 `project_cost_tasks_central_performer_check`。`resolvePerformer` も SX を返す）。
- SX のデータでは、処理の運転（`ct_run_circulation` / `ct_run_injection`）を `site` にした（migration 399）。循環カートリッジの処理の運転は、2026-09-14 に画面から `customer` で保存されたが、同日のまさの回答（「オフサイトならSX」）で `site` に戻した（migration 410）。色素分解の脱水と処分の手配（`ct4_post_dye`）は、汚泥の処分と同じく `site`（migration 403）。巡回、モジュールと膜の交換、金属回収の後処理、安全委員会と顧客工場の立入制限・教育訓練は `sx` のまま。顧客工場の処理設備の密閉性能検査と除菌フィルター交換（強化株、経費だけの作業）は、顧客の装置の点検・消耗品として `site`（migration 410）。
- 作業リストの「誰がやるか」で試算として変えられる。オンサイトで SX が運転まで請け負う形にすると、その分（強化株・色素分解・直接投入で 300円/m³、年2,250時間）が SX の原価と作業工数に入る。
- 無人運転で処理の運転の時間が減る効果は、SX が運転するオフサイト（と SX が請け負う形）の原価にだけ効く。

## 誰が持つか（2026-09-14、migration 402）

明細ごとに誰が持つか（`project_cost_items.bearer`）を持つ。**SX の原価に入れるのは SX が持つ明細だけ**。値と意味は作業の「誰がやるか」と同じ。

| `bearer` | 画面の選択肢 | 実際に誰が持つか（`resolveBearer`） |
|---|---|---|
| `sx`（既定） | SX | SX |
| `customer` | 顧客 | 顧客。どの方式でも SX の原価に入れない |
| `site` | 場所による | 処理する場所の持ち主。オンサイトは顧客、オフサイトは SX |

- 菌体の製造拠点の明細（`scenario='中央培養'`）は常に SX（制約 `project_cost_items_central_bearer_check`。`resolveBearer` も SX を返す）。
- 顧客が持つ明細は、総コスト・内訳・確度の帯グラフ・精度を下げている項目・初期投資のどれにも入れない。
- **オンサイトの槽を誰が持つか**は前提 `onsite_tank_bearer`（`value_text` が `customer` / `sx`。前提が無い試算は `sx`）で持つ。顧客のときはオンサイトの槽の2通り（既設 / 新設）を出さず、既設（SX の負担0）の1通りにする（`tankModesFor(location, onsiteTank)`）。シナリオの `key` は `${用途}:${装置}-既設` のままで、表示名は「直接投入」。オフサイトの槽は、この前提によらず SX工場の設備として SX が持つ。
- 選択肢から選ぶ前提は `TEXT_CHOICE_ROLES`（role_key → 選択肢）に置き、操作パネルは数字の欄の代わりに選択肢を出す。
- SX のデータ（migration 403）: オンサイトで効く CAPEX 26行（顧客工場に置くリアクター。循環カートリッジ・直接投入の装置、処理槽の閉鎖系の設備など）と、色素分解の使用済み菌体の処分（`ci2_dye_disposal`）を `site`、それ以外は `sx`。オンサイトの槽を持つのは顧客。金属回収の酸処理（`シアノ回収後処理`）は `sx` のまま。migration 410 で、顧客工場の装置を動かす OPEX（循環カートリッジ10行: 洗浄・監視点検・保守・菌体保持モジュール交換費・電力、直接投入17行: 洗浄・監視点検・保守・膜の洗浄・逆洗・前処理・差圧監視・回収残渣対応・電力）と、処理水の分析（色素分解）・不活化の薬剤（強化株）を `site` に移した（まさ「それ普通いれないでしょ」）。オンサイトで SX に残る現場の OPEX は、菌体の補充分（ロス・性能低下）と菌体を運ぶ容器（強化株・色素分解・直接投入で 2.1円/m³）、金属回収の後処理。
- 明細の「誰が持つか」と槽の前提で試算として変えられる。明細をすべて SX・槽を SX にする（設備・槽・装置の費用・汚泥の処分まで持つ）と、強化株・オンサイト・直接投入で色素分解 34.1 → 232.2、金属回収 225.8 → 400.4円/m³（顧客工場の処理設備の密閉性能検査とフィルター交換も SX がやると 239.2 / 407.4）。

## 年に作る量と培養設備の系列（2026-09-14、migration 404）

菌体の製造拠点で年に作る量は、入力ではなく年間処理量から計算する（まさ 2026-09-14）。

- 前提 `business_annual_volume`（年間処理量（オンサイト）、単位/年。migration 419 までは「年間処理量（事業全体）」）。SX は **20,000,000 m³/年**（IPOできる大量生産の状態として、売上100億円 ÷ 売価500円/m³）。顧客1社あたり年30,000m³なら約667社分。
- 年に作る量 `capacityKgYear` ＝（`business_annual_volume` × その用途でオンサイトに使い切る菌体量 ＋ 別に持つときは `offsite_annual_volume` × オフサイトで使い切る菌体量）÷ 販売率（`productionScaleOf`）。オフサイトで使い切る菌体量は、オフサイトの濃さを別に持つときはその濃さで出す（下の「オフサイトで引き取る液の濃さ」）。売る量 `soldKgYear` ＝ 年に作る量 × 販売率。**用途ごとに、その用途だけでこの量を処理したときとして出す**ので、第1段も用途ごとに持つ（`biomassByApplication`。画面は `biomassOf(computed, 用途)` で引く。`biomassByStrain` は株 × 用途）。
- 製造拠点の明細（`scenario='中央培養'`）は培養設備の**1系列**。1系列の年間生産能力は前提 `culture_line_capacity_kg_year`（SX は 33,333 kg/年、仮置き）。系列数 `productionLines` ＝ 年に作る量 ÷ 1系列（端数も比例で数える）。
- 初期投資・償却年額・年額固定費は1系列ぶん × 系列数。1kgあたりは「1系列の年額 ÷ 1系列の量 ÷ 販売率」で、作る量によらない。
- 製造拠点の作業は `count_driver` で、拠点に1つの作業（`fixed`）と、培養設備の系列ごとの作業（`production_line`。年間回数 ＝ `count_per_year` × 系列数）に分ける。`production_line` は製造拠点の作業だけ（制約 `project_cost_tasks_production_line_check`）、製造拠点の作業は `fixed` か `production_line`（`project_cost_tasks_central_fixed_check`）、どちらも `count_per_year` を持つ（`project_cost_tasks_fixed_count_check`）。**拠点に1つの作業だけが、年に作る量が増えるほど1kgあたり薄まる**。
- SX のデータ（migration 405）: 系列ごとは培養・濃縮の運転（1系列 年300日）・培養設備の密閉性能検査（年1回）・除菌フィルターの交換（年4回）。拠点に1つは安全委員会の運営・教育訓練・記録保存（年1回）。品質確認の年額固定（24万円/年）は1系列あたり。
- シナリオに事業全体の年額を持つ: `businessVolume`、`customerCount`（年間処理量 ÷ 顧客1社の年間処理量）、`businessRevenueAnnual`（年間処理量 × 売価）、`businessTotalAnnual`（1単位あたりの総コスト × 年間処理量）、`businessProfitAnnual`。オフサイトの年間処理量を別に持つ試算は、方式ごとの年間処理量と売価で出す（下の「オフサイトの売価と年間処理量」）。
- **年間処理量の前提が無い試算は、これまでどおり**年間生産能力 `culture_capacity_kg_year` をそのまま年に作る量として使う（系列は1つ、事業全体の年額は0）。年間処理量があって1系列の前提が無いときは、`culture_capacity_kg_year` を1系列の量として使う。
- 量産で設備や原料をまとめて買ったときの値下がりは入れていない。製造拠点を何箇所に分けるかも決めていない（系列はすべて1拠点に並べる前提）。

## オフサイトの売価と年間処理量（2026-09-14、migration 419）

オフサイト（顧客の排液をSX工場まで運んで処理）は、売価と年間処理量をオンサイトと別の前提で持つ（まさ 2026-09-14「オフサイトは売価も処理量も別に分けて試算したい」「将来的にサイドビジネス的に、オフサイトもやれたらいいかなっていうくらいのadditionalな要素ではある。自社での処理をしたくないケースもあるだろうし。ペインがあれば割高でも成立するから」）。

- 前提 `offsite_sale_price`（想定売上単価（オフサイト）、円/単位）と `offsite_annual_volume`（年間処理量（オフサイト）、単位/年）。SX は **50,000円/m³（1Lあたり50円）・30,000m³/年**（仮置き。売価はまさの見立て「液を引き取りに来てもらうときは1Lあたり50円くらいが相場」と、業者サイトの目安（廃酸・廃アルカリの処分費 1kgあたり30〜100円）から。量は SX工場1か所がいまの前提（100m³/日 × 300日）で処理する量）。これまでの `business_annual_volume` と `sale_price` は、オンサイトの分として「年間処理量（オンサイト）」「想定売上単価（オンサイト）」と呼ぶ。
- 物量 `CostDerived.offsiteSalePrice`（`offsite_sale_price` が無ければ `sale_price`）と `offsitePriceSeparate`。シナリオの `salePricePerUnit` は方式の売価で、売上・利益・利益率・売価との差（`gapToAllowedPerUnit`）もこの売価で出す。
- **総コスト目標はオンサイトにだけ当てる**。目標（300円/m³）はオンサイトの売価 500円/m³ に対して置いた値なので、売価を別に持つオフサイトは `gapToTargetPerUnit` を null にし、判定は「黒字 / 赤字」だけ。
- 第1段の `productionScaleOf` は、年に作る量 ＝（`business_annual_volume` × オンサイトで使い切る菌体量 ＋ `offsite_annual_volume` × オフサイトで使い切る菌体量）÷ 販売率。同じ製造拠点で両方の菌体を作る。`CostBiomassCost` に `onsiteVolume` / `offsiteVolume` / `offsiteVolumeSeparate`（migration 427 で方式ごとの菌体量 `onsiteBiomassKgPerUnit` / `offsiteBiomassKgPerUnit` を足した）。
- シナリオの全体の年間（`businessVolume` と `businessScope`）: オフサイトの年間処理量を別に持つ試算は、オンサイトは `onsite`（オンサイトの年間処理量）、オフサイトは `offsite`（オフサイトの年間処理量）。持たない試算は `total`（どちらも `business_annual_volume`）。
- **前提が無い試算（ほかのPJ）は、これまでどおり**オフサイトもオンサイトの売価と年間処理量で出し、目標も当てる。
- 効く前提（`rolesInEffect`）: `sale_price` と `offsite_sale_price` は `CONDITIONAL_ROLE_KEYS`。選んだ方式の売価だけが効く（オフサイトの売価を別に持たない試算では、オフサイトにも `sale_price`）。年間処理量は2つとも年に作る量に効くので、どちらの方式でも薄くしない。
- 画面: 事業の規模と売価に4つの前提（オンサイトの量・売価、オフサイトの量・売価）と総コスト目標（オフサイトの売価を別に持つとき「総コスト目標（オンサイト）」と、その下に「売価を別に置いたオフサイトは、売価との差だけを見る」）。割り算は「オンサイトの売上 ＝ …」「オフサイトの売上 ＝ 年間処理量 × 売価 ＝ …（約N社分）」「年に作る菌体は、オンサイトとオフサイトの年間処理量に、それぞれの濃さで使い切る菌体の量を掛けて足した量から計算する」（migration 427 から）。結果の欄は、方式の見出しに「・売価 500・目標 300」「・売価 50,000」を添え、棒の売価の線はそれぞれの方式の売価で引き、目標の線はオンサイトの行だけ（凡例は線の種類だけ）。年に作る量の行は「年間処理量 オンサイト＋オフサイト N m³」。全体の年間の見出しは「オンサイトの年間」「オフサイトの年間」で、顧客の数は見出しの下の行に出す（見出しの幅を広げると金額が1行増え、結果の欄が伸びるため）。読み物のシナリオの内訳に「売価（売上）」の行。

## オフサイトで引き取る液の濃さ（2026-09-14、migration 427）

オフサイトは、対象物質の濃さもオンサイトと別の前提で持つ（まさ 2026-09-14「置いて」。報告「オフサイトの売価は液の引き取りの値段（1Lあたり50円）に置いたが、液の濃さは顧客工場の排水のままなので、利益率94%前後は濃さを据え置いたための数字」と、オフサイトに別の液の濃さを置くかの確認への返事）。引き取りの値段が付くのは顧客が自社で処理しにくい濃い液なので、使い切る菌体の量と、それに比例する費用（菌体費・使用済み菌体の後処理・菌体量に比例する消耗品）が排水より大きくなる。

- 前提 `offsite_target_concentration`（対象物質の濃度（色素・オフサイト）/（金属・オフサイト）。単位はオンサイトの `target_concentration` と同じ）。SX は **色素分解 1,000mg/L・金属回収 5,000ppm**（どちらも確度 C の仮置き。色素は染色の残液を想定して排水の仮置き50mg/Lの20倍、金属はめっき排水の目安（鉄500ppm程度）とめっき液そのもの（ニッケル換算 約50,000〜100,000ppm）の間。顧客候補がいま産業廃棄物として出している液の分析値で置き換える）。
- 物量 `deriveCostBasis(前提, 選択, 方式)`: 方式で変わるのは対象物質の濃さだけ。オフサイトは `offsite_target_concentration` があればその濃さ、無ければオンサイトの `target_concentration`。`CostDerived` に `location` と `offsiteConcentrationSeparate`。
- 第2段は用途ごとにオンサイトとオフサイトの物量を持ち（`derivedByApplication[].derived` / `offsiteDerived`）、シナリオは方式の物量で菌体費・明細・作業を数える。**画面は `derivedOf(computed, 用途, 方式)` で引く**（用途だけで引くとオフサイトの濃さが抜ける。契約チェック22）。
- 年に作る量は、方式ごとに使い切る菌体量を掛けてから足す（上の「年に作る量と培養設備の系列」）。
- 効く前提（`rolesInEffect`）: `offsite_target_concentration` は `CONDITIONAL_ROLE_KEYS` に入れない。オンサイトを選んでいても年に作る量（系列数と、拠点に1つの作業の薄まり方）に効くので、年間処理量と同じくどちらの方式でも薄くしない。
- **前提が無い試算（ほかのPJ）は、これまでどおり**オフサイトもオンサイトの濃さで出す。
- 画面: 操作パネルの「対象物質と菌体の量」で、オンサイトの濃さのすぐ下にオフサイトの濃さを並べる（`COST_PARAM_GROUPS`）。割り算は、オフサイトの濃さを別に置く試算で、選んだ方式の濃さを先頭に出す（「オフサイトの濃さ 1,000mg/L（オフサイトで引き取る液の濃さ）で、必要な菌体 …」「オンサイトの濃さ 50mg/L（顧客工場の排水の濃さ）で、…」、`data-testid="cost-substance-formula"`）。「菌体の製造量と原価」の割り算は「年に作る量 ＝（オンサイト 20,000,000 m³ × 使い切る菌体 0.111 kg/m³ ＋ オフサイト 30,000 m³ × 使い切る菌体 2.222 kg/m³）＝ …」（`data-testid="cost-production-formula"`）。結果の「使い切る菌体」、明細・作業リストの額、読み物の数字も選んだ方式の物量で出す。
- 金属回収のオフサイトは、使い切る乾燥菌体が1m³あたり約105kg（強化株）〜約132kg（自然株）で、液の重さの約1割になる。この量を菌体に取り込ませる処理が成り立つかは確かめていない（確認事項。計算は費用だけを出す）。

## 排ガス利用可能（2026-09-14、migration 430）

まさ 2026-09-14「「排ガス利用可能」のスイッチをCO2コストのところに設置してほしい。それがONのときはCO2コストがゼロになるようにして」。
培養の原料を「使う量 × 買値」に組み直すと、CO2 が菌体1kgあたり 114.5円（原料の中で一番大きい）になった。前の額（4.5円）の元は、ちこさんの試算シートの 2026-07-16版で「排ガス利用等も想定した最小構成。詳細仕様未確定。」として置かれた「CO2/ガス・補助剤　処理水1m³あたり10円」（2026-07-30版から「CO₂ 5円」）だった。

- 前提 `co2_flue_gas`（`value_text` が `on` なら使える。無い・`off` は使えない）。SOL は両方の試算に1行ずつ（`ca13_co2_flue_gas`・`caf_co2_flue_gas`、既定 `off`）。区分は OPEX の「菌体の製造拠点（原料・品質確認）」（燃料は「培養の原料・品質確認」）だが、**前提の一覧には出さず、CO2 の明細の行にスイッチ（`FlueGasSwitch`、`role="switch"`）を出す**（`ITEM_INLINE_ROLES`）。切り替えは試算中の変更で、保存は「保存していない変更」から（`value_text` の patch。一覧には「使える（CO2は0円）」「使えない（液化炭酸ガスを買う）」と出る）
- 明細の単価の連動のしかた（`price_rule`）を2つ足した（DB の check 制約も）:
  - `co2_supply`（CO2 の行 `ci_260820_123`・`cif_culture_123`）: `co2_flue_gas` が `on` なら単価0円、`off` なら `unit_price`（液化炭酸ガスの買値）。買値の欄は ON でも書き換えられ、残る。行の下の計算は ON のとき「単価 ＝ 液化炭酸ガスの買値 50 円/kg × 工場の排ガスを使うので 0 ＝ 0 円/kg」、OFF のときは単価の出し方を出さない
  - `culture_loss`（培養ロス補充 `ci_260820_134`・`cif_culture_134`）: 単価 ＝ 同じ群（`group_label`）・同じ効く範囲・`毎kg菌体比例` の OPEX の行（`culture_loss` 以外）の、数量 × 実効単価 × 年の回数 の合計（`cultureLossSources`）。作り直す割合は数量（5%）。行の下の計算は原料9行の足し算（`CalcOp` に `+` を足した）。**明細の束を渡さない呼び出しは `unit_price` を使う**ので、`effectiveUnitPrice` / `annualAmount` / `centralItemPerKg` / `costItemCalc` の最後の引数に `items` を渡す（エンジンの中と、操作パネル・読み物の行の計算。燃料は `FuelPriceContext`）。426 の `unit_price`（261.6円）は丸めた合計で、430 から丸めない合計（261.55円）を使うので、OFF のままでも一部の数字が0.1〜0.4円動いた
- 効くとき（`rolesInEffect`）: 単価が `co2_supply` の明細を数えるとき（製造拠点の行なので、菌体の製造原価を上書きしていないとき）。買値が0円の行は数えない
- 読み物の費用明細は、CO2 の行の発生ロジックに「排ガス利用可能 ON / OFF」、ON のときは単価 0 と「買うなら 50」を出す。培養ロス補充は「原料の合計」

### 「工場から」の3つを枠の上端にも並べる（2026-09-15）

まさ 2026-09-15「排液、排ガス、排熱を利用するのスイッチは、一番上の「株」「用途」「方式」「装置」の切り替えスイッチの右にも並べてほしい」。

排液（`waste_medium`）・排ガス（`co2_flue_gas`）・排熱（`waste_heat`）の3つは、明細の行のスイッチに加えて、**枠の上端の切り替えの右にも並べる**（`FactoryUtilitySwitches`。廃液は「株 / 用途 / 方式 / 装置」の右、燃料は「FAME転換 / 収率 / 株」の右）。押すと同じ前提を切り替えるので、行のスイッチと上端は必ず同じ状態になる。保存値と違うときは枠を AMD Blue にする。切り替えの下の一文に「工場から＝排液・排ガスをもらう前提（培養の拠点を工場の隣に置く）」と出す。

## 工場の排液を培地に使える（2026-09-15、migration 434）

まさ 2026-09-15「その結果次第では、燃料事業は、顧客の工場のCO2と排熱、排ガスをフル活用してやる方向も見えてくる」。

培地の原料（窒素源・リン源・カリウムなど）の3行に、**「工場の排液を培地に使える」のスイッチ**を置いた。前提 `waste_medium`（`value_text` が `on` / `off`、既定 off）と `waste_medium_reduction`（減る割合、%、既定80）。ON にすると、その3行の買値が割合だけ引かれる（単価の連動のしかた `medium_supply`）。量と試薬の買値は行に残り、切ると戻る。培養ロス補充（`culture_loss`）は原料の合計から出すので一緒に下がる。

- スイッチは前提の一覧に出さず、培地の原料の行に出す（`ITEM_INLINE_ROLES`、`WasteMediumSwitch`）。減る割合は前提の一覧で変える
- 排ガス利用可能（430）と同じ形で、両方 ON にできる（まさの「顧客の工場のCO2と排熱、排ガスをフル活用」）
- `rolesInEffect` は、スイッチが OFF のときに減る割合を「効いていない」と数える（OFF では割合を変えても数字が動かないため）
- **80% の出どころ**: ちこさんの試算シート 2026-07-30版の前提「培地原料低減率 80%（排液利用で大幅低減）」。その版の額はすべて出所「仮置き」で、80% の根拠は書かれていない。2026-09-14 に培養の原料を「使う量 × 買値」（試薬を買う前提）へ組み直したときに消えた前提を、切り替えとして戻したもの
- **使える排液の条件**（注記に書いた。2026-09-15 に「色」の置き方を直した。まさ「色がついてなきゃいけない理由がわからん」）: 排液は培養液そのものではなく培地の栄養として入れるので、**要る窒素の量から薄める倍率が決まり、色も同じ倍率だけ薄まる**（吸光度は濃さに比例する）。したがって条件は「色が付いていない」ではなく ①**窒素が濃いか**（培養液の窒素は約400mg/L要る。排液が X mg/L なら薄める倍率は X÷400 倍。**400mg/Lに届かない排液は薄める余地が無く色が残る**。味噌の排液は全窒素150mg/L で該当）②薄めたあとに残る色で光が通るか（実例: 佐賀市下水浄化センターの実証は脱水分離液を**3倍希釈**して上水・試薬と同等、0.54 g/L/7日）③菌体に毒になる金属や薬剤が入っていない ④塩分・油分 ⑤量と質が年間を通して安定 ⑥培養の拠点をその工場の隣に置ける。3つ（排液・排ガス・排熱）を出す工場自体はどこにでもある
- **排ガスの窒素酸化物（NOx）は窒素源にならない**（2026-09-15、`co2_flue_gas` の注記に書いた。まさ「NOxが栄養源になった、という話は過去に出てきてたように記憶してる」）。取り込むこと自体は SX 側の記録（「反応性窒素 ◎ 利用して増殖」2026-01-16、「硝酸・亜硝酸を短時間で取り込む」2026-09-02、先生の資料「N源 ≈2 ppm; 亜硝酸でも良い」）でも文献（Nagase ら 1998・2001）でも確かだが、**量が構造的に足りない**。CO2 と NOx は同じ燃焼から出るので比が決まっていて CO2 が約250〜2,000倍、菌体の炭素と窒素の比は約7.3。炭素をまかなう量の排ガスでは窒素は**必要量の0.4〜3%**にしかならないので、値引きは入れていない

|---|---|---|---|---|

## 数字の出どころと変更の記録（2026-09-14、migration 431）

まさ 2026-09-14「「前の額が何を前提にしていたかは、記録が無くて分からない。」→これはまずいと思う。えいみが作ったんだから、えいみしか分からんよ。こういうことが起きないようにして」。
培養の原料の前の額（CO2 4.5円/kg など）の前提は、ちこさんの試算シートの古い版（2026-07-16版の「排ガス利用等も想定した最小構成」、2026-07-30版の「培地原料低減率 80%（排液利用で大幅低減）」）に書いてあった。えいみは取り込み（2026-08-23）と二段階版への換算（2026-09-13）で説明に書き写さず、426 で額を組み直したあと、古い版をたどらずに「記録が無い」と答えた。同じことを起こさないために、次の4つを決まりにする。

- **根拠の無い数字を置かない** — 計算に使う明細（内訳・参考を除く）・前提（`COST_ROLE_KEYS` / `FUEL_ROLE_KEYS`）・作業は、すべて説明（画面の「根拠」）を持つ。書くことは、どの資料のどの版のどの行（またはどの回答・どの公開資料）から来た数か、元の単位と式、前提、確かめ方。決め方が資料に書かれていないなら「書かれていない」と書く。SOL は 431 で、根拠が空だった明細20行（培養設備の CAPEX `ci_260820_044`〜`056` の13行、処理設備 `ci_260820_066`・`077`〜`081`・`109` の7行）と前提2行（バッチ容量・稼働日）に出どころを書いた
- **組み直した数字は前の額を残す** — 前の額と、その額の出どころ（版・行・メモ・前提）を説明の最後に「前の額（…）:」で書く。SOL の培養の原料20行（両方の試算）に書き、版の履歴 `cn15_h15`・`cnf_history_origin`「培養の原料の前の額は、どこから来たか」に版ごとの表を置いた
- **書き換えは自動で記録に残る** — `project_cost_change_log`（`table_name`・`row_id`・`cost_model_id`・`op`（UPDATE / DELETE）・`changed_columns`・`old_values`・`new_values`・`reason`・`changed_by`・`changed_at`）。トリガー `project_cost_log_change`（security definer。`project_cost_items` / `project_cost_assumptions` / `project_cost_tasks` の after update or delete、行ごと）が、変わった列だけの前の値と後の値を書く。画面の保存（API）も migration も残る。`changed_by` は JWT の email → role → `session_user`。読めるのは admin と service_role
  - migration で書き換えるときは、書き換えの前に `select set_config('amd.cost_change_reason', '<何を・なぜ・どこから来た数か>', true);` を呼ぶ。燃料の契約チェックの20が、431 以降の migration で `update project_cost_items|assumptions|tasks set` を含むのに呼んでいないと止める
  - 431 は、426 と 430 で書き換えた明細24件の前の値を、適用前の DB の写しから記録に入れた（`changed_by` = `migration 426` / `migration 430`）
  - 画面から保存した変更の `changed_by` は API の service_role になり、誰が保存したかは出ない（時刻と前の値は残る）。`project_cost_notes` / `project_cost_questions` / `project_cost_models` の文章は記録しない
- **出どころを聞かれたら、たどってから答える** — 変更の記録 → 明細の説明と版の履歴 → migration と取り込みの台本（`pwa/scripts/gen_sx_cost_seed.py`）→ 元の資料のすべての版（Drive で同じ名前の版を探す）→ 議事録 の順にたどる。たどった範囲を書き、それでも分からないことは誰に聞けば分かるかを書く。「記録が無い」で止めない

## 選んだ組み合わせで効く前提（2026-09-14、`rolesInEffect`）

操作パネルと読み物の「すべての前提」は、選んだ組み合わせ（株・用途・方式・装置・槽）で値を変えても SX の数字（総コスト・内訳・作業工数）が動かない前提を、明細や作業と同じく薄く出す（まさ 2026-09-14「オンサイトを選んだときもグレーアウトしてないのでグレーアウトさせて」）。書き換えはできる。

- 組み合わせで効き方が変わる前提は `CONDITIONAL_ROLE_KEYS` だけで、ほかの計算用の前提（`COST_ROLE_KEYS`）はどの組み合わせでも効く。
- `rolesInEffect(bundle, { strain, application, location, method, tankMode })` が、その組み合わせで数える行から効く前提を集める。数えるのは SX が持つ明細（`resolveBearer`）と SX がやる作業（`resolvePerformer`）で、製造拠点の明細と作業は菌体の製造原価を上書きしていないときだけ。

| 前提 | 効くとき |
|---|---|
| `module_unit_price` | 単価が `module_swap` の明細を SX が持つとき（SX はオフサイトの循環カートリッジ。オンサイトは顧客の装置の費用） |
| `module_durability_batches` | 同上か、年間回数が `module_swap` の作業（工数か経費がある）を数えるとき |
| `power_unit_price` / `power_kw_circulation` `hrt_circulation` / `power_kw_injection` `hrt_injection` | 単価が `power_circulation` / `power_injection` の明細を SX が持つとき（SX はオフサイト。電力単価はどちらの装置でも。オンサイトの電力は顧客） |
| `spent_wet_factor` / `sludge_disposal_price` | 単価が `spent_disposal` の明細を SX が持つとき（SX は色素分解のオフサイト。オンサイトは顧客が処分する） |
| `patrol_batches_per_delivery` | 年間回数が `visit` の作業を数えるとき（SX はオンサイトの菌体の搬入・搬出と移動） |
| `membrane_life_years` | 年間回数が `membrane_swap` の作業を数えるとき（直接投入） |
| `truck_capacity_m3` | 年間回数が `truck_trip` の作業を数えるとき（オフサイト） |
| `labor_rate` | 工数のある作業を数えるとき |
| `new_tank_capex` / `tank_life_years` | 槽を SX が新設するとき（オフサイトは常に。オンサイトは槽を SX が持ち、新設を選んだとき） |
| `onsite_tank_bearer` | オンサイトのとき |
| `co2_flue_gas` | 単価が `co2_supply` の明細（買値が0円でない）を数えるとき（菌体の製造原価を上書きしていないとき） |
| `sale_price` / `offsite_sale_price` | 選んだ方式の売価だけ（オンサイトは `sale_price`、オフサイトは別に持つとき `offsite_sale_price`、持たないとき `sale_price`） |

- 契約チェック（19）は、SX のデータとその変形（槽を SX が持つ・工数がすべて空欄・作業は処理の運転だけ・菌体の原価を上書き）の全組み合わせで、効かないとした前提を動かしても数字が変わらず、効くとした前提を動かすと数字が変わることを確かめる。明細の連動のしかたや作業の回数の決め方を足したら、`ROLES_BY_PRICE_RULE` / `ROLES_BY_TASK_DRIVER` に足す（足さないとこのチェックで落ちる）。

## 計算エンジン

`pwa/src/lib/project-cost-model.ts`（純関数。DBアクセスもReactも持たない）

### 第1段 菌体の製造原価（`computeBiomassCost`）

菌体の製造拠点（`scenario='中央培養'`）の明細と作業で、選んだ株に効く行だけを使う。

```
年に作る量 (kg/年)           = Σ方式(年間処理量 × その方式で使い切る菌体量) ÷ 販売率   （年間処理量の前提が無ければ年間生産能力）
系列数                       = 年に作る量 ÷ 1系列の年間生産能力            （年間処理量の前提が無ければ 1）
培養設備の償却 (円/kg)       = Σ(1系列の初期投資 ÷ 耐用年数) × 系列数 ÷ 年に作る量 ÷ 販売率
年ごとの固定費 (円/kg)       = Σ1系列の年額固定 × 系列数 ÷ 年に作る量 ÷ 販売率
製造拠点の作業 (円/kg)       = (Σ系列ごとの作業の年額 ＋ Σ拠点に1つの作業の年額) ÷ 年に作る量 ÷ 販売率
菌体量に比例する費用 (円/kg) = Σ毎kg菌体比例の単価 ÷ 販売率
菌体の製造原価 (円/kg)       = 上の4つの合計
                              （biomass_cost_per_kg_override に正の値があれば、「上書き値 ÷ 販売率」で置き換える）
```

- 年に作る量と系列数は `productionScaleOf`（上の「年に作る量と培養設備の系列」）。第1段は株と用途ごとに出す（`computeBiomassCost(bundle, 株, 用途)`）。
- **販売率**は `sales_rate`（%、既定100、1〜100に丸める）。生産した菌体のうち売れる割合。**売れ残りも作った分の費用はかかるので、第1段の費用（償却・固定費・作業・比例費）を売れた量で割る**（まさ 2026-09-13。この解釈を既定にする）。年間処理量から出す形では、売る量（年間処理量 × 使い切る菌体量）は変わらず、作る量が販売率で割った分だけ増える。系列ごとの費用と比例費は1kgあたり 1/販売率 倍になり、拠点に1つの作業は増えない。年間生産能力を入力で持つ形では、全行がちょうど 1/販売率 倍（50%で2倍）。前提が無い試算は100%と同じ。
- 上書き値は「販売率で割る前の、生産1kgあたりの原価」として入れる。
- 出力: `productionPerKg`（生産1kgあたり）、`computedPerKg`（売れた1kgあたり）、`perKg`（第2段で使う原価）、`salesRate`、`soldKgYear`、`capacityKgYear`（年に作る量）、`onsiteBiomassKgPerUnit` / `offsiteBiomassKgPerUnit`（年に作る量の割り算に出す方式ごとの菌体量）、`lineCapacityKgYear`、`productionLines`、`fromVolume`、`businessVolume`、`capexInitial`（系列の数だけ並べた総額）、`lineCapexInitial`、`tasksAnnual`（= `lineTasksAnnual` ＋ `siteTasksAnnual`）、行ごとの `rows`（`capex` / `fixed` / `tasks` / `variable`、いずれも販売率で割った後）。

### 第2段 用途別の処理原価（`computeCostModel`）

用途ごと、方式（オンサイト / オフサイト）× 装置（循環 / 投入）× 槽（オンサイトは既設 / 新設。槽を顧客が持つときは既設だけ。オフサイトは新設）。SX は4シナリオ、槽を SX が持つ試算は6シナリオ（オフサイトの行が無い試算は4シナリオ）。

```
必要吸着菌体量       = 対象物質濃度 × k_ppm ÷ 取り込み効率α        （オフサイトは offsite_target_concentration があればその濃さ）
ロス込必要菌体量     = ÷ 菌体回収率η
使い切る菌体量 (kg)  = ロス込 ÷ 菌体使用回数 ÷ 1000        （金属回収は菌体使用回数 = 1 で固定）
菌体費 (円/単位)     = 第1段の原価 × 使い切る菌体量
総コスト             = 菌体費 + 方式・装置に効く明細のうち SX が持つもの（resolveBearer）+ 方式・装置に効く作業のうち SX がやるもの（scopesFor・resolvePerformer、選んだ株と用途に効く行）+ 槽（SX が持つ新設のとき）
```

- **金属回収は菌体使用回数を1回で固定する**（`deriveCostBasis` の `reuseFixed`）。前提 `reuse_count` に金属回収の行や共通の行があっても読まない。使い回せるのは色素分解だけ（まさ 2026-09-13）。SX の金属回収の使用回数の前提は migration 397 で消した。
- 輸送の回数 `truckTripsPerYear` = 年間処理量 ÷ `truck_capacity_m3`（既定10）。`count_driver='truck_trip'` の作業が使う。

`basis` による年間発生額:

| basis | 年間発生額 |
|---|---|
| `初期投資配賦` | 数量 × 単価 × 年換算 ÷ 耐用年数 |
| `毎m³比例` | 数量 × 実効単価 × 年換算 × 年間処理量 |
| `バッチ連動` | 数量 × 単価 × 年換算 |
| `毎kg菌体比例` | 数量 × 実効単価 × 年換算 × 使い切る菌体量 × 年間処理量（製造拠点の行は第1段で1kgあたりへ畳む） |
| `年額固定` | 数量 × 単価 × 年換算 |
| `内訳` | 0 |

`price_rule` による実効単価:

| price_rule | 計算 |
|---|---|
| `null` | `unit_price` をそのまま |
| `module_swap` | モジュール単価 ÷ 耐用バッチ数 ÷ バッチ容量 |
| `power_circulation` / `power_injection` | 動力kW × HRT × 電力単価 ÷ バッチ容量 |
| `spent_disposal` | 円/kg-DCW = 脱水後の湿重量倍率 × 汚泥の処分単価（`毎kg菌体比例` と組む） |
| `co2_supply` | 前提 `co2_flue_gas` が `on` なら0円、それ以外は `unit_price`（液化炭酸ガスの買値）。migration 430 |
| `culture_loss` | 同じ群・同じ効く範囲・`毎kg菌体比例` の OPEX の行（`culture_loss` 以外）の 数量 × 実効単価 × 年の回数 の合計。明細の束（`items`）を渡さないときは `unit_price`。migration 430 |
| `biomass` / `broth` | 旧形式。`unit_price` × 旧基準値との比。二段階版の SX 明細では使わない |

- **人件費は作業リストで持つ**（`taskAmount`）。2026-09-13 まで明細の `price_rule` にあった `labor_batch` / `patrol` / `patrol_module` / `patrol_membrane` は作業リストへ移して廃止した（migration 395 で制約からも外した）。**人件費だけを抜いた総コスト（`totalWithoutLaborPerUnit` など）は計算も表示もしない**。
- `breakdown` は総コストの内訳で、**足すと総コストに一致する**。区分と並び（`BREAKDOWN_ORDER`、積み上げ棒の順と色の順）: 菌体費 `biomass` / 運ぶ（巡回・輸送）`transport` / 運転・保守・管理 `labor` / 菌体の後処理 `postProcess` / 消耗品・電力・放流 `consumables` / 設備と槽の償却 `capex`。
  - 運ぶ = `count_driver` が `visit`（菌体の巡回）か `truck_trip`（排液の輸送）の作業（`isTransportTask`）。運転・保守・管理 = それ以外の作業。
  - 各区分は `parts`（中身。大きい順で、足すと区分の額）を持つ。菌体費は第1段の行（培養設備の償却 / 年ごとの固定費 / 製造拠点の作業 / 培地・CO2・濃縮など）× 使い切る菌体量、運ぶは作業名、運転・保守・管理は作業の流れの段、後処理・消耗品・償却は明細名（CAPEX は中項目、OPEX は中項目と小項目の長い方）と槽。
- `breakdown` の運ぶ・運転・保守・管理は **SX がやる作業だけ**で作る。顧客がやる作業はどの区分にも入らない。
- `siteTaskAnnual` / `siteTaskPerUnit` / `siteTaskHours` は方式・装置に効く作業のうち **SX がやるもの**の年額・1単位・年間工数（製造拠点の作業は含まない。拠点全体の工数は `biomass.taskHoursAnnual`）。**顧客がやる作業の時間や円はシナリオに持たせない**（顧客側の時間は SX の試算の対象外。まさ 2026-09-14）。`transportPerUnit` は運ぶの額。`location` は `onsite` / `offsite`、`method` は `循環` / `投入`。
- `strainSpecificPerUnit` は株固有の行（閉鎖系の追加など）の合計で、現場の明細・作業と、第1段から配った分を足す。内訳の外側に「うち」として出す。
- `postProcessPerUnit` は `group_label` が `シアノ回収後処理` / `使用済み菌体の処分` の OPEX 明細のうち SX が持つもの。
- 確度の帯グラフは、明細と作業を行ごとに数え、第1段の各行は「1kgあたりの額 ÷ 販売率 × 使い切る菌体量」で配る。上書き値のときは上書きの前提の確度で1本にする。
- 株・用途・作業を持たない試算（`strains=[]`, `applications=[]`, `tasks` なし）は、用途なし1系列・4シナリオとして従来どおり計算する。
- `COST_ROLE_KEYS` は計算が読む role_key の一覧。画面の操作パネルはこの前提だけを並べる（ここに無い前提は動かしても総コストが変わらないため、読み物の「すべての前提」に「計算に使っていない」と出す）。`onsite_tank_bearer` は数字ではなく `value_text` で読む（`onsiteTankBearer`）。

### 作業の流れ（`computeTaskFlow`）

選んだ株・用途・方式・装置で発生する作業（`rowAppliesTo`）を、`sort_order` の順に `group_label`（段）で束ねる。段の順は、段に含まれる作業の最小の `sort_order`。

- 段ごとに、SX がやる作業の顧客1社分の年間工数 `siteHours`、製造拠点の年間工数 `productionHours`（拠点全体）、SX がやる作業のうち工数が未確認の作業の数、SX がやる作業の顧客1社分の年額、SX の原価の1単位あたりの額（製造拠点の作業は「年額 ÷ 年に作る量 ÷ 販売率 × 使い切る菌体量」で、系列ごとの作業はその用途で年に作る量の系列数で数える。上書き値のときは0。顧客がやる作業は含まない）を出す。作業の行は、その方式で実際に誰がやるか（`performer`: `sx` / `customer`）を持つ。顧客がやる作業は行として段に残すだけで、工数・年額・1単位・未確認の数のどれにも入れない。
- 合計の `siteHours` / `siteAnnual` / `sitePerUnit` は、同じ株・用途・方式・装置のシナリオの `siteTaskHours` / `siteTaskAnnual` / `siteTaskPerUnit` と一致する（契約チェック）。

### 試算中の変更（`project-cost-model-draft.ts`）

`pwa/src/lib/project-cost-model-draft.ts`（純関数）

- 保存値（DB から読んだ束）はそのまま持ち、画面での書き換えは**下書き**（`CostDraft`: `${entity}:${id}:${field}` → 値）に持つ。計算と表示は `applyDraft(保存値, 下書き)` で行い、結果には保存値からの差を出す。
- 書き換えられる欄: 前提の `value`（選択肢で持つ前提は `valueText`）、明細の `unitPrice` / `quantity` / `usefulLifeYears` / `bearer`（`sx` / `customer` / `site` だけ）、作業の `hoursPerOccurrence` / `countDriver` / `countPerYear` / `expensePerOccurrence` / `performer`（`sx` / `customer` / `site` だけ）、試算の `targetTotalCostPerUnit`。
- `setDraftValue` は、保存値と同じ値に戻すと下書きから消す。数字でない値、前提以外の負の値、空欄にできない欄の空欄は受け付けない。
- `draftToPatches` が下書きを API の patch（DB の列名）に変える。作業を「固定の回数」か「系列ごと」に変えるときは年間回数も同じ patch に入れる（DB の制約を満たすため）。

- 下書きと表示の選択（株・用途・方式・装置・槽）は、タブを行き来しても消えないようモジュールに持つ。**再読み込みで消える**。既定は自然株（自然株が無い試算は最初の株。まさ 2026-09-14）・オンサイト・直接投入・既設槽（槽を顧客が持つときは既設だけ）。

- 選択肢で持つ前提（オンサイトの槽を持つのは）は、数字の欄の代わりに選択肢（顧客 / SX）を出す。
- 書き換えた入力欄は AMD Blue の枠と面になり、保存値を title に出す。前提の欄は横に「戻す」を出す（表の狭い欄は出さず、上の一覧から戻す）。
- **保存**: admin だけ、上の一覧の「この値を保存」（1件）か「すべて保存」。保存したら `saveCostPatches` → キャッシュを捨てる → `fresh=1` で読み直す。保存できなかったときは理由を出し、下書きは残す。閲覧だけの人・ワークスペースでは保存ボタンを出さず、「保存はコックピットの管理者だけ。再読み込みすると消える」と出す。
- 色: 選択・現在地・保存は sky（`#027fdc`）。赤字は rose、目標超は amber で、必ず言葉を添える。試算の増減の矢印には色を付けない（試算の増減は良し悪しの判定ではない）。emerald は使わない。
