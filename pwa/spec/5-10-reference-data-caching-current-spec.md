# 参照系データのキャッシュ仕様（体感速度の既定設計）

> **この章は何か**: 画面が「開くたびに待たされる」のを設計段階で潰すための contract。
> どのデータをキャッシュし、どこに置き、どう捨て、何を機械で止めるかを決める。
> 全PJ共通の規範は `/Users/masa/projects/AGENTS.common.reference.md`「参照系データの体感速度」節。

## なぜこの章があるか

まさから繰り返し出ている指摘は同じ形をしている。

> 「モーダルを開いたときに◯◯が表示されるまでに時間がかかる。
> そもそも頻繁に変更される内容じゃないから、最初から設計上そうするべきだった」

原因も毎回同じで、めったに変わらない読み取り専用データを、画面を開くたびに
素の `fetch` で読み直していること。認証・DB往復・ペイロード転送を毎回払うので、
データ量が小さくても体感で1〜2秒かかる。一度直しても次の画面で同じ書き方が復活するため、
規範（この章）と guard（`pwa/scripts/check_reference_data_cache_contract.mjs`）を対にする。

## データの二分類

新しいデータ取得を書く前に、まずどちらかを決める。迷ったら参照系に倒す。

| 区分 | 定義 | 例 | 既定の扱い |
|---|---|---|---|
| **参照系** | 読み取り専用で、更新頻度が日〜週単位以上に低い | 一次選別スクリーニング帯、ルーブリック、マスタ（メンバー・PJ・機関）、確定済み評価、設定値、モデル定義 | 3層キャッシュを必ず通す |
| **可変系** | 秒〜分単位で変わる、または編集中の状態 | 残高、進行中タスク、通知、未保存の下書き、実行中ジョブの進捗 | キャッシュしない。毎回読む |

「一覧では最新でなくてよいが、編集画面では最新が要る」ものは参照系に置き、
編集の保存直後に明示的にキャッシュを捨てる（後述）。

## 0. 先に固定費を疑う

キャッシュ層を作る前に、**どの画面にも等しく乗る固定費**を確認する。
1画面のクエリを削るより効果が大きく、直せば全画面が速くなる。

| 固定費 | 確認方法 | AMD OS の現行 |
|---|---|---|
| サーバのリージョン | `vercel.json` の `regions` がDBと同じ地域か | `["hnd1"]`（東京。Supabase も東京） |
| 認証の往復回数 | `requireMember` / `requireAdmin` が1リクエストで何回DBへ出るか | JWT検証1回のみ（members 照合は30秒キャッシュ） |
| コールドスタート | 連続アクセスで初回だけ遅いか、毎回遅いか | — |

これを飛ばして個別クエリを最適化すると、実測で数字が動かず原因を見失う（2026-08-23 に実際にやった。後述）。

## 3層キャッシュ

参照系は次の3層をすべて通す。1層だけだと、別タブ・別セッション・コールドスタートのいずれかで穴が開く。

| 層 | 置き場所 | 効くケース | TTL |
|---|---|---|---|
| 1. サーバのプロセス内スナップショット | `src/lib/<domain>.ts`（`server-only`） | 別ユーザー・別セッションからの同じ読み取り | 既定5分 |
| 2. HTTP キャッシュ | API route の `Cache-Control` | 同じブラウザの再アクセス、リロード | `max-age=60, stale-while-revalidate=600` |
| 3. クライアントのモジュールキャッシュ | `src/lib/reference-data-cache.ts` | 画面遷移、モーダルの開き直し | 既定5分 |

### 1. サーバのプロセス内スナップショット

**一覧が必ず使う軽いデータはテーブル単位でまとめて1回読み、以後はメモリから配る。**
1リクエストにつき1行だけ読む設計は、往復回数がリクエスト数に比例するのでやらない。

ただし**重い列を含む詳細行まで全件先読みしてはいけない**。
帯の詳細を全件（約3MB）読むと1.3秒かかり、最初にアクセスした1人が必ずその待ちを食う。
軽いサマリはスナップショット、重い詳細は**キー単位で引いて貯める**、の2段構えにする。
実装の型は `src/lib/seed-screening-bands.ts`。

- 関連テーブルは `Promise.all` で並列に読む（直列で4本張ると往復が4回積む）
- PostgREST の1レスポンス上限（既定1000行）を跨いでも落とさないよう、`.range()` でページ読みする
  — ここを素の `select()` にすると、行が1000を超えた日に**黙って切り捨てられる**
- 同時アクセスは1本のロードへ束ねる（single-flight）。TTL 切れの瞬間に N 本走らせない
- `invalidate...Cache()` を export し、書き込み経路から呼べるようにする

### 2. HTTP キャッシュ

参照系の GET route は `Cache-Control` を明示する。既定の `no-store` に落とすと、
ブラウザ側で確実に往復が発生する。書き込み直後の確認用に `?fresh=1` を用意し、
そのときだけ `no-store` + サーバ層の強制再読込にする。

### 3. クライアントのモジュールキャッシュ

`src/lib/reference-data-cache.ts` が土台。ドメインごとに薄いクライアント層を1枚かぶせる
（例 `src/lib/seed-screening-bands-client.ts`）。画面は必ずそのクライアント層を通す。

- `peekReferenceData` … キャッシュ済みなら**同期で**返す。モーダルの初回描画を待たせない
- `loadReferenceData` … 無ければ1回だけ取得。同時呼び出しは束ねる
- `prefetchReferenceData` … 一覧行の `onMouseEnter` / `onFocus` で先読みする。
  マウスが乗ってからクリックが届くまでの数百ミリ秒で取得が終わるので、モーダルは開いた時点でデータを持っている
- `invalidateReferenceData(prefix)` … 保存直後に捨てる

## 表示の作法

キャッシュが外れた初回だけは待ちが出る。そのとき節が**あとから生えてくる**と、
「無いのか、遅いのか」が読み手に区別できない。参照系の節は次のどちらかにする。

- 骨組み（スケルトン）を先に出し、見出しと枠は最初から確定させる
- 一覧が既に持っているサマリ値があれば、それを先に描いて詳細だけ差し替える

`{data && <Section/>}` で節ごと消すのは、取得が遅いときに画面が跳ねるので使わない。

## 機械で止める（guard）

`pwa/scripts/check_reference_data_cache_contract.mjs`（`npm run test:reference-data-cache`）。
`pwa/scripts/deploy.sh` が本番反映の前に必ず走らせるので、違反したまま deploy できない。

| # | 契約 | 破ったときに起きること |
|---|---|---|
| 1 | 登録済み参照系エンドポイントは、専用クライアント層からしか `fetch` しない | 新しい画面が同じ遅さを再発させる |
| 2 | 参照系 route は `Cache-Control` を明示する | HTTP 層の再利用が効かない |
| 3 | 参照系クライアント層は `@/lib/reference-data-cache` を通す | 層だけ作ってキャッシュしていない状態になる |
| 4 | **ラチェット**: クライアントからの素の `/api` fetch は baseline に載っている既存分だけ許す | 未分類の取得が静かに増え続ける |

契約4を足したときの baseline は `pwa/scripts/reference_data_cache_baseline.json`。
2026-08-23 時点の実態をそのまま基準線にしたものなので、**中身が正しいという意味ではない**。
既存分にも参照系として直す価値があるものが混ざっている。増やさないことだけを保証する。

新しい取得を書いたときの分岐は2つだけ。

- 参照系 → `reference-data-cache` 経由のクライアント層を作る。baseline には足さない
- 可変系 → `reference_data_cache_baseline.json` の `reasons` に理由を書いて足す

## 適用例: 会社の記録（ホーム下段）

**直す前**: ホームの client component が、名簿・沿革・メディア掲載・写真台帳を含む
**9本のクエリをブラウザから `Promise.all` で投げ**、全部そろうまで節を描かなかった。
キャッシュは3層とも無し。画面を開くたびに払うので、下までスクロールしても
「会社コンテンツ読み込み中…」が残ることがあった（2026-08-27 に本番で再現を確認）。
どれも日〜週単位でしか変わらない参照系で、毎回読み直す理由が無かった。

**直した後**:

- サーバ: 9本を service client で並列に読み、組み立て済みの表示用データをプロセス内に5分持つ
  （同時アクセスは1本へ束ねる）。`invalidateCompanyContentCache()` を写真の書き込み経路から呼べる
- route: `requireMember()` + `portfolio` scope gate の後に service client を作り、
  `Cache-Control: private, max-age=60, stale-while-revalidate=600`
- クライアント: ホームは `company-content-client.ts` 経由。同じセッションで読み込み済みなら
  画面下まで来るのを待たずにそのまま描く（初回だけ従来どおり `IntersectionObserver` で遅延）

## 適用例: 一次選別スクリーニング帯

まさの指摘（2026-08-23「シーズリストのモーダルを開いたとき、一次選別スクリーニング帯以下が出るまで遅い」）の対応。

**直す前**: モーダルを開くたびに `/api/seeds/screening-bands?seedId=...` を素で叩き、
サーバ側で「帯1行」＋「根拠Lv用に seeds / seed_contact_log / seed_projects の3本」を
**直列**に読んでいた。Supabase への往復が1リクエストあたり4回。キャッシュは3層とも無し。

**直した後**:

- サーバ: サマリ帯と根拠Lvの3テーブルを**テーブル全体1回・並列**で読み、プロセス内に5分持つ。
  詳細行はシーズ単位で引いて同じく5分貯める（同時アクセスは1本へ束ねる）
- route: `Cache-Control: private, max-age=60, stale-while-revalidate=600`
- クライアント: 一覧・モーダル・AMD Score タブ・土壌シーズがすべて
  `seed-screening-bands-client.ts` 経由。一覧行の hover で詳細を先読みし、
  開いた時点で `peek` が当たるようにした
- 表示: 帯が未取得のあいだはスケルトンを出し、節が跳ねないようにした

### 実測（ローカルから東京リージョンへ直結、2026-08-23）

| クエリ | 中央値 |
|---|---|
| 旧: モーダル1回ぶん（帯1行＋根拠Lv3本を直列） | 138ms |
| 新: 帯 詳細1件だけ | 39ms |
| 新: 根拠Lv 3テーブル全件（並列） | 40ms |
| 新: 帯 サマリ全件（735行） | 184ms |
| （不採用）帯 詳細全件（q_evidence込み・約3MB） | 1333ms |

**詳細全件のスナップショットは最初に測って捨てた案**。1.3秒は「最初の1人が必ず待つ」形になり、
まさの指摘（開くたびに待たされる）を別の場所へ移すだけになる。
数字を見ずに「まとめて読めば速い」と決めないこと。

### 本番で測ったら、遅さの主因はDBではなかった（2026-08-23）

キャッシュを入れた後、まさのログイン済みブラウザから本番を測った。

| 測ったもの | 結果 |
|---|---|
| 帯 詳細1件（DBキャッシュ命中中・URLを毎回変えて計測） | 1081〜2126ms |
| そのときのサーバ側スナップショット齢 | 20秒→25秒と増加（＝DB再読込ゼロ） |
| 同一URLの2回目以降（HTTPキャッシュ命中） | 1〜4ms・転送量0 |

**DB往復がゼロなのに1.5秒かかっていた**。つまり遅さの主因はクエリではなく、
リクエストごとの固定費だった。内訳は2つ。

1. **Vercel関数のリージョン未指定**。`pwa/vercel.json` に `regions` が無く、既定の米国東海岸で動いていた。
   まさの端末（日本）→ Vercel（米国東海岸）→ Supabase（東京）と大陸を2往復していた。
   → `"regions": ["hnd1"]`（東京）を指定。**全APIに効く**
2. **認証で毎回2往復**。`requireMember` は `auth.getUser()`（JWT検証）と `members` 照合で
   Supabaseへ2回出ていた。`members` はめったに変わらない参照系なので照合結果だけを
   プロセス内に30秒持ち、往復を1回に減らした（`src/lib/supabase/api-auth.ts`）。
   **JWT検証はキャッシュしない** — ここを省くとログアウトや失効が効かなくなる

**教訓**: 「表示が遅い」を見たとき、クエリだけ見て直すと外す。
DBキャッシュを効かせた状態でもう一度測り、残った時間がどこに行っているかを先に確定させる。
リージョンと認証は、どの画面にも等しく乗る固定費なので、1画面の最適化より効果が大きい。

キャッシュが効く2回目以降は、この固定費も含めてネットワークに出ない（1〜4ms）。

副次的な修正として、帯・シーズの取得をページ読みにした。
帯は 2026-08-23 時点で853行あり、PostgREST の1000行上限に届いた時点で
**黙って切り捨てられる**状態だった（この修正で解消）。
