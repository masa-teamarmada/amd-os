# ゴールツリー

> **目的**: PJの計画を「やることの階層」ではなく「到達点から分かれた、分からないことをつぶす順序」として持つ。到達点を根に置き、問いを分解し、答えを出す行為をぶら下げ、答えが出たときに何が決まって何が新しく生まれたかまで一続きでたどれるようにする。

正本ステータス: 確定（まさ 2026-09-10、到達点・MS・ptは 2026-09-11）。実装済み。仕様変更はこのファイルと同じcommitで反映する。

**名称**: 2026-09-11 から「問いの木」ではなく **ゴールツリー** と呼ぶ。画面のタブ名は「論点・仮説」のまま（変えるかはまさへの確認事項）。設計の全体像と、pt・委託・検収の設計は [3-22](3-22-goal-tree-plan.md)。

## なぜ作り直したか

2026-09-10時点の実データ。

| 事実 | 数 |
|---|---|
| 目的・成立条件・工程を持つPJ | 4件（p19 / p25 / p30 / p00）のみ |
| SX（p21）の目的 / 成立条件 / 工程 | 0 / 0 / 0 |
| SXが実際に使っているもの | 論点17件・やること17件・技術試験22件 |
| どの工程にも成立条件にも接続されていない論点 | 62件中32件 |
| 「決着した」と記録された論点 | 0件 |

`目的 → 成立条件 → 工程` という階層は、最も進んでいるPJが使わずに済ませていた。論点はその階層の外に置かれ、決着の記録が一度も発生していない。閉じるのに仮説・根拠・検証・判断をすべて埋める必要があり、実務の速度に合わなかった。

まさ確定（2026-09-10）でこの階層を廃止し、問いの木を計画の背骨に置く。ZMP（p19）を含む既存の全PJデータを新構造へ移す。

## 型は3つ

11種類あった管理項目を3つへ畳む。

| 新 | 旧 |
|---|---|
| 問い | 目的 / 成立条件 / 論点 / 仮説 / 決めること |
| やること | 工程 / 予定日MS / やること / 検証 / 技術試験 / 決定後の行動 |
| 分かったこと | 根拠 / 反証 |

仮説を独立の型にしない。「より多くの油分を産出できる強化株は実現可能か」は答えの候補であると同時にそれ自体が問いであり、分ける理由がない。答えの候補は、親の問いにぶら下がる `alternative` の子として表す。

### 問い（`project_questions`）

答えが出れば閉じるもの。

| 列 | 内容 |
|---|---|
| `id` / `project_id` | |
| `parent_id` | 親の問い。NULLなら根。木であり、多重の親は持たない |
| `contribution` | 親から見たこの子の役割。`required`（これが解けないと親は解けない）/ `alternative`（これが解ければ親に答えが出る。他の代替は不要）。根はNULL |
| `title` | 問いの文 |
| `background` | 経緯・前提・成立条件の式など。結論で上書きせず積む |
| `question_kind` | `open`（分からないこと）/ `decision`（意思で決まること）/ `goal`（到達点）/ `milestone`（MS）。**到達点は根だけ、MSは到達点の直下だけ**。DBのCHECKとtrigger、APIの検査、画面の選択肢の3か所で同じ決まりを守る（2026-09-11 追加） |
| `status` | `open` / `answered` / `dropped`（追わないと決めた） |
| `answer` | 答え。1行で足りる |
| `answered_on` / `answered_by` | |
| `confidence` | `unknown` / `low` / `medium` / `high`。答えの確からしさ |
| `owner_label` / `due_date` | 誰が、いつまでに答えを出すか |
| `origin_kind` | `manual` / `meeting` / `automation` |
| `origin_ref` | 生まれた元（議事録ID等） |
| `origin_question_id` | どの問いを議論していて生まれたか。派生の記録 |
| `sort_order` | 同じ親の中での並び。手動並び替えの正本 |
| `last_verified_at` / `created_at` / `updated_at` / `deleted_at` / `version` / `client_token` | |

`origin_question_id` が「論点を整理すると新しい論点が出てくる」を保持する。答えを出す過程で生まれた枝が、どの議論から生えたかを失わない。

**到達点（`goal`）とMS（`milestone`）**（2026-09-11 追加、[3-22](3-22-goal-tree-plan.md) §3）。到達点は「シーズンの終わりにこうなっている」という状態で、木の根に置く。MSは到達点を成り立たせる条件で、到達点の直下だけに置き、`contribution='required'` で入る。MSはシーズンのマイルストーン（`value_milestones`）と対応し、対応は `project_question_milestones`（問い × MS、多対多）で持つ（Phase 1 で行を入れる）。到達点を消すと直下のMSは種類を論点へ戻してから根へ上がる — 「親を消しても子は消さない」と、MSの置き場所の決まりを両立させるため。定常業務のMS（定例運営、事務手続き、CEO業務）はツリーに出さず、MSリストにだけ置く。

### やること（`project_actions`）

実行すれば終わるもの。答えは出さない。

| 列 | 内容 |
|---|---|
| `id` / `project_id` | |
| `parent_id` | 親のやること。工程はこの入れ子で表す。深さの制限は設けない |
| `title` / `detail` | 何を、どうやって |
| `action_kind` | `work`（作業）/ `measure`（確かめる行為。測る・調べる・見積もる・相手に聞く） |
| `status` | `unassessed`（進捗未登録）/ `not_started`（着手していないと人が宣言した）/ `running` / `blocked` / `done` / `dropped`。既定は `unassessed` で、進捗率を実績として表示せず0%と偽らない |
| `owner_label` | |
| `planned_start` / `planned_end` / `actual_end` | 開始日と完了日が同じか両方NULLなら一点の予定日 |
| `date_certainty` | `confirmed` / `provisional` |
| `progress_pct` | |
| `blocker` | 詰まり |
| `done_criteria` / `done_evidence` | 完了条件と完了証跡 |
| `target` / `actual` / `unit` | 測定系のときだけ埋まる。目標値・実測値・単位 |
| `origin_kind` / `origin_ref` / `origin_question_id` | |
| `sort_order` / `last_verified_at` / 監査列 | |
| `estimated_pt` / `accepted_pt` | 見積ptと確定pt。小数1桁、0以上。0 は「やるが報酬には乗らない」（2026-09-11 追加、[3-22](3-22-goal-tree-plan.md) §6 原則6・原則10） |
| `accept_state` | `unassigned` / `assigned` / `accepted` / `negotiating`。担当が付くと `assigned` へ、全員外れると `unassigned` へ戻る（DBのtrigger）。受託の動き自体は Phase 2 |
| `accepted_at` / `accepted_by` / `reviewed_at` / `reviewed_by` / `review_result` | 受託と検収の記録。Phase 2 で使う |

担当は `project_action_owners`（やること × メンバー、多対多、`share` は NULL で均等）で持つ。既存の `owner_label` は、名簿にいない人（相手側の担当者、「研究側」のような役割名）を書く欄として残す。3-22 §7「届け先は `members` にいる人だけ」に合わせ、名簿にいない人は担当にしない。

`measure` は問いに答えを出すための行為で、`work` は答えが出た後に実行する作業。この区別が「枝が宙に浮いている」判定に効く。

### 分かったこと（`project_findings`）

事実と出どころ。

| 列 | 内容 |
|---|---|
| `id` / `project_id` | |
| `summary` | 何が分かったか |
| `finding_kind` | `supports` / `contradicts` / `neutral` / `missing`（分かっていないことが分かった） |
| `observed_on` | |
| `source_label` / `source_url` | 出どころ。外部情報は必ず出典を持つ |
| `confidence` | |
| `from_action_id` | どのやることの結果か。外部由来ならNULL |
| 監査列 | |

### つなぎ

| テーブル | 内容 |
|---|---|
| `project_question_actions` | 問い ↔ やること。多対多。ひとつの測定が複数の問いに答えることを表す |
| `project_question_findings` | 問い ↔ 分かったこと。多対多 |
| `project_action_dependencies` | やること間の前後関係。`finish_to_start` のみ |
| `project_action_owners` | やること ↔ メンバー。多対多（2026-09-11 追加） |
| `project_question_milestones` | 問い（MS）↔ シーズンのMS。多対多（2026-09-11 追加、行が入るのは Phase 1） |

問いの親子は単一親の木、やることと問いの結び付きは網。SXの「総脂肪酸量と炭素数の分布を1回測ると、油の量と炭化水素株の両方に答えが出る」がこの形で入る。

## 判定

画面が出す状態はすべて導出値で、人が直接編集しない。

### 問いの状態

| 状態 | 条件 |
|---|---|
| 判断できる | `required` の子がすべて `answered` か `dropped`、`alternative` の子がある場合は1件以上 `answered`、紐づく `measure` がすべて `done` |
| 手が止まっている | 未閉じで、子もやることも1件も無い |
| 枝が死んだ | `alternative` の子がすべて `dropped`、または `required` の子が1件でも `dropped` |
| 期限超過 | 未閉じで、自分または子孫の最も近い期限が基準日より前 |
| 更新切れ | 自分と子孫の `last_verified_at` の最新が7日以上前。日付欠損も更新切れ |

### やることの状態（2026-09-11 追加）

| 状態 | 条件 |
|---|---|
| 未アサイン | 未完了で、担当（`project_action_owners`）が空か、期限（`planned_end`）が空。会議中にタイトルだけで足したまま、まだ割り振られていない |
| 受託待ち / 検収待ち | Phase 2。`accept_state` と検収の記録から導く |

「配りすぎ」「回収候補」は Phase 1（MSのptと配下の見積ptを突き合わせる）。

**子がすべて片付いても親を自動で閉じない。** 「判断できる」として判断キューへ出すところまでで止め、答えを書くのは人。

**枝が死んだ問いも自動で `dropped` にしない。** 警告を出し、親の判断材料として見せる。

**親を消しても子は消さない。** 子は根へ上がり、`contribution` は外れる。根に「必須」の印だけが残ると、何に対して必須なのか読めなくなるため。読み込み側も、親が見つからない子を同じ扱いにする。

**閉じた問いは同じ並びの末尾へ落とす。** 未閉じが上に来ないと、いま何が残っているのかを目で拾えない。

### 手を打つべき問いの示し方

未閉じの問いのうち、`判断できる` / `手が止まっている` / `枝が死んだ` / 期限超過 のいずれかに当たるものを、**木の中でその行のまま強調する**。左の縦線と地色で示し、状態ごとに色を変える。

上部へ抜き出した一覧は作らない（まさ 2026-09-10「上にピックアップされても、それがどの論点のどの部分なのかが分からん」）。抜き出すと親子の文脈が切れ、拾った問いがどの大きな問いの下にあるのかを読み手が復元できなくなる。

**未アサインのやること**も同じで、行の中に印を出すだけにする。ヘッダーの「未アサイン n件」は押せて、押すと畳まれた枝を開いて木の中の最初の該当行へ移る（2026-09-11 追加）。件数が多く出るPJがあるので（2026-09-11 の実データで SX 40/50件、ZMP 14/66件）、印は警告色にしない。

初期表示では、強調される問いへ至る道をすべて開く。畳まれたままだと強調しても目に入らない。

ヘッダーには件数だけを出す（問い / 未閉じ / 判断できる / 手が止まっている / 枝が死んだ / 期限超過 / 答えが出た）。

### 並び替えと親の付け替え

行の左のつまみを掴んで動かす。**上下の縁へ落とすと同じ親の中で並びが変わり、行の真ん中へ落とすとその問いの子になる。** 並び替えと付け替えを1つの操作でやり、ボタンは増やさない（まさ 2026-09-10「ボタンが無駄に増えるとUXがどんどん悪くなる」）。

まさが並びを手で決める理由は「先に解決できるものや重要なものを上にしたい」から。自動ソートで上書きしない。

| 決まり | 内容 |
|---|---|
| 掴んでいる見え方 | 行の複製がカーソルへ追従する（`position: fixed` + `translate3d`）。複製は body 直下へ出るのでCSS変数の継承が切れる。掴んだ行の computed style から色を移す |
| 落とし先の表示 | 兄弟として挿すときは上下の線、子にするときは枠と地色 |
| 保存 | `reorder_project_questions`（DB関数）1回。親の付け替えと同じ親の中の採番を同じトランザクションで確定する |
| 採番 | 同じ親の中を10刻みで振り直す。間に挿す余地を残す |
| `contribution` | 根へ出すと外れる。子へ入れるときに未設定なら `required` から始める |
| 循環の防止 | 自分の子孫の下へは動かせない。画面で先に止め、DB関数でも弾く |
| 取り消し | Esc。掴んでいる複製と自動スクロールを片付ける |
| 端でのスクロール | 上下120px以内に居るあいだは送り続ける。指を止めても止まらない |

### 木の見せ方

**やることも木の子として出す**（まさ 2026-09-10「TODOがあるなら、その論点の子として追加しないとじゃないの?」）。問いの下に何が積まれているかを1つの木で読む。ひとつのやることが複数の問いに効くときは、その問いすべての下に出る。

子を足す入口は「子を追加」の1つだけで、種類をフォームで選ぶ。ボタンを種類ごとに置かない。

| 選択肢 | 実体 |
|---|---|
| MS | `question_kind='milestone'` の問い。**到達点の行でだけ選べる** |
| 論点 | `contribution='required'` の問い |
| 仮説 | `contribution='alternative'` の問い |
| 決めること | `question_kind='decision'` の問い |
| やること・確かめる | `action_kind='measure'` のやること |
| やること・作業 | `action_kind='work'` のやること |

到達点は親を持たないので、この入口からは作れない。木の頭に「到達点を追加」を1つだけ置く。

階層は罫線（`├` `└` と祖先の `│`）で示す。インデントの空白だけでは、どこまでが同じ親の下なのかが読めない（まさ 2026-09-10）。あわせて次を守る。

- **1階層につき2枡進める。** 罫線の枡と開閉マークの枡を同じ幅（15px）にすると、**子の `├` が親のタイトルの1文字目の真下**へ来る（まさ 2026-09-10「子側の『├』は『バイオディーゼル事業〜』の『バ』の下にないと変」）。枡と開閉マークの幅が違うと、この対応が崩れる。
- **印（必須 / 代替 / 決める / 確かめる）はタイトルの後ろへ置く。** 前に置くと幅が可変なぶん、親のタイトル位置が行ごとに動いて子の罫線と合わなくなる。
- **罫線とタイトルのあいだに余白を入れない。** その分だけ子の `├` が左へずれる。
- **根の行は左端まで寄せる**（まさ「大元の親はもっと左側にないと変」）。
- **状態は丸で示す。** 縦棒は罫線と重なって読みにくい（まさ「丸の方が信号っぽい」）。タイトルの後ろに8pxの丸を置く。
- **子を持つ問いはタイトルを太字にする。** 枝の分かれ目を字面で分からせる。
- 行の高さは詰める。1行あたりの上下余白は2px。

画面に「問いの木」という名前は出さない（まさ 2026-09-10「いらない」）。件数は`論点`と数える。

## 画面

問いの木は**PJワークスペースの`論点・仮説`タブの中身そのもの**である（`QuestionTreeView` を `embedded` で描画）。専用ページは作らない（まさ確定 2026-09-10「新たなコンテンツにしないで、論点仮説タブの中身をそれにして」）。旧・6層リスト（論点カード／絞り込み／手動並び替え）は同じcommitで撤去した。

| 面 | 内容 |
|---|---|
| 木 | 問いの木。状態・担当・次の期限・残っている確認の件数つき |
| 詳細 | 行を押すと**重畳モーダル**で開く。背景・答え・ぶら下がるやること・分かったこと・派生した問いを同じ場所で読み書きする |
| 末尾 | どの問いにもつながっていないやること |
| ガント | **同じ画面の別モード**（`mode="gantt"`）。左列がゴールツリー、右列のバーがやること。工程レーンは持たない（2026-09-11 実装。ガントタブの中身がこれになった） |

**ガントは別コンポーネントにしない。** 木・詳細モーダル・その場編集・担当の付け外し・保存経路をタブ間で共有し、どちらの面で直しても同じ1行が変わる（[3-22](3-22-goal-tree-plan.md) §2）。行の右側だけを入れ替える。

| ガントで足すもの | 内容 |
|---|---|
| 横軸 | やることの日程と基準日から決める。月の区切りと今日の縦線 |
| バー | やること（`planned_start` / `planned_end`）。掴んで移動・開始・完了の3操作。期限だけのものは一点として引く |
| 細い線 | 問いの行に出す、配下やることの広がり。人が編集する値ではない |
| 前後関係 | バー右の常設「＋」で起点を決め、次に押したバーが後ろになる（Escでやめる）。既存の線はバーの実座標から引き、やることの詳細から外せる |
| 日程未設定 | 期限の無いやることを下にまとめる。**ここで付けるのは日程だけ**。担当と見積ptはツリーのやることの詳細で付ける |

行の高さは木と同じ密度に揃える。タブを切り替えたときに、同じ木が違う高さで見えると別物に読めるため。

詳細を行の下へ展開しない（まさ 2026-09-10「トグルで開くんじゃなくてモーダルにしてくれた方が分かりやすい」）。背景欄は長く積むため、行の下に開くと木が縦に伸びて上下の文脈が飛ぶ。

モーダルは `createPortal` で `document.body` 直下へ出し、`useModalContainment` で背面のスクロールとfocusを止める。開閉前後で `scrollY` を変えない。**CSS変数は `.page` と `.backdrop` の両方で定義する** — portal で body 直下へ出た `.backdrop` は `.page` の子孫ではないので、片方だけだとモーダルの地色と文字色が未定義になって透ける。

モーダルの見出しには根からの道をパンくずで出し、押すとその問いの詳細へ移る。開いた先でも「どの問いのどの部分か」を見失わせない。

**詳細の各項目は、値を押すとその位置だけが入力欄へ変わる**（まさ 2026-09-10「それぞれの枠のクリックで編集できるようにして」）。担当・期限・確からしさ・種類・親との関係・見出し・背景・答え・取り下げた理由が対象。導出値（状態・次の期限・最終更新）は `（自動）` と付けて押せなくする。人が触れない値を押せるように見せない。

**直せる欄は、読んでいる状態でも入力欄の枠（1px の実線・白地・`cursor: text`）を見せる。** 点線の下線だけでは押せることに気づけなかった（まさ 2026-09-10「まだ編集できないよ」— 機能は動いていたが、見た目が読み取り専用に見えていた）。

**読んでいるときと編集中で欄の大きさを変えない**（まさ 2026-09-10「入力状態になると欄の大きさが変わるのやめて。混乱する」）。複数行の欄は `textarea` を中身の高さへ合わせ、1行の欄は読んでいるときも折り返さず1行に留める。余白・字送り・枠幅も読み取りと編集で同じ値を使う。

**やることも押せば詳細が開く。** 問いと同じモーダルで、種類・状態・担当メモ・期限・着手予定・完了日・**見積pt**・目標値・実測値・単位・見出し・方法条件・完了条件・完了証跡・詰まりをその場で直せる。末尾に「これが答えを出す論点」を出し、押すとその論点の詳細へ移る。

**担当（複数可）**は名簿から押して付け外しする（2026-09-11 追加）。押した瞬間に保存し、フォームの保存を挟まない — 担当が付いた瞬間が委託にあたるため（[3-22](3-22-goal-tree-plan.md) §4）。名簿は在籍者をそのまま出し、人を選り分けない。**前後関係**も同じモーダルで読み、外せる。

担当・期限・見積ptを決めるのは、まさかPMが Codex / Claude のセッションでえいみと話しながら決め、えいみが更新APIで書き込む（3-22 §4、まさ確定 2026-09-11）。人が手でひとつずつ付ける運用にも、自動バッチにもしない。**画面のこれらの入力欄は、あとから直す入口として残す。** 提案用の列も採用ボタンも足さない。

### 割り振りセッションが使うAPI（2026-09-11 追加）

画面ではなくセッションから叩く。どちらも `canManage` が要る。

| 経路 | 内容 |
|---|---|
| `GET /api/project/{id}/question-tree?view=unassigned` | 未アサインのTODOを、**到達点からの道**（到達点 → MS → 論点）・所属MS・完了条件・前後関係つきで返す。あわせて名簿と、MSごとの配分済みpt・TODO件数・未アサイン件数を返す。3-22 §4「えいみが読むもの」の1回目に要るものをこれ1本で揃える |
| `PATCH { resource: "action_bulk", items: [...] }` | 決まった割り当てをまとめて書き込む。`items` は `{ action_id, planned_start?, planned_end?, estimated_pt?, member_ids? }` の配列で、**キーが無い項目は触らない**。`member_ids` を渡したときだけ担当を入れ替える。1回200件まで |

まとめ書き込みは DB関数 `apply_goal_tree_assignments` の**1トランザクション**で、全部入るか何も入らないかにする。1件ずつのPATCHを何十回も投げると、途中で落ちたときに半端に入って、どこまで書けたのかを人が数え直すことになるため。別PJのTODOや名簿にいない人が1件でも混ざれば、手前の項目ごと巻き戻る。

書いたあとは同じ `view=unassigned` を読み戻して件数を報告する（3-22 §4「書く前に差分を見せ、書いたあと読み戻して件数を報告する」）。

`目的構造`タブは廃止する。

## つくよみが拾うもの

つくよみの役割は**書き漏らしの検出**であって、議事録から全部を作ることではない（まさ確定 2026-09-11）。

まさは会議中に自分でこのタブへ書き足す。論点の分解そのものは Claude / Codex のセッションでえいみと相談しながら進める。つくよみが担うのは、**そこで忘れたり書き漏らしたりしたものを毎日拾うこと**だけ。

- **入力**: 前日以降の議事録（`project_meeting_summaries.narrative_md`）。
- **照合**: 既存の木（`project_questions` / `project_actions`）のタイトルと突き合わせ、**記録に出ているのに木へ無いものだけ**を出す。文字列一致ではなく意味で照合する。
- **出力**: `review_state='proposed'` で入れる。木へはつながず、`proposed_parent_id` / `proposed_contribution` / `proposal_reason` に「どこへ付くと考えたか」と「なぜそう考えたか」を添える。
- **件数**: 1回の巡回でPJあたり最大5件。多すぎると読まれない。
- **確定**: 画面の「つくよみが拾った、まだ木に無いもの」で、`木に入れる`（承認）か `いらない`（論理削除）を人が押す。承認で初めて `parent_id` と線が入る。却下は論理削除にして、同じものを次の巡回で拾い直させない。
- **経路**: 抽出は outbox JSON を吐くだけで、DBへは直接書かない。`pwa/scripts/apply_question_tree_outbox.mjs` が取り込む（既存のD-6経営ハイライトと同じ形）。

### daily 検出ルーチン

Codex automation `4-35` が毎日04:35 JSTに動く。前日00:00 JST以降の開催済み議事録を読み、PJごとの accepted / 提案中 / 却下済みの問い・やることと意味で照合する。正本手順は `pwa/scheduled-tasks/amd-os-l11-question-extract/SKILL.md`。

- 出力は問いとやることだけ。議事録の「次の一手」を全件転記せず、既存・提案中・却下済みと同じ意味のものを除く。
- 問いとやることの合計でPJあたり最大5件。親候補は accepted かつ未削除の問いに限定し、候補IDと理由を必須にする。
- `client_token` はPJ・議事録・種類・正規化した内容から決定的に作る。取り込み側は `on_conflict` に依存せず、既存・提案中・却下済みのtokenを先に読んでから新規だけをPOSTする。同じoutbox内の重複も除く。
- 非LLM LaunchAgent `jp.teamarmada.amd-os-question-tree-outbox-applier` が5分ごとにoutboxを確認する。抽出automationはGETとJSON作成だけで、DBを直接書かない。
