# PWA UIデザインコード

> **この章は何か**: AMD OS PWAの業務画面で、情報密度・比較可能性・状態表現を一貫させるための実装規約。特定コンポーネントの見た目ではなく、今後の新規画面と改修に共通する確定仕様。

## 目的

対象画面の利用権限を持つ人が業務画面を開いたとき、スクロールや個別カードの開閉より先に、全体像・異常・未確認・次に触る場所を数秒で判断できる状態を作る。PJワークスペースではAMD内部・外部を問わず、当該PJメンバーが同じ共有情報を同じ視覚体系で読む。業務データを大きなカードへ1件ずつ置くのではなく、同種の項目を同じ軸で比較できることを優先する。

## 情報密度

- タスク/MSの共有root editorは、desktopで内容と担当・日程を左右に配置する（wide最大1120px）。短文のために大きいtextareaを縦積みせず、主要入力と保存を1440×900で同時に確認する。mobileは16px入力・44px操作と可変本文スクロールを維持する。契約テストは`test:theme-history`。

- 比較対象の一覧は、原則として表または同じ列構造の高密度行にする。1件ずつ独立した大型カードへ分解しない。
- 既知の中核一覧が **10件以下なら全件** を、`desktop 1440×900` の実寸で同一セクション内に表示する。ページ共通ヘッダーなどの外枠を含めても、一覧の確認に何度もスクロールさせない。
- desktopの比較行は原則 **44〜64px**。1行で読めない本文は2行までに抑え、完全な説明・根拠・編集フォームはダイアログや詳細面へ段階的に開示する。
- 反復する行操作は32〜36px程度のコンパクトなボタンにし、行幅いっぱい・高さ60px超の同一ボタンを各行へ並べない。mobileでは操作領域44px以上を保つ。
- 件数、全体判定、異常・要対応・未確認・安全の内訳など、一覧を解釈する要約を一覧より先に置く。ただし件数だけを品質・確率・進捗率の代替にしない。
- 一覧に意味の異なる運用群がある場合、タブやfilterで一方を隠さず、群見出しで分けたうえで同じ画面へ同時表示する。比較軸が逆方向なら、群ごとに段階名と「どちらへ進むと良い/悪いか」を明記する。
- 余白は4px基準で組み、情報階層の分離に必要な分だけ使う。カード内の大きな上下余白や、同じ意味の見出し・説明・操作の重複で縦幅を消費しない。

## 状態表現

- **未確認を安全扱いしない**。データがない状態と、根拠を確認して異常なしとした状態を必ず分ける。
- 全体判定を出す場合、重大状態、要対応、要観察、未確認、安全の優先順位と集計式を純粋関数またはサーバー側の同じ契約へ固定する。色だけで判定を伝えず、名称と件数を併記する。
- 二値で扱う根拠がない連続的な状態を「ある/ない」へ潰さない。段階数は判断に必要な最小限とし、各段階を観測可能な言葉で定義する。
- rose/redは発生・逸脱などの重大状態、amberは明確な悪化・未整備・整備中、skyは要観察・実装済み、emeraldは根拠確認済みの安全、slateは未確認または中立に限定する。
- 主要操作をすべて同じ強い色にしない。通常の状態更新は中立、追加は標準操作、重大状態だけを危険色にする。

## 色役割とOS統一

- 通常のOS業務画面の主色はsky（`--amd-action: #027FDC`）と白・slateに固定する。PJ名、技術領域、機能名から連想した色を、画面全体、選択、現在地、focus、追加、保存、DnDへ持ち込まない。PJ固有色が必要な場合も、識別用の小さな印に限定し、操作体系を塗り替えない。
- emeraldは、根拠確認済みの安全・完了・成功だけに使う。`active`、`selected`、`current`、当方ボール、進行中、通常リンク、通常CTAには使わない。未確認と保留はslate、注意と当方アクション待ちはamber、重大状態はrose/redを使い、必ず文言または記号を併記する。
- 通常画面の実装は`globals.css`の`--amd-action* / --amd-success* / --amd-warning* / --amd-ink / --amd-muted / --amd-line / --amd-surface*`を使う。役割不明の`--green`やfeature-localな主色トークンを新設しない。
- PJワークスペースはコックピット埋込と共有ページの双方で同じcomponent rootを使うため、mount rootにも`--amd-*`の確定値を置く。global CSS chunkの分割・cache状態に左右されず、skyの構造色、emeraldの完了色、amberの注意色が必ず解決されなければならない。変数未解決を透明・黒へのfallbackとして放置しない。
- `npm run test:ui-design-code`は、PJワークスペースで退役済みteal主色が復活していないこと、ガント・目的構造の操作色がskyであること、emeraldが充足・完了表示に限定されていることを検査する。`test:critical-ui`と本番deploy前ゲートから必ず実行する。

## Responsive契約

- desktop基準は `desktop 1440×900`。列の位置を揃え、全件比較と全体要約を同時に成立させる。
- mobile基準は `mobile 390×844`。横スクロールへ逃がさず、行内の方式・型・状態を先頭に置き、内容を短い縦積みに組み替える。
- desktopをそのまま縮小して文字や操作を小さくしない。mobileの44px操作領域と本文の可読性を保ちつつ、装飾的な余白は増やさない。

## 実装・検証ゲート

1. 実装前に、利用者が最初の5秒で比較する軸と、一覧より先に必要な全体判定を決める。
2. `desktop 1440×900` と `mobile 390×844` の実寸でブラウザ確認する。
3. desktopでは、10件以下の中核一覧が全件見えているか、反復行の実測高が44〜64pxか、同じ大型操作が縦に反復していないかを確認する。
4. mobileでは、横方向の本文切れ、画面外へ逃げた操作、44px未満の主要操作がないかを確認する。
5. 未確認が安全件数へ加算されていないことを、集計関数の単体テストと画面表示の両方で確認する。

このゲートを満たさない画面は、機能が動いていてもUI完了としない。

## キラー要素カタログへの適用例

`CockpitKillerFactorCatalog` は、全体判定と5区分件数を先頭に置き、その下へ予防統制・常時監視をfilterなしの独立した群として同時表示する。予防統制は `未整備 → 整備中 → 実装済 → 運用確認済` の成熟度、常時監視は `兆候なし → 要観察 → 明確な悪化 → 重大事象` の悪化度であり、同じ段階番号でも進行方向の意味を混同しない。desktopでは初版7件を一画面で比較し、状態操作だけをコンパクトな反復ボタンにする。予防統制の詳細入力、監視状態の根拠、共通要素追加はダイアログへ分離する。`unchecked` は「未確認」であり、`clear` または `controlled` になるまで安全件数へ含めない。
