# PJ週次管制画面 仕様

> **目的**: 計画の再作成ではなく、既に管理されている計画・進捗から「先週からの変化」「今回決めること」「決定後の介入」を週次会議で短時間に確認する。論点・仮説を担当・期限・検証・根拠・判断へ接続し、放置を防ぐ。

## 正本境界

- 正規画面は `/project/[projectId]/workspace`。`SxWeeklyControlDashboard`をPJワークスペース本体として表示する。
- 旧 `/project/[projectId]/weekly-control` は正規workspaceへredirectする互換URL。独立画面・独立状態は持たない。
- 新画面はUIを先に固定する。週次差分の自動抽出が未接続の項目は、0件・変化なしと断定せず `抽出接続待ち` と表示する。
- ガントと関係先はこの画面から手動修正でき、手動で確認・保存した現在値を正本とする。将来の自動抽出は既存値を直接上書きせず、差分候補として人の確認へ回す。
- H1見出しは `SolvioraX PJワークスペース` の固定文言。プロジェクト名を動的に埋め込まない。

## 2026-08-04 現行ガント契約（本文中の旧工程表記より優先）

- 週次管制の利用者に見せる計画単位は **タスク** と **MS** の2つだけとする。`phase` は既存データ・外部キーを保つための内部互換コンテナであり、名称・行・選択肢・パンくず・モーダルに出さない。
- 全体ガントは事業開発／技術開発／組織開発の3レーンだけ。タスクはレーン内で親子をネストし、各レーン末尾の常設 `＋ 新規タスク` 行から追加する。親子の変更は左のグリップを親タスクへドラッグし、レーン見出しへ戻すと最上位タスクになる。工程選択・親タスク選択のフォームは置かない。
- MSはタスク行や親行にはせず、所属レーンの全行を縦断するMSマーカーとして表示する。日程があるMSは日付位置にレーンを縦断する幅12pxのゲート帯（v3.58.14。旧・1px縦線＋◇）、日程未設定のMSは同じレーン見出し帯に同じ幅のキャップと名称を置く。設立ゲート2件は塗りを濃く境界線を2pxにして通常MSと区別する。設立条件のMSも独立レーン／カード／親行にせず、事業開発または組織開発のレーン全体にかかる。マーカー名は必ずMSレコードの`title`をそのまま表示し、`gate`は達成条件の短い補助名として表示名の代わりに使わない。大きい既存計画レコードは同名の最上位タスクとして残し、2026-08-02に手順例としてseedした未着手・日程なしの細かい12タスクはガントに出さない。MSの達成はMS自身の状態と完了証跡で判定し、見えないタスク一覧には依存させない。
- MS／タスクの◇・バー・名称を押すと、ガント上の1枚の詳細モーダルを開く。値を押すと、その値の場所だけが入力欄へ置き換わる。タイトルはモーダルヘッダーそのものを直接置き換える。別の編集カード、共有トレイ、第二のモーダルは作らない。
- 新規MSはガントの空白日付を押し、`MSを追加する？` の確認でYを選んだ後に同じ作成フォームを開く。必須は配置するグループ（複数選択可）・MS名・予定日のみ。完了条件は任意とする。

## 画面構造

1. **PJ全体の管制入口（旧・週次状態帯を再構成）**: 工程・タスク・論点・仮説・検証・判断・action・関係先保有事項を`sxProjectOwnerLoads`が正規化した同じ未完了作業単位の共通母集団から、`停止 / 期限超過 / 7日以内 / 担当不明 / 期限なし / 判断待ち`の6バケットをクリック可能な帯で表示する。算出値自体は編集させず、バケットを押すと同じ帯の直下へ該当元項目一覧（種別・担当・期限・影響工程つき）を絞り込み表示し、一覧の各項目を押すと必ず元の編集文脈へ移動する（工程/タスクはガント該当行・詳細を全画面モーダルで開く、論点/仮説/検証/判断/actionは該当論点/仮説/検証/判断/actionレコードそのものを開くroot editorモーダル）。検証（`kind: "validation"`）は`edit_validation`で押した`SxValidationRun`そのものを開き、仮説・判断・actionと同様、IDが一致するレコードを見つけられない場合は親論点編集へ黙ってフォールバックせず「元の項目を見つけられなかったよ」のnoticeで終える。工程/タスク/論点系（論点・仮説・検証・判断・action）は対象issueと子recordのID・存在をすべて検証し、次に開く編集先を組み立ててからだけ既存のworkloadFilter絞り込み・詳細/plan field editor・ガント選択などの既存overlay stateを一括解除する。無効IDのクリックはnoticeだけを出し、既存の詳細・editor・絞り込みは閉じない。論点系root editorは全画面backdropの重畳モーダルであり、開く前にガント側の選択（工程/タスク）を必ず解除し、背景ページはスクロールしない（開閉前後でscrollYを変えない）。関係先由来の項目はスクロールせず、`SxProjectWorkUnit.originResource`（`partner_work_item` / `commitment` / `partner_next_action`）と`recordId`/`partnerId`から対象レコードを直接引いて、由来別の単一編集モーダルを直接開く（`partner_work_item`は既存の保有事項編集フォーム、`commitment`は約束・次アクション専用の編集フォーム、`partner_next_action`＝構造化保有事項が無いフォールバック行は関係先編集のうち`次にやること / 当方担当 / 期限 / 期限精度 / 現在の保有側 / 現在の担当`の6項目だけに絞ったフォーム）。IDの一致だけで別resourceへ探索をフォールバックしない。開く前に選択中の詳細/インラインfieldエディタは閉じ、開くモーダルは常に1つだけにする。静的な5枚のKPIカードとゲート専用カウントは廃止した。今週入力（人員配分の入力人数）は作業遅延の6バケットと混ぜず、7.データ接続状況側だけに表示する。
2. **PJ全体の担当負荷**: 工程、タスク、必須ゲート、論点、仮説、検証、判断、action、関係先保有事項を同じ未完了作業単位へ正規化し、担当ごとに `停止 / 期限超過 / 7日内 / 期限なし / 全未完了 / 影響ゲート` を表示する。関係先だけの件数をPJ全体負荷として扱わない。行は1で使う共通母集団と同じ`SxProjectWorkUnit`を使い、各行を押すと1と同じ導線で元の編集文脈へ移動する（dead endにしない、aria-labelは実動作どおり「〜を編集」）。desktop（`lg`以上）の閉じた担当者行は左右2カラムに並ぶが、実体は`OwnerLoadColumn`という完全に独立したcolumn要素で、`partitionOwnerLoadColumns()`（`src/lib/sx-project-owner-load.ts`）が担当者配列を偶数index=左列・奇数index=右列のrow-major順で分割する（前半/後半split=`Math.ceil(length/2)`ではない。旧CSS gridの暗黙行ペアリングと同じ見た目のペア順を独立column構造でも保つため）。mobile（`lg`未満）はこの分割結果を連結せず、常に元の担当者配列順を単独DOMで描画する（連結だと`[0,2,4,1,3,5]`という別順序になるため）。desktop用2列DOMは`hidden lg:grid`、mobile用単列DOMは`lg:hidden`で常に片方だけをa11y treeへ出し、重複ノードを作らない。desktop 2列gridは`lg:items-start`を持ち、各`OwnerLoadColumn`はgrid行の高さ（＝展開している側の高さ）へstretchせず、自列の内容高さだけで止まる（`items-start`が無いとalign-items:stretchの既定でOwnerLoadColumn自身の`bg-[#d9cfde]`背景がgrid行高さへ伸び、片側detailsを開いた反対列の下に紫の空白帯として実ブラウザで見える）。gridコンテナ自体と外側`section`の大面積背景は生成り`#fffdf7`とし、左右境界の1px線はgapの背景色ではなく、`relative`コンテナ内の`aria-hidden`な独立absolute 1px divider（`inset-y-0 left-1/2`、`bg-[#d9cfde]`）で描く。各`OwnerLoadColumn`内部のdetails間1px区切りだけは列ローカルな`gap-px bg-[#d9cfde]`のまま維持する（この背景は列が自列高さで自己完結するため伸びない）。片側のdetailsを展開しても反対列のカード高さ・次カードのY座標は変わらない。
3. **週次変化レール**: `先週→今週`、`今回の会議`、`決定→介入` の3段。差分未接続はプレースホルダーのままにする。

## 論点・仮説の放置防止

### 段階

| 段階 | 判定 |
|---|---|
| 要整理 | 未解決で、検証中・判断待ち・完了の条件を満たさない |
| 検証中 | 論点/仮説が `validating`、または検証が `planned/running` |
| 判断待ち | `decision_needed`、未決の意思決定、または `validated` 仮説がある |
| 決定・棄却 | 論点が `closed/decided`、または全仮説が `rejected/decided` |

段階と警報は別に扱う。期限超過・更新切れは列を移動する条件ではなく、どの段階でも重ねて表示する。
決定・棄却列でも未完了の決定後actionがあれば要フォローへ残し、判断だけ記録して実行が忘れられる状態を作らない。

### 警報

- **要フォロー**: 未完了で、担当不明、次の期限なし、仮説なし、検証中なのに検証予定なし、期限超過、更新切れのいずれか。
- **次の期限**: 論点、活動中の仮説、計画/実施/停止中の検証、未決判断、未完了actionから最も近い日を採用する。
- **最終更新**: 親論点だけでなく、仮説・根拠・判断・actionの `lastVerifiedAt` の最新日を採用する。子だけを更新した論点を更新切れにしない。
- **更新切れ**: 最終更新から7日以上。日付欠損も更新切れとして扱い、0日扱いしない。
- **期限超過**: 未完了論点の次の期限が基準日より前。完了済み論点へ赤警報を残さない。

## 書き込み契約

画面から次を既存管理APIへ保存できる。

- タスク: 新規追加と、名称 / 状態 / 担当 / 計画開始・完了 / 実績完了 / 進捗 / 日程確度 / 詰まり / 完了条件 / 完了証跡の更新。親子は同一PJ・同一表示レーン内に限定し、循環参照をAPI/DBで拒否する。ネストはガント左のグリップを親タスクへドラッグして付け替え、レーン見出しへ戻すと最上位タスクになる。
- MS: 新規追加と、名称 / 配置レーン / 予定日 / 状態 / 担当 / 完了条件 / 完了証跡の更新。現行2件のMSを含め、達成判定はMS自身の状態と証跡だけで行う。週次管制の依存種別は `finish_to_start` に限定する。
- 担当欄: 編集トレイとインライン編集の担当は、管制データに実在する担当名から選ぶプルダウン。候補は当該PJのMS・タスク・成果・論点・仮説・検証・判断・決定後の行動・関係先作業・技術試験・組織役割の担当実績とログイン中の本人名を重複排除して五十音順に並べ、`担当未確認` などの欠測表現は候補から外す。既存値が候補に無い場合も選択状態を失わないよう先頭へ足す。末尾の `＋ 新しい担当を追加` を選ぶと自由入力へ切り替わり、`一覧から選ぶ` で開く前の担当へ戻る（空のまま残さない — 変更していないのに未保存扱いが居座り、破棄確認から抜けられなくなるため）。自由入力かどうかはフィールド単位のモードとして保持し、入力途中の文字列が既存候補と一致した瞬間に入力欄が閉じない。インライン編集セルは幅が狭いので、自由入力の入力欄と `一覧から選ぶ` は1行に収まらなければ折り返し、名前の入力欄が数文字分に潰れない。メンバー台帳ではなく実データを候補源にするため、社外の人名やチーム名もそのまま扱える。
- 状態の `未着手`: MS・タスク共通の状態に、手入力専用の `未着手` を持つ。自動判定（`deriveMilestoneStatus`）はこの値を生成せず、人が「まだ着手していない」と宣言した時だけ入る。進捗未登録（`unassessed`）と同じく進捗率を実績として表示せず、進捗欄・統合タイムラインとも `未着手` と表示して 0% と偽らない。実行経路の分類では、期限超過・停止より弱く、推定の進捗未登録より強い状態として扱う。成立条件ナビゲーションの表示トーンは中立とし、`unassessed` の未確認トーンへ落とさない。
- 関係先: 新規追加と現在値更新。やり取り履歴、誰が抱える具体的保有事項、役割分類を同じ画面から追加編集する。
- 論点: 新規、title / kind / status / owner / due / confidence更新。
- 仮説: 論点配下へ新規、statement / status / owner / due / confidence更新。
- 根拠・反証: 論点または仮説へ supporting / counter / missing / observation を追加。
- 検証: 仮説へ方法・担当・予定・期限・状態を追加。既存検証（`SxValidationRun`）は共通母集団・PJ全体の担当負荷から`edit_validation`（`resource: "validation"`のPATCH）で直接編集でき、押した検証レコードそのものが開く（親論点の編集へフォールバックしない）。
- 判断: 論点または仮説を今週の判断キューへ追加。
- 決定: 判断待ちを決定済みまたは保留へ更新し、決定内容・決定者・決定日を記録。
- 決定後の行動: 決定配下へ担当・期限・完了条件・次回確認日を追加し、実行中・停止・完了と完了証跡を更新。

カードの「次の動き」は種類の固定順ではなく、`停止中 → 期限超過 → 期限が近い → 期限なし` の順で選ぶ。同順位では決定後action、判断、検証の順とし、決定後の実行が判断記録の陰に隠れないようにする。カード詳細は折りたたみ内で根拠・判断・actionを全件表示し、件数だけ見えて履歴へ到達できない状態を作らない。

保存成功後はAPIが返す最新 `SxManagementBundle` で画面を更新する。画面内で楽観的に完了へ移動させない。PATCHは `last_verified_at` と手入力由来をAPI側で更新する。

ガントは記号だけに意味を預けない。凡例は `計画期間 / 実績 / マイルストーン` の3項目だけにする。通常工程の各行は `予定 / 実績 / 前提` を文字で出し、進捗未登録は `0%` でなく `未登録` と表示する。◇とマイルストーン名は上記2件だけに使い、通常工程の終端は単純な予定日線で示す。

行の名称または実バー／◇を選ぶと、全画面幅でガントを背景に残した重畳モーダルへ詳細を出す。desktopの右ペインとガント直下の詳細帯は使わず、mobileは同じ情報構造を画面下端へ寄せる。背景クリック、Esc、閉じるで閉じる。管理者はモーダルの名称・担当・状態・日付・進捗・内容・詰まり・完了条件そのものを選んで修正する。既存値を選んだときはモーダル本文全体をフォームへ差し替えず、押した値の表示位置だけを入力欄・保存・キャンセル・局所エラーへ置き換える。PATCHはその位置に対応する変更fieldだけを送り、計画期間だけは開始日と完了日の2fieldを同時に送る。保存またはキャンセル後は同じ詳細の同じ位置へ戻る。編集開始時はその入力欄へfocusを移す。編集中に背景・Esc・外側の閉じるを使う場合は、未保存変更の破棄を確認してから詳細を閉じる。独立した `編集` ボタンや鉛筆アイコンを置かない。新規タスク追加は複数fieldの入力が必要なためroot editorを使うが、入口は各3レーンの最終タスク直下に常設する48pxの `＋ 新規タスク` 行だけとし、ツールバーや詳細モーダルに別の追加ボタンを置かない。追加フォームは表示レーンから親工程を推測せず、同じレーン内でガントに表示中の未完了工程を `接続する工程` として必須選択させる（候補1件だけなら事前選択、0件なら先に工程と日程を追加するよう示して保存しない）。新規タスクは工程直下へ追加し、ガント左側のグリップを親タスクの行へドラッグして子にする。工程行へ落とせばネスト解除できる。受け皿は同じ工程内で、子孫・自分自身・現親はdrop targetにせず、APIも同じ工程・循環なしを検証する。関係先はモーダルを編集入口にせず、一覧の編集可能cellを同じ位置で直接修正する。進捗railから開くモーダルは履歴閲覧専用とし、そこから第二の編集モーダルや関係先全体フォームを開かない。唯一の例外は履歴モーダル内の`試料台帳`節で、管理者は試料行をその場で行内編集（試料名/状態/受領日/保管場所/担当/要確認）でき、試料名1項目だけの追加フォームで新規登録できる。この場合も第二モーダルは開かない。

## ガント直接編集とマイルストーン配置（v3.55.0）

`project_management_milestones.timeline_kind`（`'phase' | 'milestone'`、DB CHECK制約付き）が「工程バー」と「マイルストーン◇」の描き分けを持つ唯一の正本。レンダリングはこの列だけを見る — slugからの推測はしない。

**一般MSと設立ゲートは別物**。`timeline_kind='milestone'`の行は原則「計画上の一点日程（point-MS）」で、`planned_start`と`planned_end`は常にnull同士か等しい同じ日付のどちらかしか取らない（DB CHECK `project_management_milestones_point_ms_check` / API側 `isValidPointMilestoneRange` / `normalizePointMilestonePatch`）。唯一の例外が既存の設立前提2件（`business-paid-poc-oral-agreement` / `funding-investment-oral-agreement`）で、ゲート判定・強制レーン配置・バー＋◇の複合表示という既存のslug固有ロジック（`sxIsBlockingMilestone`）をそのまま維持し、`planned_start < planned_end`の実レンジを保持できる。一覧・ガントのラベルもこの2種を区別し、一般MSは「MS」「マイルストーン」、設立ゲートの2件だけが「設立ゲート」と表示される — 全てのMSを設立ゲート扱いにしない。凡例も一般MSを「計画上の到達目印」、設立ゲートを「先へ進む前提（2件のみ）」と分けて説明する。

デスクトップのポインタ操作で、`canManage`かつ`projectId`ありのユーザーは工程/タスクのバーとマイルストーン◇を直接編集でき、実バー／◇以外の行内空白はその日付へのMS追加確認を開く。`projectId`なしの埋め込み（`SxExecutiveControlDeck`の経営状況図など、書き込み面を持たない場所）は空白日付クリックを無効にし、click-select-onlyのまま変化しない。ドラッグの起点は実際のバー本体／◇だけで、行の余白からは始まらない。◇は透明な当たり判定の上へ描くだけにせず、見えている◇そのものを44px以上のsemantic button内へ置く。したがって、ドラッグなしのクリック／タップは必ずそのMSの詳細編集を開き、ドラッグは日程変更だけを行う。視覚上のバーは8pxのままだが、中央移動の当たり判定・両端の取っ手・◇の当たり判定はいずれも44px以上を確保し、取っ手は行のhoverまたはfocusで可視化される（`group-hover`）。取っ手はpointerdownだけを受け取り、pointermove/up/cancelは親のRowBar 1箇所だけで処理する（同じイベントが取っ手とRowBarの二重発火でPATCHが2回飛ぶ回帰を防ぐ）。開始・完了がある通常バーは、同日や数日の狭いバーでも移動・開始変更・完了変更の3操作を維持する。16pxの開始取っ手はバー開始位置の左外側、完了取っ手はバー終了位置の右外側へ完全に逃がし、中央移動の当たり判定を覆わない。一般MSと設立ゲートの◇は見た目でも区別する: 設立ゲート2件は塗りつぶした紫の◇、一般MSは中抜きの◇（凡例と一致）。
同日を含む狭いバーは描画上の中央移動領域を最低16px確定してから、その左右外側へ取っ手を置く。日付領域の左右には22pxの操作余白を予約し、0%/100%へ丸められる表示期間端でも取っ手と44pxの◇を固定列・scroll edgeの内側へ保つ。

- バー中央をドラッグ: 計画開始・完了の両方を同じ日数だけ移動し、期間を保つ（`computeBarMove`）。
- バー左端の取っ手をドラッグ: 計画開始だけを変更し、計画完了を追い越さない（`computeBarResizeStart`）。
- バー右端の取っ手をドラッグ: 計画完了だけを変更し、計画開始を追い越さない（`computeBarResizeEnd`）。
- 一般MSの◇をドラッグすると、計画開始・完了を同じ新しい日付へ揃えたまま移動する（`computeMilestoneMove`）— 元データが揃っていなくても常に一点化する。
- 設立ゲート2件の◇をドラッグすると、計画完了だけが動き、計画開始は保持される（`computeGateEndMove`）。開始日が未設定のゲートも、終了日さえあればこの◇でドラッグできる。

新規マイルストーンの配置は**その場でPOSTしない**。専用の「MSを追加」ボタンや「日付上に置く」配置モードは置かず、デスクトップガントの各行にある実バー／◇以外の空白日付ポイントを直接クリックすると、そのポイントの近くへ非モーダルの `MSを追加する？ / Y 追加する / N 閉じる` を出す。モバイルの縦一覧では各レーン末尾（常設の新規タスク行より前）に同じ期間の小型日付軸を置き、タップ位置を日付へ変換する。キーボード操作はfocus中の日付面の中央を仮日付として同じ確認とフォームを開き、フォーム内の予定日で調整できる。確認は画面上端で切れないよう、上側に収まらない場合だけクリック位置の下へ反転する。Yでこの確認を先に閉じてから既存の単一IssueEditor作成フォームを、クリックしたレーン・日付・一致する成果・`timeline_kind='milestone'`で事前入力して1回だけ開き、N・Esc・外側クリック・スクロールでは確認だけを閉じて何も書かない。実バー／◇のクリックは詳細選択、バー／◇／取っ手のpointer gestureは日程編集のままで、空白クリックと二重発火させない。クリックした表示レーンは作成フォームの「配置するグループ」に事前チェックとして入る（v3.58.15。旧・レーン内の成果を候補として並べるselect）。フォームの「保存」を押して初めてPOSTが飛び、閉じる/キャンセルすればDBには何も残らない。一般MSのフォームは開始・完了の2fieldではなく単一の「予定日」fieldを持ち、保存時にその値を`planned_start`・`planned_end`の両方へ書く。レーンは常に事業開発／技術開発／組織開発の3つだけ。MS/工程作成フォームにDB内部の4track（事業開発・技術開発・資金調達・体制構築）を独立した「柱」選択として出してはならず、MS作成の配置先は「配置するグループ」の3レーン名チェックボックスだけで選ばせる。保存payloadの厳密な`track`値は選んだ先頭グループから逆算したoutcomeから導出し、fundingとorganizational_buildingはいずれも表示上の組織開発へ入る一方、DBの`milestone.track = outcome.track`不変条件は維持する。

### 依存線は常設の「＋」ポートから引く（v3.58.9）

依存線の作成は**モードではない**。`依存を接続`トグルは廃止し、編集権限がある限り、日程を持つ全タスクと全MSの右側に常設の「＋」ポートを置く。ポートはhover・focusで現れ、押したままドラッグして別のタスクまたはMSの上で離すと接続する（クリックだけならキーボード同様に起点をarmし、次に押した行が接続先になる）。

「＋」は行が既に持つ操作面と**一切重ならない位置**に置く。タスクバーではバー右端＋16px（終了日リサイズ取っ手の外側）、MSでは◇中心＋22px（◇の44pxドラッグ判定の外側）から始まる幅24pxの領域とする。これにより常設化しても日程ドラッグ・詳細クリックを奪わない。

日程ドラッグ・階層ドラッグ・空白点MS追加を止めるのは「モード中」ではなく**起点をarmしてから接続が確定するまでの間だけ**とする。したがって通常時はこれらの操作が従来どおり全て効く。Escは未保存の線だけを破棄する。接続先の候補は接続元と同じく**タスクとMSの両方**（`successor_type` / `successor_milestone_id`、migration 230）。

### MSのゲート帯・レーン折りたたみ・接続中の自動スクロール・タスク削除（v3.58.14）

- **MSはゲート帯**: MSは点の出来事ではなく、そのレーン全体が通過する関門として描く。◇ではなく幅12pxの縦帯をレーン全高に伸ばし、レーン見出し上の同じ幅のキャップをクリック・ドラッグの取っ手にする。帯自体は`pointer-events: none`のままにし、帯を横切るタスクバーのクリックを奪わない。依存線のMS側端点は◇の頂点ではなく帯の縦辺（中心±6px）に接する。
- **レーンの折りたたみ**: 事業開発／技術開発／組織開発のレーン見出し行はボタンで、押すとそのレーンのタスク行と`＋ 新規タスク`行をまとめて畳む。畳んだ状態でもMSのゲート帯とレーン見出しは残る（MSはレーン見出し帯に描くため）。開閉はクライアントのローカル状態で、DBには保存しない。行の高さ計算・依存線の座標は`collapsed`を含めた同じ計算式（`lanesTotalHeight` / `visibleRowLayout`）から導く。desktopとmobileの両方に同じトグルを置き、`data-gantt-nest-root-lane`（階層ドラッグの「最上位へ戻す」ドロップ先）は見出しに残す。
- **接続中の自動スクロール**: 依存線をドラッグして接続先が画面外にある場合、ポインタがスクロール領域の端56px以内に入っている間はrequestAnimationFrameで最大18px/frameまで自動スクロールする。縦にスクロールできないときはページ自体（`window.scrollBy`）へ委ねる。プレビュー線はスクロール後の座標へ追随する。
- **タスク削除**: タスク詳細トレイの末尾に「このタスクを削除」を置き、同じトレイ内の2段階確認（削除する／やめる）で確定する。第2モーダルは開かない。削除はAPIの`PATCH { resource: "task", id, delete: true }`によるsoft delete（`deleted_at`）で、成功時は返ってきたbundleで置き換えて選択を解除する。子タスクを持つタスクはボタンを出さず「子タスクがあるから削除できないよ」と理由だけを示す。MSの削除はv3.58.16で同じトレイに追加した（下記）。

### MS接点の縦中央・タスクの手動並び替え・MSの配置グループ複数選択（v3.58.15）

- **MS接点は帯の縦中央**: 依存線がMSへ接する高さは、レーン見出し帯の中央ではなくレーン全高（見出し＋そのレーンの全タスク行＋`＋ 新規タスク`行）の中央にする。ゲート帯が縦に伸びている以上、線が帯の上端付近だけに集まるのは帯の意味と合わない。折りたたみ中は行数が0になるので中央も見出し帯の中央へ自然に縮む。同じMSが複数グループに描かれる場合、依存線の端点は最初に現れたレーンのものを使う（first-wins）。
- **タスクの手動並び替え**: 左のグリップのドラッグは、親子のネスト変更に加えて同じ階層内の並び替えも担う。行の上下端バンド（行高の32%）へ落とすとその行の前／後ろへ挿入、中央帯へ落とすと従来どおりその行の子になる。挿入位置は行の境界に出るインジケータで示す。ドラッグ中は掴んだタスクがポインタへ追従するゴースト（`position: fixed`、ポインタの右12px）として動き、どれを動かしているかを見失わせない。並び順の正本は`project_management_tasks.sort_order`で、確定時に同じ兄弟集合（同一`parent_task_id`、最上位タスクは同一表示レーン）を10刻みで採番し直す。画面は兄弟集合全体の`id / expected_version / sort_order`を1リクエストで送り、`reorder_project_management_tasks`が対象PJ・同一親・全versionを行ロック後に検証して1トランザクションで更新する。1件でも競合・不正があれば全件rollbackし、409後に正本を再取得する。表示順は`sort_order → title`。
- **MSの配置は「グループ」を複数選べる**: MS作成フォームの先頭は、個別の成果を1件選ぶselectではなく `事業開発 / 技術開発 / 組織開発` の3チェックボックス（`配置するグループ`、必須、1行に並べる）にする。人が扱う単位はレーンであって内部の成果ではないため、生の4trackも成果名もフォームに出さない。複数グループを選ぶと1件のMSレコードがそれらのレーンすべてにゲート帯として描かれる（レコードを複製しない — 複製すると編集・削除・依存線が二重になる）。表示先は`project_management_milestones.display_lane_keys text[]`（migration 241、追加のみ・NULL許容。NULL/空なら従来どおり`track`から導出）に保存する。DBの親成果（`outcome_id`）と`track`は、選んだ先頭グループに一致する成果から自動で逆算し、`milestone.track === outcome.track`不変条件を保つ。該当する成果が1件も無いグループだけを選んだ場合は保存せず「このグループにMSを置くための基準情報がまだないよ」を出す。

### MSの削除（v3.58.16）

- **入口はタスクと同じ共有トレイ**: MSを選んで開く詳細トレイの末尾に「このMSを削除」を置き、同じトレイ内の2段階確認（`削除すると、このMSはガントと一覧から消えます。` → `削除する` / `やめる`）で確定する。第2モーダルも別の削除ボタンも作らない。タスクを選んでいるときはタスクの削除、MSを選んでいるときはMSの削除が同じ位置に出る。
- **soft deleteで、成功時はサーバの返すbundleに従う**: `PATCH { resource: "milestone", id, delete: true }`（`deleted_at` / `deleted_by`）。楽観更新はせず、返ってきた`SxManagementBundle`で置き換えて選択を解除し、`MSを削除したよ`を出す。削除PATCHは`expected_version`を要求しない（可視性の切り替えでありデータ編集ではない）。
- **配下タスクがあるMSは削除できない**: MSを消すとその配下タスクが親を失うため、live なタスクが1件でも紐づくMSはAPIが400で断り、UIもボタンを出さず「このMSに紐づくタスクがあるから削除できないよ。先にタスクを別のMSへ移すか削除してね」と理由だけを示す。UIのガードとサーバのガードは同じ条件を二重に持ち、判断が食い違った場合は最後にサーバの答えを通知として見せる。
- **依存線は孤児を残さず消える**: MS（およびタスク）を非表示化しても依存線の行自体は残るが、`getSxManagementBundle` が「live な端点だけを持つ依存線」に絞ってから配るため、削除済みMSを指す線はDAG計算にもガント描画にも入らない。依存線を個別に消してから削除する手順は不要。

### 依存線の直接解除と簡潔な経路（v3.57.22）

保存済みの依存線は常時矢印で表示する。PCの通常モードでは、透明10pxの当たり判定へhoverした線だけを強調し、ポインタ近くに出る`外す`からsoft deleteできる。接続中は解除UIを出さず、新しい接続を優先する。mobileとキーボードは既存の依存関係一覧から同じ解除に到達する。描画線は1.5pxで、通常の前方接続は11px、迂回時の始点側は5px・終点側は4pxだけを逃がす。端点は接続元バーの右端中央、接続先バーの左端中央、MSはゲート帯の縦辺（v3.58.14。旧・◇中心）へ正確に接する。MS側の縦位置はレーン見出し帯の中央ではなく、見出しと全タスク行を合わせたレーン全高の中央とする（v3.58.15）。視覚上のタスクバーは10pxであり、上の8pxという旧値は現行仕様ではない。

### ガントの表示依存・固定ヘッダー・MS作成密度（v3.56.3）

工程ゲートの達成判定に使う既存の`project_management_milestone_dependencies`と、日程表上の終了→開始関係は意味が違う。ガントで手動作成する線は新設の`project_management_schedule_dependencies`だけへ保存し、前者のゲート充足・NewCo判定を変えない。接続元は日程を持つタスクまたはpoint-MS/設立ゲート、接続先は別のタスクまたはMSとし、種類は`finish_to_start`だけとする。

（v3.58.9で改訂: この段落が定めていた`依存を接続`モードは廃止し、上の「常設の＋ポート」節へ置き換えた。以下は端点とDB制約の記述として残す。）接続元は日程を持つタスクまたはMS、接続先も別のタスクまたはMSとし、キーボードとモバイルは同じ順序を「起点」→「接続先」の2操作で完了できる。保存済みの線は常時矢印で表示し、線上の解除操作からsoft deleteできる。自己接続・重複・task→taskの循環・別PJの端点・削除済み端点・MS自身の配下タスクへのMS→task接続はDB triggerでも拒否する。DBロックは端点行（task同士はUUID順）→PJ単位advisory lockの順へ全経路を統一し、循環検査を直列化しつつ端点更新とのロック順逆転を作らない。

desktopガントは横方向だけでなく内部の縦方向にもスクロールする枠を持つ。月・設立目標・左側の`工程 / タスク`を置く先頭ヘッダーはその枠の`top: 0`へ固定し、縦スクロール後も日付軸と行名列の意味を失わせない。左側の工程名列は横スクロールでも固定する。

point-MS追加フォームは`配置するグループ（複数選択可） / MS名 / 予定日`の3項目だけを必須とし、`完了条件`は任意にする。`到達点`はpoint-MSでは完了条件と重複するため作成フォームへ出さず、`次の成果物`は次工程が未定のMSにも入力を強制しない。既存DBの非NULL列は削除せず、APIが明示的な`未設定 / 未確認`を保存して後から詳細で補えるようにする。作成時の非表示`criticality`は`medium`とし、point-MSを置くだけで重要案件・高重要度の情報不足を増やさない。工程（phase）の作成契約は変更しない。

タスク/MS作成・編集のroot editorはdesktopで通常幅640px、wide 760px、最大高720px、詳細PlanInspectorは幅820px・最大高720pxを上限とし、header 54px、入力36px、footer操作38pxへ圧縮する。390px相当ではbottom sheetへ切り替え、入力・閉じる・footer操作を44px以上、入力文字16pxへ戻す。密度を上げるためにモバイルの操作性を削らない。

ドラッグ中はポインタ移動のたびにローカルpreviewだけを更新し、サーバーへは何も送らない。pointerupで初めて1回だけPATCHする。4px未満の移動はドラッグではなく通常のクリック（行の詳細を開く）として扱い、クリックとドラッグを競合させない（`isWithinClickThreshold`）。Esc・pointercancelはpreviewを破棄するだけで何も送らない。ポインタキャプチャの喪失（`lostpointercapture`）は、自分自身のpointerupによる正常な解放（保存処理が既に始まっている）となら区別し、保存中のpreviewを誤って巻き戻さない — 本当にキャプチャを異常に失った場合だけpreviewを破棄する（`shouldCancelOnLostPointerCapture`、同期refで判定）。ドラッグ状態は`dragRef`（同期ref）を単一の真実として扱い、pointermoveの直後にpointerupが同じバッチで来ても最後のpreviewを取りこぼさない — PATCH送信もこのrefから読む（Reactのstate更新は次のイベントハンドラに即時反映される保証がないため）。保存に失敗した場合（409以外も含む）はベストエフォートで`management`を再取得し、その再取得自体が失敗したら「保存できたか確認できなかったので再読み込みしてね」と明示する。日付計算・しきい値判定・並行制御の正規化はすべて`src/lib/sx-gantt-drag.ts`の純関数（DOM非依存）に集約し、`npm run test:sx-gantt-drag`・`npm run test:sx-gantt-pointer-gesture`で単体テストする。

工程/タスクのPATCHは`project_management_milestones.version` / `project_management_tasks.version`（既存の自動採番列）を使った楽観的並行制御を**必須**で通す。ドラッグ・ガント空白点のY確認から開いたフォームのPATCH・週次管制のroot editor・SxNavigationDashboard・`/workspace`のManagementEditor、milestone/taskを触る全てのPATCH経路が、読み込んだ時点の`version`を`expected_version`として送る。`expected_version`が欠落・不正なら400、`before`行の`version`と不一致なら409（`code: "version_conflict"`）を返す。該当行のUPDATE自体も`.eq("version", expected_version)`で絞ることで検出漏れをなくす。クライアントは409を「他の人が更新した」通知として表示し、最後に保存した側で黙って上書きしない — 必ず最新の`SxManagementBundle`を再取得してUIへ反映する。監査履歴insertが失敗したときの補償ロールバックも、自分の更新が生んだ`version`へ`.eq("version", updatedVersion)`でCASし、その後さらに別の変更が乗っていたら（CAS不一致）ロールバックを実行せず「補償復元は安全に実行できなかった」と報告する（後発の編集を黙って踏みつけない）。

マイルストーンの新規作成・PATCHどちらも、選択した`outcome_id`が選択した`objective_id`に属し、outcomeの`track`がmilestoneの`track`と一致することをサーバー側で検証する（`assertMilestoneParentIntegrity`、APIレイヤ）。migration 220はこの整合性を全PJ横断の一般不変条件としてDBレベルでも強制するtrigger（`project_management_milestone_parent_integrity()` + `project_management_milestones_parent_integrity_trigger`、outcome_id/objective_id/track更新時にBEFORE INSERT/UPDATEで発火）を追加する — APIパス以外から書かれた行にも同じ不変条件を保証するbackstopで、追加前に既存データの不整合を検査し明確な例外で失敗する（同一トランザクション）。

計画開始・完了の日付はサーバー側で厳密なYYYY-MM-DDカレンダー日付として検証する（`2026-02-30`のような実在しない日付は正規表現だけでは弾けないため、`isStrictCalendarDate`でカレンダー変換の往復一致を見る）。PATCH/POSTのどちらも、送信fieldと既存行をマージした計画開始・完了の組で`planned_start <= planned_end`を検証し（DBの`project_management_milestones_planned_range_check` CHECKと同じ規則）、逆転した範囲は保存前に拒否する。

### タブ化・論点表の再適用と「hydration停止」誤診の記録 (build v3.65.0→v3.67.1撤回→v3.67.2再適用、2026-08-08)

- **教訓 (検証手順の恒久ルール)**: 背面タブでの「操作が効かない」「hydrationが進まない」はまず visibilityState を疑う。ページ検証は (1) スクリーンショット取得などで描画を蹴る (2) hydrate済み要素数 (`__reactProps` 付き要素) を数える (3) それでも疑わしいときだけ前面化、の順で確認する。
