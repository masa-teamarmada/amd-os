# PJ週次管制画面 仕様

> **目的**: 計画の再作成ではなく、既に管理されている計画・進捗から「先週からの変化」「今回決めること」「決定後の介入」を週次会議で短時間に確認する。論点・仮説を担当・期限・検証・根拠・判断へ接続し、放置を防ぐ。

## 正本境界

- 新画面は `/project/[projectId]/weekly-control`。
- 既存の `/project/[projectId]/workspace` は、計画詳細・技術証明・関係先・工数入力を扱う統合ワークスペースとして維持する。置換・redirectしない。
- 新画面はUIを先に固定する。週次差分の自動抽出が未接続の項目は、0件・変化なしと断定せず `抽出接続待ち` と表示する。
- ガントと関係先はこの画面から手動修正でき、手動で確認・保存した現在値を正本とする。将来の自動抽出は既存値を直接上書きせず、差分候補として人の確認へ回す。
- H1見出しは `SolvioraX PJワークスペース` の固定文言。プロジェクト名を動的に埋め込まない。

## Route / Auth

| 項目 | contract |
|---|---|
| page | `src/app/(app)/project/[projectId]/weekly-control/page.tsx` |
| view | `SxWeeklyControlDashboard` |
| auth | `getCurrentMemberAccess()`。未ログインは同URLを `next` に保持してloginへ送る |
| PJ境界 | `getProjectWorkspaceBundle(projectId, access)` と `projectScopedPathAllowed()`。PJ限定ユーザーは所属PJだけ閲覧可 |
| shell | `/workspace` と同じ埋め込みshell。月初合意overlayの対象外 |
| write | portfolio/adminだけ。既存 `/api/project-workspace/[projectId]/management` を使い、clientからDBへ直接書かない |

## 画面構造

1. **PJ全体の管制入口（旧・週次状態帯を再構成）**: 工程・タスク・論点・仮説・検証・判断・action・関係先保有事項を`sxProjectOwnerLoads`が正規化した同じ未完了作業単位の共通母集団から、`停止 / 期限超過 / 7日以内 / 担当不明 / 期限なし / 判断待ち`の6バケットをクリック可能な帯で表示する。算出値自体は編集させず、バケットを押すと同じ帯の直下へ該当元項目一覧（種別・担当・期限・影響工程つき）を絞り込み表示し、一覧の各項目を押すと必ず元の編集文脈へ移動する（工程/タスクはガント該当行・詳細を全画面モーダルで開く、論点/仮説/検証/判断/actionは該当論点/仮説/検証/判断/actionレコードそのものを開くroot editorモーダル）。検証（`kind: "validation"`）は`edit_validation`で押した`SxValidationRun`そのものを開き、仮説・判断・actionと同様、IDが一致するレコードを見つけられない場合は親論点編集へ黙ってフォールバックせず「元の項目を見つけられなかったよ」のnoticeで終える。工程/タスク/論点系（論点・仮説・検証・判断・action）は対象issueと子recordのID・存在をすべて検証し、次に開く編集先を組み立ててからだけ既存のworkloadFilter絞り込み・詳細/plan field editor・ガント選択などの既存overlay stateを一括解除する。無効IDのクリックはnoticeだけを出し、既存の詳細・editor・絞り込みは閉じない。論点系root editorは全画面backdropの重畳モーダルであり、開く前にガント側の選択（工程/タスク）を必ず解除し、背景ページはスクロールしない（開閉前後でscrollYを変えない）。関係先由来の項目はスクロールせず、`SxProjectWorkUnit.originResource`（`partner_work_item` / `commitment` / `partner_next_action`）と`recordId`/`partnerId`から対象レコードを直接引いて、由来別の単一編集モーダルを直接開く（`partner_work_item`は既存の保有事項編集フォーム、`commitment`は約束・次アクション専用の編集フォーム、`partner_next_action`＝構造化保有事項が無いフォールバック行は関係先編集のうち`次にやること / 当方担当 / 期限 / 期限精度 / 現在の保有側 / 現在の担当`の6項目だけに絞ったフォーム）。IDの一致だけで別resourceへ探索をフォールバックしない。開く前に選択中の詳細/インラインfieldエディタは閉じ、開くモーダルは常に1つだけにする。静的な5枚のKPIカードとゲート専用カウントは廃止した。今週入力（人員配分の入力人数）は作業遅延の6バケットと混ぜず、7.データ接続状況側だけに表示する。
2. **PJ全体の担当負荷**: 工程、タスク、必須ゲート、論点、仮説、検証、判断、action、関係先保有事項を同じ未完了作業単位へ正規化し、担当ごとに `停止 / 期限超過 / 7日内 / 期限なし / 全未完了 / 影響ゲート` を表示する。関係先だけの件数をPJ全体負荷として扱わない。行は1で使う共通母集団と同じ`SxProjectWorkUnit`を使い、各行を押すと1と同じ導線で元の編集文脈へ移動する（dead endにしない、aria-labelは実動作どおり「〜を編集」）。desktop（`lg`以上）の閉じた担当者行は左右2カラムに並ぶが、実体は`OwnerLoadColumn`という完全に独立したcolumn要素で、`partitionOwnerLoadColumns()`（`src/lib/sx-project-owner-load.ts`）が担当者配列を偶数index=左列・奇数index=右列のrow-major順で分割する（前半/後半split=`Math.ceil(length/2)`ではない。旧CSS gridの暗黙行ペアリングと同じ見た目のペア順を独立column構造でも保つため）。mobile（`lg`未満）はこの分割結果を連結せず、常に元の担当者配列順を単独DOMで描画する（連結だと`[0,2,4,1,3,5]`という別順序になるため）。desktop用2列DOMは`hidden lg:grid`、mobile用単列DOMは`lg:hidden`で常に片方だけをa11y treeへ出し、重複ノードを作らない。desktop 2列gridは`lg:items-start`を持ち、各`OwnerLoadColumn`はgrid行の高さ（＝展開している側の高さ）へstretchせず、自列の内容高さだけで止まる（`items-start`が無いとalign-items:stretchの既定でOwnerLoadColumn自身の`bg-[#d9cfde]`背景がgrid行高さへ伸び、片側detailsを開いた反対列の下に紫の空白帯として実ブラウザで見える）。gridコンテナ自体と外側`section`の大面積背景は生成り`#fffdf7`とし、左右境界の1px線はgapの背景色ではなく、`relative`コンテナ内の`aria-hidden`な独立absolute 1px divider（`inset-y-0 left-1/2`、`bg-[#d9cfde]`）で描く。各`OwnerLoadColumn`内部のdetails間1px区切りだけは列ローカルな`gap-px bg-[#d9cfde]`のまま維持する（この背景は列が自列高さで自己完結するため伸びない）。片側のdetailsを展開しても反対列のカード高さ・次カードのY座標は変わらない。
3. **週次変化レール**: `先週→今週`、`今回の会議`、`決定→介入` の3段。差分未接続はプレースホルダーのままにする。
4. **全体ガント**: `SxUnifiedTimeline` / `deriveSxUnifiedTimeline` を再利用するが、`SxUnifiedTimeline` は表示直前に**必ず事業開発／技術開発／組織開発の3レーンだけへ統合し直す**（`DISPLAY_LANE_ORDER`/`DISPLAY_LANE_LABEL`）。`deriveSxUnifiedTimeline`自体が返す4本柱（事業開発・技術開発・資金調達・体制構築）のうち、資金調達（funding）は独立レーンを持たず組織開発（旧・体制構築）へ統合する。週次管制は `dateMode="planned_only"` とし、完了見込み日・予定との差・差分線・予測ひし形・重要経路の破線接続を表示、範囲、並びの全てから外す。DBの `project_management_milestones` はこの画面では通常の工程として扱い、依存や `gate` 列があるだけでゲート・マイルストーンへ格上げしない。現時点の停止条件として表示するマイルストーンは `business-paid-poc-oral-agreement`（NewCo設立の最低条件は1社の有償PoC口頭合意。2社目を禁じる意味は持たせない）と `funding-investment-oral-agreement`（現時点は事業計画未完成・DD未着手）の2件だけ。この2件は**ガント外の独立したカード帯も、4本目の合成レーン（旧・独立した「設立前提」レーン）も持たず、`BLOCKING_MILESTONE_LANE`で`business-paid-poc-oral-agreement`は事業開発レーンへ、`funding-investment-oral-agreement`は組織開発レーンへそれぞれ強制配置する**（milestoneの実際の`track`列の値によらない）。desktopの月軸グリッドとmobileの縦一覧のどちらも、この2件を対象レーン内の行として扱い、独立したsectionへ切り出さない。日程未設定の行は右列にバーの代わりに「日程未設定・状態」「達成充足バッジ」「必須タスク完了数/総数・次の未完了タスク」をテキストで表示し、この2件については日程未設定でも◇（マイルストーン）マーカーを消さない——位置は日付比例（バー上のleft:X%）ではなく、既存の「日程未設定」テキストのすぐ横という非時間的な位置に置き、捏造した日付やX印は使わない。`timeline.valid`が偽（日程付き工程が0件）でもこの2件の行と説明文は表示し続ける。配下の`project_management_tasks`（有償PoCは5件、出資は7件の必須タスク）は初期展開し、完了数（`sxMilestoneRequiredTaskSummary`の`completed/total`）と次の未完了タスクを同じ行で示す。タスクは手動編集可能。通常の柱レーンにはこの2件を表示せず、二重表示しない。他の通常工程をこの2件のようなMSへ格上げしない。`unassessed` は未確認、明示的未完了は未達、`completed` でも証跡不足なら未確認とする。**この2件の達成判定（充足）は、口頭合意の4項目証跡（`先方または投資家 / 合意内容 / 確認日 / 根拠`）が揃い、かつ配下の必須タスクが全件完了しているときだけ「充足」となる（`sxGateRequirementState`）。4項目証跡だけでは充足にしない。** 工程配下は `project_management_tasks` のタスク→子タスクを初期折りたたみで表示する（設立前提2件は例外で初期展開）。mobile/tabletは横ガントを主表示にせず、日付・工程・前提・担当の縦一覧へ切り替える。ガント行の高さ（`ROW_H`）は約48pxとし、月軸/凡例/ピン行/ツールバーも同じ密度で圧縮する。
5. **関係先リスト**: `SxPartnerPipeline` を唯一の一覧とし、大学・金融機関・試作先・PoC候補先・VCを同じ台帳へ1社1行で表示する。`全関係先 / PoC候補先 / VC` は同じ表を絞る排他的なタブであり、別リストや別データを作らない。PoC候補先タブは候補全件を表示し、VCタブは保存済みroleの `role_kind='shareholder_investor'` だけで判定する。名称から推測しない。主列は `関係先 / 現在の状況 / ゴール / 詰まり・PJ影響 / 次にやること / 担当・期限 / 現在地の根拠 / 履歴・保有`。一覧の `現在の状況` は関係先本体の現在ボールだけを扱い、`保有側 / 担当` の2slotを閲覧時から明示する。編集時も同じ2slot・同じ高さ・同じ列幅のまま値だけをselect/inputへ置き換え、PATCHは `current_ball_side / current_ball_owner` に限定する。期限をこのcellへ重複表示・編集せず、`担当・期限` は主要対応事項1件の担当と期限だけを扱う。主要対応事項が関係先本体へfallbackする場合も `owner_label / due_date / due_date_precision` を使い、`current_ball_*` と保存先を重ねない。`ゴール` は目標状態だけを表示する。管理者は表示中の編集可能な値そのものを押し、そのセルだけで入力・保存・取消・エラー表示を完結させる。行全体はボタンにせず、行の余白や読み取り専用cellを押してもモーダルを開かない。確認済み接点（古い順）→現在地→未完了作業→次の一手→ゴールの可変長 `進行状況` と全履歴は、会社名下のsegment railだけから開く閲覧専用モーダルへ置く。railとモーダル内の進行blockは同じstep配列を使い、件数と順序を必ず一致させる。PoC/VC表示では役割groupや保留foldで行を分断しない。行動、担当、期限、関連工程は同じ構造化保有事項から選び、別レコードの値を合成しない。構造化保有事項がない場合だけ関係先本体の対応事項へフォールバックし、関連工程を推測接続せず `PJ影響 未接続` とする。上部は担当別の未完了件数・危険件数・情報不足を集計する。履歴モーダルは進行状況、全やり取り履歴、未完了/完了保有事項を表示し、関係先全体の編集フォームへ切り替えない。メール本文、アドレス、URL、個人連絡先、内部source refは保存・表示しない。p21のVCはPartners Fundに加え、別交渉主体としてDAVP、BNV、いよぎんキャピタルを保存済みpartner+roleで持つ。接触段階・合意・ボール・期限・ゴールの根拠がない3社は未確認のままにする。
6. **論点・仮説リスト**: `要整理 → 検証中 → 判断待ち → 決定・棄却` の4状態で一覧する。desktopは4列、tabletは2列、mobileは1列へ再配置し、ページ横スクロールを発生させない。セクション名・列名は業務上の名詞を使い、目的説明やコピーを見出しへ置かない。
7. **データ接続状況**: 週次差分、論点・仮説、工数（今週入力の人数はここに表示し、1の作業遅延バケットとは混ぜない）、関係先メール接点の接続状態を示す。

## 論点・仮説の放置防止

### 段階

| 段階 | 判定 |
|---|---|
| 要整理 | 未解決で、検証中・判断待ち・完了の条件を満たさない |
| 検証中 | 論点/仮説が `validating`、または検証が `planned/running` |
| 判断待ち | `decision_needed`、未決の意思決定、または `validated` 仮説がある |
| 決定・棄却 | 論点が `closed/decided`、または全仮説が `rejected/decided` |

段階と警報は別に扱う。期限超過・更新切れは列を移動する条件ではなく、どの段階でも重ねて表示する。
決定・棄却列でも未完了の決定後actionがあれば要フォローへ残し、判断だけ記録して実行が忘れられる状態を作らない。

### 警報

- **要フォロー**: 未完了で、担当不明、次の期限なし、仮説なし、検証中なのに検証予定なし、期限超過、更新切れのいずれか。
- **次の期限**: 論点、活動中の仮説、計画/実施/停止中の検証、未決判断、未完了actionから最も近い日を採用する。
- **最終更新**: 親論点だけでなく、仮説・根拠・判断・actionの `lastVerifiedAt` の最新日を採用する。子だけを更新した論点を更新切れにしない。
- **更新切れ**: 最終更新から7日以上。日付欠損も更新切れとして扱い、0日扱いしない。
- **期限超過**: 未完了論点の次の期限が基準日より前。完了済み論点へ赤警報を残さない。

## 書き込み契約

画面から次を既存管理APIへ保存できる。

- 工程: 新規追加と、名称 / 状態 / 担当 / 計画開始・完了 / 実績完了 / 進捗 / 日程確度 / 詰まり / 完了条件 / 完了証跡の更新。
- 設立前提: 現行2マイルストーンの状態・担当・日付・証跡を値の選択から直接修正できる。接続値を選ぶと依存条件を修正できる。週次管制の依存種別は `finish_to_start` に限定する。
- タスク: 工程直下またはタスク配下へ新規追加し、計画、実績、進捗、親タスク、作業内容を更新。親子は同一PJ・同一工程内に限定し、循環参照をAPI/DBで拒否する。
- 関係先: 新規追加と現在値更新。やり取り履歴、誰が抱える具体的保有事項、役割分類を同じ画面から追加編集する。
- 論点: 新規、title / kind / status / owner / due / confidence更新。
- 仮説: 論点配下へ新規、statement / status / owner / due / confidence更新。
- 根拠・反証: 論点または仮説へ supporting / counter / missing / observation を追加。
- 検証: 仮説へ方法・担当・予定・期限・状態を追加。既存検証（`SxValidationRun`）は共通母集団・PJ全体の担当負荷から`edit_validation`（`resource: "validation"`のPATCH）で直接編集でき、押した検証レコードそのものが開く（親論点の編集へフォールバックしない）。
- 判断: 論点または仮説を今週の判断キューへ追加。
- 決定: 判断待ちを決定済みまたは保留へ更新し、決定内容・決定者・決定日を記録。
- 決定後の行動: 決定配下へ担当・期限・完了条件・次回確認日を追加し、実行中・停止・完了と完了証跡を更新。

カードの「次の動き」は種類の固定順ではなく、`停止中 → 期限超過 → 期限が近い → 期限なし` の順で選ぶ。同順位では決定後action、判断、検証の順とし、決定後の実行が判断記録の陰に隠れないようにする。カード詳細は折りたたみ内で根拠・判断・actionを全件表示し、件数だけ見えて履歴へ到達できない状態を作らない。

保存成功後はAPIが返す最新 `SxManagementBundle` で画面を更新する。画面内で楽観的に完了へ移動させない。PATCHは `last_verified_at` と手入力由来をAPI側で更新する。

ガントは記号だけに意味を預けない。凡例は `計画期間 / 実績 / マイルストーン` の3項目だけにする。通常工程の各行は `予定 / 実績 / 前提` を文字で出し、進捗未登録は `0%` でなく `未登録` と表示する。◇とマイルストーン名は上記2件だけに使い、通常工程の終端は単純な予定日線で示す。

行の名称または実バー／◇を選ぶと、全画面幅でガントを背景に残した重畳モーダルへ詳細を出す。desktopの右ペインとガント直下の詳細帯は使わず、mobileは同じ情報構造を画面下端へ寄せる。背景クリック、Esc、閉じるで閉じる。管理者はモーダルの名称・担当・状態・日付・進捗・内容・詰まり・完了条件そのものを選んで修正する。既存値を選んだときはモーダル本文全体をフォームへ差し替えず、押した値の表示位置だけを入力欄・保存・キャンセル・局所エラーへ置き換える。PATCHはその位置に対応する変更fieldだけを送り、計画期間だけは開始日と完了日の2fieldを同時に送る。保存またはキャンセル後は同じ詳細の同じ位置へ戻る。編集開始時はその入力欄へfocusを移す。編集中に背景・Esc・外側の閉じるを使う場合は、未保存変更の破棄を確認してから詳細を閉じる。独立した `編集` ボタンや鉛筆アイコンを置かない。新規タスク追加は複数fieldの入力が必要なためroot editorを使うが、入口は各3レーンの最終タスク直下に常設する48pxの `＋ 新規タスク` 行だけとし、ツールバーや詳細モーダルに別の追加ボタンを置かない。追加フォームは表示レーンから親工程を推測せず、同じレーン内でガントに表示中の未完了工程を `接続する工程` として必須選択させる（候補1件だけなら事前選択、0件なら先に工程と日程を追加するよう示して保存しない）。子タスクにする場合は同フォームの任意 `親タスク` から、現在選択している工程の配下だけを選べるようにし、工程を変えたら以前の親タスク選択を解除する。関係先はモーダルを編集入口にせず、一覧の編集可能cellを同じ位置で直接修正する。進捗railから開くモーダルは履歴閲覧専用とし、そこから第二の編集モーダルや関係先全体フォームを開かない。

## ガント直接編集とマイルストーン配置（v3.55.0）

`project_management_milestones.timeline_kind`（`'phase' | 'milestone'`、DB CHECK制約付き）が「工程バー」と「マイルストーン◇」の描き分けを持つ唯一の正本。レンダリングはこの列だけを見る — slugからの推測はしない。

**一般MSと設立ゲートは別物**。`timeline_kind='milestone'`の行は原則「計画上の一点日程（point-MS）」で、`planned_start`と`planned_end`は常にnull同士か等しい同じ日付のどちらかしか取らない（DB CHECK `project_management_milestones_point_ms_check` / API側 `isValidPointMilestoneRange` / `normalizePointMilestonePatch`）。唯一の例外が既存の設立前提2件（`business-paid-poc-oral-agreement` / `funding-investment-oral-agreement`）で、ゲート判定・強制レーン配置・バー＋◇の複合表示という既存のslug固有ロジック（`sxIsBlockingMilestone`）をそのまま維持し、`planned_start < planned_end`の実レンジを保持できる。一覧・ガントのラベルもこの2種を区別し、一般MSは「MS」「マイルストーン」、設立ゲートの2件だけが「設立ゲート」と表示される — 全てのMSを設立ゲート扱いにしない。凡例も一般MSを「計画上の到達目印」、設立ゲートを「先へ進む前提（2件のみ）」と分けて説明する。

デスクトップのポインタ操作で、`canManage`かつ`projectId`ありのユーザーは工程/タスクのバーとマイルストーン◇を直接編集でき、実バー／◇以外の行内空白はその日付へのMS追加確認を開く。`projectId`なしの埋め込み（`SxExecutiveControlDeck`の経営状況図など、書き込み面を持たない場所）は空白日付クリックを無効にし、click-select-onlyのまま変化しない。ドラッグの起点は実際のバー本体／◇だけで、行の余白からは始まらない。視覚上のバーは8pxのままだが、中央移動の当たり判定・両端の取っ手・◇の当たり判定はいずれも44px以上を確保し、取っ手は行のhoverまたはfocusで可視化される（`group-hover`）。取っ手はpointerdownだけを受け取り、pointermove/up/cancelは親のRowBar 1箇所だけで処理する（同じイベントが取っ手とRowBarの二重発火でPATCHが2回飛ぶ回帰を防ぐ）。開始・完了がある通常バーは、同日や数日の狭いバーでも移動・開始変更・完了変更の3操作を維持する。16pxの開始取っ手はバー開始位置の左外側、完了取っ手はバー終了位置の右外側へ完全に逃がし、中央移動の当たり判定を覆わない。一般MSと設立ゲートの◇は見た目でも区別する: 設立ゲート2件は塗りつぶした紫の◇、一般MSは中抜きの◇（凡例と一致）。
同日を含む狭いバーは描画上の中央移動領域を最低16px確定してから、その左右外側へ取っ手を置く。日付領域の左右には22pxの操作余白を予約し、0%/100%へ丸められる表示期間端でも取っ手と44pxの◇を固定列・scroll edgeの内側へ保つ。

- バー中央をドラッグ: 計画開始・完了の両方を同じ日数だけ移動し、期間を保つ（`computeBarMove`）。
- バー左端の取っ手をドラッグ: 計画開始だけを変更し、計画完了を追い越さない（`computeBarResizeStart`）。
- バー右端の取っ手をドラッグ: 計画完了だけを変更し、計画開始を追い越さない（`computeBarResizeEnd`）。
- 一般MSの◇をドラッグすると、計画開始・完了を同じ新しい日付へ揃えたまま移動する（`computeMilestoneMove`）— 元データが揃っていなくても常に一点化する。
- 設立ゲート2件の◇をドラッグすると、計画完了だけが動き、計画開始は保持される（`computeGateEndMove`）。開始日が未設定のゲートも、終了日さえあればこの◇でドラッグできる。

新規マイルストーンの配置は**その場でPOSTしない**。専用の「MSを追加」ボタンや「日付上に置く」配置モードは置かず、デスクトップガントの各行にある実バー／◇以外の空白日付ポイントを直接クリックすると、そのポイントの近くへ非モーダルの `MSを追加する？ / Y 追加する / N 閉じる` を出す。モバイルの縦一覧では各レーン末尾（常設の新規タスク行より前）に同じ期間の小型日付軸を置き、タップ位置を日付へ変換する。キーボード操作はfocus中の日付面の中央を仮日付として同じ確認とフォームを開き、フォーム内の予定日で調整できる。確認は画面上端で切れないよう、上側に収まらない場合だけクリック位置の下へ反転する。Yでこの確認を先に閉じてから既存の単一IssueEditor作成フォームを、クリックしたレーン・日付・一致する成果・`timeline_kind='milestone'`で事前入力して1回だけ開き、N・Esc・外側クリック・スクロールでは確認だけを閉じて何も書かない。実バー／◇のクリックは詳細選択、バー／◇／取っ手のpointer gestureは日程編集のままで、空白クリックと二重発火させない。クリックした表示レーンに接続可能な成果が1件だけならその成果を事前選択し、組織開発のように内部outcome候補が複数ある場合は勝手に1件を選ばず未選択で開く。フォームにはクリックした表示レーン内の成果だけを候補として出す。フォームの「保存」を押して初めてPOSTが飛び、閉じる/キャンセルすればDBには何も残らない。一般MSのフォームは開始・完了の2fieldではなく単一の「予定日」fieldを持ち、保存時にその値を`planned_start`・`planned_end`の両方へ書く。レーンは常に事業開発／技術開発／組織開発の3つだけ。MS/工程作成フォームにDB内部の4track（事業開発・技術開発・資金調達・体制構築）を独立した「柱」選択として出してはならず、「接続する成果（配置レーン）」の選択肢もこの3レーン名だけで表示する。保存payloadの厳密な`track`値は選択したoutcomeから導出し、fundingとorganizational_buildingはいずれも表示上の組織開発へ入る一方、DBの`milestone.track = outcome.track`不変条件は維持する。

### ガントの表示依存・固定ヘッダー・MS作成密度（v3.56.3）

工程ゲートの達成判定に使う既存の`project_management_milestone_dependencies`と、日程表上の終了→開始関係は意味が違う。ガントで手動作成する線は新設の`project_management_schedule_dependencies`だけへ保存し、前者のゲート充足・NewCo判定を変えない。接続元は日程を持つタスクまたはpoint-MS/設立ゲート、接続先は開始日を持つ別タスクに限定し、種類は`finish_to_start`だけとする。

通常のバー移動・両端リサイズと端点が重なるため、接続は明示的な`依存を接続`モードだけで行う。このモードでは通常の日程ドラッグと空白点MS追加を止め、タスク/MSの右端を起点にして別タスクの左端へドラッグする。キーボードとモバイルは同じ順序を「右端を起点」→「左端へ接続」の2操作で完了できる。Escまたはモード解除は未保存の線だけを破棄する。保存済みの線は常時矢印で表示し、接続モード中に線上の解除操作からsoft deleteできる。自己接続・重複・task→taskの循環・別PJの端点・削除済み端点・MS自身の配下タスクへのMS→task接続はDB triggerでも拒否する。DBロックは端点行（task同士はUUID順）→PJ単位advisory lockの順へ全経路を統一し、循環検査を直列化しつつ端点更新とのロック順逆転を作らない。

desktopガントは横方向だけでなく内部の縦方向にもスクロールする枠を持つ。月・設立目標・左側の`工程 / タスク`を置く先頭ヘッダーはその枠の`top: 0`へ固定し、縦スクロール後も日付軸と行名列の意味を失わせない。左側の工程名列は横スクロールでも固定する。

point-MS追加フォームは`接続する成果 / MS名 / 予定日`の3項目だけを必須とし、`完了条件`は任意にする。`到達点`はpoint-MSでは完了条件と重複するため作成フォームへ出さず、`次の成果物`は次工程が未定のMSにも入力を強制しない。既存DBの非NULL列は削除せず、APIが明示的な`未設定 / 未確認`を保存して後から詳細で補えるようにする。作成時の非表示`criticality`は`medium`とし、point-MSを置くだけで重要案件・高重要度の情報不足を増やさない。工程（phase）の作成契約は変更しない。

タスク/MS作成・編集のroot editorはdesktopで通常幅640px、wide 760px、最大高720px、詳細PlanInspectorは幅820px・最大高720pxを上限とし、header 54px、入力36px、footer操作38pxへ圧縮する。390px相当ではbottom sheetへ切り替え、入力・閉じる・footer操作を44px以上、入力文字16pxへ戻す。密度を上げるためにモバイルの操作性を削らない。

ドラッグ中はポインタ移動のたびにローカルpreviewだけを更新し、サーバーへは何も送らない。pointerupで初めて1回だけPATCHする。4px未満の移動はドラッグではなく通常のクリック（行の詳細を開く）として扱い、クリックとドラッグを競合させない（`isWithinClickThreshold`）。Esc・pointercancelはpreviewを破棄するだけで何も送らない。ポインタキャプチャの喪失（`lostpointercapture`）は、自分自身のpointerupによる正常な解放（保存処理が既に始まっている）となら区別し、保存中のpreviewを誤って巻き戻さない — 本当にキャプチャを異常に失った場合だけpreviewを破棄する（`shouldCancelOnLostPointerCapture`、同期refで判定）。ドラッグ状態は`dragRef`（同期ref）を単一の真実として扱い、pointermoveの直後にpointerupが同じバッチで来ても最後のpreviewを取りこぼさない — PATCH送信もこのrefから読む（Reactのstate更新は次のイベントハンドラに即時反映される保証がないため）。保存に失敗した場合（409以外も含む）はベストエフォートで`management`を再取得し、その再取得自体が失敗したら「保存できたか確認できなかったので再読み込みしてね」と明示する。日付計算・しきい値判定・並行制御の正規化はすべて`src/lib/sx-gantt-drag.ts`の純関数（DOM非依存）に集約し、`npm run test:sx-gantt-drag`・`npm run test:sx-gantt-pointer-gesture`で単体テストする。

工程/タスクのPATCHは`project_management_milestones.version` / `project_management_tasks.version`（既存の自動採番列）を使った楽観的並行制御を**必須**で通す。ドラッグ・ガント空白点のY確認から開いたフォームのPATCH・週次管制のroot editor・SxNavigationDashboard・`/workspace`のManagementEditor、milestone/taskを触る全てのPATCH経路が、読み込んだ時点の`version`を`expected_version`として送る。`expected_version`が欠落・不正なら400、`before`行の`version`と不一致なら409（`code: "version_conflict"`）を返す。該当行のUPDATE自体も`.eq("version", expected_version)`で絞ることで検出漏れをなくす。クライアントは409を「他の人が更新した」通知として表示し、最後に保存した側で黙って上書きしない — 必ず最新の`SxManagementBundle`を再取得してUIへ反映する。監査履歴insertが失敗したときの補償ロールバックも、自分の更新が生んだ`version`へ`.eq("version", updatedVersion)`でCASし、その後さらに別の変更が乗っていたら（CAS不一致）ロールバックを実行せず「補償復元は安全に実行できなかった」と報告する（後発の編集を黙って踏みつけない）。

マイルストーンの新規作成・PATCHどちらも、選択した`outcome_id`が選択した`objective_id`に属し、outcomeの`track`がmilestoneの`track`と一致することをサーバー側で検証する（`assertMilestoneParentIntegrity`、APIレイヤ）。migration 220はこの整合性を全PJ横断の一般不変条件としてDBレベルでも強制するtrigger（`project_management_milestone_parent_integrity()` + `project_management_milestones_parent_integrity_trigger`、outcome_id/objective_id/track更新時にBEFORE INSERT/UPDATEで発火）を追加する — APIパス以外から書かれた行にも同じ不変条件を保証するbackstopで、追加前に既存データの不整合を検査し明確な例外で失敗する（同一トランザクション）。

計画開始・完了の日付はサーバー側で厳密なYYYY-MM-DDカレンダー日付として検証する（`2026-02-30`のような実在しない日付は正規表現だけでは弾けないため、`isStrictCalendarDate`でカレンダー変換の往復一致を見る）。PATCH/POSTのどちらも、送信fieldと既存行をマージした計画開始・完了の組で`planned_start <= planned_end`を検証し（DBの`project_management_milestones_planned_range_check` CHECKと同じ規則）、逆転した範囲は保存前に拒否する。

## 表示上の禁止

- 工数0、差分0、論点0を「活動なし」「変化なし」と言い換えない。
- `judgment` の全体判定を論点・仮説の放置防止件数として流用しない。
- `open` を「未着手」と表示しない。検証や根拠が進んでいる可能性があるため「未解決」とする。
- 週次管制へ完了見込み、予定との差、予測diamond、差分線、工程間の破線接続を戻さない。
- 自動推測した依存線や意味不明な破線を戻さない。手動の終了→開始矢印は`project_management_schedule_dependencies`だけを使い、既存のゲート依存へ混ぜない。
- 通常工程・タスクへゲートタグやマイルストーン記号を付けない。停止条件は上記2件から推測で増やさない。
- 関係先の進行状況を固定段階へ丸めない。一覧では現在の状況とゴールを分離し、全stepは詳細に置く。会社名下のsegmentと詳細内の進行状況blockを別々の配列から作らない。PoC候補先をタブ内で隠さず、VCを別台帳に分けない。
- 関係先の行全体を詳細ボタンへ戻さない。編集は表示cell内、履歴は会社名下の進捗railだけを入口にする。
- 既存値の修正に独立した `編集` ボタンを戻さない。値そのものを操作対象にする。
- 内部ID、raw source ref、メール本文・宛先、議事録全文を出さない。関係先台帳へ取り込む接点情報は、確認済みの要点・日付・送受信方向・以後のボールに限定する。
- 既存 `/workspace` の導線・auth・memberHomeを新URLへ置換しない。

## 受入条件

- 1440px、768px、390pxでページ本体の横あふれがない。
- 最上段の6バケット（停止/期限超過/7日以内/担当不明/期限なし/判断待ち）は工程・タスク・論点・仮説・検証・判断・action・関係先保有事項の共通母集団から算出され、30秒以内に最大の詰まりと件数を読める。バケットを押すと同じ帯の下に該当元項目一覧（種別・担当・期限・影響工程つき）が開き、各項目を押すと必ず元の編集文脈（工程/タスクはガント該当行・詳細、論点系は該当カード/詳細、関係先は該当行）へ移動する。算出値自体は編集できない。今週入力はこの6バケットと別に、データ接続状況側で確認できる。
- PJ全体の担当負荷の各行（最大100件規模）は押すと同じ導線で元項目へ移動でき、dead endにならない。
- 全体ガントは常に事業開発／技術開発／組織開発の3レーンだけを表示し（資金調達は組織開発へ統合、4本目の合成レーンを作らない）、各レーンの計画・実績、工程→タスク→子タスクを同じ時間軸で確認できる。設立前提（有償PoC口頭合意・出資口頭合意）の2件はガント外のカード帯でも独立レーンでもなく、それぞれ事業開発／組織開発レーンへ強制配置された行として日程未設定でも確認でき、日程未設定でも◇マーカーが「日程未設定」テキスト横（非時間的な位置）に表示される。配下の必須タスク（有償PoC5件・出資7件）が初期展開され、完了数と次の未完了タスクが同じ行で読める。この2件の充足は4項目証跡＋配下必須タスク全完了の両方が揃って初めて成立し、証跡だけでは充足にならない。
