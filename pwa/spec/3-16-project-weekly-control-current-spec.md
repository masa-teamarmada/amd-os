# PJ週次管制画面 仕様

> **目的**: 計画の再作成ではなく、既に管理されている計画・進捗から「先週からの変化」「今回決めること」「決定後の介入」を週次会議で短時間に確認する。論点・仮説を担当・期限・検証・根拠・判断へ接続し、放置を防ぐ。

## 正本境界

- 新画面は `/project/[projectId]/weekly-control`。
- 既存の `/project/[projectId]/workspace` は、計画詳細・技術証明・関係先・工数入力を扱う統合ワークスペースとして維持する。置換・redirectしない。
- 新画面はUIを先に固定する。週次差分の自動抽出が未接続の項目は、0件・変化なしと断定せず `抽出接続待ち` と表示する。
- ガントと関係先はこの画面から手動修正でき、手動で確認・保存した現在値を正本とする。将来の自動抽出は既存値を直接上書きせず、差分候補として人の確認へ回す。
- H1見出しは `SolvioraX PJワークスペース` の固定文言。プロジェクト名を動的に埋め込まない。

## Route / Auth

| 項目 | contract |
|---|---|
| page | `src/app/(app)/project/[projectId]/weekly-control/page.tsx` |
| view | `SxWeeklyControlDashboard` |
| auth | `getCurrentMemberAccess()`。未ログインは同URLを `next` に保持してloginへ送る |
| PJ境界 | `getProjectWorkspaceBundle(projectId, access)` と `projectScopedPathAllowed()`。PJ限定ユーザーは所属PJだけ閲覧可 |
| shell | `/workspace` と同じ埋め込みshell。月初合意overlayの対象外 |
| write | portfolio/adminだけ。既存 `/api/project-workspace/[projectId]/management` を使い、clientからDBへ直接書かない |

## 画面構造

1. **PJ全体の管制入口（旧・週次状態帯を再構成）**: 工程・タスク・論点・仮説・検証・判断・action・関係先保有事項を`sxProjectOwnerLoads`が正規化した同じ未完了作業単位の共通母集団から、`停止 / 期限超過 / 7日以内 / 担当不明 / 期限なし / 判断待ち`の6バケットをクリック可能な帯で表示する。算出値自体は編集させず、バケットを押すと同じ帯の直下へ該当元項目一覧（種別・担当・期限・影響工程つき）を絞り込み表示し、一覧の各項目を押すと必ず元の編集文脈へ移動する（工程/タスクはガント該当行・詳細を全画面モーダルで開く、論点/仮説/検証/判断/actionは該当論点/仮説/検証/判断/actionレコードそのものを開くroot editorモーダル）。検証（`kind: "validation"`）は`edit_validation`で押した`SxValidationRun`そのものを開き、仮説・判断・actionと同様、IDが一致するレコードを見つけられない場合は親論点編集へ黙ってフォールバックせず「元の項目を見つけられなかったよ」のnoticeで終える。論点系root editorは全画面backdropの重畳モーダルであり、開く前にガント側の選択（工程/タスク）を必ず解除し、背景ページはスクロールしない（開閉前後でscrollYを変えない）。関係先由来の項目はスクロールせず、`SxProjectWorkUnit.originResource`（`partner_work_item` / `commitment` / `partner_next_action`）と`recordId`/`partnerId`から対象レコードを直接引いて、由来別の単一編集モーダルを直接開く（`partner_work_item`は既存の保有事項編集フォーム、`commitment`は約束・次アクション専用の編集フォーム、`partner_next_action`＝構造化保有事項が無いフォールバック行は関係先編集のうち`次にやること / 当方担当 / 期限 / 期限精度 / 現在の保有側 / 現在の担当`の6項目だけに絞ったフォーム）。IDの一致だけで別resourceへ探索をフォールバックしない。開く前に選択中の詳細/インラインfieldエディタは閉じ、開くモーダルは常に1つだけにする。静的な5枚のKPIカードとゲート専用カウントは廃止した。今週入力（人員配分の入力人数）は作業遅延の6バケットと混ぜず、7.データ接続状況側だけに表示する。
2. **PJ全体の担当負荷**: 工程、タスク、必須ゲート、論点、仮説、検証、判断、action、関係先保有事項を同じ未完了作業単位へ正規化し、担当ごとに `停止 / 期限超過 / 7日内 / 期限なし / 全未完了 / 影響ゲート` を表示する。関係先だけの件数をPJ全体負荷として扱わない。行は1で使う共通母集団と同じ`SxProjectWorkUnit`を使い、各行を押すと1と同じ導線で元の編集文脈へ移動する（dead endにしない、aria-labelは実動作どおり「〜を編集」）。desktopの閉じた担当者行は左右2カラムに並ぶが、実体は`OwnerLoadColumn`という完全に独立したcolumn要素（前半/後半で担当者配列を分割、mobileで連結表示しても元の配列順序と一致する）で、片側のdetailsを展開しても反対列のカード高さ・次カードのY座標は変わらない。
3. **週次変化レール**: `先週→今週`、`今回の会議`、`決定→介入` の3段。差分未接続はプレースホルダーのままにする。
4. **全体ガント**: `SxUnifiedTimeline` / `deriveSxUnifiedTimeline` を再利用するが、`SxUnifiedTimeline` は表示直前に**必ず事業開発／技術開発／組織開発の3レーンだけへ統合し直す**（`DISPLAY_LANE_ORDER`/`DISPLAY_LANE_LABEL`）。`deriveSxUnifiedTimeline`自体が返す4本柱（事業開発・技術開発・資金調達・体制構築）のうち、資金調達（funding）は独立レーンを持たず組織開発（旧・体制構築）へ統合する。週次管制は `dateMode="planned_only"` とし、完了見込み日・予定との差・差分線・予測ひし形・重要経路の破線接続を表示、範囲、並びの全てから外す。DBの `project_management_milestones` はこの画面では通常の工程として扱い、依存や `gate` 列があるだけでゲート・マイルストーンへ格上げしない。現時点の停止条件として表示するマイルストーンは `business-paid-poc-oral-agreement`（NewCo設立の最低条件は1社の有償PoC口頭合意。2社目を禁じる意味は持たせない）と `funding-investment-oral-agreement`（現時点は事業計画未完成・DD未着手）の2件だけ。この2件は**ガント外の独立したカード帯も、4本目の合成レーン（旧・独立した「設立前提」レーン）も持たず、`BLOCKING_MILESTONE_LANE`で`business-paid-poc-oral-agreement`は事業開発レーンへ、`funding-investment-oral-agreement`は組織開発レーンへそれぞれ強制配置する**（milestoneの実際の`track`列の値によらない）。desktopの月軸グリッドとmobileの縦一覧のどちらも、この2件を対象レーン内の行として扱い、独立したsectionへ切り出さない。日程未設定の行は右列にバーの代わりに「日程未設定・状態」「達成充足バッジ」「必須タスク完了数/総数・次の未完了タスク」をテキストで表示し、この2件については日程未設定でも◇（マイルストーン）マーカーを消さない——位置は日付比例（バー上のleft:X%）ではなく、既存の「日程未設定」テキストのすぐ横という非時間的な位置に置き、捏造した日付やX印は使わない。`timeline.valid`が偽（日程付き工程が0件）でもこの2件の行と説明文は表示し続ける。配下の`project_management_tasks`（有償PoCは5件、出資は7件の必須タスク）は初期展開し、完了数（`sxMilestoneRequiredTaskSummary`の`completed/total`）と次の未完了タスクを同じ行で示す。タスクは手動編集可能。通常の柱レーンにはこの2件を表示せず、二重表示しない。他の通常工程をこの2件のようなMSへ格上げしない。`unassessed` は未確認、明示的未完了は未達、`completed` でも証跡不足なら未確認とする。**この2件の達成判定（充足）は、口頭合意の4項目証跡（`先方または投資家 / 合意内容 / 確認日 / 根拠`）が揃い、かつ配下の必須タスクが全件完了しているときだけ「充足」となる（`sxGateRequirementState`）。4項目証跡だけでは充足にしない。** 工程配下は `project_management_tasks` のタスク→子タスクを初期折りたたみで表示する（設立前提2件は例外で初期展開）。mobile/tabletは横ガントを主表示にせず、日付・工程・前提・担当の縦一覧へ切り替える。ガント行の高さ（`ROW_H`）は約48pxとし、月軸/凡例/ピン行/ツールバーも同じ密度で圧縮する。
5. **関係先リスト**: `SxPartnerPipeline` を唯一の一覧とし、大学・金融機関・試作先・PoC候補先・VCを同じ台帳へ1社1行で表示する。`全関係先 / PoC候補先 / VC` は同じ表を絞る排他的なタブであり、別リストや別データを作らない。PoC候補先タブは候補全件を表示し、VCタブは保存済みroleの `role_kind='shareholder_investor'` だけで判定する。名称から推測しない。主列は `関係先 / 現在の状況 / ゴール / 詰まり・PJ影響 / 次にやること / 担当・期限 / 現在地の根拠 / 履歴・保有`。一覧の `現在の状況` は関係先本体の現在ボールだけを扱い、`保有側 / 担当` の2slotを閲覧時から明示する。編集時も同じ2slot・同じ高さ・同じ列幅のまま値だけをselect/inputへ置き換え、PATCHは `current_ball_side / current_ball_owner` に限定する。期限をこのcellへ重複表示・編集せず、`担当・期限` は主要対応事項1件の担当と期限だけを扱う。主要対応事項が関係先本体へfallbackする場合も `owner_label / due_date / due_date_precision` を使い、`current_ball_*` と保存先を重ねない。`ゴール` は目標状態だけを表示する。管理者は表示中の編集可能な値そのものを押し、そのセルだけで入力・保存・取消・エラー表示を完結させる。行全体はボタンにせず、行の余白や読み取り専用cellを押してもモーダルを開かない。確認済み接点（古い順）→現在地→未完了作業→次の一手→ゴールの可変長 `進行状況` と全履歴は、会社名下のsegment railだけから開く閲覧専用モーダルへ置く。railとモーダル内の進行blockは同じstep配列を使い、件数と順序を必ず一致させる。PoC/VC表示では役割groupや保留foldで行を分断しない。行動、担当、期限、関連工程は同じ構造化保有事項から選び、別レコードの値を合成しない。構造化保有事項がない場合だけ関係先本体の対応事項へフォールバックし、関連工程を推測接続せず `PJ影響 未接続` とする。上部は担当別の未完了件数・危険件数・情報不足を集計する。履歴モーダルは進行状況、全やり取り履歴、未完了/完了保有事項を表示し、関係先全体の編集フォームへ切り替えない。メール本文、アドレス、URL、個人連絡先、内部source refは保存・表示しない。p21のVCはPartners Fundに加え、別交渉主体としてDAVP、BNV、いよぎんキャピタルを保存済みpartner+roleで持つ。接触段階・合意・ボール・期限・ゴールの根拠がない3社は未確認のままにする。
6. **論点・仮説リスト**: `要整理 → 検証中 → 判断待ち → 決定・棄却` の4状態で一覧する。desktopは4列、tabletは2列、mobileは1列へ再配置し、ページ横スクロールを発生させない。セクション名・列名は業務上の名詞を使い、目的説明やコピーを見出しへ置かない。
7. **データ接続状況**: 週次差分、論点・仮説、工数（今週入力の人数はここに表示し、1の作業遅延バケットとは混ぜない）、関係先メール接点の接続状態を示す。

## 論点・仮説の放置防止

### 段階

| 段階 | 判定 |
|---|---|
| 要整理 | 未解決で、検証中・判断待ち・完了の条件を満たさない |
| 検証中 | 論点/仮説が `validating`、または検証が `planned/running` |
| 判断待ち | `decision_needed`、未決の意思決定、または `validated` 仮説がある |
| 決定・棄却 | 論点が `closed/decided`、または全仮説が `rejected/decided` |

段階と警報は別に扱う。期限超過・更新切れは列を移動する条件ではなく、どの段階でも重ねて表示する。
決定・棄却列でも未完了の決定後actionがあれば要フォローへ残し、判断だけ記録して実行が忘れられる状態を作らない。

### 警報

- **要フォロー**: 未完了で、担当不明、次の期限なし、仮説なし、検証中なのに検証予定なし、期限超過、更新切れのいずれか。
- **次の期限**: 論点、活動中の仮説、計画/実施/停止中の検証、未決判断、未完了actionから最も近い日を採用する。
- **最終更新**: 親論点だけでなく、仮説・根拠・判断・actionの `lastVerifiedAt` の最新日を採用する。子だけを更新した論点を更新切れにしない。
- **更新切れ**: 最終更新から7日以上。日付欠損も更新切れとして扱い、0日扱いしない。
- **期限超過**: 未完了論点の次の期限が基準日より前。完了済み論点へ赤警報を残さない。

## 書き込み契約

画面から次を既存管理APIへ保存できる。

- 工程: 新規追加と、名称 / 状態 / 担当 / 計画開始・完了 / 実績完了 / 進捗 / 日程確度 / 詰まり / 完了条件 / 完了証跡の更新。
- 設立前提: 現行2マイルストーンの状態・担当・日付・証跡を値の選択から直接修正できる。接続値を選ぶと依存条件を修正できる。週次管制の依存種別は `finish_to_start` に限定する。
- タスク: 工程直下またはタスク配下へ新規追加し、計画、実績、進捗、親タスク、作業内容を更新。親子は同一PJ・同一工程内に限定し、循環参照をAPI/DBで拒否する。
- 関係先: 新規追加と現在値更新。やり取り履歴、誰が抱える具体的保有事項、役割分類を同じ画面から追加編集する。
- 論点: 新規、title / kind / status / owner / due / confidence更新。
- 仮説: 論点配下へ新規、statement / status / owner / due / confidence更新。
- 根拠・反証: 論点または仮説へ supporting / counter / missing / observation を追加。
- 検証: 仮説へ方法・担当・予定・期限・状態を追加。既存検証（`SxValidationRun`）は共通母集団・PJ全体の担当負荷から`edit_validation`（`resource: "validation"`のPATCH）で直接編集でき、押した検証レコードそのものが開く（親論点の編集へフォールバックしない）。
- 判断: 論点または仮説を今週の判断キューへ追加。
- 決定: 判断待ちを決定済みまたは保留へ更新し、決定内容・決定者・決定日を記録。
- 決定後の行動: 決定配下へ担当・期限・完了条件・次回確認日を追加し、実行中・停止・完了と完了証跡を更新。

カードの「次の動き」は種類の固定順ではなく、`停止中 → 期限超過 → 期限が近い → 期限なし` の順で選ぶ。同順位では決定後action、判断、検証の順とし、決定後の実行が判断記録の陰に隠れないようにする。カード詳細は折りたたみ内で根拠・判断・actionを全件表示し、件数だけ見えて履歴へ到達できない状態を作らない。

保存成功後はAPIが返す最新 `SxManagementBundle` で画面を更新する。画面内で楽観的に完了へ移動させない。PATCHは `last_verified_at` と手入力由来をAPI側で更新する。

ガントは記号だけに意味を預けない。凡例は `計画期間 / 実績 / マイルストーン` の3項目だけにする。通常工程の各行は `予定 / 実績 / 前提` を文字で出し、進捗未登録は `0%` でなく `未登録` と表示する。◇とマイルストーン名は上記2件だけに使い、通常工程の終端は単純な予定日線で示す。

行の名称またはバーを選ぶと、全画面幅でガントを背景に残した重畳モーダルへ詳細を出す。desktopの右ペインとガント直下の詳細帯は使わず、mobileは同じ情報構造を画面下端へ寄せる。背景クリック、Esc、閉じるで閉じる。管理者はモーダルの名称・担当・状態・日付・進捗・内容・詰まり・完了条件そのものを選んで修正する。既存値を選んだときはモーダル本文全体をフォームへ差し替えず、押した値の表示位置だけを入力欄・保存・キャンセル・局所エラーへ置き換える。PATCHはその位置に対応する変更fieldだけを送り、計画期間だけは開始日と完了日の2fieldを同時に送る。保存またはキャンセル後は同じ詳細の同じ位置へ戻る。編集開始時はその入力欄へfocusを移す。編集中に背景・Esc・外側の閉じるを使う場合は、未保存変更の破棄を確認してから詳細を閉じる。独立した `編集` ボタンや鉛筆アイコンを置かない。新規タスク追加は複数fieldの入力が必要なため、従来の詳細本文全体フォームを使ってよい。関係先はモーダルを編集入口にせず、一覧の編集可能cellを同じ位置で直接修正する。進捗railから開くモーダルは履歴閲覧専用とし、そこから第二の編集モーダルや関係先全体フォームを開かない。

## 表示上の禁止

- 工数0、差分0、論点0を「活動なし」「変化なし」と言い換えない。
- `judgment` の全体判定を論点・仮説の放置防止件数として流用しない。
- `open` を「未着手」と表示しない。検証や根拠が進んでいる可能性があるため「未解決」とする。
- 週次管制へ完了見込み、予定との差、予測diamond、差分線、工程間の破線接続を戻さない。
- 通常工程・タスクへゲートタグやマイルストーン記号を付けない。停止条件は上記2件から推測で増やさない。
- 関係先の進行状況を固定段階へ丸めない。一覧では現在の状況とゴールを分離し、全stepは詳細に置く。会社名下のsegmentと詳細内の進行状況blockを別々の配列から作らない。PoC候補先をタブ内で隠さず、VCを別台帳に分けない。
- 関係先の行全体を詳細ボタンへ戻さない。編集は表示cell内、履歴は会社名下の進捗railだけを入口にする。
- 既存値の修正に独立した `編集` ボタンを戻さない。値そのものを操作対象にする。
- 内部ID、raw source ref、メール本文・宛先、議事録全文を出さない。関係先台帳へ取り込む接点情報は、確認済みの要点・日付・送受信方向・以後のボールに限定する。
- 既存 `/workspace` の導線・auth・memberHomeを新URLへ置換しない。

## 受入条件

- 1440px、768px、390pxでページ本体の横あふれがない。
- 最上段の6バケット（停止/期限超過/7日以内/担当不明/期限なし/判断待ち）は工程・タスク・論点・仮説・検証・判断・action・関係先保有事項の共通母集団から算出され、30秒以内に最大の詰まりと件数を読める。バケットを押すと同じ帯の下に該当元項目一覧（種別・担当・期限・影響工程つき）が開き、各項目を押すと必ず元の編集文脈（工程/タスクはガント該当行・詳細、論点系は該当カード/詳細、関係先は該当行）へ移動する。算出値自体は編集できない。今週入力はこの6バケットと別に、データ接続状況側で確認できる。
- PJ全体の担当負荷の各行（最大100件規模）は押すと同じ導線で元項目へ移動でき、dead endにならない。
- 全体ガントは常に事業開発／技術開発／組織開発の3レーンだけを表示し（資金調達は組織開発へ統合、4本目の合成レーンを作らない）、各レーンの計画・実績、工程→タスク→子タスクを同じ時間軸で確認できる。設立前提（有償PoC口頭合意・出資口頭合意）の2件はガント外のカード帯でも独立レーンでもなく、それぞれ事業開発／組織開発レーンへ強制配置された行として日程未設定でも確認でき、日程未設定でも◇マーカーが「日程未設定」テキスト横（非時間的な位置）に表示される。配下の必須タスク（有償PoC5件・出資7件）が初期展開され、完了数と次の未完了タスクが同じ行で読める。この2件の充足は4項目証跡＋配下必須タスク全完了の両方が揃って初めて成立し、証跡だけでは充足にならない。
- `全関係先 / PoC候補先 / VC` を同じ一覧の排他的タブとして切り替えられる。PoC候補先タブは候補全件、VCタブは保存済みの株主・投資候補roleだけを表示し、Partners Fund / DAVP / BNV / いよぎんキャピタルへ到達できる。各行は `現在の状況` と `ゴール` を別列で比較できる。`現在の状況` は閲覧時から `保有側 / 担当` の2slotが見え、押した後も同じ2slot・同じ寸法を維持し、期限や期限精度を追加表示しない。1440 / 1280 / 1279 / 768 / 390pxで、閲覧・編集中・保存中・局所エラー時のcell/行/次行の座標差を1px以内とする。編集可能な表示cellを押すとそのcellだけが編集欄へ変わる。行全体や右端件数は履歴入口にしない。会社名下segment railだけが履歴モーダルを開き、railとモーダル内の進行状況blockの件数・順序が一致する。具体的な詰まり、同じ保有事項に属する行動・担当・期限、止まる工程、直近の根拠を比較できる。担当別の未完了/危険/情報不足を上部で確認でき、履歴を開いても編集フォーム、本文・アドレス・URL・内部source refはDOMへ出ない。ガント行の詳細は右側へ幅を奪わず、ガント上の重畳モーダルで読める。通常バー末尾に縦線を出さない。
- 任意行の計画、実績、必須条件の充足数、次の未達条件を5秒以内に説明できる。進捗未登録を0%と表示しない。
- 管理者はガントの詳細値を選ぶと、独立した編集ボタンを経由せず、押した値の位置だけが入力欄へ変わってfocusが移る。PATCHは変更fieldだけ、期間は開始・完了の2fieldだけを送る。保存・キャンセル・エラーはその位置で完結し、詳細本文全体を既存値編集フォームへ差し替えない。編集中も`aria-modal=true`のdialogとbackdropは各1つだけで、未保存変更がある状態で背景・Esc・外側の閉じるを使うと破棄確認が出る。新規タスク追加だけは詳細本文全体フォームを使い、追加操作は `＋` ボタンから行う。
- 論点追加は2操作以内、既存論点への仮説追加はカードから1操作。編集・追加ボタンはアイコンだけにしない。
- 5秒で要フォロー件数、30秒で論点→仮説→根拠→検証→判断の接続を説明できる。
- H1は常に `SolvioraX PJワークスペース` の固定文言で表示される。
- 共通母集団・PJ全体の担当負荷から関係先由来の項目を押すと、スクロールせずその場で由来別（`partner_work_item` / `commitment` / `partner_next_action`）の単一編集モーダルが開く。押す前に開いていた詳細/インラインfieldエディタは自動で閉じ、常にモーダルは1つだけになる。`partner_next_action`（構造化保有事項が無いフォールバック）は関係先編集の全項目ではなく、次にやること・当方担当・期限・期限精度・保有側・現在の担当の6項目だけを表示する。
- 六指標帯（1のバケット帯）はdesktopで高さ64px以下、各バケットボタンは44px以上のヒットターゲットを維持する。週次フローレール（3の3段）は各カード約200pxに収まる。PJ全体の担当負荷の閉じた担当者行はdesktopで2カラム、mobileで1カラムに並び、片側の展開が反対列のカード高さ・次カードのY座標（差1px以内）を変えない。
- 論点系root editor（`edit_issue` / `edit_hypothesis` / `edit_validation` / `edit_decision` / `edit_action` 等）はcreatePortalでdocument.body直下へ描画されるため、`.editorBackdrop`が`--sheet` / `--ink` / `--muted` / `--line` / `--green` / `--red` 等のCSS変数一式を自前で再定義し、`.page`の継承チェーン外でも生成り `#fffdf7`（`rgb(255,253,247)`）の不透明dialog背景・濃墨文字・深緑CTAを保つ。閉じるボタン・保存/キャンセルCTA・input/select/textarea・checkbox行は44px以上のヒットターゲットを持ち、focus-visibleは3:1以上のコントラストを持つ可視outlineで示す。dialog roleの要素は常に1つだけ。
- `npm run lint -- <changed files>`、`npm run test:sx-weekly-control`、`npm run test:sx-project-owner-load`、`npm run test:sx-partner-holdings`、`npm run test:critical-ui`、`npm run build` を通す。
- `/project/[projectId]/workspace` の既存受入anchorを維持する。
