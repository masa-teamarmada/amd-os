# PJ別 利益構造ダッシュボード 現行仕様

> **この章は何か**: `/admin/project-profitability`（PJ別 利益構造）の contract。
> まさが「どのPJが儲かっていて、どのPJがまさの稼働で回っているか」を判定するための画面。

## 目的

> **2026-08-30 まさ**: 「どのPJが儲かっていて、どのPJがまさの持ち出しで回っているか」
> 「現金が出ていかないだけの状態を利益と呼ばない。まさの労働の対価を会社に付け替えているだけ」

ここでの「儲かっている」は、**まさ自身の稼働を織り込んだうえで**の話。会社の口座から現金が出ていかない
だけの状態は利益ではない。まさが働いたから外部への支払が要らなかっただけで、まさの時間は有限だから。

$$
\text{まさ込み利益} = \text{会社に残る現金} - (\text{まさの投下時間} \times \text{時間単価})
$$

| 記号 | 意味 | 出どころ |
|---|---|---|
| 会社に残る現金 | 請求額から、社外へ出ていく分をすべて引いた残り | 下の計算式 |
| まさの投下時間 | tally に記録されたまさの開発時間 + MTG時間 | `tally_weekly_effort_entries` |
| 時間単価 | まさの1時間の値段。**画面のスライダーで動かせる** | 既定 25,000円/時 |

## お金の流れ

請求額 $R$、契約バッファ $B$ のシーズンで、報酬計算の正本
（[`7-1 報酬計算ロジック`](../manual/7-1-reward-calc-spec.md)）が定める分岐は次のとおり。

$$
R - B = \underbrace{(R-B) \times 0.65}_{\text{配分原資 } P} + \underbrace{(R-B) \times 0.35}_{\text{AMD運営費30\% + クローザー報酬5\%}}
$$

配分原資 $P$ はさらに2つに分かれる。

| 分岐先 | reward_summary_json のキー | 現金は社外へ出るか |
|---|---|---|
| 支払対象メンバーへの現金支払 | `externalPayoutCapYen` | **出る** |
| 支払対象外メンバーへの非現金配賦 | `companyReserveYen` | 出ない（会社に残る） |

**クローザーは全PJまさ**（`project_members.is_closer` の13行すべて `ID001`、2026-08-30 実データ確認）
なので、35%枠も社外へは出ない。したがって社外へ出る現金は次の2つだけになる。

$$
\text{会社に残る現金} = R - B - \text{externalPayoutCapYen の合計}
$$

契約バッファ $B$ は営業費用・旅費などの実費枠。AMD運営費30%は会社に入る扱いとし、全社の固定費は
この画面では引かない（PJに紐づかないため。全社の収支は `/management-score`）。

### 請求額の逆算

`billing_cycles` に請求額そのものの列が無いため、シーズン原資から戻す。

$$
R = \frac{\text{本契約原資} + \text{別財布原資}}{0.65} + B
$$

| 項 | 出どころ |
|---|---|
| 本契約原資 | `value_plan_cycles.budget_yen`（= $(R-B) \times 0.65$ の確定値） |
| 別財布原資 | Σ `billing_cycles.extra_budget_yen`（cap_extra プール。ZMPのOkuDoor受託など） |
| 契約バッファ $B$ | `value_plan_cycles.buffer_breakdown_json.total` が正本。無ければ Σ `billing_cycles.budget_buffer_amount` |

月額固定のPJで契約書の月額 × 月数と一致することを確認済み（2026-08-30）。

| PJ | 逆算した請求額 | 契約上の月額 × 月数 |
|---|---|---|
| SX 202604-202703 | 10,480,000 | 1,048,000 × 10 = 10,480,000 |
| KUTE 202605-202703 | 7,199,991 | 654,545 × 11 = 7,199,995（4円は丸め差） |
| ZMP 202601-202612 | 5,600,000 | 300,000 × 12 + 別財布 2,000,000 = 5,600,000 |

## なぜ年ではなくシーズン単位か

> **2026-08-30 まさ確定**: 「そのシーズンで払うべき額は最初から決まっているわけなので、
> シーズン全体で試算した方がよくない？ 現状未払かどうかって、そのPJの収益率を見るうえでは
> 邪魔な情報だと思う。」

シーズンで払う総額は `value_plan_cycles.budget_yen` として最初から確定している。月ごとの cap 按分は
**いつ払うか**を決めているだけで、**いくら払うか**ではない。月末時点の未払残はノイズにしかならない。

シーズンは年をまたぐ（SX は 202604-202703）。1つのPJが複数シーズンを持つ（SX は 202601-202603 と
202604-202703）。年で切ると1シーズンが分断され、比較の単位として成立しない。

## この画面が扱わないもの（禁止事項）

すべて 2026-08-30 のまさの指摘が根拠。guard（`scripts/check_project_profitability.mts`）で機械的に止める。

| 扱わないもの | 理由（まさの言葉） |
|---|---|
| ポイント（MS pt）・稼働需要 `grossDueYen` | 「ポイントなんて、ここで考慮する必要すらなくない？ マイルストーンをどのように設定しようが、原資を超える支出にならない設計じゃん」。配る内訳を決めるだけで会社の収支に効かない |
| 「需要が原資のN倍」という警報 | 上と同じ理由で意味を持たない |
| 未払残 `stockYen` | 「現状未払かどうかって、そのPJの収益率を見るうえでは邪魔な情報」 |
| 「持ち出し」「取り分ゼロ」という語 | 意味を定義せずに使い、しかも中身が逆だった |
| 「枠超え」という表示 | 「そもそも枠ってなに？ ちゃんと65%の予算に収まってるように見えるんだけど」。cap按分で必ず原資内に収まる |
| メンバー支払0円を問題として出すこと | 「理想的でしょ？」 |
| 未計算を「未配分の金額」として出すこと | 「報酬を渡すべき人には渡し終わってるよ。計算ができてないだけ」 |
| まさ以外のメンバーとの稼働比較 | 「tallyはおれの稼働だけをカウントするアプリだよ。そもそも前提が間違ってる」 |

**まさへの現金支払0円は設計どおり**であり、配分の放棄でも持ち出しでもない。まさが動けば
MSのポイント消化をまさが取れるので、メンバーに払う額が減る。

## 4つの区分

1行を混ぜず、性質ごとに表を分ける。

### 1. 会社の売上があるPJ（判断に使えるのはここだけ）

`value_plan_cycles` の1シーズン = 1行。次の**両方**を満たすものだけを出す。

- `value_plan_cycles.budget_yen > 0`（シーズン原資がOSに登録されている）
- シーズン期間の**全月**で `billing_cycles.reward_summary_json.members` が1人以上入っている

| 列 | 定義 |
|---|---|
| 請求額(推定) | 上の逆算式 |
| 実費 | 契約バッファ |
| 社外へ現金 | Σ `externalPayoutCapYen` |
| 会社に残る現金 | 請求額 − 実費 − 社外へ現金 |
| まさ時間 | Σ `development_hours + meeting_hours`（`member_id='ID001'`、シーズン期間の週） |
| まさの労働の対価 | まさ時間 × 時間単価 |
| **まさ込み利益** | 会社に残る現金 − まさの労働の対価 |
| まさ1時間あたり | まさ込み利益 ÷ まさ時間 |
| 請求額の行き先 | 実費 / 社外へ現金 / まさの労働の対価 / 利益 の4色バー。合計が請求額 |

並び順は「利益順」と「時給順」を切り替えられる。

### 2. まさ個人へ報酬が支払われるPJ

`projects.fee_payee = 'masa_personal'` のPJ。会社の売上ではなく、まさ個人へ直接振り込まれる。

> **2026-08-30 まさ**: 「CLGとLSTはそれぞれ月10万円がおれ個人に振り込まれてる。
> 個人の報酬だけど、これもこの表ではカウントしてほしい。」

この2件は請求サイクルも計画サイクルも1行も無いため、`projects` に金額を持たせた
（migration `354_project_fee_payee.sql`）。**金額を画面のコードへ直書きしない。**

| 列 | 定義 |
|---|---|
| 月額 | `projects.fee_amount` |
| 期間 | `projects.start_ym` 〜（`end_ym` があればそこまで、無ければ当月） |
| まさ個人への報酬 | 月額 × 月数 |
| 差引 | まさ個人への報酬 − まさの労働の対価 |

**支払開始月はまさ未確認**。`projects.start_ym` を起点に置いているので、画面には必ず対象期間を
実月数で表示し、違っていれば気づけるようにする。

### 3. まさが時間を使っているのに、収入の記録がOSに無いPJ

tally に時間があり、シーズンも `masa_personal` の月額も無いPJ。まさの時間だけが出ている状態。
2026-08-30 時点で EHM 43.3h / KENQ 25.8h。

### 4. 報酬計算のデータがそろっていないシーズン

上の 1. の条件を満たさないシーズン。**金額を1つも出さない。**
「シーズンNヶ月中、報酬計算ができているのはMヶ月」とだけ書く。

> OSで計算ができていないことを、お金の状態として語らない。前セッションが
> 「シーズンが終わったのに275万が未配分」と表示して、まさから
> 「報酬を渡すべき人には渡し終わってるよ。計算ができてないだけ」と指摘された。

2026-08-30 時点で BWE（7ヶ月中4ヶ月）/ JC（10ヶ月中0ヶ月）/ SE（12ヶ月中0ヶ月）/ AMD / CTB / CX旧。

## まさの時間単価

既定 **25,000円/時**。画面のスライダーで 5,000〜60,000円/時 の範囲で動かせ、`localStorage` に残る。

根拠は、OSがまさの労働へ実際に配賦している額（`members[].companyReserveYen` のシーズン合計）を、
同じ期間のまさの投下時間で割った実績平均 **25,514円/時**（8,306,769円 ÷ 325.6時間、2026-08-30 時点）。

PJ別では 2,344〜38,913円/時 とばらつくが、これはMS設計とポイント配分の差なので、**PJ横断で1つの
単価に固定する**。PJごとに変えると、PJ間の比較へ配分設計の差が混ざる（＝ポイントが収益率に効いてしまう）。

## この画面の限界（画面にも明記する）

- **まさ以外のメンバーの労働を引いていない。** りり・あき・きよへの配分（`companyReserveYen`）は
  現金で出ていかないので、会社に残る現金の中に入ったままになる。その人たちの投下時間はOSに記録が無い。
  > **2026-08-30 まさ**: 「りりあききよを差し引けないのは全く問題ないよ。」
- **まさの投下時間はtallyに記録がある分だけ。** 記録は 2025-08-31 以降にしか無く、それより前の
  稼働は0時間として出る。画面に記録開始月を表示する。
- 請求額は逆算した推定値。月額固定のPJでは契約書と一致することを確認しているが、変動費のPJ（CX）は
  照合できない。

期末の未払残を厳密に検算したいときは `/admin/season-pl`（plan_cycle 単位の予実表）を使う。

## データソース

集計はDBを持たない純粋な TypeScript（`pwa/src/lib/project-profitability.ts`）。
**時間単価を掛けた値は返さない**（単価が可変なので、掛け算は画面側で行う）。

| 入力テーブル | 用途 |
|---|---|
| `value_plan_cycles` | シーズン行の単位。`budget_yen` / 期間 / `status` / `buffer_breakdown_json` |
| `billing_cycles` | `reward_summary_json`（社外への現金支払）、`extra_budget_yen`（別財布原資）、`budget_buffer_amount` |
| `projects` | 表示名、`fee_payee` / `fee_amount` / `start_ym` / `end_ym`（まさ個人への報酬） |
| `tally_weekly_effort_entries` | まさ（`member_id='ID001'`）の `development_hours + meeting_hours` |

`members` は読まない。メンバー別の内訳を出さなくなったため（区分の判定は `reward_summary_json` 側で済む）。

## 参照系キャッシュ

`billing_cycles` / `value_plan_cycles` は月次締めでしか更新されない参照系。規範は
[`5-10 参照系データのキャッシュ`](5-10-reference-data-caching-current-spec.md)。3層すべてを通す。

| 層 | 実装 | TTL |
|---|---|---|
| 1. サーバのプロセス内スナップショット | `src/lib/project-profitability.ts`（全件1本、single-flight、`.range()` でページ読み） | 5分（`PROJECT_PROFITABILITY_CACHE_TTL_MS`） |
| 2. HTTP キャッシュ | `src/app/api/admin/project-profitability/route.ts` の `Cache-Control` | `max-age=60, stale-while-revalidate=600` |
| 3. クライアントのモジュールキャッシュ | `src/lib/project-profitability-client.ts`（`@/lib/reference-data-cache` 経由） | 既定5分 |

シーズン数は十数件なので1回で全件返す。年やPJでの分割読みはしない。

- `?fresh=1` で 1 層を強制再読込し、`Cache-Control: no-store` を返す（月次締め直後の確認用）。
- 月次締め・報酬再計算の書き込み経路からは `invalidateProjectProfitabilityCache()` を呼ぶ。
- guard（`scripts/check_reference_data_cache_contract.mjs`）の `REFERENCE_DATA_ENDPOINTS` に登録済み。
