# 5-12 BZM 3.0 自動算出 — 設計（plan）

状態: **設計（plan）。実装はこの文書の承認ライン通過後に着手する。**
起点: まさ 2026-08-27「そのうえで、OSの全データとネット上の情報を使って算出するようにして。」
（`model/APPROVALS.md` #2026-08-27-1）

## 0. 何を解くか

2026-08-26〜27 の算出は、えいみが手でウェブを調べ、手で書いたスクリプトへ数値を打ち込んだものだった。
**OS に入っている情報（SE の経営体制、CLG の資金繰りなど）が1件も計算に入らず、
新しい PJ を立ち上げて情報を入れてもスコアは出ない。** これを、OS が自動で計算する形へ変える。

原則（AMD OS の既存規律に従う）:
- **生データから自動構築。手動入力前提の機能は作らない**（つくよみ原則）
- **LLM 抽出は Codex automation（定額枠）**。PWA から Anthropic API を直接叩かない
- **提案中の値を未承認と明示せずに使わない**（model/README (b)）——データ構造の列で守る

## 1. 入力の3層と、それぞれの出どころ

| 層 | 中身 | 出どころ | 更新 |
|---|---|---|---|
| **L-係数** | Q1〜Q33（§6.I。承認済みの初期値） | `model/CURRENT.json` 経由で参照実装の既定値 | まさの承認でのみ変わる |
| **L-観測状態** | 次に越えるゲート・会社化の有無・資金残高・権利残件・受託契約・担い手 | **OS の生データから自動抽出**（下の 2.） | 夜間バッチ（毎日） |
| **L-案件パラメータ** | 用途の切り分け・天井 $\bar P_u$・置き換え分 $\delta_u$・控除 $\alpha_u$・追い風 $\sigma$・専有可能性・自走力の実額 | **ネット調査＋OSの文書**から候補を自動生成 → **まさ承認で確定** | 四半期＋イベント時 |

観測状態は「事実の抽出」なので自動確定してよい。案件パラメータは「判断を含む推定」なので、
候補までを自動で作り、承認で確定する（σ の判定に統治を課す §6.I-1-4 の既存規律と同じ形）。

## 2. 観測状態の抽出 — どの生データから何を取るか

| 取る量 | 生データ | 抽出の手がかり |
|---|---|---|
| 会社化の有無・時期 | `projects.client_name`（法人名）・登記情報 | 「株式会社」等の法人名の有無 |
| 資金残高・調達 | 月報・取締役会資料（`workspace_documents` / `meeting_assets`）・月次損益 | 調達イベント（J-KISS・増資）、現預金、ランウェイの記述 |
| ゲート位置 | `project_xrl_log`（TRL/BRL/HRL）・月報・議事録の narrative | XRL→ゲートの対応表（§6.A の標準ゲート表へ写像） |
| 権利残件 | 議事録・月報（出願・共同出願の同意・COI の記述） | 種類別の残件抽出 |
| 受託契約 | `projects.fee_type`・契約書・月次請求 | 月額・拘束・本業との近さ |
| 担い手の充足 | 月報・議事録の実働記録（会議・意思決定・対外説明） | 機能分解表 §6.B への割当。**肩書ではなく実働** |
| 追い風の判定材料 | ニュース（`news_search_query`）・公募の採択率・予算額 | 12区分×四半期の判定は中央で行い版管理 |

抽出は L2 抽出基盤（3-1）と同じ経路（Codex automation の夜間バッチ）に載せ、
**全出力に出所タグ（document / record / hearing / missing）と根拠引用を付ける**。

## 3. 案件パラメータの調査 — ネット上の情報

- 用途ごとに、**年額の市場規模・出典 URL・取得日・検索語**を保存する（M1: 年額の一つの数）
- 置き換え型（国内に既存産業がある用途）は差分の積み上げで置く（p21 の論点。$\delta_u$ の扱いはまさ判断待ち）
- 競合の棚卸し（$\alpha_u$・$L_u$・$\kappa_{\mathrm{IP}}$ の材料）
- 調査エージェントの実行も Codex automation。**出典の無い数値は保存させない**（validator で弾く）

## 4. データの置き場（新設テーブル。migration は実装フェーズで）

- `bzm30_inputs` — 案件×入力成分。値・出所タグ・根拠引用・出典URL・**status（candidate / approved / rejected）**・承認ID・版
- `bzm30_scores` — 案件×版。下限/中央/上限・価値が立つ経路の確率（自走・ライセンス・M&A・知財売却）・
  入力のスナップショット・係数の版（LOCK の approval_ref）・計算時刻
- 画面: モデルページ配下に案件別ページ（入力の根拠がマウスオーバーで出る形。evidence 印の既存規約）。
  **candidate の値で計算したスコアは「暫定」の札を付け、approved のみの計算と分けて表示する**

## 5. 計算の実行

- 参照実装 `model/tools/bzm30_forward.cjs` を唯一の計算体として Node worker で実行（1案件あたり2〜5分）
- 夜間 cron で「入力が変わった案件だけ」再計算。結果は `bzm30_scores` へ append（版管理、上書きしない）
- 係数は `model/LOCK.json` の approval_ref と紐づけ、**ロックが変わったら全件再計算**

## 6. 実装の順序（着手条件: この設計の承認）

1. migration（テーブル2本）+ 手で作った9件分の入力を `bzm30_inputs` へ移す（candidate として。既承認の観測状態は approved）
2. 計算 worker + cron + `bzm30_scores`
3. 観測状態の自動抽出（XRL・会社化・資金から。既存 L2 基盤に相乗り）
4. 案件パラメータの調査エージェント（ネット調査。出典必須）
5. 画面（案件別ページ + 一覧。§5.8 の報告様式）

## 7. この設計で決めていないこと（まさ判断待ちを含む）

- $\delta_u$（置き換え分）の数え方（p21 の論点: 生産性の向上だけを純増と数えるか）
- 休眠の改訂（`model/proposals/2026-08-27_bzm30-dormancy.md`。未承認）が入るかで水準が変わる
- 較正の取り直し（休眠が入ると M4 到達の絶対水準が動く）
