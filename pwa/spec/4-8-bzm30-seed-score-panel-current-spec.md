# BZM 3.0 スコアパネル 実装仕様

シーズ詳細（`/seeds` の行クリック、研究機関PJコックピットの行クリック、`/seeds/[id]`）で開く
**産業創出価値 $V$ の算出パネル**の契約。実装は
[`Bzm30ScorePanel`](../src/components/bzm30/Bzm30ScorePanel.tsx)。

まさ 2026-08-27:「シーズリストの各シーズをクリックしたときに出てくるモーダルの中の計算式を
『一次選別スクリーニング』なんていう存在しないスクリーニング方法にせずに BZM3.0 の SPS 算出のモデルを入れてほしい。
そのモデルの各数式を書いて、そこに入るパラメータの数値をすべて記して、そのパラメータの算出根拠も書く仕様に直してほしい」。

## 1. モデルの正本はここではない

式・記号の意味・係数の値の正本は**モデルページ**（`/model`、読み込み元は `model/MODEL_VERSION_LEDGER.md`）。
この章はその表示の契約だけを持つ。**画面が式や値を書き起こさない**のが最上位の規律で、次の3段で守る。

| 何を | どこから取るか | 壊れたときの挙動 |
|---|---|---|
| 式（TeX） | モデル正本の `$$…$$` をそのまま。抽出は [`loadBzm30Formulas`](../src/lib/bzm30/formulas.ts) | 目印の文字列が正本に見つからない行は**静かに落ちる**（古い式を持ち続けるより出ないほうが安全） |
| 記号の意味 | 式の直後の記号表の「意味」列（正本の地の文） | 表が無ければ記号を出さない |
| 係数の値 | 参照実装 `model/tools/bzm30_forward.cjs` の `CFG` | 生成物 `tier0.json` が無ければビルドが落ちる |
| 根拠レベル・正本の節 | `model/tools/bzm30_export.cjs` の `buildParams`（§6.I の表からの転記） | — |
| 計算結果 | 同じ export が書き出す格子（型 × 規制属性 × 証拠水準） | 空なら「計算結果が未生成」と出し、生成コマンドを示す |

**前向き計算は1件あたり2〜3分かかるので、リクエストの中で走らせない。** 必ず
`node model/tools/bzm30_export.cjs --grid` で [`tier0.json`](../src/lib/bzm30/tier0.json) へ書き出したものを読む。

## 2. パネルの構成（6ブロック）

1 と 2 は常時展開、3〜6 は折りたたみ（初期閉じ）。

### 2.1 このシーズで、式に入る値がいくつ埋まっているか

[`buildSeedInputs`](../src/lib/bzm30/seed-inputs.ts) が組む13項目を、
**記号（LaTeX）/ 入力名 / このシーズの値 / 出どころ / 根拠・何を調べれば埋まるか**の5列で出す。

出どころは4値で色分けする。

| 値 | 意味 | 色 |
|---|---|---|
| 観測 | シーズの登録情報から埋まっている | 緑 |
| Tier 0 既定 | 観測が無いので分野・段階の既定値を使っている | 灰 |
| 未調査 | 案件ごとに調べないと置けない量で、まだ調べていない | 赤 |
| 承認待ち | OS 側にデータはあるが、BZM 3.0 の入力へ写す規則がモデルページに載っていない | 琥珀 |

**埋まっていない入力を既定値で埋めたことにしない。** どこまでが観測で、どこからが Tier 0 の既定かが
画面から見えることを最優先にする。天井 $\bar P_u$・工程の型 $\tau_{\mathrm{proc}}$・証拠水準 $g_0$ の
いずれかが空なら、冒頭に「円のスコアはまだ出せない」の断りを出す。

### 2.2 スコアの定義と、金額になるまでの道筋

正本の式3本（$V$ の定義 §5 / $v(\theta)$ と $V$ §5.8 / $\Pi(\omega)$ §5.7）をカードで出し、その下に4段の手順を書く。

1. 工程の型 × 規制属性を決める（ゲートの列・所要月数・バーンレート・自走力の既定値がここで決まる）
2. 評価日の証拠水準を決める（列のどこから始めるか）
3. 前向きに計算して、天井1円あたりの現在価値 $v$ を出す（1 と 2 が決まれば自動）
4. 天井を掛けて金額にする $V = (\bar P_u - \delta_u) \times v$

天井が未調査なら4段目に踏めない旨を出す。**天井は用途ごとに年額の一つの数で置き、幅を持たせない**
（モデルページ §5.3 改訂 M1。到達の不確かさはシナリオの確率が担っているので、天井にも幅を置くと二重に数える）。

### 2.3 型 × 規制属性 × 証拠水準ごとの $v$

格子を表で出す。列は **型 / 規制 / 証拠水準 / 次のゲート / 量産到達 / 到達月数 / $v$ 下限・中央・上限 /
幅の倍率 / 資本自立 / ライセンス / M&A / 用途転換**。

**出すのは価値が立つ経路の確率だけ**——自走（資本自立）・ライセンス・M&A・知財売却と、その合計。
価値がゼロの経路（撤退・清算・未決着）は「残り」であって指標ではない（承認 #2026-08-27-1 の追補）。
まさ 2026-08-27「そもそも撤退確率を最上段に書く意味が分からん。一定確率で倒産するとは思うんだけど、
SPSってそもそも倒産確率を算出するものではないよね」「成功する確率だけ出せばいいのでは。」

### 2.4 モデルの式

正本から抜いた式を**1行1式の表**で出す（式 / 何を決めている式か + 正本の節へのリンク / 記号の意味 + 案件ごとの入力）。
記号の意味は**切り詰めない**（`loadCurrentFormulas({ meaningMaxLen: 400 })`。`/model` の一覧は行が高くなるので30字で切っている）。

### 2.5 式に入る係数の実値と、その根拠

73件をグループ別の表で**全件**出す。グループは 期間と割引 / ゲートの基準速度 / 担い手の充足 / 資金調達 /
経済性の乗数 / 実現の申し出と受託 / 撤退の四経路 / 権利・承認 / 消失 / 案件パラメータの事前分布 / 資金繰り /
価値の側 / 計画規則。

列は **記号 / 名前 / 値 / 根拠レベル（A・B・C・規約・確定）/ 一言 + 正本の節 + 効く先**。
効く先は、その係数がどの量を動かすかを日本語の呼び名（価値・スコア・ゲートの前進・採択・実現の申し出など）で書く。

### 2.6 計算が置いている近似と、数値の誤差

近似6件（A1〜A6）と、格子の刻みを 1/2 と 1/8 で比べた差 2.0〜2.5%、**$V$ は有効数字2桁で読む**こと。

## 4. 承認待ちの2つの写像

モデルページの規律（`model/README.md` (b)）により、正本に無い当てはめ規則はまさの承認まで本番表示に使わない。
下の2表は [`seed-inputs.ts`](../src/lib/bzm30/seed-inputs.ts) に書いてあるが、
`LANE_ASSIGNMENT_APPROVED` / `STAGE_ASSIGNMENT_APPROVED` が `false` のあいだ画面に出ない。
承認が下りたらフラグを `true` にするだけで、工程の型・規制属性・証拠水準が「観測」として埋まる。

### 4.1 分野レーン → 工程の型 × 規制属性

| 分野レーン | 型 | 規制 | 判定の理由 |
|---|---|---|---|
| materials | F1 | REG-0 | 素材・化学のプロセス。規模を上げると挙動が非線形に変わる型で、事前承認は要らない |
| gx_circular | F1 | REG-0 | 資源回収・分解・転換の化学プロセス。装置よりプロセスが律速 |
| life | F1 | REG-2 | バイオ生産で、医薬・再生医療・食品機能性表示のいずれかで監督官庁の承認が律速する |
| gx_energy | F2 | REG-1 | 発電・蓄電・変換の装置。系統連系と型式認証の規格が要る |
| robo | F2 | REG-1 | 機構と制御の組立。機械安全・電気用品の認証が要る |
| ict | F3 | REG-0 | ソフトウェア・データ。技術ゲートより市場ゲートが律速する |
| other / null | — | — | 割り当てない（未判定のまま） |

確度は全件**仮**。個別に見れば外れる（life に計測機器、ict に半導体デバイスが混じる）ので、
シーズごとの判定が入ったらそちらを優先する。

### 4.2 旧の段階仮説 S0〜S5 → BZM 3.0 の証拠水準 0〜6

旧側の定義は `bzm/SEED_STAGE_AXIS_TEMPLATE_2026-08-15.md` §1、BZM 3.0 側はモデルページ §6.I-1-4。

| 旧 | 旧の定義 | BZM 3.0 | 理由 |
|---|---|---|---|
| S0 | 構想・原理提示（論文・提案のみ） | 段階0 | 原理実証 T1 をまだ越えていない |
| S1 | ラボ実証（再現データ・実験室規模） | 段階1 | 原理実証 T1 の通過に当たる |
| S2 | プロトタイプ・ベンチ機 | 段階2 | 再現性 T2 の通過に当たる |
| S3 | オンサイト実証（実環境・顧客先） | 段階3 | 実環境・実規模の検証 T3 の通過に当たる |
| S4 | 有償実証・初期顧客 | 段階4 | 有償PoC M2 の通過に当たる |
| S5 | 事業化準備（量産設計・調達活動） | 段階4 | 量産条件 M3 は権限者の署名つき文書を要求するので、段階4 に留める |

## 5. 旧の一次選別の帯の位置づけ

2026-08-27 より前は「一次選別スクリーニング帯（SPS = 産業創出価値）」の見出しでシーズ詳細の主役だった。
モデルページ §5.9 改訂 M2 で、旧 SPS の $P^{\mathrm{ind}}$ 帯は
**「$V$ と同じ次元の量であり、到達確率を掛ける前の $V$ ＝全部うまくいったときの上限」**と位置づけ直された。

- 破棄しない。**$V$ がこれを超えていないかの検算の基準**として、BZM 3.0 パネルの下に折りたたみ（初期閉じ）で残す。
  見出しは「（参考）2026-08 の一次選別の帯 — BZM 3.0 の $V$ の上限としての検算基準」
- 中身は従来どおり共通UI [`SpsScreeningBandSection`](../src/components/sps/SpsScreeningBandSection.tsx)
  （数式パネル + 使い方の制限 + 総合判断・11要因の根拠）。**冒頭に「この測り方は退役している」の札**を出す
  （同じ共通UIを使う PJ コックピットの「スコア詳細」タブにも同じ札が出る）
- **この帯から天井 $\bar P_u$ を割り戻さない。** 式から出てきた値を式の入力へ戻す向きになるため
  （まさ 2026-08-26「$V$ を算出するために市場規模が必要なわけで、$V$ から割り戻すってどういうこと？ 因果関係が逆だよ」）

## 6. 横幅の扱い

数式と表は**自分の中でだけ横スクロールさせる**。ラッパに `w-0 min-w-full overflow-x-auto` を使い、
`min-w-0` だけに頼らない——内容の最小幅がページ全体へ伝播して、モバイル幅でページ本体が横スクロールする。
mobile（375px）で `documentElement.scrollWidth === clientWidth` になることを確認してから出す。

## 7. 案件ごとの入力とスコア（migration 331）

まさ 2026-08-27「こんなの、それぞれのPJについてひとつずつネットで調べるだけじゃないの？
それをやるだけで算出できるなら、そこで止まってる理由が分からないんだけど。せめてPJ化されてるものだけでもその数字入れてよ。」

### 7.1 テーブル

| テーブル | 何を持つか | 書き込む人 |
|---|---|---|
| `seed_value_ceilings` | 用途ごとの天井 $\bar P_u$（国内の年額の付加価値）と置き換え分 $\delta_u$、売上ベースの市場規模、付加価値率、出典、確度 | 調査（人） |
| `seed_bzm30_inputs` | 工程の型 × 規制属性、評価日の証拠水準、観測状態（会社化・自由資金・権利残件・受託契約）、案件パラメータ（$\sigma$・$e$・$\kappa_{\mathrm{IP}}$・自走力・単位採算・未着手の用途）と、**パラメータ1件ずつの根拠**（migration 332） | 調査（人） |
| `seed_bzm30_scores` | 天井1円あたりの現在価値 $v$（10%点・中央・90%点）、天井を掛けた金額、9区分の確率、量産到達確率と到達月数、計算に使った入力の写し | 算出バッチ |

**根拠を調べる前の材料は会社メモ (`seed_company_facts`) に貯める**（2026-09-02）。会議や資料で分かった断片的な事実を1行1件で置く台帳で、同じシーズ詳細モーダルのサブセクションの先頭に出る。`sps_relevance` に `bzm30` の印が付いた行が、下の `*_reason` を埋めるときの材料になる。**この台帳から入力値が自動で決まることはない**——値と根拠を置くのは人で、会社メモはその手前の観測にとどまる。仕様は [`pwa/design/seeds.md`](../design/seeds.md) の「会社メモ」。

**根拠は1件ずつの欄に置く**（`free_cash_reason`・`rights_open_reason`・`under_contract_reason`・
`kappa_ip_reason`・`sigma_reason`・`evangelist_e_reason`・`unit_margin_reason`・`incorporated_reason`・
`burn_rate_reason` と、既存の `classification_reason`・`evidence_stage_reason`・`self_revenue_note`）。
§2.1 の表の5列目はこの欄をそのまま出す。案件ぜんぶを1つの `note` にまとめると、
どの値の根拠なのかが読み手に割り当てられず、必ず片方だけ古くなる（`model/README.md` (a-2) と同じ理由）。

**バーンレート `burn_rate_yen_month` は記録するが、前向き計算には入らない。**
参照実装は案件ごとのバーンレートを受け取らず、工程の型と会社化の有無から引く既定値
（モデルページ §6.I-9-2）で計算する。それでも表に出すのは、既定値が実績と何倍ずれているかが見えないと
資金の残り月数を読み違えるためで、出どころは**琥珀（承認待ち）**として出す
——OS側にデータはあるが、入力へ写す経路がモデル側に無い、という状態そのものが §2.1 の琥珀の定義に当たる。

RLS は `seeds` と同じ（member の SELECT、admin の全操作、service_role の bypass）。

### 7.2 用途の切り方

**市場が別かどうかで切る**（`model/cases/README.md` の規約 M1）。原料や作り方が違っても売り先の市場が同じなら同じ用途にする——
同じ市場を二つの用途として立てると、価値の式が同じ天井を二回数える。1シーズに複数用途を持てる（`UNIQUE (seed_id, use_case)`）。

**天井は売上ベースの市場規模に付加価値率を掛けて出す。** 付加価値率は全件 0.35 の暫定値（根拠レベル C）で、
産業連関表の該当部門から分野ごとに引き直すのが宿題。**売上ベースの値も必ず残す**（`market_sales_yen`）——
付加価値率を直すときに、元の数字へ戻れなくなるため。

**国内に既存の産業がある市場へ入る案件は、置き換え分 $\delta_u$ を必ず置く。** 市場の大きさをそのまま天井に置くと純増を大きく見誤る。
$\delta_u$ の解釈が定まらない案件（産業排水の処理・動画制作）は、**天井を `NULL` のままにして `note` に理由を書く**。
埋めたことにしない。

### 7.3 算出

`model/tools/bzm30_score_seeds.cjs`。1件あたり2〜3分かかるので、引数に `seed_id` を1件だけ渡す形にしてある。

```
node model/tools/bzm30_score_seeds.cjs --list                        # 対象の seed_id を1行ずつ
node model/tools/bzm30_score_seeds.cjs --list | xargs -P 6 -I{} \
  node model/tools/bzm30_score_seeds.cjs {}                          # 並列で全件
node model/tools/bzm30_score_seeds.cjs <seed_id> --dry               # 書き戻さず結果だけ
```

DB の入力を参照実装の `init` へ写し、**埋まっていない項目は渡さない**（参照実装が Tier 0 の既定を使う）。
天井が未調査でも計算する——$v$ は出るので、天井が入った時点で金額になる。

**係数か入力を変えたら計算し直す。** `seed_bzm30_scores` は append-only で、画面は最新の1件だけを読む。

### 7.4 画面

パネルの最上部に**このシーズの産業創出価値**のブロックを置く。

- 金額の中央値を大きく、下限〜上限と**幅の倍率**（＝この案件についてまだ分かっていないことの大きさ）を添える
- **「年額の純増 × 天井1円あたりの現在価値 ＝ 金額」の式に実値を代入して出す**。どこから来た数字かが一目で追えること
- 天井が未調査なら、金額の代わりに $v$ を出し「天井が入れば金額になる」と書く
- **価値が立つ経路の確率**を1枠にまとめて出す——自走（資本自立）・ライセンス・M&A・知財売却の四つと、その合計。
  **撤退・清算・未決着は出さない**（§2.3 と同じ理由）
- そのほかに 量産へ届く確率 / 到達月数 / 継続価値の比率 / $v$ の四つ

## 8. 入力を動かして見る（`/seeds/sensitivity`・migration 353）

まさ 2026-08-30「全案件のスコアが表形式で並んでて、右側の列にずらーっと各パラメータが並んでて、
それらのパラメータを変えたときにSPSが変わる様子がUI上で見れるといいかもって思った。」

### 8.1 曲線は先に計算して置く

**前向き計算を画面のリクエストの中で走らせない**（`model/README.md` (g)。1件10秒〜数分）。
`model/tools/bzm30_sensitivity.cjs` が、案件ごと・パラメータごとに、そのパラメータだけを振った曲線を
1点1行で `seed_bzm30_sensitivity` へ書く。画面はその上を滑らせるだけで、計算はしない。

| 列 | 何を持つか |
|---|---|
| `param` | 振ったパラメータ。`free_cash` / `burn` / `ceiling` / `evidence_stage` / `e` / `c` / `quiet_months` / `kappa_ip` / `sigma` の9種 |
| `point_index` | 曲線の上での位置。小さいほうから大きいほうへ |
| `is_base` | いま置いてある入力そのものの点。`seed_bzm30_scores` の最新行と一致する |
| `param_value` / `param_label` | 振った値と、**画面に出す表示文字列**。「3,141万円」「段階4」「追い風 (+1)」 |
| `v_median` ほか | 天井1円あたりの現在価値 |
| `score_lower_yen` / `score_median_yen` / `score_upper_yen` | 天井を掛けた金額。天井が未調査の案件は `NULL` |
| `p_reach_m4` / `months_to_m4` | その点での自力の量産到達率と、到達までの平均月数 |

**数字の整形を画面側で作り直さない。** つまみの目盛りの表示は `param_label` をそのまま出す。
点と点のあいだへつまみを置いたときだけ、両側の `param_label` を「A 〜 B のあいだ」と並べて出す。

**承認済みの実装で計算した行だけを画面に出す。** 読み取り層は、その案件の最新の評価
（`seed_bzm30_scores` の `model_version` × `approval_ref`）と一致する曲線だけを返す。
一致する行が無い案件は「計算中」と出す。**空欄にしない。**

### 8.2 画面の構成（上下2段）

カードのグリッドにしない。項目数がばらつくものは表か密なリストにする（`pwa/spec` 2-7 情報密度）。

**上段 — 全案件の一覧（13列）**
順位 / PJ / 案件 / 下限 / 中央 / 上限 / 天井（年額の純増） / 天井1円あたり / 型×規制 / 現在地 に加えて、
**何で決まっているかを見分ける3列**を置く。

- 量産到達率（`p_reach_m4`）。0 の案件は、価値がライセンス・M&A・知財売却の裾から立っている
- ゲートまで（`months_to_m4`）
- **資金÷ゲート**＝（自由資金の残高 ÷ バーンレート）÷ `months_to_m4`。
  1前後の案件は残高が価値をそのまま決める（`model/cases/SCORES.md`「気をつけて読むところ 9. 資金の崖」）。
  1.5 以下を琥珀で出す

行をクリックすると下段が切り替わる。行の hover / フォーカスでその案件の曲線を先読みする。
つまみを動かしているあいだ、その案件の行は「105万 → 232万」と変更後を並べ、順位列は「21 → 20 ＋1」と動きを出す。
**他の案件の順位も連動する**（順位は毎回、中央値の降順で組み直す）。

**下段 — 選んだ案件のつまみ（1行1パラメータ・9行）**
パラメータ / いまの値 / つまみ / その点での金額 / 根拠。

- つまみは `point_index` の目盛りの上を動く。点と点のあいだは線形補間する。
  目盛りの近く（0.08以内）では点に吸い付く。**矢印キーは目盛りから目盛りへ動かす**
  ——細かい刻みのままだと吸い付きに打ち消されて1回押しても動かない
- `is_base` の目盛りを AMD Blue（`#027FDC`）で出す
- 「根拠」は `seed_bzm30_inputs` の `*_reason` を2行に省略し、マウスオーバーで全文
  （`model/README.md` (f) と同じ考え方）。用途の天井だけは `*_reason` を持たないので、
  `seed_value_ceilings` の `use_case` / `source` / `note` から読み取り層が文を組み立てる
- 入力が無くて振れなかったパラメータは「この案件では入力が無いので振っていない」と出す

### 8.3 近似であることを画面に書く

曲線は**1本ずつ振ったもの**しか無い。したがって:

- **つまみを1本だけ動かしているあいだは、その曲線の点の値そのもの。近似ではない**
- **2本以上を同時に動かした結果は、それぞれの倍率（その点の値 ÷ 基準点の値）を掛け合わせた近似**で、
  厳密な計算ではない。画面の見出し直下に常時この断りを置き、2本以上動かしているときは
  操作の結果の横に「近似（N本を同時に操作）」を出す
- 基準点の値が 0 で、動かした先が 0 でない量（自力の量産到達率など）は倍率を作れない。
  そのときは近似せずに「—」を出す

`pwa/scripts/check_bzm30_sensitivity_base.mjs`（`npm run check:bzm30-sensitivity-base`）が、
曲線の基準点と `seed_bzm30_scores` に保存済みの金額がずれていないかを見る。

### 8.4 参照系キャッシュ

曲線は再計算のときだけ変わる完全な参照系。3層すべてを通す（`pwa/spec` 5-10）。

| 層 | 実装 |
|---|---|
| サーバのプロセス内スナップショット（TTL 5分） | `src/lib/bzm30/sensitivity.ts` |
| HTTP キャッシュ | `src/app/api/seeds/bzm30-sensitivity/route.ts`（`private, max-age=60, stale-while-revalidate=600`。`?fresh=1` で強制再読込） |
| クライアントのモジュールキャッシュ | `src/lib/bzm30-sensitivity-client.ts`（一覧行の hover で先読み） |

一覧は全案件を1回で読み、曲線は案件単位で引いて貯める。
`seed_bzm30_sensitivity` は 21件 × 9パラメータ × 3〜7点で PostgREST の1000行上限を超えるので、
**必ず `.range()` のページ読みにする**。素の `select()` にすると黙って切り捨てられる。

型とパラメータの並び順は `src/lib/bzm30/sensitivity-types.ts` が正本。
読み取り層（`sensitivity.ts`）は `server-only` なので、画面から値を import できない。
