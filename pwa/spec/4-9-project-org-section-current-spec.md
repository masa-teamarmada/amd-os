# 《組織》セクション 実装仕様

PJコックピット「スコア詳細」タブ（`/project/[projectId]/cockpit?tab=score-detail`）の最下段に置く
**経営チームの担い手**の面。実装は [`CockpitOrgSection`](../src/components/cockpit/CockpitOrgSection.tsx)。

まさ 2026-08-28:「SXの経営ハイライトに、杉浦先生の対人の壁の話が書かれちゃってる。
これどうみても経営ハイライトじゃなくない？ こういうのを経営ハイライトに書かないでほしい。
一方で、こういう情報はSPSのスコアリングに必須なので、スコア詳細タブの中に『組織』のコーナーを作って、
そこにこういう情報を入れておこうよ。メンバーリスト（SU設立後なら組織図）とあわせて。」

## 1. なぜスコアの面に置くか

産業創出価値のモデルは、経営チームを**八機能**（モデル台帳 §6.B-1 の $\mathcal F$）に分解し、
各機能が誰かの責任になっているかを**担い手の充足係数 $\eta_t$** として計算に入れる。
空席は減点ではなく**ゲートの前進の遅れ**として効き、採択（$\phi$）と申し出の到来（$\nu_k$）にも乗る。
エバンジェリスト機能はさらに、案件パラメータ **$e$（この案件でその機能が埋まる見込み）** として別に効く。

つまり人と組織の話は感想ではなく**スコアの入力**なので、経営ハイライト（事象の棚）ではなくここに置く。
経営ハイライト側の線引きは [3-6](3-6-strategy-signals-current-spec.md)。

## 2. モデルの正本はここではない

機能の一覧・充足の条件・記録の様式の正本はモデル台帳（`model/MODEL_VERSION_LEDGER.md`）。
この章は表示とデータの契約だけを持つ。

| 何を | どこから取るか | 壊れたときの挙動 |
|---|---|---|
| 八機能（番号・名前・中身・移せるか・空席の埋まり方） | 正本 §6.B-1 の表。抽出は [`loadTeamFunctions`](../src/lib/bzm30/team-functions.ts) | 見出しか表が見つからなければ**機能表を丸ごと出さない**（古い八機能を持ち続けるより安全） |
| 充足の判定条件 | 正本 §6.B-2。計算なので [`team-fulfillment.ts`](../src/lib/bzm30/team-fulfillment.ts) の `FULFILLMENT_RULE` に数字で持つ | `npm run check:team-function-contract` が正本と突き合わせて落ちる |
| 記録薄の扱い | 正本 §6.C-3 の3 | 同上 |
| 観測の種類 | 正本 §6.C-2 の24種のうち、人・組織の 15・16・17 | — |

**役職の台帳を充足の判定に入れない。** 正本が「肩書・名義・意思表明では充足にしない」と定めているため、
判定の入力は実働の記録だけにする。誰が何の役職かは §5 の人の一覧に出すが、それは判定の根拠にならない。

## 3. 3ブロック

### 3.1 担い手の機能

八機能を行に、**機能 / 状態 / 担い手 / 直近の実働 / 判定の理由 / 空席の埋まり方**の6列。

状態は4つ。

| 状態 | 意味 |
|---|---|
| 充足 | 直近12か月に、3か月以上あけた2時点以上の実働の記録がある |
| 充足見込み | 実働の記録はあるが、時点数・間隔・出所のどれかが足りない。**評価版の確定では空席として扱う** |
| 空席 | 実働の記録が無い、または直近12か月で途切れた |
| 未記帳 | 記録薄（下記）のため、空席かどうかを判定していない |

エバンジェリスト機能（機能1）だけは、出所が**第三者証言か相手方の記録**のものしか数えない（正本 §6.B-2 の4）。
面談メモや自己申告は充足の材料にしない。

正本の「拡張枠」（移せるか・空席の埋まり方がともに `—` の行）は、まだ機能ではないので判定しない。

**記録薄**（正本 §6.C-3 の3）: 直近6か月の記録が1件以下の PJ では、状態を「空席」ではなく「未記帳」にし、
表の上に断りを出す。記録を怠っただけの案件が、実態と無関係に空席・失速扱いになるのを防ぐための規定で、
**記録の薄さを案件の悪材料と混同しない**。

### 3.2 人・組織の観測

`project_org_observations` を新しい順に、**日付 / 種類 / 誰 / 効く機能 / 何が起きたか / 出所 / 効き先**の7列。

`direction` で向きを出す。

| 値 | 画面の呼び名 | 扱い |
|---|---|---|
| `positive` | 追い風 | 充足の材料になる |
| `neutral` | 観測 | 同上 |
| `negative` | 重し | **充足へ数えない**。機能表の「直近の実働」欄には赤字で併記する |

`direction` は**モデル正本にまだ無い拡張**。正本の充足判定は「実働の記録があるか」だけを見て質を見ないので、
「対外説明の主体として動いたが相手の判断を悪い方へ動かした」を充足の証拠にすると、
逆効果の実働が機能を埋めたことになってしまう。数値への効かせ方はモデル側で検討中で、
それまでは**記録して画面に出すだけ**にする（充足の判定からは外す）。

### 3.3 メンバー

いま3つのテーブルに散らばっている人を**名前で束ねて**1つの表にする。
**名前 / 区分 / 役割 / 状態 / 担当していること / 最終観測**の6列で、`inactive` は既定で畳む。

| 元 | 中身 | 画面での出どころ表示 |
|---|---|---|
| `project_venture_members` | SU側とAMD内部の手入力 | SUメンバー |
| `project_founding_members` | 議事録・月報からのLLM抽出（関連メンバー） | 関連メンバー抽出 |
| `project_management_organization_roles` | 役職と空席の台帳 | 「まだ誰も入っていない役職」として別枠 |

同姓の別表記（「石原」と「石原 裕香」）を**画面側で寄せない**。同一人物とは限らず、推測で寄せると別人を混ぜるため。
表記を揃えるのはデータ側の仕事で、次の2つで守る。

- 同一人物と確認できたら、`project_founding_members` の `person_name` を SU側の登録と同じ表記へ揃える
  （2026-08-28、SX の「石原」→「石原 裕香」。まさ「同一人物なので揃えて」）
- 議事録からの自動抽出には、`project_founding_members` の既存名だけでなく
  **`project_venture_members` の名前も既知として渡す**。ここを渡していなかったために、
  SU側にフルネームで登録済みの人が、姓だけの別行として増えていた

**同じ人が別の役割で複数登録されているときは、役割を `／` で併記する。** 先勝ちで片方を捨てると、
どちらか一方の担当が画面から消える（石原先生は SU側で「産連メンバー」、抽出側で「事業アドバイザ」）。

**会社設立後は登記上の役員と部門による組織図へ切り替える。** ただし元になるデータ（役員の登記・部門・指揮系統）を
まだどこにも持っていないので、現時点では全 PJ で同じ一覧を出す。

## 4. データ

### 4.1 テーブル（migration 333）

`project_org_observations`。様式は正本 §6.C-1（事象1件が1行）に合わせる。

| 列 | 中身 |
|---|---|
| `observed_on` | 出来事の日付。記録日ではない |
| `kind` | `staffing`（種類15 着任・退任・実働）/ `departure`（16 異動・定年・卒業）/ `structure`（17 体制の変化） |
| `person_name` | 誰の話か。組織全体なら NULL |
| `function_no` | 八機能の番号 1〜8。機能に紐づかない体制の話は NULL |
| `headline` / `detail` | 要旨（固有名詞を含む事実）と背景 |
| `source_tag` | `document` / `interview` / `third_party` / `public` / `masa` |
| `effect` | どのスコアの入力を動かす観測か |
| `direction` | §3.2 |
| `model_version` | どの版の機能番号として書いたか。粒度が変わる版更新で読み替えが要る行を特定する |

RLS は **member の SELECT / admin の全操作 / service_role の bypass** のみ。
`anon` の SELECT を作らない——個人の評価を含むので、外部ワークスペースから開けてはならない
（まさ 2026-08-28「外部には見せないよ、スコア詳細タブの中にあるし」）。

### 4.2 取得

`GET /api/project/{projectId}/org`（member 認証）が、機能表・観測・人の一覧・空席の役職を1回で返す。
純粋な参照系なので3層キャッシュを通し（[5-10](5-10-reference-data-caching-current-spec.md)）、
コックピットのタブの hover で `prefetchProjectOrg` を呼んでから開く。

## 5. 経営ハイライトからの移設（migration 334）

2026-08-26〜28 に「各PJが死ぬとしたらどこからか」を洗い出した内容が、行き先が無いまま経営ハイライトへ入っていた。
人の性質・組織の状態にあたる3件を `status='archived'` にして観測へ移し、
事象にあたる行（ORB の担い手喪失など）は経営ハイライトに残したまま、観測も別に立てた。

| PJ | 元の経営ハイライト | 扱い |
|---|---|---|
| SX | 起源PIの対人の壁 | 移設（機能1・重し） |
| CX | チームの一体感 | 移設（体制・追い風） |
| SE | 事業範囲を限定する判断の固定 | 移設（機能4・重し） |
| ORB | 技術の担い手が消え、経営者の交代もできない | 経営ハイライトに残し、観測を2件立てた（機能2の喪失／支配権で入れ替え不能） |
