> **状態**: まさ未承認の設計案（2026-09-11 えいみ起草）。**同日まさ指摘: この案は作業を人に割り当てて追いかける経路だけで、シーズン終了時の到達状態と、そこからの遅れの判定が入っていない。骨格の合意前であり、§7 の判断3点は取り下げ。** 到達点の置き場所をまさと決めてから書き直す。承認後は `-plan` を外し、確定した部分だけを current-spec として書き直す。

## 1. 何を解くか

まさの言葉（2026-09-11）をそのまま置く。

- ZMPは議事録にTODOとやったことを書いているだけで、プロマネができていない。
- SXはかるが管理しているが、新たに発生する論点を拾えず、全体的に遅れているのかも見えない。
- それができていないと、まさが業務を巻き取る。するとメンバーが育たない。
- AMDメンバーは全員業務委託なので、業務ひとつずつをAMDが委託し、メンバーが受託する形が理想。管理側の工数が大きすぎて非現実的だと思っていたが、AIの発達でOSがそれをやれるのではないか。
- まさときよの工数をなるべくかけず、OSにプロマネをさせ、各メンバーが想定どおりに動く状態を作りたい。

## 3. 設計の中心：「やること」1件 = 委託1件

まさの「業務ひとつずつを委託・受託する」を、OSでは **問いの木の「やること」1件を委託1件として扱う** ことに置き換える。発注書を毎回作る代わりに、OSが起票・配信・受託・催促・検収・報酬接続を担う。

| 段階 | 何が起きるか | 人がすること | 誰が |
|---|---|---|---|
| ① 起票 | 会議に出たAMD側の人が、会議中か当日に「やること」「問い」を木へ書く。つくよみは前日以降の議事録と木を照合し、**記録にあって木に無いものだけ**を提案として置く（PJあたり1日最大5件。まさ確定 2026-09-11） | 木へ書く。提案は「木に入れる / いらない」を押し、入れるときに担当（人名）と期限を付ける | 会議に出た人とPM（ZMP=あび、SX=かる） |
| ② 確定 | 採用された「やること」に担当（人名）・期限・完了条件が入る | ①と同じ操作の中で済む | PM |
| ③ 受託 | 担当者本人へ届き、本人が「受ける」か「期限を相談」を返す | 1回押す | 担当メンバー |
| ④ 催促 | 期限前・期限超過・更新切れを、本人へ届ける。PMには週1でPJの状態を1行で届ける | 受け取る | OS |
| ⑤ 完了 | 本人が完了にする。完了証跡（リンクか一文）が無いと完了にできない | 証跡を1つ置く | 担当メンバー |
| ⑥ 検収 | PMが検収する。差し戻しは理由つきで元に戻す | 承認 / 差し戻し | PM（PM本人の分はPL=まさ） |
| ⑦ 報酬 | 検収済みの「やること」を、その月の実績配分の第一の材料にする。月初合意の「担当する仕事」に「今月受託しているやること」を並べる | 従来どおり月初に合意 | 担当メンバー |

まさときよが出てくるのは、⑥のうちPM本人の分の検収と、週1回の全PJ横断の確認（PMが7日以上放置したものだけ）に限る。個々のやることの起票・催促・検収には出てこない。

## 5. 経路ごとの仕様

### 5.1 起票（人が書く。つくよみは書き漏らしを拾う）

3-21「つくよみが拾うもの」（まさ確定 2026-09-11）に従う。議事録の「次の一手」を全件自動で起票することはしない。

- **誰が書くか**: 会議に出たAMD側の人。まさが出た会議はまさ、出ていない会議はそのPJのPM。会議中か当日に、論点・仮説タブへ「やること」「問い」を書く。ZMPの定例はこたさん（クライアント側）が議事録を書くため、AMD側のPM（あび）が会議後に木へ写す。この運用を 2-9 の使い方に書き足す。
- **つくよみが拾うもの**: 前日以降の議事録と既存の木を意味で照合し、記録にあって木に無いものだけを `review_state='proposed'` で置く（PJあたり1日最大5件）。親の候補と理由を添える。経路は outbox → `apply_question_tree_outbox.mjs`（既存）。
- **提案を木に入れるとき**: 既存の「木に入れる / いらない」に、担当（人名、`members` から選ぶ）と期限の入力を添える。空のまま入れてもよいが、その場合は「担当未確認」「期限なし」として週報（5.3）に載る。「担当未確認」という文字列を担当名として保存しない。
- **議事録の主語がまさのとき**: 提案の担当を空にし、`proposal_reason` に「記録上の主語はまさ。PMが担当を決める」と添える。PMが入れるときに、まさに戻すか他へ振るかを決める（5.6）。
- **PMへの通知**: 翌朝9:00に1通。「昨日の {PJ} の会議の記録にあって木に無いもの n件。木に入れるか決めて」。宛先はそのPJの `is_pm`。PMが未設定のPJはPL。
- **やらないこと**: `next_actions` の全件起票、担当・期限・親の推測値を人の確認なしに正本へ入れること、`narrative_md` の書き換え。

### 5.2 受託（本人への配信）

- `accepted` になった「やること」を、担当者本人へえいみ名義のSlack DMで届ける。宛先は `members.slack_id`。本文は PJ / やること / 完了条件 / 期限 / 親の問い / ワークスペースのリンク（そのやることの詳細モーダルが開くURL）。
- 本人は詳細モーダルで **「受ける」** か **「期限を相談」** を押す。受ける＝ `accepted_at / accepted_by`。相談＝ `blocker` に理由を1行入れ、PMへ通知。
- 返答が無い場合: 48時間で本人へ再送、96時間でPMへ「未受託 n件」。
- まさが担当の「やること」も同じ扱いにする。例外を作ると比率（5.6）が測れない。
- 1人1日1通に束ねる。配信キュー `member_delivery_queue`（新規）に積み、朝9:00と17:00の2回で束ねて送る。即時に送るのは期限当日のものだけ。
- Slackの返信は読まない。返答は必ずOSの画面で受ける（Slack側の状態とOSの状態が二重にならないようにする）。

### 5.3 催促と週次の状態

- **本人へ**: 期限3日前 / 期限当日 / 期限超過後7日ごと。7日以上更新が無い「やること」も同じ通知に載せる。全PJぶんを1通に束ねる。
- **PMへ**: 毎週月曜9:00にPJ1行。`未完了 / 期限超過 / 担当未確認 / 受託待ち / 更新切れ / 手が止まっている問い / 判断できる問い` の件数と、先週からの差分。数え方は3-21の導出値をそのまま使い、新しい状態を作らない。
- **まさへ**: 毎週月曜、全PJ横断で1通。載せるのは **PMが7日以上放置しているもの**（未確認の提案、未検収、未受託の督促が止まっているもの）だけ。個々のやることは載せない。
- 送る相手は `members` にいる人だけ。クライアント側の人（こたさん等）には送らない。担当がクライアント側の人になっている「やること」は、そのPJのPMへ「相手側ボール」として週報に載せる。

### 5.4 完了と検収

- 本人が「完了」にするとき、`done_evidence`（成果物のリンク、または一文）が空なら完了にできない。DBの制約とAPIの両方で止める。
- 検収者は `project_members.is_pm`。PM本人の「やること」は `is_pl`（まさ）が検収する。検収＝ `reviewed_at / reviewed_by / review_result in ('accepted','returned')`。差し戻しは `status` を `running` へ戻し、理由を `blocker` に残す。
- 検収待ちが5日を超えたら検収者へ催促。10日を超えたらまさへの週報に載る。
- 検収済みは木の中で色を変えない（3-21の色の意味を増やさない）。詳細モーダルに「検収済み（誰が・いつ）」を出すだけ。

### 5.5 報酬への接続

- 現在の実績配分は、メール・カレンダー由来の活動記録（`member_activities`）から推定している（7-1「予定担当比率と当月実績配分」）。この推定は、まさの受信箱を主な入力にしているため、まさに偏る（直近30日でまさ296件、かる7件、ちこ4件）。
- **検収済みの「やること」を実績配分の第一の材料にする**。重みは `target / unit` があればそれ、無ければ件数。活動記録は補助に下げる。
- 「やること」がどのMSに属するかは、やること→親の問い→MSの対応表 `project_question_milestones`（問い×MS、多対多）で引く。親が無い「やること」は、そのPJの定常業務MS（`tag='routine'`）に寄せる。
- 月初合意の「01 あなたが担当する仕事」に、MS名に加えて **「今月受託しているやること」** を列挙する。これは表示だけで、合意のhashには入れない。受託の増減で再合意を求めると、月の途中で合意が止まって支払が止まる（3-14 の2026-08-27の事故と同じ形になる）。
- 契約上の位置づけは、3-14 の記述と同じく「OS上の月次合意の明細」までにする。個別発注書として法的効力を持たせるかは §7 の判断。

### 5.6 巻き取りを構造で止める

- PMへの週報に **「まさが担当の未完了やること」の比率** を出す。閾値（暫定30%）を超えたPJでは、まさ担当のやることを「委譲候補」として並べる。
- 起票のとき、主語が「まさ」の文は、提案の担当を空にして `proposal_reason` に「議事録の主語はまさ。PMが担当を決める」と書く。PMが採用するときに、まさに戻すか他へ振るかを決める。
- まさへの週報に、まさ担当比率のPJ別推移を1行だけ載せる。

## 6. 段階と安全弁

| 段階 | 範囲 | 中身 |
|---|---|---|
| Phase 1 | SX・ZMP、2〜3週 | 5.1 起票（提案まで）と 5.3 のPM週報。最初の1週間は送信を止めたまま本文を出力し、まさが読んでからPM宛→本人宛の順に送信を開ける |
| Phase 2 | SX・ZMP | 5.2 受託、5.4 検収。列の追加と制約。月初合意の明細表示 |
| Phase 3 | 全PJ | 5.5 報酬接続、5.6 の閾値運用。全PJ展開 |

安全弁として最初から入れるもの。

- 対人通知は既定OFF。送信を開けるのはまさの明示だけ（AGENTS.common の既定に従う）。
- 通知本文の型はDBで版管理し、管理画面で全文を読める形にする（LLMの文面をコードに直書きしない既定に従う）。
- 1人1日2通まで（朝・夕）。期限当日だけ即時。
- つくよみの提案は必ず「提案」で止め、木の正本を直接書き換えない（3-21「つくよみが拾うもの」の既定と同じ）。
- 送信ログ（誰に・いつ・どの「やること」について）を `member_delivery_queue` に残し、二重送信を防ぐ。

## 7. まさに決めてほしいこと

1. **本人へのSlack DMをOSから送ってよいか。** 既定案は「本人→PM→まさ」の順で、本人へは朝夕の2回に束ねる。送らないなら、催促はワークスペースを開いたときのバッジだけになり、いまと同じ「見に行かないと分からない」が残る。
2. **「受託」をどこまで正式にするか。** A: OS上の記録（運用上の合意）にとどめる。B: 月初合意の支払ゲートに含め、受託していない「やること」は実績配分に入れない。Bは業務委託契約の改定とメンバー同意が要る。
3. **検収者をPMにするか。** ZMP=あび、SX=かる。まさはPM本人の分の検収と週1の横断確認だけ。PMに検収を任せない場合は、まさが全件検収することになり、巻き取りが構造として残る。

## 8. 変えないもの

- 問いの木の判定・並び・色・モーダル（3-21）。増えるのは提案の帯とボタン3つだけ。
- 月初合意の hash と支払ゲート（3-14）。
- 報酬計算式（7-1）。実績配分の材料が増えるだけ。
- H-1 の議事録本文。起票は読むだけで、`narrative_md` を書き換えない。
- まさの採否ゲート `/notifications`。メンバー向けの通知はSlackとワークスペースで完結させ、まさの通知面に混ぜない。
- 先手TODO `/proactive`。会議の次アクションをまさのTODOへ昇格させない既定（2-4）はそのまま。

## 9. 検査

- 契約テスト: 「いらない」にした提案を次の巡回で拾い直さない（既存） / `accepted` の行を提案で上書きしない / 証跡なしで `done` にできない / 1人1日2通を超えない / 送信先が `members` 外にならない。
- ドライラン: 送信を止めた状態の出力を `design_log` に1週間ぶん残し、まさが本文を読んでから送信を開ける。
- 参照系/可変系: 「やること」「問い」は可変系（既存の baseline のまま）。PM週報の集計は日次で作って保存し、画面はそれを読む。
- 実データで見る: 開けてから2週間で、SX・ZMPの「担当未確認」「期限なし」「未更新」の件数が減っているかを §2 と同じ数え方で比べる。減っていなければ、通知の間隔ではなく起票の質（担当推定・親推定）を先に疑う。
