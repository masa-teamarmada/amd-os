# 月次会計締め (毎月27日)

## なぜ27日か

給与は毎月25日支給で、freee人事労務の確定はその前後。27日なら当月分の給与が確定済みで、月末の締めにも間に合う。

## 絶対に守ること

1. **freee APIで取引を作らない。** freee APIには未処理明細を処理済みにする公開エンドポイントが無い（[freee-api-schema#541](https://github.com/freee/freee-api-schema/issues/541)）。APIで取引を作ると口座明細が未処理のまま残り、あとで画面から登録された時点で二重計上になる。freeeへの書き込みはブラウザ操作で、freee本来の登録経路を通す。
2. **対応先が一意に決まらないものは処理しない。** 金額が請求額・未決済取引と一致しないもの、勘定科目の判断が要るもの（税金の納付、現金引き出し、飲食、備品など）は触らず、報告に回す。
3. **「自動で経理」一覧の `登録` ボタンを安易に押さない。** これは新規に費用や収益を立てる操作。給与の振込のように既に仕訳がある支払いに使うと二重計上になる。消込は明細を開いて `未決済取引の消込` タブで行う。
4. **役員報酬の明細を費用として登録しない。** 正しくは「役員報酬(総額) / 預り金(源泉所得税・社会保険料本人負担) / 普通預金(手取り)」の複合仕訳で、これは給与の会計連携が作る。口座明細はその未払金を消し込むだけ。

## 事前に読む

- `pwa/manual/6-10-freee-accounting-reconciliation-spec.md` — 会計連携の押し忘れ検知、消込導線、履歴
- `pwa/manual/6-11-kiyo-money-flow-spec.md` — きよ「お金の流れ」がこの結果をどう表示するか

## Phase 1: 給与の会計連携

freee人事労務 `https://p.secure.freee.co.jp/payroll_statements` を開き、当月と前2か月のタブを順に確認する。

| ボタン表示 | 意味 | やること |
|---|---|---|
| `会計連携` | **未実行**。給与仕訳が会計に無い | 押して `実行` で確定 |
| `会計連携の取消し` | 実行済み | 触らない |

- 給与が `計算完了` かつ `確定` になっている月だけが対象。未確定の月は飛ばして報告に書く。
- 仕訳の発生月は**支給月ではなく賃金計算期間の末日**。8月25日支給（7月勤務分）は 202607 に載る。

## Phase 2: AMD OSへ取り込み

対象月ごとに叩く。`includeFreee=1` が無いと試算表は同期されない。

```
GET /api/cron/management-score-raw-data?includeFreee=1&ym=YYYYMM
Authorization: Bearer $CRON_SECRET
```

取り込み後、`company_actual_monthly` の `category='fixed_cost'` に対象月の `役員報酬` `法定福利費` が入ったことをSQLで確認する。入っていなければ Phase 1 が効いていないので、報告して止まる。

## Phase 3: 給与振込の消込

freee会計の `自動で経理`（`https://secure.freee.co.jp/wallet_txns/stream`、ステータス=未処理）で、役員・メンバーへの振込明細を給与仕訳の未払金と消し込む。

手順（1件ずつ）:

1. 明細の `詳細` を開く
2. `未決済取引の消込` タブを開く（**一覧画面には出ない**）
3. 給与仕訳の未決済取引（勘定科目に `役員報酬` を含む行）にチェック
4. 明細金額と決済残額が違う場合は `一部出金にする` を押し、`今回決済金額` に**明細金額と同額**を入れる
5. `金額が一致しています` になったことを確認してから `登録`

**振込が複数人に分かれている場合**: 1件の未決済取引に対して人数ぶん部分消込する。例: 2026-06-30 の給与仕訳 843,313円 = まさ 561,292円 + きよ 282,021円。1人目を部分消込すると、2人目はfreeeが `差額 0` で消込先を推測してくるので、一覧の `登録` を押すだけでよい（この場合の `登録` は消込であり、新規計上ではない。行に `未決済取引の消込（支払）` と出ていることを必ず確認する）。

合計が未決済取引の残額とぴったり一致しない組み合わせは処理しない。

## Phase 4: 入金の消込

`入金` で絞り、クライアントからの振込を処理する。

- `未決済取引の消込` タブに売掛金の候補があればそれと消し込む
- 候補が0件で、かつ既存の自動登録ルールに合致している明細は、そのルールのまま `登録`
- ルールが無く候補も無いものは**処理せず報告**（売上の計上方法の判断になるため）

あわせて AMD OS 側の入金確認も進める。

```
GET /api/cron/freee-payment-sync?dryRun=1&ym=YYYYMM   # 先に必ず dry-run
GET /api/cron/freee-payment-sync?ym=YYYYMM            # 結果が妥当なら適用
```

dry-run の結果で、当たった請求月と金額が実際の入金と合っているかを必ず目視する。摘要がカタカナで一致しない相手は `project_knowledge` に `category='payment_alias'` で表記を足すと次回から自動で当たる。

## Phase 5: カードの引き落とし

`ＪＣＢカード` `フリ−カ−ド` など、銀行口座からカード会社への引き落とし明細は、明細の `口座振替・カード引き落とし` タブで対応するカード口座と紐付ける。カード側の個別明細（店名が出ているもの）は勘定科目の判断が要るので**処理せず報告**。

## Phase 6: 報告

まさへ次の形で出す。技術用語を使わず、画面で見えるもので書く。

- 給与の会計連携: どの月を実行したか、できなかった月と理由
- 消込できた件数と金額
- **処理せず残したもの**: 日付・摘要・金額・なぜ判断が要るか。金額の大きい順
- きよ「お金の流れ」の「まだ分類できていない」がいくらからいくらに減ったか

## 判断が要るものの例（自動処理しない）

| 明細 | なぜ |
|---|---|
| 税務署への納付 | 法人税・消費税・源泉所得税のどれかで科目が変わる |
| ATM出金 | 何に使ったかは明細に出ない |
| 飲食・小売 | 交際費か会議費か消耗品費かは中身次第 |
| 自社名義の振込 | 口座間振替か、別の入金かの区別が要る |
| 社名が読み取れない振込 | 相手先を推測で決めない |
