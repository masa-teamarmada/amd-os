# kaku-report

報告書を、データの保管場所ではなく判断の道具として書く。
`kaku` や `cognitive-rhythm-writing` は読み込まず、この規範だけで完結させる。

## 入力を分ける

書き始める前に、入力を次の5種類へ分ける。

1. **確認済み事実**：実施したこと、発生したこと、得られた結果
2. **判断と合意**：誰が何を決めたか、何が未決か
3. **成果と変化**：前月から何が進み、何が使える状態になったか
4. **リスクと次の行動**：障害、期限、担当、次に決めること
5. **監査情報**：取得件数、参照ID、生成時刻、コネクタ名、snapshot名

監査情報は本文の材料にしない。
必要ならデータベースの監査列や作業メモへ分離する。

## 統合する

- メール、会議、チャットなどの取得元別に並べない。
- 会議順の議事録ダイジェストにしない。
- 当月の仕事を2〜5個の業務領域へまとめ、各領域を「背景、実施、到達点、残課題」の順で書く。
- 同じ出来事が予定カードと実績記録にある場合は、実績記録を正本として1件に統合する。
- `決定:`、`確認:`、`次アクション:`、配列、表のセル断片は、そのまま貼らず完全な文へ書き直す。
- 根拠が少ない月は短く書く。文字量を満たすための一般論や推測を足さない。

## 概要を書く

概要は3〜5文で、次の順に書く。

1. 当月に最も進んだ仕事と到達点
2. 並行して進んだ重要事項
3. 判断、合意、または未解決のリスク
4. 次月へつながる焦点（必要な場合）

概要には次を書かない。

- 取得件数、確認範囲、データソース一覧
- draft、collection summary、source refs、L2、snapshotなど生成側の語
- 「本文は〜から構成した」など文書の作り方
- 「月次断面」「補強した」「更新した」など作業者視点の説明
- 個別会議の羅列

概要の各文は、プロジェクトの状況を一つ以上更新しなければならない。

## 本文を書く

- 段落の先頭で、その段落が扱う業務領域または判断を示す。
- 日付は、順序や期限の理解に必要なときだけ残す。
- 成果物名は、その成果が何を可能にしたかと組み合わせる。
- 判断は「誰が、何を、どの状態まで決めたか」を書く。
- 未確定事項は「未確認」「協議中」「予定」を区別し、確度を上げない。
- 次の行動は、担当、対象、期限が根拠にある場合だけ具体化する。
- 根拠欄は日付、種別、自然な件名に留め、内部ID、URL、取得件数、raw本文を載せない。

## 文体

- 平易な業務文で書く。結論を先に置き、理由と具体を続ける。
- 文芸的な比喩、情景描写、修辞疑問、溜め、劇的な転回を使わない。
- 「重要なのは」「本質的に」「多角的に」など、中身を増やさない強調を使わない。
- 同じ事実を概要、進捗、判断の各章で繰り返さない。章ごとに役割を変える。
- 箇条書きは並列関係が明確な場合だけ使い、文章の代わりにしない。
- 文や配列を途中で切らない。`...`、`…`、句点直後のカンマを残さない。
- 章間へMarkdown水平線 (`---` / `***` / `___`) を入れない。見出しと余白だけで区切る。

## 関係者への敬意

- 対外提出版では、共同研究者、大学教員、協力先、候補先の個人名を活動評価の主語にしない。正式な決裁者・契約当事者の特定など、氏名が判断根拠として不可欠な場合だけ記載する。
- 「氏名＋先生／教授／准教授は〜を開始・実施した」のように、外部関係者の働きを提出者が査定する文を書かない。個人の働きではなく、PJとして何が進んだか、関係者間で何を確認するかを書く。
- 打合せ記録は、出席者名が様式上必須でない限り「大学研究チーム」「関係機関」「弊社」のような組織・チーム単位で表す。
- 人を「経営体制候補者」などの評価ラベルだけで呼ばない。「経営体制に関する個別打合せ」のように、論点や協議内容を主語にする。
- 外部関係者を「巻き込む」「動かす」対象として書かない。参画の意義、実務上のメリット、共同で確認する条件を書く。
- 次の行動を一方的な指示として置かない。担当の合意が確認できない場合は「関係者間で確認する」「共同で検討する」とする。

## 既存稿を直す

1. 生成過程を説明する文を削除する。
2. raw dataの列挙を業務領域ごとにまとめ直す。
3. 事実、判断、リスク、次の行動が混ざった段落を分ける。
4. 概要を本文から改めて書き起こす。
5. 修正箇所だけを継ぎ足さず、影響する章全体の重複を取り除く。

## 提出前の品質ゲート

次をすべて確認する。

1. 概要だけで、当月の進展、判断、次の焦点がわかる。
2. 各段落がプロジェクトの状況を更新している。生成・収集作業だけを説明する文はない。
3. 「今月進んだこと」が会議ログや取得元別一覧になっていない。
4. 判断済み、提案、予定、推測を区別している。
5. 数値、日付、人物、成果物が根拠と一致している。
6. rawラベル、配列のカンマ連結、途中省略、内部ID、URLが残っていない。
7. 同じ事実の重複と、根拠のない一般論がない。
8. 読み手が次に確認または判断すべきことが明確である。
9. 章間にMarkdown水平線が残っていない。
10. 外部関係者の個人名や肩書を、活動評価の主語として使っていない。
11. 人を候補者・資源・動かす対象として扱う表現がない。
12. 次の行動が、共同作業の事実または合意済みの役割として書かれている。

1つでも満たさない場合は、その章を直してから提出する。
